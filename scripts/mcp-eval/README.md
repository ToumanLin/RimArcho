# MCP A/B evaluation harness

Design and case list: [docs/research/mcp-eval-design.md](../../docs/research/mcp-eval-design.md). Everything real stays under `D:\RimArcho-test\mcp-eval\` (never in the repo).

| Script | Where | What |
| --- | --- | --- |
| `cases.mjs [case...]` | host | Writes `cases/<id>/` (overlay, answer key, correct-fix layer) from the pristine Mods; with ids, only those cases (the others keep their files). c3, h2 and h7 build DLLs with `dotnet` (h7: Pawn Comp Profiler from `mods/pawncompprofiler`, into `cases/_mods/`). `Player.log` and `reference.Player.log` come from `sandbox.mjs <case> --run` and `--fixed --run` (copy `run/<id>[-fixed]/Player.log` into the case). |
| `sandbox.mjs <case> [--run] [--fixed] [--layer dir]` | host | Junctions the real 1.6 game and the case's Mods into `run/<name>/`, runs the game with `-savedatafolder`/`-logFile`, kills it after ~40 s of log silence. Runtime cases (`case.json` `runtime: {ticks}`, h7) start with `-quicktest` instead and stop at the first autosave, which the sandbox Prefs schedule `ticks` game ticks after the map starts (about 100 s in all). A changed Mod gets real folders only where files change; the rest are junctions (overlay `omit` leaves pristine files out). `--layer` applies a submission (files at `<packageId>/<path>`, `ModsConfig.xml`, `enable.json`, `delete.json`). |
| `package.mjs <case>...` | host | Packs the case for the VM into `pkg/<case>/` (manifest, ModsConfig, Player.log with VM paths, overlay). The log keeps its `Mono path[0]` line, rewritten to `C:\Eval\RimWorld`, so Archo knows the log is the guest game's (06 §4); packs made before 2026-11-04 dropped it (all eight cases repacked 2026-11-04). |
| `guest/stage.ps1` | VM, once | Builds `C:\Eval` (lib of non-Workshop Mods, game junctions, `archo.exe`). Already in snapshot `RimArcho-Eval-Staged`. |
| `run-case.ps1 -Case h1 -Group A -Run 1 [-Minutes 15]` | host | One run: revert to `RimArcho-Eval-Staged4` (powered off; `新玩家` signs in by autologon), push the case, `guest/overlay.ps1` (admin: faulty files written into the Mod's real folder, original timestamps), `guest/case.ps1` (Mods junctions, config, log; groups A and B also scan with Archo), delete the staging package, `guest/agent.ps1` (the agent, `-Minutes` limit, also written into the task text), collect `results/<case>-<group>-<run>/`, stop the VM. Groups: A = Pi + Archo MCP; B = dsh + Archo MCP (since 2026-11-04; also collects dsh's full session log `session.v4.jsonl.zstd`, which Node 26 reads with `zlib.zstdDecompressSync`); N = Pi with `--no-mcp` and no `archo.exe` on disk (group B before 2026-11-04). `-VMX <vmx>` picks the eval VM (default Player-Test); a mutex per VM keeps each VM to one run at a time, and only that VM is stopped or reverted. `-Archo <exe>` replaces the snapshot's Archo with that build (a copy stays in the result folder); `-StageOnly` stops after staging and leaves the VM running. Pi starts with `-interactive` (the signed-in desktop session, which must be `新玩家`): in session 0 the game cannot open a window and hangs. |
| `guest/dsh-eval.yml` | VM, per run | dsh patch layer for group B: magpie gateway and `apikeyfan/deepseek-flash` at reasoning effort `high` (as Pi), Archo as MCP server `archo` (15 min per call), web tools, session titles and telemetry off. `agent.ps1` takes the gateway URL and key from Pi's `models.json` and sets `DSH_HOME=C:\Eval\dsh` (the user's profile path is not ASCII and reaches node garbled). |
| `setup-dsh-vm.ps1 -VMX <vmx>` (+ `guest/setup-dsh.ps1`) | host, once per VM | Staged3 -> Node 26.13.0 (MSI from nodejs.org, hash checked) and dsh 0.2.1-rc.5 in `C:\Tools\npm` (install scripts allowed) -> powered-off snapshot `RimArcho-Eval-Staged4`. dsh needs Node >= 24.9 (`import.meta.main`; under Node 22 it exits silently). |
| `guest/probe-testrun.mjs` | VM, after `-StageOnly` | Calls `test_run` through Pi's own MCP client (60 s request timeout, progress requested), no model; writes `C:\Eval\out\probe.txt`. |
| `matrix.ps1 [-VMs <vmx>,...] [-Runs 1,2,3] [-Cases h1,h2,h5] [-Groups A,B] [-Minutes 15]` | host | The whole matrix (default cases h1, h2, h5; c1 to c5 are settled): one worker per VM takes the next free cell (`results/<cell>/claim`, created atomically), runs `run-case.ps1`, `summarize.mjs` and `grade.mjs`; grading starts the game on the host, so a global mutex keeps it to one at a time. Cells with `grade.json` are skipped, so it can be restarted; claims without a grade are freed at start. Logs: `matrix.log`, `matrix-detail-<vm>.log`. Keeps the host awake. |
| `summarize.mjs <resultDir>` | host | Tool calls per name, turns (model calls), tokens, final text -> `summary.json`; reads Pi's and dsh's JSON streams. |
| `grade.mjs <resultDir>` | host | Culprit from `answer.json` (list, else explanation); applies the submitted files, starts the game, compares the log with `reference.Player.log`; the fix also has to keep the culprit enabled and change it where the fault is -> `grade.json`. `GRADE_REUSE_LOG=1` re-scores without starting the game. |

Every group gets the same `guest/task.md`. Run in the background (a run takes 5 to 15 minutes).

**Parallel VMs.** `D:\VMs\Eval-2` and `D:\VMs\Eval-3` are folder copies of Player-Test (2026-11-04): `vmrun clone` refuses the encrypted VM ("Cannot read the virtual machine configuration file"). Each copy has its own `displayName`, `uuid.action = "create"` and `msg.autoAnswer = "TRUE"`, so it got a new BIOS UUID; reverting to Staged3 restores Player-Test's MAC in the vmx, but every boot regenerates it from the new UUID, so the three VMs never share a MAC. All three revert to the same snapshot name (each got its own Staged4 from its own Staged3 with `setup-dsh-vm.ps1`, so the identities stay). Inside, the guests are identical (computer name `WIN11-PLAYER`, Steam signed in to the same account), which is fine because the game starts from the exe, not through Steam. RAM: 8 GB per VM. Example: `pwsh matrix.ps1 -VMs D:\VMs\Player-Test\Win11-Player-Test.vmx,D:\VMs\Eval-2\Win11-Player-Test.vmx,D:\VMs\Eval-3\Win11-Player-Test.vmx`.
