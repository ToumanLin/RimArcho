Spike corpuslabel — labelling the real cause of log error clusters (design §6.4, §6.5, R1, R2)
Run: 2026-10-21, local machine. Only aggregates here. Sample, packets, labels and per-item scores
stay next to the corpus (corpus-kb\labels\pilot1\, not in any repository).

== What it is

  sample    stratified clusters from corpusrun results (logs >= 80% library coverage; classes
            other and mod-report excluded; per class the 2 templates found in most logs; 2
            clusters per template; at most 1 cluster per log)
  cooc      per sampled cluster key: mods over-represented in the corpus logs with the same key
            (>= 20 logs, >= 50% of them, >= 2x the other logs)
  packets   loads each log's list into a research environment, re-runs RimArcho's attribution,
            writes <item>.txt (what the labeller reads, 1.5-7.5 KB, mean 3.7 KB) and <item>.json
            (adds RimArcho's verdict, the log's packageIds)
  validate  label schema check (fixed enums; gist, key and packageIds must exist; quotes
            verbatim from the packet)
  score     labeller vs reviewer, then RimArcho vs the reviewed labels, by class
  exec      reviewer lookups: load one log's list and run any archo command

Packet facts come from the same cmds commands as the MCP tools (def, harmony --target,
patches --failed, files search) plus stack type owners, Harmony owners, folder owners, a byte
search of the list's DLLs for a missing assembly name, About.xml (dependencies missing from the
list, declared rules broken) and corpus co-occurrence. The labeller does not see RimArcho's
attribution (anchoring would inflate agreement).

Why not let the labeller call the MCP tools itself: the research environment holds one log's
mod list at a time, so parallel labellers cannot share it; packets are reproducible, bounded,
cheap and reviewable. An agent diagnosing through MCP is the §6.5 evaluation, scored against
these labels.

== Found on the way

parsed.jsonl drops mod entries written with [v:…] or [ov:…] (spikes/hugslogs accepts only
[mv:…]): ~78k of ~244k entries in the raw corpus, 7,082 of 7,091 logs. All corpusrun Loadouts
(results-v3, G1/G2 numbers) miss these mods, e.g. Combat Extended. This spike reads the list from
the raw upload. In this sample the bug cost RimArcho 2 of its 13 correct sources (both CE patch
failures): results-v3 finds 11.

== Pilot: 32 clusters, 8 classes x 4

Labeller claude-haiku, 8 parallel subagents x 4 items, three rounds; reviewer claude-opus-5-5
labelled all 32 independently with the raw log, exec lookups and co-occurrence. Every label of
every round passed validate (96/96).

Labeller vs reviewer (same source mods, or both none):

  round  packet / prompt                                      disagree   labeller says cause
  p1     facts, file search, DLL refs                          43.8%      11 of 32
  p2     + corpus co-occurrence, prompt on how to weigh it     31.2%      15
  p3     + lines after the message, exact ">name<" search,     21.9%      20
         Workshop id -> Steam title; prompt: a mod frame
         calling the throwing game method is the lead
  reviewer                                                                25

  p3, other fields: cause/no cause 78%, stage 75%, cause type 34%, fix kind 19%.

What the labeller gets wrong (p3, 7 items):
  - Says "unknown" where one clear hint exists (P02 Prepatcher fork not in the co-occurrence
    list; P10 the same shader warning it attributed in p2: run-to-run variance).
  - Over-applies a new rule: after p3's "calling mod frame" rule it blamed Replace Stuff for an
    NRE inside vanilla GenSpawn.Spawn (P05).
  - Cannot see a cause that sits in other clusters of the same log (P07: Gloomy Furniture Fix
    ships defs whose classes live in the inactive GloomyFurniture; the NRE comes later).
  - Has no file evidence when the player's mod is not in the research library (P28, an older
    Ratkin package).
  - P19/P20 (stale save references held by VEF's RaidGroup) are debatable; the reviewer named VEF
    with low confidence. Without them: 5 of 30.
  - Fix kind and cause type are inconsistent between labeller and reviewer: the enums are too
    loose ("update" the mod vs the game, "other").
  Never: a validation failure, a mod outside the list, a fabricated quote, a Ludeon package as
  source.

Where RimArcho is silent but the cause is findable (rules for G1):
  - xml-load "Exception loading UnityEngine.Texture2D from file." (2): the next line
    "absFilePath: …\294100\<id>\…" is not attached to the entry, so folder attribution never
    sees it.
  - xml-load "XML error: <field> doesn't correspond to any field" (2): search the literal
    "<field>value</field>" in the list's files.
  - material shader warnings, Prepatcher's ReflectionOnly assembly error (4): no mod in the text;
    corpus co-occurrence names them (100% vs 3%; 98% vs 11%).
  - harmony-stack: Map Preview's own frames (MapPreview.*) were not resolved to the mod by type
    owner (P06); a cause in an earlier cluster (P07).
  - save-load "curParent=VEF.…" gives role "mentioned" only (P19/P20).

Limits: 4 clusters per class; strata are frequent templates, not a random sample, so the
per-class rates do not weight to the corpus. One reviewer; the reviewer saw RimArcho's verdict
for a few items while checking packets (P19, P29). Mods are current Workshop versions.

== Benchmark v2 (G6, 2026-10-22): 140 labelled clusters in two tiers, RimArcho accuracy by class

Only aggregates here. Sample, packets, labels, transcripts and tasks are in
corpus-kb\labels\v2\ (not in any repository). Schema: SCHEMA.md (corpuslabel/2).

Sample (bench-sample, results-v4, logs >= 80% library coverage, pilot logs excluded, one
cluster per log): tier 1 patch-failed, xref-missing, texture-missing, xml-load, 20 each;
tier 2 exception, harmony-stack, assembly (TypeLoad, ReflectionTypeLoad, MissingMethod,
"Cannot resolve dependency"), static-ctor (static constructor / TypeInitialization), 15 each.
assembly and static-ctor are RimArcho exception/harmony-stack clusters picked by key pattern.
~60% "head" (most frequent templates, one per template family) and ~40% "tail" (uniform over
(log, template) pairs of the other templates, at most 4 per template, 2 in tier 2).
Packets: as the pilot plus the log upload date, each involved mod's version in the log vs the
research library's, and co-occurrence over distinct mod lists (near-identical lists, Jaccard
>= 0.8, count once; >= 15 lists). The old count let one player's repeat uploads make
unrelated mods look 88% vs 1%.

Labellers (blind to RimArcho's verdict):
  tier 1   claude-haiku on the packet only, 10 agents x 8 items, three prompt rounds
  tier 2   claude-sonnet, one agent per cluster, with the packet, the raw log and `corpuslabel
           exec` on its own research home (fact commands only; log and problems are blocked):
           source, source search, harmony, def, patches, files search, mod, why. Every call is
           logged; validate checks code quotes against the decompiled .cs (file, type, method,
           lines +-3) and env:/log: quotes against the transcript and the raw log.
  reviewer claude-opus-5-5: all 60 tier-2 labels; 32 of 80 tier-1 labels (8 per class, the
           odd items 01..15, head and tail), labelled independently from packet and raw log.

-- Labeller vs reviewer

                     source mods  cause/none  cause type  fix kind  stage  difficulty
  pilot p3 (n 32)       78.1%        78%         34%        19%      75%       -
  tier 1 round 1        68.8%        68.8%       68.8%      25.0%    93.8%    40.6%
  tier 1 round 2        87.5%        87.5%       71.9%      40.6%    93.8%    43.8%
  tier 1 round 3        87.5%        90.6%       68.8%      87.5%    96.9%    46.9%
  tier 2 (n 60)         91.7%        91.7%       96.7%      93.3%    100%     95.0%

  Source-mod disagreement: 12.5% in tier 1 (Haiku), 8.3% in tier 2 (Sonnet; 6 of 60 labels
  corrected). Round 1 tied "verdict unknown" to "cause type unknown" both ways, so Haiku
  dropped clear sources (a failed patch's owner) when the reason was unclear; round 2
  separates who from why. Round 3 states that the class default fix applies without a named
  source (13 of 19 fix disagreements were ignore vs unknown). Cause type stays the weakest
  tier-1 field: optional-absent vs outdated-mod needs to know whether the patched mod is in
  the list, which the packet shows only for "involved" mods. Haiku's difficulty is not
  reliable (it calls most unknowns L3).
  Tier-2 corrections: 4 of 6 were the same who-vs-why slip (the mod's own static constructor
  or patch throws, but its code is not in the library, so the agent said unknown); 1 wrong
  inference about which mod ships a stale AchtungMod.dll (the log header disproves it); 1
  added co-source (Explicit Timings' unguarded GetTypes).

  xref-missing    20      6       6    0     0       0      14     100%     100%
  texture-missing 20      7       4    0     3       0      13     100%      57%
  xml-load        20      7       2    0     5       2      11      50%      29%
  exception       15      5       2    0     3       2       8      50%      40%
  harmony-stack   15      4       3    0     1       2       9      60%      75%
  assembly        15     11       4    1     6       0       4      80%      36%
  static-ctor     15     13       4    3     6       1       1      50%      31%
  all            140     73      40    4    29       7      60      78%      55%

  precision = hit / clusters where RimArcho names a source; recall = hit / clusters whose gold
  names a source. Reviewed labels only (92): precision 70%, recall 45%. The packet re-run on a
  fresh home gives the same picture (78% / 53%).
  The 11 named-but-wrong clusters were checked against the evidence after scoring; no gold
  label changed. 4 are debatable (HugsLib's own log-upload error; Humanoid Alien Races code
  or patch on the stack where some race def supplies the null; VEF's unguarded patch on a
  method missing in an old RPG Style Inventory). 7 are clear errors from two rules:
    - "<F>V</F> doesn't correspond to any field": the literal search matches the same value
      in unrelated def types (selectionWeight in GeneDefs/PreceptDefs for a LayoutRoomDef
      error). Restrict the search to the def type and context of the message.
    - topmost mod frame: names infrastructure callers instead of the failing mod: Mod Error
      Checker (scans assemblies), Loading Progress (runs static constructors), Defaults and
      HugsLib Quickstart (trigger vanilla code that hits another mod's broken def). "Error in
      static constructor of X" should attribute X's owner; such callers should be "mentioned".
  Against the pilot: "never wrong" holds for the tier-1 classes except xml-load; the code
  classes are 50-80% precise. Silence is still the larger gap (29 silent vs 11 wrong).
  Gold distribution: many clusters have no decidable source even with code (tier 2: 17 of 60
  unknown: NREs inside vanilla code with null-safe patches, save data of removed mods, machine
  problems such as an unwritable harmony.log.txt). Version mismatch (the player's copy older
  than the library's, and the library code fixed) decides 11 clusters, mostly in tier 2.

-- Task set for G7 (corpus-kb\labels\v2\tasks.jsonl)

  140 tasks: gist, cluster key, Loadout source (raw log header) and rebuild command, packet,
  question, answer (corpuslabel/2 label; code quotes copied to code\), answer status (92
  reviewed, 48 Haiku labels), difficulty (L1 21, L2 59, L3 60), split: 44 held out (~30% per
  class, by hash; G7 must not tune on them).

Limits: one reviewer; 48 tier-1 gold labels are unreviewed labeller labels; strata are
frequent templates plus a tail, not weighted to the corpus; research mods are current Workshop
versions (version mismatch is decided from code differences when headers carry no version).
Packet bug found and fixed after labelling: GetNamed def names kept the sentence's period
("konf."), so those packets' def lookups and searches came back empty. `patches --failed`
prints the filtered count as "N operations", which reads as "this mod has no patches".
