Spike patterns — error pattern library v0 (docs/research/00-日志语料顶层设计.md §3 G5)
Run: 2026-10-21, local machine. Input: spikes/hugslogs parsed.jsonl, regenerated with the fixed
mod-list parser (ef86650; upload time, mod lists), and corpusrun results-v3.jsonl (clusters with RimArcho's v3 attribution), 6,734 logs of 1.6. Output:
patterns-v0.json (aggregates only: no gist ids, no mod lists, mod-specific patterns need >= 10 logs
from >= 5 sessions, templates that look like paths or user data are dropped). Draft of how it
would enter the product: docs/research/01-范式库接入草案.md.

== Method

- Generic patterns: 46 hand-written rules over the cluster template (message with names and
  numbers removed), first match wins, ordered specific -> fallback. Each rule has a failure stage
  (load / save / runtime / noise), a summary, common causes, an MCP route, fix types and whether
  the current MCP Instructions cover it (yes / partial / no; judged by hand against desc.go).
  Fallback rules (rt.nre, rt.other, xml.other, patch.other, save.other) only name the class and
  do not count as matched.
- Mod-specific patterns: a template whose cluster names exactly one source mod (v3 attribution).
- Resolution (design §5 L1, source "session"): sessions as hugslogs stats (same version, package
  Jaccard >= 0.9, <= 48 h). Each consecutive pair A -> B is classified by its list change: none,
  order only, 1-3 package/version changes ("small"), more (excluded). For every pattern in A:
  is it gone in B? For small/order pairs where it went, what changed: the source mod removed
  (disable-source), another mod removed, a mod added (enable), a version changed, mods moved.
  Pairs without change are the control.

== Coverage

problem clusters 610,910 in 6,459 logs (informational classes excluded)
  matched by a non-fallback rule   87.0% of clusters, 75.5% of occurrences, 87.6% mean per log
  by stage                         load 70%, save 21%, runtime 9%, noise 0.2%
  current MCP workflow covers      30.0% of clusters fully, 29.1% partly, 40.9% not at all;
                                   74.5% of logs have at least one cluster it does not cover
The fallback rest is mostly bare NullReferenceException / ArgumentNullException messages
(rt.nre 2,502 logs, rt.other 2,148 logs): the message says nothing, the stack does. v1 needs the
StackShape of design §5 L1 (innermost game method, innermost mod assembly).

== Sessions

951 sessions with 2+ uploads (2,678 logs, 40%); 1,727 consecutive pairs: no change 936, order only
80, 1-3 changes 400, more 311 (excluded).

Disappearance without any list change (the control) depends on the stage:
  load-stage patterns   0-6%   (xref.sound 0%, xml.no-field 0%, xref.def 1%, patch.xpath 2%)
  save / runtime        5-26%  (rt.nre 6%, save.loadid 7%, rt.tick 12%, rt.collection-modified 26%)
So for load-stage patterns a disappearance after a small change is real evidence; for save and
runtime patterns it has to beat the control (rt.tick: 56% after small changes vs 12%; save.loadid
34% vs 7%; rt.ui 51% vs 9%).

Load-stage errors rarely go away after a small change either (xref.def 3%, xref.sound 1%,
patch.xpath 10%, xml.no-field 9%): players remove or add a mod, but not the one that matters.
The strongest form, the source mod removed and the error gone, is rare: 87 mod-specific patterns
(RocketMan's start-up errors 2-3 times each, the rest once).

== Known issues

- Before ef86650 parsed.jsonl dropped the mod entries written with [v:…] or [ov:…] (1.6: 1,425,158
  -> 1,498,974 entries, +4.9%; median mods per log 159.5 -> 165; every log lost HugsLib). The numbers
  here are on the corrected file; the old one gave the same coverage and nearly the same session
  rates (949 sessions, 96 disable-source patterns).
- The clusters and their attribution are from results-v3 (run on the old mod lists): HugsLib and
  the other dropped mods are never a source there.
- Attribution is RimArcho v3 (coverage, not accuracy): a mod-specific pattern is "a template
  attributed to this mod", not "this mod's bug".
- Fix evidence co-occurs with a change; it is not causal. A player who removes three mods and
  loads another save also loses save-stage errors.
- Workflow coverage is a manual judgement of the current Instructions text.

Reading
- Exposure is high, active use is low: 88 of 96 dev tasks (all assembly, static-ctor,
  texture-missing, patch-failed and xref-missing tasks) show a non-fallback pattern on the
  cluster, but agents called `analyze_log pattern=` only twice in 140 tasks. The checklist's
  save-loading part is never exercised: the benchmark has no save-load class.
- Source finding: no measurable change (dev recall 86.7 in both same-day runs; held-out 20 -> 21
  of 28 gold sources, one task). Cause type is up on both splits (dev +4.2 vs the same-day run,
  held-out +4.5), fix kind is mixed (dev +3.1, held-out -9.1: the pattern's fix list,
  e.g. xref.def "enable-dependency, update, disable", competes with the brief's class defaults
  such as "patch failures -> ignore"). Each is within one or two tasks per class.
- Risk seen: on assembly tasks the version-mismatch summary ("the mod or a dependency is
  outdated") led two agents to name the assembly's mod where the gold says unknown.
- Cost unchanged: median 32 s vs 24 s (same-day rerun), 6 tool calls, 7 archo calls, ~81k
  final context; the pattern section adds ~600 bytes to a cluster view.
- Conclusion: keep the library as background (it does not hurt source finding and helps cause
  type), but it is not the lever for the weak classes (static-ctor 20%, tier 2). Next: StackShape
  for the fallback patterns, fix kinds in the benchmark's vocabulary, and a save-load slice in
  the benchmark before tuning the checklist further.
