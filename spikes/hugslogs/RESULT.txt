== Answers

1. Bulk collection works, but only as a rolling window.
   - Account: HugsLibRecordKeeper (default HugsLib uploads are public gists).
   - The GitHub API is not usable from this environment (the session proxy only allows
     repository-scoped API paths). The gist web listing + gist.githubusercontent.com raw content work.
   - The listing serves at most 100 pages = the newest ~1,000 gists. That was 2.6 days
     (2026-10-17 09:08 .. 2026-10-20 00:32), i.e. ~380 uploads per day. Ascending order only reaches
     the 2016 end. Older logs can only come from links found elsewhere (Steam threads).
   - Listing faster than ~1 page / 2 s gets HTTP 429 (Retry-After 120 s). 998 of 1,000 raw logs
     downloaded; 2 were 404 (deleted).
   => P1 needs a scheduled fetch at least once a day; the index is append-only, so runs resume.
   UPDATE 2026-10-19 (local run, own token): the GitHub API is not limited to 100 pages.
   `hugslogs probe` found 7,041 pages x 100 = ~704,100 gists, oldest 2016-11-17. Page 100 =
   2026-09-28, page 1,000 = 2026-02-01, page 3,000 = 2024-02. History can be backfilled by date
   range (`api -from`); the constraint is storage (~600 KB/log), not the rolling window.

2. Format. Header sections are exactly as in HugsLib's LogPublisher: "Loaded mods:" (load order,
   name(packageId)[mv:…]: assemblies), "Active Harmony patches:" (target: PRE/post/TRANS/FIN …),
   "Harmony versions present:", "Platform information:" (dropped), "Log file contents:".
   Two surprises:
   - RimWorld 1.7 (runtime "Waylith", .NET 10) writes a different Player.log: every line is
     "<date> <time> <LEVEL> [<category>] <message>", continuation lines can start at column 0, every
     entry (warnings too) carries a stack whose leading frames are the logger (Brutal.Logging.*,
     Verse.Log.*), and the "RimWorld x.y.z revN" line comes after line 50. internal/logs does not
     handle this (no version; INFO lines become entries; warnings classify as exception). The spike
     converts 1.7 logs to the Unity form (fromWaylith) and keeps the level per cluster. Product fix
     recorded in docs/backlog.md.
   - An unofficial publisher (m00nl1ght.UnofficialUpdates.HugsLogPublisher, 71 of 998 logs) omits
     the "Log file contents:" line before a 1.7 log.

3. Cleaning: 975 of 998 kept. Dropped: 16 version-out-of-scope (1.5), 7 empty-log (mod list only).
   Version mix: 1.6 936, 1.7 39, 1.5 16. 34 of the 39 1.7 logs load the official HugsLib, so 1.7 is
   rare because players are still on 1.6, not because the publisher fails => scope 1.6 main,
   1.7 tracked separately.
   12% of kept logs are truncated (10,000-line limit).

4. Sessions (repeat uploads; same version, package-set Jaccard >= 0.9, <= 48 h apart): 135 sessions
   cover 389 logs (40%). 254 consecutive pairs; 71 differ by 1-3 packages; in 51 of those at least
   one error cluster disappeared. => repeat uploads are a real source of fix evidence (G5), even in
   2.6 days. Caveat: a cluster can vanish for reasons other than the change (different save, menu
   only, truncation); P1 must control for that.

5. Packages: 14,290 distinct packageIds in 201,928 entries (median 150 mods per log, p95 521).
   Top 100 cover 19% of entries, top 1,000 57%, top 3,000 80%. The tail is heavier than assumed in
   §5 L2: a local mod library of a few hundred mods will not cover typical logs; G3/G4 need ~3,000
   mods or must be limited to the mods they concern.

6. Errors: every kept log has clusters (median 38, p95 739). Harmony section present in all kept
   logs (median 2,047 patched methods).

7. Thread route (B): Steam workshop discussion pages can be fetched; they contain HugsLib gist links
   (inside steamcommunity.com/linkfilter redirects) and replies.

== Expansion to 40k logs with a download-time filter (2026-10-22/23, local, branch claude/corpus-expand)

Commands (RimArcho-corpus/scripts/fetch.ps1 -Mode even wraps them; topup.ps1 is the monthly one):
  hugslogs api -from 2025-07-01 -list-only      listing: 181,373 gists 2025-07-01 .. 2026-10-22
  hugslogs even -from 2025-07-01 -until 2026-10-23 -per-month 2500 [-max N]
  hugslogs verdicts -from … -until …            filter rates for a window
  hugslogs stats                                parsed.jsonl + the summary below

Filter (filter.go judge, applied after download, before anything is written to raw/):
  keep  1.6 with a "Loaded mods" list and >= 1 problem cluster (any class but other / mod-report);
        every 1.7 log (tagged mm 1.7).
  drop  gone (404), duplicate-content (sha256 prefix of the raw upload), version-out-of-scope,
        no-problems, too-short (< 20 log lines), too-large (> 90 MB), and the parser's drops
        (empty-log, no-log-section, no-game-version). Dropped logs get no raw file; every
        candidate gets an index.jsonl line with verdict, mm, hash. Logs collected before the filter
        are judged in place and tagged legacy (their raw files stay).
Sampling: per month, whole days in a fixed order (15, 1, 8, 22, 4, …) until 2,500 kept.

Result: 16 months x ~2,500 kept. Judged 43,559: kept 40,160 (92.2%; 1.6 40,050, 1.7 110).
  Drops: version-out-of-scope 1,559 (3.6%), no-problems 1,532 (3.5%), gone 200, empty-log 55,
  no-log-section 21, no-game-version 18, too-short 14, duplicate-content 0, too-large 0.
  Judged at download time only (without the 7,091 legacy logs): 36,468 judged, 33,652 kept (92.3%).
  1.7 share: none before 2026-10-15; of kept logs per sampled day 3% (10-15), 2% (10-17), 2% (10-18),
  9% (10-19), 18% (10-22). 1.7 is arriving now, so the monthly top-up matters more than the backfill.
Storage: 40,743 raw files, 23.3 GB raw, 2.61 GiB packed in git (pushed in 4,000-log batches; largest
  file < 95 MB; fetch.ps1 -MaxPackGB raised from 2 to 4 deliberately).
Content of the 40,436 parsed ok logs (stats; this includes 276 legacy no-problems logs):
  mods per log median 176 (p95 620); clusters per log median 40; Harmony section in all, median
  1,859 patched methods; 12% truncated; 42,130 distinct packageIds; top 1,000 cover 58% of entries,
  top 3,000 80% (same curve as the 1k sample). Sessions: 5,607 with 2+ uploads cover 15,853 logs (39%).

== Cleaning problems found (to fix in P1)

- "other" is the largest class (76k clusters in 925 logs). internal/logs' Interesting() keeps any
  line with "failed", "missing", "not found" …, so status lines ("[XML Extensions] N total patch
  operations run in Nms, N failed"), translation summaries, mod self-reports ([MeleeAnim] …,
  GAGARIN …) count as errors. G1's coverage metric must be computed on a cleaned set.
- Per-type messages do not merge ("Type X probably needs a StaticConstructorOnStartup attribute"
  once per type; "[SafePatcher]The xPath … not found" once per def). G5 needs template-level
  normalisation on top of internal/logs' cluster key.
- 1.7 warnings with caller frames classify as exception (1,692 "WARN exception" clusters); use the
  level.

== Small-model enrichment pilot (R1)

One Steam bug-report thread (7 reports) converted to text and given to one Haiku sub-agent with a
fixed JSON schema (symptom, verbatim error text, replies, resolution_status, fix, implicated mods,
evidence quote). Result: valid JSON; gist ids correctly decoded from linkfilter URLs; no invented
error text; uncertain cases marked unclear. Problems, all in the pre-processing, not the model:
- the HTML-to-text step cut replies at the first nested quote block, so the mod author's answers
  were lost ("replied with only a quote");
- the author of the mod was not given, so is_mod_author was always null — supply it from the page;
- one naming overlap was labelled other_mod_conflict_identified: the label set needs definitions.
=> For P1: robust thread extraction (quotes, pagination, developer badge), labels with written
   definitions, schema validation, and a sampled manual check per batch (design §10 R2).
