# RimArcho 顶层设计（草案 v1）

> 状态：D1–D8 已定。MVP specs 见 `docs/specs/`。
> 原则：RimCrow 只作为“需求与边界情况的来源”。本设计不沿用它的界面、导航和模块划分。

## 1. 定位

**RimArcho 是给 RimWorld 玩家用的 Mod 管理器。它同时以 MCP server 的形式，把 Mod 集合的事实开放给任何 AI agent。**

- 主要用户是玩家（D2）。所有功能都要在没有 AI 的情况下好用。
- AI 能力是一层附加的东西：RimArcho 提供语义化的事实和命令，推理、权限和对话交给 Claude Code、Codex、Pi 这类 harness（D6）。
- RimArcho 不内置 LLM 调用，不做 agent loop，也不管理 API key。

## 2. 设计原则

1. **一套核心，三个表面。** TUI、CLI、MCP 调用的是同一套查询和命令，不存在各写一套逻辑的情况。
2. **可引用的实体。** 每个对象都有稳定的引用，可以出现在任何输出里，也可以继续追问：
   - `#a3f9`（内部实例 ID 的短写，见第 6 节）
   - `def:ThingDef/Gun_Revolver`
   - `patch:#a3f9/Patches/Foo.xml#3`
   - `harmony:Verse.Pawn.Tick#prefix`
   - `log:E42`（本次日志中的第 42 条错误簇）
3. **结论必须带证据。** 每个问题（Finding）都写清结论、证据引用和来源类型（声明、推断、日志、社区数据）。
4. **玩家的改动可撤销。** Loadout 的每次修改都记入历史，可以 diff、回退、分享。这是给玩家用的功能，不是权限机制。
5. **默认省资源。** 不常驻进程。索引增量更新，重活交给短命子进程。

## 3. 领域模型

```
Environment（游戏安装 + 用户数据目录）
  └─ Source（来源根目录：工坊 / 本地 Mods / SteamCMD / 其他）
       └─ Instance（磁盘上的一份 Mod，内部 ID 见第 6 节）
            ├─ Snapshot（某次扫描时的内容指纹与元数据）
            └─ Facts：ModDecl · Def · PatchOp · Harmony · Asset
Lineage（“同一个 Mod” 的家族：原版 + 本地副本 + 改名前后）
Loadout（有序 Instance 列表 + 游戏版本 + DLC，带历史）
Rule（用户规则 / 社区规则 / 替代规则；挂在 Lineage 上）
Finding（结论 + 证据[]）
LogRun（一次 Player.log，错误簇归因到 Instance / Finding）
```

## 4. 模块分层

```
┌──────────── 表面层（薄）─────────────┐
│  TUI（MVP 主界面）  CLI   MCP server  │
└───────────────┬──────────────────────┘
┌───────────────▼──────────────────────┐
│ 语义层：引用解析 · 大纲文本渲染 · 命令  │
├──────────────────────────────────────┤
│ 分析层：resolve · order · defs ·       │
│   patches · harmony · log-attribution  │
├──────────────────────────────────────┤
│ 身份层：Instance 对账 · Lineage · 变更事件 │
├──────────────────────────────────────┤
│ 事实层：SQLite，按快照增量更新          │
├──────────────────────────────────────┤
│ 采集层：文件系统 · ACF · ModsConfig ·   │
│   社区数据 · Player.log · .NET 元数据   │
└──────────────────────────────────────┘
外部：Steam 客户端（订阅 / 下载）、ilspycmd（按需看源码，D5）
```

交付形态是**单个二进制** `archo`：
- `archo`：启动 TUI（D3）。
- `archo <命令>`：一次性执行的 CLI。
- `archo mcp`：stdio MCP server。工具按 MCP 规范标注 `readOnlyHint` 和 `destructiveHint`，是否放行由 harness 决定（D6）。

## 5. 交互模型（TUI，不沿用 RimCrow 的布局）

TUI 只回答三个问题：**现在装了什么、哪里有问题、发生了什么变化。**

- **Loadout**：主列表，有序，支持移动、搜索、筛选，并按问题着色。只有一个列表，“已停用”是筛选条件，不是第二列。
- **Problems**：问题列表，展开后看到证据，一键跳到相关实体。
- **Inspect**：任意引用的详情页（Mod、Def、Patch、Harmony 目标、日志簇），带反向链接。
- **Changes**：上次扫描以来的变化，例如更新、改名、换包名、移动、消失（见第 6 节）。
- **命令行**：`:` 唤起，命令名与 CLI 相同。

不做：库存枢纽、工坊浏览器、贴图优化、推荐清单导出、主题系统、休眠屏、内置 AI 对话。

## 6. Mod 身份与变化追踪（D8）

### 6.1 问题

候选的身份信号都不可靠：

| 信号 | 失效场景 |
| --- | --- |
| 绝对路径（RimCrow 的 `path_hash`） | 玩家移动游戏目录或库目录后，全部变成新 Mod |
| 工坊 ID | 复制到本地后，副本的 `About/PublishedFileId.txt` 仍然声称同一个 ID |
| packageId | 作者可以改；不同 Mod 可以撞名；一个包可以有多个实例 |
| 名字、作者 | 随时会改 |
| 内容哈希 | 每次更新都会变 |

### 6.2 核心判断

**不存在可靠的自然主键。** 身份不能“读出来”，只能由 RimArcho 自己“维护”：
1. 首次见到一份 Mod 时，分配一个内部 ID，即 **Instance ID**。
2. 之后每次扫描，用多个信号把新观测“对账”到已知 Instance 上，而不是重新计算身份。
3. 对不上时不猜。生成一个“可能是同一个”的待确认项，交给玩家决定。

这和 git 识别文件改名、照片库处理“文件夹被移动”的思路相同。

### 6.3 观测（每次扫描为每个 Mod 目录记录）

- **位置**：`Source ID + 相对路径`。只记录相对来源根目录的路径，不记录绝对路径。
- **声明**：About.xml 中的 packageId、name、author、支持版本、依赖；`PublishedFileId.txt`。
- **外部状态**：工坊来源下的 ACF 条目（manifest ID、更新时间）；Git 来源下的 commit。
- **内容指纹**：分层计算，控制成本。
  - 结构清单：所有文件的相对路径和大小。
  - 语义哈希：About、LoadFolders、Defs、Patches、DLL 的内容哈希。这些文件小，又决定行为。
  - 贴图等大文件只比大小，不读内容。
  - 用 mtime 跳过未变化的文件，但不用 mtime 判断身份，因为复制会重置 mtime。

### 6.4 来源（Source）本身也有身份

游戏路径变化通过**来源重新绑定**解决，而不是靠 Mod 级别的猜测：
- 工坊来源的身份是“AppID 294100 的 content 目录”。本地来源的身份是“某个 Environment 的 Mods 目录”。
- 玩家修改游戏路径时，RimArcho 用新根目录下若干 Mod 的指纹抽样，与旧来源比对。匹配后只更新根路径，所有 Instance 的相对路径保持不变，ID 也就不变。
- 联接点（junction）和符号链接要先解析到真实路径，再记为同一 Instance 的别名位置。RimCrow 用链接部署工坊 Mod，这种情况会出现。

### 6.5 对账规则（按优先级）

| 级别 | 条件 | 结论 |
| --- | --- | --- |
| 1 | 同一来源、同一相对路径 | 同一 Instance。内容变了就记为“更新” |
| 2 | 工坊来源、文件夹名为同一个工坊 ID | 同一 Instance。packageId、名字、作者变了都只记变更事件 |
| 3 | 原位置消失，新位置出现；语义哈希高度相似，且声明的 packageId 或工坊 ID 相同 | 同一 Instance，记为“移动” |
| 4 | 新目录与已知 Instance 相似，但原 Instance 仍在 | 新 Instance。推断为“副本”，挂入同一 Lineage |
| 5 | 都不满足 | 新 Instance。若与已消失的 Instance 有一定相似度，生成待确认项 |

消失的 Instance 不会立即删除，而是保留为“墓碑”一段时间。这样能处理退订后又重新订阅、移动硬盘暂时拔出的情况。

### 6.6 Lineage：解决“复制到本地”

- 由 RimArcho 执行 copy-local 时，在副本中写入 `.rimarcho/origin.json`，记录来源 Instance、工坊 ID 和复制时的快照。副本自带出身，下次扫描可以直接挂回同一 Lineage。
- 如果玩家手动复制，就靠规则 4 推断，并标注“推断”。
- RimArcho 绝不往工坊目录里写标记文件，因为 Steam 校验或更新时可能删除它。

### 6.7 引用规则：什么挂在哪一层

| 数据 | 挂在 | 原因 |
| --- | --- | --- |
| Loadout 条目 | Instance ID | 玩家选的是“这一份”，不是“这个包名” |
| 用户规则、别名、分组、备注 | Lineage | 原版和本地副本应该共享；改名后也不能丢 |
| 社区规则、替代规则 | packageId（匹配时解析到 Lineage） | 外部数据只认 packageId |
| ModsConfig.xml | 导出结果 | 根据 Loadout 生成，是投影而不是事实来源 |

由此带来一个直接收益：**作者改了 packageId 之后，Loadout 和用户规则都不会断。** RimArcho 会提示“#a3f9 的包名由 A 改为 B”，下次写 ModsConfig 时自动使用新包名。

### 6.8 变更事件（Changes 视图与 MCP 的数据来源）

`updated`、`package-id-changed`、`renamed`、`author-changed`、`moved`、`copied`、`disappeared`、`reappeared`、`version-support-changed`、`dependencies-changed`。

每个事件都带前后两个快照的引用，可以下钻到具体文件的差异。

### 6.9 已知的难题（MVP 的处理方式）

- 作者分叉出新 Mod，工坊 ID 不同但 packageId 相同：判为不同 Lineage，并给出“包名冲突”问题。
- 同一个工坊 ID 同时存在于 Steam 客户端目录和 SteamCMD 目录：判为两个 Instance、同一 Lineage。
- 很老的 Mod 没有 packageId：沿用游戏的派生规则生成临时包名，并标注为推断。
- 玩家在同一时间既改了游戏路径又删了 Mod：来源重新绑定后，剩下的缺口进入待确认项。

## 7. 决策记录

| # | 决策 | 结论 |
| --- | --- | --- |
| D1 | 产品定位 | 保持“管理器”定位 |
| D2 | 主要操作者 | 玩家。AI 在玩家群体中渗透率还不高 |
| D3 | MVP 界面 | TUI |
| D4 | 与 RimCrow 的数据关系 | 独立运行，可选择一次性导入别名、分组、用户规则 |
| D5 | 程序集分析 | Go 原生读 .NET 元数据，拿到 Harmony 和类型引用；看源码时再调 ilspycmd |
| D6 | agent 写权限 | 不在 MVP 范围内，由 harness 决定。RimArcho 只是 MCP server，不是 harness |
| D7 | 现有 inspector 和两个 skill | 能力并入 MCP 后删除 |
| D8 | Mod 身份与变化追踪 | 采用第 6 节方案。墓碑默认保留 90 天，可配置 |
