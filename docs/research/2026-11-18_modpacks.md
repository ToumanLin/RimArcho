# Modpacks, revisited

> Status: research note (2026-11-18), card "整合包再研究". Nothing implemented here. Builds on 10 (packs), 07 §7 (list exchange) and `2026-11-18_mod-config.md`. Decisions in §5.

## 1. What players mean by a modpack

Talking about RimWorld, "modpack" covers four different things, from light to heavy:

| Level | Content | Typical form today |
| --- | --- | --- |
| L1 list | Mod IDs in load order | Steam collection, RimSort/RimPy XML, Rentry page, share code |
| L2 list + versions | L1 plus *which* version of each Mod (Workshop update time or hash) and the game build | rarely done; "works on 1.6.4633 with Mods as of 11-01" in a description |
| L3 list + settings | L1/L2 plus Mod settings (`Config\Mod_*.xml`, HugsLib) and sometimes game options/keys | zip of `Config\`, posted on Discord |
| L4 full | L3 plus the Mod files themselves, including local/non-Workshop Mods and patches | zip of `Mods\` (multiplayer servers, Chinese modpack sites), multi-GB |

Players want: one thing to send, "it runs like mine", nothing breaks when Workshop updates, and their own saves and settings left alone. Multiplayer groups need L2 (identical versions) more than anything.

## 2. What RimArcho has

| Level | RimArcho | Where |
| --- | --- | --- |
| L1 | list import (12 formats) and export (7 formats); Steam collection follow with catch-up | 07 §7, 16 §2.17–2.18 |
| L2 | RimArcho list carries `hash` per entry and allowed `versions`; import groups local copies as same / other version / not installed. Locked versions (07 §5) pin a Mod locally | 07 §7.3, 10 §4 |
| L3 | **none for sharing.** Packs copy the local Config into `userdata/` on first launch and never export it | 10 §3, §4 |
| L4 | `.archopack`: Mod copies + manifest with full game version, digests, origins; checked on import; launched from its own folder with its own user data | 10 |

So RimArcho already has the hardest part (L4 with integrity and isolation). The gaps:

1. **No settings in a pack** (L3). The pack author's tuned settings — often the point of a pack — don't travel.
2. **Pack size.** A full pack duplicates Workshop Mods the receiver could download. There is no "Workshop Mods by reference, local Mods bundled" middle ground; light = list only.
3. **Updating a pack.** No "version 2" of a pack: the receiver imports a new full file and gets a second pack; saves don't move with it.
4. **Discoverability.** Packs appear as a sidebar entry and on Launch, but "create a pack" is a sub-page of a list and export is on the pack page; the UX note (S7) counts 4–6 clicks.
5. **Pack vs list wording.** Players say "modpack" for L1 collections; RimArcho's "pack" means L4. The Import page's "A pack" card is clear; elsewhere it is not.

## 3. Options

### 3.1 Settings in packs (gap 1)

- **M1** — "include Mod settings" on Create a pack: copy the list Mods' `Mod_*.xml` and HugsLib packs into the pack under `settings/` keyed by packageId + class. On first launch they seed `userdata/` (the receiver's own Config is not copied then). Game settings (`Prefs.xml`, keys) excluded.
- **M2** — same, but the author ticks Mods one by one (preview with values from 16 §2.9).

### 3.2 Mixed pack (gap 2)

- **N1** — a "reference pack": Workshop Mods as `workshop_id` + `workshop_updated` + `hash`, non-Workshop Mods bundled. Import subscribes/downloads (SteamCMD can't fetch old Workshop versions, so a version mismatch shows as "other version" — L2 best effort). Much smaller, but not reproducible.
- **N2** — keep full packs only; offer texture slimming (exists) and say clearly what the size is.

### 3.3 Pack updates (gap 3)

- **U1** — a pack keeps an `id` and `revision`; importing a newer revision of the same id offers "update this pack" (replace Mods, keep `userdata/` and saves) with a diff of Mods added/removed/changed.
- **U2** — leave as is; a second pack is safer.

### 3.4 Wording and place (gaps 4–5)

- Call L1 things "lists" everywhere and say "pack (with Mod files)" in the first mention; put "create a pack" and "export" beside list export on the proposed Import & export page (UX note §4.5, C1).

## 4. Recommendation

1. **M1** (settings in packs) — highest value per effort, matches what pack authors ask for; uses the settings matching from the Mod settings page.
2. **U1** (revisions) — needed once packs are shared more than once; small manifest change.
3. **N1** later, only for multiplayer groups if asked; N2 meanwhile.
4. Wording fix with the UX restructure.

## 5. Decisions for the player

1. Should a pack carry Mod settings by default (M1), only on request, or per Mod (M2)?
2. Is a pack update that replaces Mods while keeping saves (U1) wanted, or should every pack stay immutable?
3. Is a reference pack (N1, not fully reproducible) worth having, or do packs stay "it runs exactly like mine"?
