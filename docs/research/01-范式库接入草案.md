# 错误范式库 v0 接入 MCP 的草案

> 状态：草案，不改产品代码。依据：`docs/research/00-日志语料顶层设计.md` §3 G5、§9；数据：`spikes/patterns/patterns-v0.json`，数字见 `spikes/patterns/RESULT.txt`。

## 1. 数据告诉我们什么

1.6 的 6,734 份日志，610,910 个问题簇：

- **按阶段**：加载期（XML、补丁、交叉引用、程序集、资源）70%，读档期 21%，运行期 9%。现有的诊断流程几乎只讲加载期的 XML 和运行期的 Assembly。
- **现有流程的覆盖**（按簇计）：完整覆盖 30%，部分覆盖 29%，**完全没覆盖 41%**。没覆盖的主要是读档错误（`save.*`，1,704 份日志有 `loadID` 错误）、缺资源（`asset.texture-missing`，1,821 份）、程序集依赖缺失（`asm.dependency-missing`，774 份）、配置检查（`xml.config-error`，2,004 份）。
- **修法证据的可信度取决于阶段**：同一玩家前后两次上传、列表没变时，加载期错误几乎不会自己消失（0–3%），读档期和运行期错误会（5–23%，因为玩家第二次做了别的事）。所以“改了列表之后错误消失”对加载期范式是有意义的证据，对运行期范式要和对照比较。

## 2. MCP `Instructions` 的诊断流程（改写方向）

第 3 步“Classify the failure”按实际分布重排，先讲最常见的，再讲少见的：

1. **交叉引用 / 缺 Def**（`xref.def`、`xref.sound`、`xref.getnamed`，3,700 份日志）：先看依赖候选；`SoundDef` 缺失只影响声音，可以不处理。
2. **补丁失败**（`patch.op-failed`、`patch.xpath`、`patch.findmod`）：现有 `get_patches failed=true` 路线不变。
3. **XML 字段或类型不存在**（`xml.no-field`、`xml.type-missing`）：Mod 版本与游戏或框架 Mod 不符；先查框架 Mod 是否启用、是否在前面加载。
4. **程序集版本不符**（`asm.version-mismatch`、`asm.harmony-target`、`asm.dependency-missing`、`asm.static-ctor`，合计约 3,000 份日志）：新增一条路线 —— `get_mod` 看程序集与依赖，确认依赖启用、顺序正确、没有两份不同版本的同一库；修法是更新或停用，不是改 XML。
5. **读档错误**（`save.*`、`rt.post-load`）：新增。说明这些通常来自存档中途增删 Mod；`curParent` 里的类型属于哪个 Mod，就是“存档里残留了谁的数据”，不等于那个 Mod 有 bug。修法：忽略、重新启用原 Mod、或开新档。不要据此停用 Mod。
6. **缺资源**（`asset.texture-missing`、`asset.maintex`、`asset.texture-create`）：新增。贴图来自未启用的 Mod 或 DLC，或文件路径大小写不符。
7. **运行期异常**（`rt.tick`、`rt.ui`、`rt.ai-job`、`rt.collection-modified`、`rt.nre`）：现有 Assembly 路线，加上 `Collection was modified` 与 `AllComps` 检查的对应关系。
8. **噪音**（`noise.*`）：HugsLib 上传失败、Analyzer 的状态行、Harmony IL 转储片段，直接说明不是问题。

## 3. `analyze_log` 的检查清单

每个错误簇匹配一个范式时，附上：

```
E12  xml-load  Could not find type named VFECore.ThingDefExtension …
     pattern g:xml.type-missing (community, 2,248 logs): XML names a C# class that no loaded assembly has
       causes: the framework mod that defines the class is not active or loads later; renamed in an update
       next:   analyze_log cluster=E12 → search_files VFECore.ThingDefExtension → list_problems code=dep
       evidence: in 156 repeat uploads with 1-3 list changes the error went away 16% (no change: 6%)
```

- 来源类型 `community`，置信度不高于 `possible`；仍遵守“不把出现位置当原因”。
- `next` 来自范式的 `route`，与现有 `Next` / `Checklist` 合并，范式在前。
- 回退范式（`rt.nre`、`rt.other`、`xml.other` 等）不显示 `pattern:`，只用现有清单。
- Mod 特定范式（`m:<packageId>:<hash>`）只在源 Mod 与归因一致时显示：“这个 Mod 的这个报错在 N 份日志中出现过（首次 / 最近月份）”，并标注“Mod 更新后可能已修复”。v0 的 Mod 版本大多缺失（见 RESULT 的已知问题），所以先用首次 / 最近出现的月份。

## 4. 新的引用 `pattern:<id>`

`get_pattern ref=pattern:g:xml.type-missing` 返回识别规则、诊断路线、常见原因、修法类型和 `resolution` 计数（按列表变化分组的“消失 / 总数”，以及无变化对照）。不新增工具也可以：作为 `analyze_log cluster=E<n>` 输出的一部分。

## 5. 分发

与社区排序规则相同：`archo data update` 下载 `patterns-v<n>.json`，记录数据集版本；产品内不联网收集。v0 的识别规则是对模板的正则，产品接入时应改为对 `internal/logs` 的模板和分类直接匹配，保证研究和产品一致。

## 6. 接入前要补的

- `parsed.jsonl` 漏掉带 `[v:…]` / `[ov:…]` 的 Mod 条目（约 5%，但每份日志都有，HugsLib 本身就是 `[ov:]`），修好后重新生成范式库，Mod 版本和“更新后消失”的证据才可用。
- 裸 `NullReferenceException` 等回退范式需要 `StackShape`（最内层游戏方法、最内层 Mod 帧所属程序集），v0 只有消息模板。
- 用评测集（00 §6.5）比较接入前后 agent 的结论，再决定 `Instructions` 的最终文字。
