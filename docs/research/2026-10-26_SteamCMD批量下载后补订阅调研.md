# SteamCMD 批量下载后补订阅调研

> 2026-10-26，Windows 本机研究；初轮实测约 19:53–20:15 PDT；§10 于同晚继续补测（UTC−07:00）。代码基线：主 checkout，`dev/0.9.0`，HEAD `81017d85f73f504ed59d4701c94ccd907363d8f6`。只新增本报告，不修改业务代码、不提交。作者 credit 是首要约束。

## 1. 决策摘要

**以“给作者 credit + 最终只维护一份内容”为目标，推荐持久保证全部真实订阅，由 Steam 客户端独占维护工坊内容；不把 CMD 预置当作零重下或立即可玩的保证。** 用户选中的全部 ID 都建立订阅义务，下载失败仍订阅；客户端未运行、程序退出、部分调用失败时，待办留盘并在原账户上下文继续。

§10 补测满足此前缺失的条件：六个实验 Mod 的内容目录、`WorkshopItemsInstalled`、`WorkshopItemDetails` 全部清空后，匿名 CMD 下载同版本并预置，再通过 `SubscribeItem` 订阅。客户端仍重新传输内容并替换预置文件；最终文件哈希一致不等于处理期间文件未被替换。此前 §4.3 的“零内容传输”只适用于该轮仍有安装记录的条件，不能推广到首次安装。

**异步不等于可以安全读取同一组待提交文件。** Valve 要求等待下载完成回调后访问内容。后台准备不阻塞界面或强制退出正在玩的游戏，但应在客户端处理结束后才将新增 Mod 标记为可启动；不能承诺边重下/提交边使用该 Mod。若必须立即使用 CMD 版本且让客户端同时处理，需另一份稳定内容供游戏使用，与严格“始终只有一份”的目标冲突。

作者 credit 继续使用现有 `ISteamUGC::SubscribeItem`：它建立真实账户订阅。本次初轮观察到退订后公开页面 Current Subscribers 减 1；重订成功但页面随后限流，不能提供无混杂的“重订后恰好加 1”页面证明。匿名或登录 CMD 下载本身都不能替代订阅，同账户重订也不制造新的唯一订阅者。

速度不作为本目标的决策标准。初轮四项客户端主动组为 21.275 / 22.567 秒；CMD 独立来源后补订阅、等客户端也完成为 32.065 / 29.615 秒。§3–§7 保留这些路径的测量和权衡；当前推荐以本节、§8、§10 为准。本次仍只做研究，不改业务代码、不提交。

## 3. 实验方法与速度

### 3.1 方法、计时与认证边界

- Steam 客户端使用已有登录会话和游戏自带 `steam_api64.dll`；DLL、`steam_appid.txt` 和外部 Python ctypes 观察脚本均放系统临时研究目录。调用 SDK，不启动游戏、不调用 RimArcho 扫描/部署，不写真实业务数据库。API 工具返回仅允许的条目结果和状态，不采集认证输入。
- 匿名 SteamCMD 是从 Valve 官方安装包初始化的独立临时实例，没有复制受管实例的 config、token 或设备信任文件。exe SHA-256 为 `7baf77927639793e11b2a02ec2fd6d9114c95432be2f23a3225e274732255cf4`。首次自更新、工具准备不计入下载耗时。
- 匿名每轮使用空 `force_install_dir`，四条下载命令同一进程串行。运行时、depotcache、OS/CDN 缓存可复用，**不是网络及缓存完全冷启动**；不清客户端 depotcache。两种下载器的分块复用量不同。
- 登录组只让 RimArcho 受管实例自己尝试复用缓存。RimArcho 没有选用账户名配置，实验仅在内存使用客户端已有非秘密账户名。stdin 关闭、禁止密码提示；检测需要认证就终止，仅保留阶段结果。没有读取配置中的凭据、token、ssfn，没有输入、保存密码或 Guard。受管实例锁与 `internal/accounts` 的路径归一化/Windows mutex 一致，运行前也检查没有其它 SteamCMD，不并发账号会话。
- 真实退订前先将四个旧客户端目录移入 Windows 回收站，避免 Steam 随后直接删掉原内容；回收失败则停止。每组对 ACF 留备份和字段快照。没有手工覆盖客户端 ACF；复制预置组只向这四个空内容目录写文件。
- 使用单调时钟。总时间从订阅调用前或 SteamCMD 启动前开始，计到客户端内容已安装；不含实验准备、退订、回收、等待退订清单收敛。客户端主动组在订阅后调用 `DownloadItem(true)` 并观察 `GetItemDownloadInfo`、flags、About.xml；只接受 Installed 且无 NeedsUpdate/Downloading/Pending。完成后重新读取状态；最终另做文件树哈希核验。
- 辅助工具初期回调等待少于现有 Go worker，曾读到尚未刷新的订阅位；后续加入前后回调等待，最终一律重新读取并确认。下表保留原始墙钟数值，**不能将其当作 RimArcho Go 程序的精确性能基准**。

### 3.3 串行、限速与队列

本机客户端主动下载日志先后处理 No Time Change Sounds、Recycling、Dubs Break、Disco；状态采样中其它项为 pending，一项完成后才处理下一项。SteamCMD 多条命令同样逐条处理。本次观察支持“这一队列按工坊条目串行”，**不证明 Steam 所有版本/场景只能串行，也不等于单 HTTP 连接**。

客户端出现过：

```text
Delaying next workshop updated 5 minutes (last update installed nothing)
AppID 294100 has no changes
... commit ... 0 updated, 0 moved, 0 deleted files
```

当实际目录已被回收而 ACF 仍称已安装时，仅重订阅没有立即修复，观察 120 秒仍缺内容；第二次观察 30 秒也如此。显式 DownloadItem 后恢复。这里包含“实验通过回收制造缺内容、清单收敛延迟”的条件，不能冒充普通全新订阅的平均表现；但它说明仅以 Subscribed/Installed 位或 ACF 存在判完成不可靠。

Valve [DownloadItem 文档](https://partner.steamgames.com/doc/api/ISteamUGC#DownloadItem)规定 `bHighPriority=true` 会暂停其它进行中的 Steam 下载并优先开始该项。加速器不能无条件循环提升全部条目的优先级、影响其它游戏下载；应提供明确动作并复用现有观察器。

本次未读取可能混有认证状态的 Steam 配置文件来找限速设置，也未改用户下载设置、隔离网卡流量或做极限带宽测试。不能认定客户端存在某个固定限速、SteamCMD 没有限速，或把 63.51 MB 解压体积除墙钟时间当互联网吞吐。

### 4.3 能否只保留一份、避免重传

| 方案 | 可行性 | 本次证据、风险与处理 |
| --- | --- | --- |
| 独立 SteamCMD 来源 + 客户端原生订阅 | 可行，默认接受两份 | 已实测重复内容传输；两份独立更新，简单且不会争写同一库 |
| 将 CMD 成功内容预置到客户端条目目录，再让客户端校验 | **有条件可复用字节** | 本机预置组四项均 `has no changes`、`0 updated,0 moved,0 deleted`，API 内容进度总量为 0；但本组仍有安装清单。§10 空两段记录补测发生重传与文件替换，不能保证首次安装零重下。检查仍花 19.373 秒，不保证加速 |
| SteamCMD 直接 `force_install_dir` 指向客户端 Steam 库 | 不作为在线默认路线 | 两个程序会共写 AppWorkshop、暂存/提交及内容；现有账号实例锁锁不住 Steam 客户端。已有并行研究证明共享库存在失真。**本次未对真实库运行该命令**，不以预置实验冒充同库写入验证 |
| Steam 完全退出后，仅合并目标项的 ACF 和内容，再重启客户端 | 可做显式修复功能，尚待独立验收 | 需要备份、严格解析、只改目标 ID、保留账户/未知字段、原子发布、逐项恢复和客户端重新校验；ACF 不是建立服务端订阅的 API，合并也不能代替 SubscribeItem |
| 把客户端条目 junction/硬链接到受管 CMD 来源 | 不建议双写共享 | Steam 退订、替换目录、校验与 CMD 更新可能破坏链接目标或让两方争写；身份去重也不等于文件系统生命周期安全 |

[Valve 的 GetItemInstallInfo](https://partner.steamgames.com/doc/api/ISteamUGC#GetItemInstallInfo)是读取实际安装目录的接口，不是“登记任意本地路径为已安装”的接口。`BInitWorkshopForGameServer` 针对游戏服务器，也不能用作普通客户端的内容导入通道。

参考项目 [RimModManager mgr_steam.py](../../../RimModManager/backend/managers/mgr_steam.py) 的 `repair_workshop_items_via_steamcmd` 明确要求 Steam 完全退出，`_apply_steamcmd_workshop_repair` 备份并合并指定项；它是离线修复设计参考，不是 Valve 对 ACF 格式/接管行为的保证，也没有在本研究中调用。

## 5. 作者 credit：真实订阅、统计及实验

### 5.1 哪些操作计入什么

Valve [ISteamUGC](https://partner.steamgames.com/doc/api/ISteamUGC#EItemStatistic)分别提供 NumSubscriptions、NumUniqueSubscriptions、UniqueWebsiteViews、Favorites、Playtime 等统计；[SubscribeItem](https://partner.steamgames.com/doc/api/ISteamUGC#SubscribeItem)建立订阅，[工坊实现指南](https://partner.steamgames.com/doc/features/workshop/implementation)也将它列为程序内订阅管理方式，没有规定程序订阅是“不算数的下载”。

| 操作 | 当前订阅数 | 唯一/历史订阅者 | 其它作者统计 |
| --- | --- | --- | --- |
| 网页、客户端按钮订阅，或 Steamworks SubscribeItem 成功 | 建立同一类账户订阅；同一账户同一项最多一份当前关系 | 首次成为该项订阅者才应贡献唯一用户；重复请求不制造新的用户 | 不自动成为点赞、收藏、网页访问或游戏时长 |
| 同一账户退订后重新订阅 | 当前关系撤销后再恢复 | **不能把每次重订阅当成 lifetime 新增**；本实验账户原已订阅，不适合验证“第一次订阅”的增量 | 不应通过循环退订/订阅刷计数 |
| SteamCMD anonymous `workshop_download_item` | **不建立订阅，不计入订阅 credit** | 不提供具名唯一订阅者 | 没有网页访问/投票/收藏/游戏时长动作；Valve 内部 CDN 或下载遥测不可见，不能声称“任何后台统计绝对为零” |
| SteamCMD 登录账号后 `workshop_download_item` | **下载本身仍不建立订阅，不计入订阅 credit** | 有账号身份也不等于订阅行为 | 同上；本次账号组需认证，未实际下载，因此登录组的统计行为是接口语义结论，非实测成功 |
| 官方 Web API SubscribePublishedFile | 获授权调用成功时语义为真实订阅；本次未验证计数 | 不应假设其可绕过去重 | 需要 publisher key，不能作为普通启动器的客户端免登录方案 |

[ISteamRemoteStorage Web API](https://partner.steamgames.com/doc/webapi/ISteamRemoteStorage#SubscribePublishedFile)的 `SubscribePublishedFile` 要求 **Steamworks publisher authentication key**，文档要求只在安全服务器调用、不得直接放客户端。普通用户 Web API key、Steam OpenID、已有客户端登录，都不能替代游戏发行方权限。RimArcho 不应收集 key、浏览器 Cookie 或 token 来绕开客户端依赖；无 key 的 `GetPublishedFileDetails` 只用于公开只读元数据。

“与按钮同类真实订阅”的结论有官方语义和下面公开计数变化支撑；**没有访问作者私有统计后台，也没有验证 Valve 内部聚合/反滥用算法逐项实现**。公开 API 的 `lifetime_subscriptions` 与 SDK “unique subscriptions”按历史唯一订阅口径解读，不能用一次重订阅或跨用户总量的自然变化证实精确计费/推荐权重。

### 5.3 credit 优先时，怎样“最终补上全部订阅”

绝对保证受 Steam 服务、账户状态和用户是否再打开 RimArcho 限制。可保证的是**意图先持久化、未确认不遗忘、恢复后继续，不能静默报全部完成**：

1. 在任何下载开始前，原子保存全部去重工坊 ID 的订阅意图，包含 AppID、目标 Steam 账户的非秘密标识、创建时间、逐项状态、重试时间和错误分类。不依赖 Instance 已被扫描出来，也不依赖 `source.json` 存在；没有下载成功目录的条目一样需要记录。
2. 下载状态和账户订阅状态分开。若采用“最后补”，**所有下载尝试结束（成功、失败、取消）即处理整个原始选择集**，不能筛选 `okIDs`。长时间卡住的下载须有取消/超时出口；退出时至少保留订阅意图，不能只依赖进程内 defer 收尾。
3. 客户端没运行时标“等待 Steam，作者订阅尚未完成”；不声称已订阅，不用 anonymous 冒充，不自动抓网页会话。应用启动/回到前台/Steam 恢复时重试；应用运行期间可低频探测，避免每秒创建 worker。没有常驻后台的产品约束下，关闭应用期间不会自行推进。
4. 本地可用会话确认目标账户后才提交。不同账户登录时等待用户确认，不能把旧账户的 obligation 自动发给当前账户。每项收到成功并刷新订阅位后原子记 confirmed；若回调/网络未知则保留 unknown，稍后查询当前状态再重发。**不得为了重试先 Unsubscribe**。
5. 崩溃发生在远端成功、本地确认前时，恢复后查询/幂等重复 SubscribeItem；允许至少一次尝试，不能承诺跨服务的 exactly-once 事务。成功条目不重新下载；业务失败与统计页面缓存分开处理。
6. 暂时故障退避、抖动，持久保存 `next_attempt_at`；例如 5 秒起指数增加至 30 分钟，达到单轮次数上限后延后/显示待处理，而不是删除义务或无限紧密重试。明确权限、删除、封禁等失败保留为“需要用户处理”，给工坊页面；网络恢复不能解决的错误不盲重试。
7. 用户明确取消“订阅意图”才可移除待办；取消下载默认不取消 credit。已经订阅的项不因本地删除/回收下载副本自动退订。任务历史清理不能抹掉尚未确认的语义待办。

**批量不是事务，速率没有可依赖的官方固定数值。** 当前 50 项/worker 可以作为上限，首版可保守分成更小窗口、批间等待并按结果调节；这些是策略值。Valve EResult 的 84 是暂时 RateLimitExceeded，25 是 LimitExceeded，24 是 InsufficientPrivilege，26 是 Revoked。网页 HTTP 429 与 SubscribeItem EResult 84 属不同接口，本次只实测到网页 429，未压测账户订阅限额。不要将 SteamCMD 每批 25 项误说成订阅 API 限额。

顺带核查发现 [workshopresult.go](../../internal/app/workshopresult.go) `WorkshopResultText` 的 24/25 文案与官方 EResult 对不上；实现这项功能时应修正错误分类，否则会错误地把权限问题当限流、把限额当撤销。原始数字应保留供诊断，本研究不修代码。

## 6. RimWorld 读哪一份、两份怎样管理

RimWorld 正常读取游戏 `Data/`、`Mods/`，Steam 版还通过 Steam 的工坊条目目录发现内容；它不会自行遍历 RimArcho 的任意 SteamCMD 来源目录。以本机为例，Steam 客户端工坊根在 `D:/SteamLibrary/steamapps/workshop/content/294100`，另有已登记的 `D:/rimworld16/steamapps/workshop/content/294100` 和受管 SteamCMD 来源。

[deploy.go](../../internal/app/deploy.go) `deployable`、`DeployName`、`planLinks` 会把所选 SteamCMD Instance 经 `Mods/_Archo_<来源标签>_<目录名>` 链接给游戏。方案指向 Instance；同一个工坊 ID 的客户端份和 CMD 份是**两个 Instance、同一 Lineage**。Lineage 合并标签/规则，不做字节去重，也不会自动把方案切换到“最后下载那份”。

[loadout.go](../../internal/loadout/loadout.go) `NewRegistry` 按 Data、Mods、workshop 顺序登记；本地/链接份已占 packageId 时，工坊份可能成为 `<packageId>_steam`。它不是按时间自动选最新，也不是两份自动内容同步。补订阅后多一份可见工坊候选，会影响 token 分配，须由现有 registry 正确写 ModsConfig，不可手写 packageId 或静默换实例。

| 模式 | 方案以哪份为准 | 更新负责人 | 去重/回收条件 |
| --- | --- | --- | --- |
| 保持客户端默认 | 客户端 workshop Instance | Steam 客户端 | 无需新增 CMD 副本 |
| 可选 CMD 加速且长期保留 | 玩家选择的 CMD Instance，经链接部署 | RimArcho 发起 SteamCMD 更新；客户端仍独立自动更新自己的份 | 接受磁盘两份，不设双写链接；报告各自版本，不自动同步 |
| CMD 仅为临时加速，最终交给客户端 | 先临时 CMD，交接后显式切换到 workshop Instance | 交接后 Steam 客户端 | 等客户端 verified、游戏未运行，处理方案引用/入链，再把不用的 CMD 副本移回收站；不能删仍被某方案或其它环境使用的副本 |
| 显式离线修复/预置客户端 | 客户端 workshop Instance | 发布完成后只让 Steam 管它 | 需独立发布/回滚合同；不对同一真实目录同时登记两种来源所有权 |

因此，“先下再订阅”可以保留作者 credit，但不会自然产生单副本或单一更新责任。推荐第一版宁可接受独立两份，也不把 ACF 合并和身份/链接迁移偷偷塞进下载加速。

## 7. 一致性、回退与玩家实际等待

| 状态 | 应呈现和继续的行为 |
| --- | --- |
| CMD 成功，账户订阅失败/未知 | 显示“内容已可用；作者订阅待完成”，保留来源、成功下载和独立订阅待办；只重试订阅，不重下、不回滚可用内容 |
| CMD 失败，账户订阅成功 | 保留真实订阅，客户端可继续下载；对失败 ID 提供客户端优先下载/页面和错误。**下载失败项仍订阅** |
| 两边失败 | 两类错误分别保留；权限错误不因换下载器消失。已有文件不当作下载成功 |
| 页面计数未更新但订阅已确认 | 以账户 API 订阅状态作业务依据，注明公开统计可能延迟；不循环退订/重订阅验证 credit |
| 匿名权限拒绝/不可见/年龄或所有权限制 | 先维持全部订阅意图；客户端当前会话有权访问时可走客户端。若用户已配置受管 CMD 账号，可串行用缓存仅重试失败项；账号组需要重新认证就暂停并提示用户在原生窗口完成，随后由用户重试 |
| 私有、仅好友、已下架、封禁、依赖许可缺失 | 登录不保证有权限，不绕过可见性/年龄/所有权。明确无法取得，打开原工坊页由用户处理；不可撤销错误不无限重试 |
| 程序退出/崩溃 | 订阅意图留盘；下次启动在原账户上下文恢复。不能让 GUI 任务历史里的 stopped 变成永久遗漏 |

对严格“最后订阅”的等待模型：

- 等两边都完成：`T_CMD + T_订阅 + T_客户端检查/重传 + 发布开销`，通常比只客户端增加阶段，本机已经如此；不能宣传整体更快。
- 允许 CMD 可玩后放行：`T_CMD + T_扫描/链接 + T_订阅确认`，客户端同步不在前台等待路径；本机 CMD 阶段较短，但未测实际启动，收益仍需集成验收。
- 只下载很快但订阅一直挂起：作者 credit 尚未完成，必须保留明显状态，不能把“快”建立在漏订阅上。
- 客户端本来就快、内容已最新、出口/磁盘已满：CMD 先行可能只增加启动和传输。应保留现有默认及随时回到客户端的选择，不先强制把全部内容送 CMD。

对于作者 credit，**最稳妥的默认仍是先真实订阅，让客户端处理下载**；需要加速时可选择独立 CMD 来源，而订阅义务从用户确认选择的那刻就建立。若产品仍坚持网络动作最后执行，应采用 §5.3 的预先落盘与失败收尾，不能让“最后”成为下载成功的前置条件。

## 8. 推荐改动位置、规格影响与验收

本节为后续实现建议，**本次未实施**。对 credit + 单份内容的目标，默认采用“先持久记账 → 对全部选择项真实订阅 → 客户端异步下载/校验 → 完成后供下一次启动使用”。不需要为了这个目标强制增加 CMD 阶段；预置只能是可失败的内容提示，不能成为正确性前提。

| 位置 | 建议 |
| --- | --- |
| `internal/app/subscribeworkshop.go` `SubscribeWorkshop` | 在任何下载/订阅网络调用前持久化全部选中 ID；分别报告订阅确认与客户端内容就绪。默认直接真实订阅，内容准备异步进行，失败条目保留订阅义务 |
| 同文件 `downloadWorkshop`、`runWorkshopSteamCMD`；`internal/app/subscribe.go` | 保留非 Steam 环境的独立来源路线。若提供 CMD 导入客户端的显式操作，复用另一分支的 25 项批量执行器，下载到客户端库以外的同卷独立 staging；不把客户端库传给 `force_install_dir`，不登记该临时目录为第二个长期来源 |
| 应用层持久订阅待办模块；`internal/store` | 用账户非秘密标识 + AppID + WorkshopID 唯一约束，原子落盘 pending/unknown/confirmed/needs-action、重试时间及错误；完成需账户订阅状态确认。下载失败或取消下载不删除待办，明确取消订阅意图才撤销 |
| `internal/app/workshopsub.go`、`internal/steamworks/worker_windows.go` | 复用逐项 SubscribeItem，部分成功逐项提交；超时先查询再幂等重试。现有每批 50 是实现值，Valve 未公开固定 QPS，使用有限窗口、限流/网络退避与抖动，不声称“一次原子订阅全部” |
| `internal/app/workshopwatch.go`、`internal/steamworks/watch.go` | 后台观察客户端结果；必要时显式 `DownloadItem(false)`，不默认抢占其它下载。等待目标 AppID/ID 的完成回调并复核 state、实际目录/版本；不能仅凭 Installed 或 About 存在提前标可用。现有完成判断还需排除 NeedsUpdate，并补完成回调及错误处理 |
| `internal/app/tasks.go`、启动/任务入口 | 启动时读取持久订阅义务并恢复，不依赖重新打开后变 stopped 的任务历史；Steam 未运行时 pending，已有原会话可用再续。应用退出暂停执行，不新增隐藏常驻进程 |
| `internal/app/deploy.go`、`linklifecycle.go`、`internal/loadout`、启动入口 | 未就绪的新工坊 Instance 不进入可启动方案；运行中的方案不自动换源、不改入链。后台任务可继续准备其它内容，但本应用不主动请求更新当前游戏正在使用的目标；外部 Steam 更新仍不能靠本应用锁保证安全 |
| `internal/accounts`、结果文案 | 保留现有实例锁、缓存和用户原生认证入口；该锁不是 Steam 客户端库锁。匿名失败可交给有权的客户端，或用现成 CMD 缓存串行重试；需要重新认证时暂停，不读认证文件。保留初轮 EResult 文案修正建议 |

若仍实现 CMD 预置：客户端下载根不是 CMD 目标。CMD 的独立 AppWorkshop ACF 只服务 staging 下载；程序只读其 manifest/size 供核验，**不复制、不合并到客户端 ACF**。在新条目未被订阅、客户端目录及两段记录均空、游戏未使用该项的条件下准备完整目录；只有客户端完全退出才有可执行的单写者交接边界。同卷原子改名发布，随后启动客户端、补全部订阅、让客户端自行重建记录和必要时重下。客户端已运行时仅检查 flags/ACF 不构成排他锁，现有账号锁也不能防客户端争写；保守回退直接订阅并让客户端装，不覆盖它的目录。

客户端接管后以 workshop Instance 为准、后续更新只归客户端；不写 CMD `source.json` 到客户端目录，不让 CMD 继续向其增量更新。已有 CMD 长期来源是另一 Instance；同 Lineage 不代表可以删。只有游戏结束、所有方案/环境入链已处理且客户端已确认完整后，才可把旧 CMD 副本进回收站；共享引用未处理时不能宣称已实现全机单份。单份指最终活跃来源，回收站和下载/提交过程仍可能占空间。

规格需评审的变化：

- **02 §3.4、08 §10/§11**：独立记录账户订阅与内容就绪；全部 ID 的 credit 义务、账号绑定、下载失败仍订阅、跨退出恢复。预置是可选导入流程，失败退回客户端，不能承诺零重下。
- **01 §4 写入清单、07 存储/生命周期**：持久待办、独立 staging、同卷发布、客户端退出边界、回收与崩溃恢复；默认路线无需开放 ACF 写权限。
- **06 库存/订阅/任务、05 命令/MCP**：分别显示“已订阅”“等待 Steam”“下载/校验中”“可用于启动”；后台任务不阻塞界面，对尚未可用的新 Mod 明示等待。
- **04 方案、08 §3 链接部署及启动合同**：Instance 不因同工坊 ID 自动换源；完整就绪后才扫描/部署，运行中不换目录或链接。严格单份与“客户端处理时立即读取同一份”的冲突必须写清。

验收覆盖：下载全部失败仍为全部 ID 订阅；退出/崩溃跨确认窗口；部分批失败与限流退避；Steam 关闭、原账号恢复及切号；ACF 暂时不可读；空 ACF 下预置被重下/替换；启动门槛、正在玩的方案不换源；客户端完成后 staging 回收；已有 CMD 副本仍被方案引用时拒绝自动回收。失败不退订、不整份恢复 ACF、不删除仍在使用的来源。

## 9. 复核方法、证据链与结束状态

### 9.1 实际步骤与复测边界

公开元数据的复测命令，不带 Cookie、密码或 key；计数会随时间变化，不应紧密轮询，遇 429 停止：

$researchIDs = @('2436747646','1722398508','3155781848','2572368517')

for ($i=0; $i -lt $researchIDs.Count; $i++) { $researchBody["publishedfileids[$i]"]=$researchIDs[$i] }

本机使用 Python 标准库 `sqlite3.connect('file:<数据库绝对路径>?mode=ro', uri=True)` 只读查询；授权集的 SQL 如下。复测前必须重新核对标签、真实路径、游戏未运行和用户许可，不能拿历史名单当永久授权：

```sql
SELECT i.id, i.rel_path, i.real_path, i.status, s.kind, s.root, n.name
FROM instance i
JOIN lineage_tag t ON t.lineage_id = i.lineage_id
JOIN source s ON s.id = i.source_id
LEFT JOIN snapshot n ON n.id = i.current_snapshot_id
WHERE t.tag = 'I Dont Need It' AND s.kind = 'workshop';
```

## 10. 空客户端条目预置补测：单份内容与运行时读取

### 10.1 条件与步骤

本节补上 §4.3 的关键缺口：**模拟首次安装的本地条件是目标目录不存在、两段 ACF 均无 ID**，不是“刚退订”或只看详情段。两轮仍使用同一账户的已有客户端会话，只用 `I Dont Need It` 授权集合；原四项加 Ruthless Faction Pursuit、BioReactor，共六项、75,396,063 字节、486 个官方包文件。授权集合最大的是 Disco!（44.35 MB），没有为加入更大 Mod 操作标签外条目。

1. 每轮先只读复核标签、客户端库、游戏未运行和没有其它 CMD 会话。备份完整 ACF、两段目标/非目标字典及原目录文件树；旧实验 Mod 目录先进回收站，然后一次提交六项 `UnsubscribeItem`，六项均回调成功。
2. 不编辑 ACF。等到六个目录、安装段、详情段全部为空，保存 `empty.acf`。第一轮等了 **308.266 秒**，第二轮 **307.829 秒**；日志均出现“五分钟后再检查”。第二轮期间正常退出/重启客户端也未立即清掉旧安装段，仍等原队列收敛；不能用重启代替检查条件。
3. 清空后才用独立匿名 CMD 实例下载六项最新版本，`force_install_dir` 指向系统临时实验库，成功耗时 **12.112 / 11.045 秒**，均 6/6，没有认证提示。没有将客户端库作为 CMD 目标，没有复制账号 config 或认证文件；全局 depotcache、OS/CDN 缓存未清，不称为彻底冷缓存。
4. 三个较大条目从 C 盘实验库复制到 D 盘客户端目录；另三个先复制到 D 盘独立实验 staging，再同卷改名到客户端条目。逐项核对全部文件哈希；不放 CMD 的 ACF 或 `source.json` 进去。预置前后客户端两段记录仍为空，客户端不会因目录存在而立即生成安装记录。
5. 第一轮在客户端运行时预置后订阅；第二轮在客户端完全退出时预置，再启动原客户端会话（观察工具约 **5.655 秒**后可访问），随后订阅。每项 `SubscribeItem` 均回调 EResult=1。观察器 SDK 会使 Steam 视该 App 为运行中，自动任务曾被 `Suspended` 暂停；约观察起点 30 秒时显式调用 `DownloadItem(false)`，六项均接受，未调用全局暂停/高优先级抢占。
6. 第二轮用 Windows 目录事件、约 30 ms 目标元数据轮询、约 0.5 秒全树哈希，以及每项一个允许 READ/WRITE/DELETE 共享的持续只读句柄观测。读句柄不阻止客户端替换。用 UGC progress、目标完成回调、ACF、工坊/内容日志、暂存目录及网卡累计数交叉核对，结束再用独立短命 SDK 进程确认。

第一轮观察器在约 35.237 秒读 ACF 时遇共享访问拒绝，监测中断；后半段只保留客户端日志和最终文件证据，**不算作全程读取安全验证**。第二轮加入短暂 ACF 锁重试，完整覆盖六项处理及完成后约三秒。其事件观察器退出等待通知，直到 **221.789 秒**才写完结果；这是工具收尾时间，不是校验耗时。唤醒退出仅对实验 About.xml 设置原来的同一时间戳，内容、mtime、文件标识均不变；该事件在有效观察窗口外。

### 10.4 客户端替换期间能否直接玩

第二轮覆盖六项处理的元数据检查 **773 轮**、全树哈希尝试 **119 轮**、持续句柄读取尝试 **714 次**；最大元数据采样间隔 **0.331 秒**，最大哈希间隔 **0.576 秒**。事件监听没有报告溢出/错误。目标根目录没有收到删除或改名事件，但这不代表目录内文件稳定。

事件记录展示逐文件提交：先建立 `0Harmony.dll~RF….TMP`，旧 `0Harmony.dll` 改名到临时名字，原路径添加新文件，然后临时备份被移除；全部 486 个原文件各有一对旧/新名事件。客户端日志示例：

```text
21:24:01 update started : download 0/28343568, reuse 0/2219008, stage 0/44352603
21:24:02 starting commit ... workshop/downloads/294100 ... workshop/content/294100 : 148 updated, 0 moved, 0 deleted files
```

这里的“0 deleted”不是“不会撤掉旧文件”，更新提交仍会逐文件替换，不是一次整个 Mod 目录的原子快照切换。若版本不同，还存在新旧内容混合的可能；本次同版本实验只证明替换行为，未实测不同版本时的具体故障。持续元数据抽查反复记录到文件标识改变；在观察起点 **35.646 秒**，Disco 的一次全树哈希遍历遇 **PermissionError**。该记录未保存具体失败路径，可能涉及正在替换的原文件或瞬时临时文件，不能据它断言游戏一定读失败，更不能推断游戏必崩。差异明细仅保留前 1,000 条，多数是同一标识变化被重复采样；不能把差异条数当作独立损坏次数，也不能用截断明细证明全部持续句柄读取都无异常。

[Valve DownloadItem 文档](https://partner.steamgames.com/doc/api/ISteamUGC#DownloadItem)明确要求在成功请求后的 DownloadItemResult_t 回调前不要访问磁盘内容，NeedsUpdate 时同样适用。已有、允许删除共享的读句柄能继续指向旧文件，并不保证游戏稍后按路径打开其它文件成功；本次没有运行 RimWorld，也没有测试真实 DLL/资源加载器的锁行为。**本机证据不支持“客户端处理这份内容时，玩家可保证直接启动并使用同一 Mod”。**

“后台异步”可以做到不阻塞 GUI，也不必为准备未使用的新 Mod 强制停止当前游戏；但当前游戏应继续读取既有稳定内容，新增 Mod 等完整就绪后再用于下一次启动。本应用不应在游戏使用该项时主动请求其替换；Steam 自己的更新策略也不受 RimArcho 的实例锁控制。如果要求在客户端提交期间立即使用 CMD 内容，需要独立稳定副本，或把接管推迟到游戏结束；不能同时承诺始终只有一份、随时接管、随时安全读取。

### 10.5 可行性、失败退化与实现边界

| 方案 / 条件 | 补测结论 | 产品处理 |
| --- | --- | --- |
| 真正空两段记录、最新完整内容、再订阅 | 两轮均重传并替换，含客户端关闭预置变体；不能保证零重下 | 允许退化成正常客户端安装；保持订阅，完成后才可用于启动 |
| 已有安装记录的同版本预置 | 初轮 §4.3 曾零内容传输；条件不同 | 可作为优化机会，不当作正确性或安全合同 |
| 目标是最终一个活跃来源 | 可由客户端最终接管实现 | CMD staging、旧副本都需处理引用后回收；下载/提交和回收站仍占空间，不承诺瞬时无副本 |
| 目标是同一份内容处理期间立即可玩 | 没有保证，已观察逐文件替换 | 不开放这条启动路径；等待就绪或接受临时第二份稳定内容 |
| SteamCMD 与运行中的客户端直接共用库/ACF | 未实施，仍有双写风险 | 不采用；账号进程锁不能协调客户端 |

若保留显式预置功能，具体方案已列 §8：CMD 永远下载到客户端库外的独立同卷 staging，自有 ACF 不导入客户端；发布只在客户端完全退出、目标无记录/无引用/无活动任务时同卷改名；客户端启动后全部补订阅并自行检查/重下，确认完成才扫描为 workshop 来源，后续只有客户端更新。**本目标的更简单推荐仍是直接真实订阅、后台等待客户端完成，省去 CMD 下载和接管。**

订阅义务与发布成功无关：先为全部选择项持久记账，成功、失败、取消下载都进入补订阅收尾；遇客户端不可用、程序退出、临时限流就保留原账户待办，下次启动续；部分成功仅确认成功项，其余退避重试。匿名失败不取消 credit，优先交给有权限的客户端；已有 CMD 登录缓存可串行重试，需要重新认证就交用户原生窗口处理。任何失败都不自动退订、不覆盖客户端 ACF、不回滚其它订阅。

未测变体：先订阅再立刻放内容的竞态、旧 manifest 内容。没有现成且可验证的旧版本，不伪造旧 manifest 或把损坏包冒充旧版；客户端已对完整同版内容重下的结果足以否定无条件零重下承诺。没有补测账号下载、公开页面统计或更大未授权 Mod，沿用 §5 的 credit 依据和认证边界。
