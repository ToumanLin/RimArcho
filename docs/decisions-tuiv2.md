# TUI v2 decisions (V0 follow-up, V1, V2)

Date: 2026-10-19. Spec: docs/specs/06-TUI.md v2. Commits 280e360 … cb39b54 (local, not pushed).

## V0 follow-up

### 1. Thumbnail ghosting: the image size is RimArcho's, never the terminal's

A thin sliver stayed under the rect after a tall preview (`thumbs-2-after-slow-scroll.png`). The cause:
WezTerm's `preserveAspectRatio=1` does not fit the image into width×height. It keeps the width and derives
the height, so a preview taller than about 0.87:1 runs below the 18×9 rect. The rect clear (ECH on rows
3–11) then leaves the overflow, and rewriting text over image cells does not erase them.

Ruling: scale the thumbnail to fit 18×9 cells, take the fewest rows N that hold it, pad it with
transparent pixels to exactly 18×N cells' pixel aspect, and send `width=18;height=N;preserveAspectRatio=0`.
The image then covers exactly those cells, and ECH over the 18×9 rect erases all of it.
Evidence (07 §6.2):
- 8 magenta test aspects: the drawn extent stays within the rect, and every clear leaves 0 px.
- The original 500-row scroll, replayed: 1398 px of sliver with the old sizing, 0 px in all 10 shots with
  the new one.

06 §6.2 states the sizing and clearing rules.

### 2. archo memory in WezTerm

The single 78–80 MB V0 sample does not reproduce. With identical inputs:
- A fresh start is 31 MB (7 runs, 3 launch methods, Go heap 5–8 MB).
- The tuimem session driven in real WezTerm is 44 MB idle (peak 53), matching the headless 47 MB.

`TuneProcess` is applied on the CLI path, and a SQLite WAL recovery after a killed process was ruled out.
No code change. Re-measure with `spikes/tuiv2-v0/archosession.ps1` after V3 adds the thumbnail cache.

7. **Needs-attention count** (top bar, until V4 defines the groups). It adds up:
   - errors and warnings a player can act on, with the version-support warnings counted once;
   - Harmony warnings only when a log shows them (06 §7.3);
   - identity questions, an external change of the list, and a list saved for another game version.

   The real environment shows 32.
8. **`archo tui`** is the TUI, the same as no arguments. **wezterm.lua** is generated by
   `internal/wezterm` (the V0 settings plus `exit_behavior = 'CloseOnCleanExit'`). The download and launch
   flow is still V5.

## V2 four columns

9. **Staging lives in the app** (`archo stage list|add|drop|restore`, 05 §3), because the TUI holds no
   business logic. It is one JSON list per environment in the meta table.
   - Each mod staged from the Loadout keeps its old position and an anchor: the mod before it. The anchor
     moves forward past mods staged earlier that stood between, so batches can be staged in any order.
   - Restore follows the anchor chain through mods that are still staged; the position is the fallback.
   - `add` and `restore` are one undo step each. A staged mod that is enabled again by any means (undo,
     enable, checkout) leaves staging.

   Tests: T9 with 20 mods, randomised batches over 12 seeds, anchors after edits, prep-area mods, `--at`.
10. **Hidden staging.** 06 §5.1 said "<140 隐藏暂存列，用 t 键查看", but `t` stages (§5.3). Ruling: `t` keeps
    staging, and ←→ / tab always reach staging, which then takes the first column's place. Below 80 it is
    the third tab (`[ ]`). 06 §5.1 is updated.
11. **Focus.** It cycles over the three lists. The detail column follows the cursor and is not focusable
    in V2; its actions come with V3/V4.
12. **`l` and `h`** now switch columns (06 §5.3), so the log chooser moved into the 需要处理 screen (`l`
    there). `f` (filter cycle) and `1/2/3` are gone: the columns replace the filters, and `!` and `c` open
    the old Problems and Changes screens, with `esc` back.
13. **Filter.** Every word must be a substring of the name, alias, author, package id or folder. Only when
    nothing matches does a subsequence of the name count ("hsl" → "Hair Style Lib"). A subsequence over
    every field matched 222 of 872 mods for "harm".
14. **Drag.**
    - From "not enabled" or staging onto an enabled row: placed at that row's number; below the last row:
      at the end.
    - Within "enabled": move.
    - Onto staging: stage. Enabled onto "not enabled": disable. Staging onto "not enabled": unstage.
    - Press and release on the same row is a click. The status line names the drop while dragging.
15. **Detail column in V2.** Name, author, source · supported versions · position, a one-line problem
    state, and the technical information collapsed behind `i` (the `mod` command, loaded only when
    expanded). The layered detail with the thumbnail is V3.

# Tags, per-column search, details (between V2 and V3)

The user's review of V1+V2 asked for three things before V3: tags, search per column by field, and
more information in the details, including the description. The spec is in 06 §2.1 rule 6 (package id
shown), §5.5 (search), §5.6 (tags), §6.1 (the detail), and §6.4 (description sources, measured).

## Decisions

1. **Search** (`/`, 06 §5.5): free words match name, alias and author fuzzily. The fields are
   `name:`, `author:`, `tag:`, `id:` (package id, Workshop id or `#ref`), `type:` (source
   `official|workshop|local|copy|git|steamcmd`, content `assembly|xml|language`, with the long forms
   `xml-only|language-pack`), and `has:problem|error|tag|note|alias`. `-` negates a term and terms
   are ANDed. A single free word with no match falls back to letters in order. Each column keeps
   its query until esc; the header shows the query and N/M.
2. **Content kinds** (`type:assembly` etc.) come from one GROUP BY over the current snapshots' file
   lists, loaded on the first such query and kept until the database changes. On the real-size copy
   (1353 mods) that is 246 ms once; every later query takes under 1 ms.
3. **Tags** (`#`, 06 §5.6): work on the selection (`v` marks); `word` or `+word` adds, `-word` removes;
   tab completes from the tags in use, most used first. Rows show their tags as a faint suffix when
   there is room. CLI: `tag add|remove <ref> <tags…> --mod <ref>…`. MCP: `set_player_data`.
4. **Detail** (06 §6.1): a non-technical section by default with the package id, version, Workshop id
   (`o` opens the page), tags, alias, note, what the mod requires (✓ enabled, ! not enabled,
   ⨯ not installed), and the description. The technical information stays folded behind `i`.
5. **Description source** (06 §6.4): About.xml is read on demand. The Workshop page is fetched for
   the selected mod only, after a 400 ms dwell, and cached by Workshop id and time_updated.
   `workshop.fetch off` keeps everything offline. Only the Workshop text is shown when About.xml is
   under 300 characters or both start alike (images ignored); otherwise both are shown. Measured on
   1274 mods: Workshop text is ≥ 300 characters for 90%, About.xml for 41%; 55% of Workshop texts
   have images, 7981 in all.
6. **Images**: drawn inline in WezTerm (OSC 1337), at most 60 columns wide; in the detail column at
   most half of the 12 description lines, in the full view at most 20 rows. While loading an image
   takes one line. Elsewhere (and with `workshop.images off`) it is a `[image · host]` placeholder.
   Downloads are cached as PNG at 720 px; GIF shows its first frame; WebP is a placeholder.
   `imgur.com/x.png` links go straight to `i.imgur.com`. Requests carry a RimArcho User-Agent.
   No OCR.
7. **Full-screen detail**: `enter` opens it, and it scrolls (↑↓ j k, PgUp PgDn, g G). `o` opens the
   Workshop page, `r` re-fetches, `#` edits tags, `i` shows the technical information, `tab` opens the
   older inspect pages, `esc` goes back.
8. **Screenshots** are now taken with PrintWindow, so a covered WezTerm window is captured as itself
   and the user's foreground window is never raised over or captured (the first try with
   CopyFromScreen caught another window and was deleted).

# V3: layered details, thumbnail, full-screen details

06 §10 V3: the layered detail, wrapping, the thumbnail and the full-screen detail (T6, T7).
Parts of the detail (the non-technical section, the description, inline images) came
with the previous round; V3 adds the rest.

## Decisions

1. **Thumbnail** (06 §6.2): `About/Preview.png` (any case; JPEG content is accepted) is scaled to
   360 px wide and cached as PNG under `<home>/cache/previews/<snapshot hash>.png`. The mod folder is
   only read. In the column the block is 18×9 cells, always reserved; the image takes the fewest
   rows that hold it (16:9 → 5), padded to exactly 18×N cells, `preserveAspectRatio=0`.
   - It is drawn only after the cursor has rested 150 ms on the mod.
   - On any selection change it disappears in the next frame, and the whole 18×9 block is erased
     with ECH in the same write.
   - A mod without Preview.png shows a faint "无预览" in the block.
   - Below 16 text cells beside the block there is no block.
   - The compatibility mode has no block, and the name starts at the top (§1.3 updated to match §6.1).
2. **Image cache**: encoded images (thumbnails and description images) are kept for at most 24
   entries; the ones not on screen are dropped first. This bounds the TUI's largest allocations.
3. **Full-screen detail** (06 §6.3): `enter`, 36×18 thumbnail, and five numbered sub-sections.
   - The sub-sections are Def, 补丁, Harmony, 规则 and 完整历史; `1`–`5` jump to them.
   - Def, patches and Harmony come from the CLI commands' text, with `#refs` replaced by names.
     Each shows at most 60 lines; `tab` opens the technical pages for the rest.
   - 规则 is About.xml's declared order plus the player's rules that name the mod, written in words.
   - 完整历史 is every change event of the mod, newest first.
   - The column shows a one-line history: the three newest events, e.g. "10 月 19 日首次发现".
4. **Wrapping** (T7): every text in the detail wraps by display width.
   - `wrap()` now shares the description's token wrapper. It breaks at spaces and between CJK
     characters, never inside a Latin word.
   - It follows the kinsoku rules, breaks over-long paths after `\` or `/`, and keeps a line's indent.
   - Status lines, description headers, long dependency names and the footer wrap instead of being
     cut. Only the column's "… enter shows all" and BBCode tables (wide columns) still use "…".

# V4: 需要处理

06 §10 V4: grouping, plain wording, one-key actions, notification-style changes (T8). It
follows 06 §7, with the additions recorded in §7.2 (V4 rulings).

## Decisions

1. **What an item is.** Each item of 需要处理 is built from the problem set and the
   environment's open questions:
   - its group (06 §7.1);
   - one sentence made from mod names;
   - the keys that act on it;
   - whether it is counted.
   Problem codes, `#refs`, `pkg:`, `p:` and the other CLI reference forms never reach the screen.
   They remain in the technical information, the CLI and MCP.
2. **The count.** The top bar shows the number of counted items. A list row has an icon exactly
   when its mod is the subject of one of them.
   - On the real data copy this is 19 instead of the old 32.
   - The 13 that dropped out are 5 `def.abstract-collision` and 8 `patch.no-match` whose target is
     absent rather than disabled.
   - The player cannot act on those, so they moved to the technical information.
   - Harmony warnings without log evidence were already excluded. The 16 errors and 46 warnings of
     the old screen counted info-only folds and stale-log rows as well.
3. **Keys.** Each item names its own keys, shown under the selected item:
   - `S` sort (preview first).
   - `space` enable the dependency, or disable.
   - `o` open the Workshop page: the declared URL, else a Workshop search.
   - `space` on an incompatible pair or a duplicated mod opens a chooser: disable which one, or
     keep which copy.
   - `enter` / `x` on an order cycle: the requirements in words, then ignore the suggested one.
   - `s` / `c` / `u` answer an identity question.
   - `L` / `I` load or ignore an outside ModsConfig.xml change.
   - `w` save a list that was saved for an older version.
   - `enter` on log items opens the log and its evidence (a technical page).
   Screen-level keys are `A` (check the files again) and `l` (choose a log).
4. **Changes** (06 §4.1). After a scan the status line reads "扫描完成 · 3 个 Mod 有更新 · 1 个改了包名 ·
   按 c 查看". `c` lists the last scans' changes in words: mod name and what happened; `enter`
   still shows the changed files. Identity questions and the outside change of ModsConfig.xml
   moved to 需要处理, and the old changes screen with codes and refs is gone.
5. **Safety found while testing.** `app.ChildAnalyze` refuses to start when the executable is a Go
   test binary.
   - A real-data test that opened the app without an in-process analyzer started `tui.test.exe
     analyze`. That binary ran the tests again, which started it again, and so on.
   - Every copy worked only on temp copies of the data, and nothing outside them changed: the real
     ModsConfig.xml md5 and archo.db time were checked afterwards.
   - The processes were stopped, and the real-data tests now set `AnalyzeRunner`.

# V5: command palette, double press, WezTerm host, bundled font

06 §10 V5 (T4, T10).

## Decisions

1. **Command palette** (06 §8): `ctrl+k`, a `❯` input line over the results.
   - It finds 19 commands by Chinese name or English alias. Each command does what its key does,
     and the key is matched as the description.
   - It finds every mod (`enter` jumps to the mod, clearing a column search that hides it), and
     the other environments (`enter` switches).
   - Ranking: prefix 4 > substring 3 > subsequence 2 > description 1. Ties go to commands, then
     environments, then mods, then the shorter name. An empty query lists commands and
     environments only.
2. **Double press** (06 §9): `arm(key, warning, run)`.
   - The first press puts "✗ 再按一次 … " on the status line; the same key does it; any other key
     cancels ("已取消").
   - Used where `u` cannot undo: loading an outside ModsConfig.xml change (`L`, replaces unsaved
     edits; it was a y/n panel) and identity answers (`s` / `c` / `u`).
3. **WezTerm host** (06 §1.1), `internal/host`. Only a bare `archo` reaches it; `archo tui`,
   `archo --here`, CLI commands and MCP never do (`wantsHost`, tested). Order of the check:
   - Already inside WezTerm (`TERM_PROGRAM`): run here.
   - `terminal.host none`: run here.
   - Look for wezterm-gui on PATH, then `%ProgramW6432%` / `%ProgramFiles%` / `%LOCALAPPDATA%\Programs`
     `\WezTerm\`, then `<data dir>/wezterm/`.
   - None found and a console to ask on: "Download the WezTerm portable build (about 66 MB)…? [Y/n]".
     - No: `terminal.host none`, run here, with a note on how to change it.
     - Yes: GitHub `releases/latest`, take `WezTerm-windows-*.zip` and its `.sha256`, download to a
       `.part` file while hashing, compare, check that every zip entry stays inside
       `<data dir>/wezterm/` before writing any, extract, and set `terminal.host wezterm`.
   - Then write `<data dir>/wezterm.lua` (CloseOnCleanExit, fonts from `<program dir>/fonts`) and
     start `wezterm-gui start --config-file … -- archo tui [--env x]`. This process exits.
   - Any failure (download, checksum, start) says so and runs the TUI here.
   - No console (redirected or piped): never ask, run here.
4. **Bundled font**: `scripts/release.ps1 -MapleTag v7.9` (pinned).
   - It downloads `MapleMono-NF-CN.zip` and `.sha256` from github.com/subframe7536/maple-font
     releases, verifies the hash, and takes `MapleMono-NF-CN-Regular.ttf` and `-Bold.ttf`.
   - `OFL.txt` comes from the repo at the same tag; the script checks it is the SIL OFL.
   - Everything goes under `fonts/` in the zip. The download is cached in `dist/cache/` (gitignored).
     No font file is in git.

# V2.1: instance picking, tag bar, widths, images, detail scrolling (06 §12)

Implements 06 §12 (commit f7ba56a). Where §12 and the rest of 06 disagree, §12 wins. Where
§12 was open or disagreed with itself, these are the calls made.

## Decisions

### Picking (§12.2)

1. **space picks.** The table says `space` picks the row when nothing is picked. The bullet
   below it says the old single keys (`space` enables or disables) still work. Both cannot
   hold, so the table wins: `space` (and `v`) pick or unpick one row. A single mod is enabled
   with `space` `→` `enter`. `J` `K`, `m`, `t`, `T`, `x`, `S`, `w`, `u` and `L` are unchanged
   when nothing is picked.
2. **shift+↑↓ has two meanings.** It extends the range until the first action. After that it
   moves the picked mods by 10, as the action table says. Before any move nobody wants "move
   by 10", and after a move a wider range is rarely wanted.
3. **ctrl+↑↓ always moves the cursor**, picked or not, so that `ctrl+space` can pick rows that
   are not next to each other.
4. **`t` ends the session.** It stages the picked mods (or takes them out of staging) and
   keeps everything as one undo step. The cursor stays in its column, as §12.2 says.
5. **Into Enabled goes to the suggested position**, also from staging. It does not go back to
   the place the mod had before it was staged; that is still `T` or `space` with nothing
   picked. The suggestion (`App.SuggestAt`) uses the sorter's edges. It is just after the last
   enabled mod a picked one must follow. With only "load before" constraints it is just
   before the first of those mods. With no constraints it is the end. The official-first
   edge is ignored.
6. **↑↓ outside Enabled** does nothing and says so ("↑↓ move mods within Enabled only").
7. **One undo step.** `App.BeginBatch` records the newest undo step. On `enter`, the steps the
   session made are replaced by one step that holds the list as it was at the start. On
   `esc`, the list and the staging list are restored exactly and the session's steps are
   deleted, so there is nothing to redo.
8. **Changing column ends the pick.** `tab`, `[` `]`, a click elsewhere, or a plain click all
   keep what was done. Only `esc` undoes it.
9. **Tags are not undone.** Tags added with `#` during a session stay after `esc`. They are
   player data, not the load order, and are not part of the list's undo.
10. **The mouse:** click moves the cursor, ctrl+click picks one more, shift+click picks a
    range. Drag-to-move from V2 is removed, as §12.2 says (no drag or box select in the TUI).

### Widths and wrapping (§12.1)

11. **Storage.** Widths and wrap flags are stored per environment as JSON in meta
    `ui.columns:<env id>`, not in `config`. They are layout state, not settings. `=` resets
    the widths of all columns but leaves wrapping on or off.
12. **Narrow screens.** From 80 to 109 columns there is no detail column, so the two lists
    share the width in proportion to their widths. Below 80 there is one list at a time and
    widths do not apply; `<` `>` say so. When the stored widths leave the detail under 40
    cells, the widest column that is not focused shrinks first, down to 12 cells.
13. **Wrapping** wraps by display width. Continuation lines start under the name and carry
    the pick bar `▌`. The unsaved dot goes on the last line, and tags are not shown on
    wrapped rows. The cursor's row always shows in full.

### Tag bar (§12.3)

14. **Preset pinned tags** are the default value of `tags.pinned`. They are not written to the
    database on first run, so `config get` shows them and `config set` replaces them. Both `,`
    and `，` separate tags.
15. **Typing on a candidate** jumps to the input and types there. `#` `←` then typing works as
    §12.3 says; typing straight away also works.
16. **The bar closes after `enter`**, as T13 needs (`#` `→` `enter` twice adds, then removes).
    The pick stays, so `#` can be used again. With nothing picked, the bar replaces the status
    line. While picking, it sits under the hint.
17. **Free-valued settings.** `config` now accepts settings with free values: `tags.pinned`,
    and `ui.preview_dwell_ms` (0–5000). `ui.previews` (on|off) is new too.

### Images (§12.4)

18. **Two loaders.** The visible images and the ±10 prefetch use separate slots, one image
    each. A miss on the current row therefore never waits behind a prefetch. A finished load
    is kept even if the cursor has moved on, since it is a prefetch for later.
19. **"One image per frame"** is done in the writer. Each frame redraws the images already
    shown, because the frame may have written over them, and adds at most one new image. The
    rest follow 16 ms apart without a new frame. In the compact detail there is only ever the
    thumbnail, so this matters for the full screen.
20. **The compact detail** replaces all description images with one line, placed where the
    first image was: `[图片 ×3 · enter 在全屏中查看]`. Outside WezTerm it is `[图片 ×3]`. The
    full screen still lists each image, as text outside WezTerm.
21. **The LRU** holds 64 encoded images. Thumbnails are already stored at 360 px wide
    (`PreviewWidth`), so 64 of them stay within a few MB. Images on screen or still loading
    are never evicted.

### Detail focus and full screen (§12.5)

22. **`→` enters the detail from Enabled and Staging** when the detail column is shown and
    nothing is picked. `tab` still cycles the three lists, so Staging is reached with `tab`
    (or `]`). `→` from Disabled still goes to Enabled.
23. **While the detail is focused** it shows the whole description (no 12-line cap). When it
    is scrolled, the first line is `▲ <name>` in the accent colour. The name line is in the
    accent colour while the detail has focus. `i`, `o`, `r`, `#` and `enter` act on the mod
    shown and keep the focus. Any other key goes back to the list and is handled there. A
    click on the detail column focuses it, and the wheel over it scrolls it.
24. **The full-screen `tab`** goes through 概要 and the five sub-sections. `1`–`5` still jump.
    The technical pages, which used to be on `tab`, are now on `I`. Each `tab` says the
    sub-section's name on the status line. `←` `→` move the list's cursor, so `esc` returns to
    the last mod viewed. The wheel scrolls three lines.

# V2.1 follow-up: thumbnail height, WezTerm memory

## Thumbnail block

The block under the thumbnail is as tall as the image. Before the size is known it is 16:9
(prefetch usually knows it first). It is one line for "no preview". The erase on moving
away covers only the image's own rows, and the old 9-row erase is gone: it could blank
unchanged text below a short image.

## WezTerm memory

V3 recorded wezterm-gui at 161 MB (V0: 91 MB) and guessed image textures. Measured with
`mem21.ps1` (scratchpad). Each run used its own `wezterm-gui start --always-new-process` on a
data copy and the same 20240203 build the host installs. The session: rest on N mods, open 5
full-screen details, idle. Working set in MB:

| Configuration | Start | After 40 mods | After 40 + 5 full screens |
| --- | --- | --- | --- |
| Default, images off | 99–157 | 145–207 | 163–223 |
| Default, images on | 98 | 160 | 172 |
| OpenGL | 107 | 143 | 161 |
| WebGpu | 155 | 383 | 379 |
| Software | 101 | 163 | 177 |
| Line caches 256 (+ image cache 16), images off | 102 | 127 | 132 |
| Line caches 256, images on | 100 | 133 | 141 |

| 150 mods, images on | After 150 mods | After + 5 full screens | CPU (s) |
| --- | --- | --- | --- |
| Default caches | 188 | 209 | 14.3 |
| shape_cache_size 256 only | 186 | – | – |
| Line caches 256 only | 144 | – | – |
| Line caches 128 (chosen) | 136 | 152 | 15.2 |
| Line caches 64 | 132 | – | – |

Findings:

1. **Images are a small part.** With images off the growth is nearly the same. The cost is
   WezTerm's per-line render caches (`line_state_cache_size`, `line_quad_cache_size`,
   `line_to_ele_shape_cache_size`, 1024 each by default). Every distinct line shown is
   cached, and browsing mods shows many distinct lines, most of them CJK. `shape_cache_size`
   makes no difference.
2. **128 lines** keeps most of the saving (64 saves only 4 MB more) and still holds a
   maximised window's lines, so frames are not reshaped. CPU over the same session matched
   the default.
3. **OpenGL is pinned.** In this build the default behaves like OpenGL. WebGpu used 2.3× as
   much memory, and a later WezTerm could make it the default.
4. **Also set:** `glyph_cache_image_cache_size = 16` (archo's own LRU holds the images) and
   `scrollback_lines = 0` (the TUI runs on the alternate screen).

The idle baseline is still about 100 MB, close to V0's 91 MB. It is the GPU context and the
font; the config does not change it. archo's own working set was 46–58 MB in these runs,
under the 80 MB gate.

Caution for later scripts: if `WEZTERM_UNIX_SOCKET` is empty, `wezterm cli` falls back to
the default socket, which may be the user's own window. `mem21.ps1` now stops if it cannot
find its own `gui-sock-<pid>`. In the one run where that happened, the CLI refused anyway
because no pane was focused, so nothing reached another window.

# V3 interaction model (06 §13)

Implements 06 §13 (commit 3e9c416). §13 replaces the pick session and floating hint of
§12.2 and the "→ into the detail" case of §12.5. §12.1, §12.3 and §12.4 are kept. These are
the calls made where §13 was open.

## Decisions

### Areas and the arrows (§13.3, §13.4)

1. **← from the detail goes back to the list whose mod it shows.** It does not go to area 3.
   At 130 columns Staging is not on screen, and from Enabled at 160 columns area 3 would show
   another mod. → from Staging (area 3) still reaches area 4. ←→ do not wrap. `tab` /
   `shift+tab` go round all the areas, the detail included.
2. **No detail column (below 110 cells):** area 4 does not exist. `4` says so and points to
   `enter`. PgUp/PgDn and the wheel page the list, because there is no detail to scroll.
3. **The wheel scrolls the detail wherever the pointer is**, as §13.4 says. It no longer
   moves a list's cursor. Lists are scrolled with the keys, or by a click.
4. **Scrolled detail:** the 12-line cap on the description only applies at the top. Once the
   detail is scrolled (PgDn from anywhere) or focused, the whole description shows, so
   `PgDn` `PgDn` reads it (§13.9). A PgDn pressed before the mod's details have loaded is
   kept until they arrive.
5. **The detail column has a title line**, `4 详情` (it becomes `▲ name` once scrolled), in
   the accent colour while area 4 has the focus. Its content starts one line lower, level
   with the first list row. While area 4 has the focus, the lists are drawn unfocused, so
   there is one bright place.
6. **In popups both pairs of arrows choose** (§13.4 table): the palette and the tag bar take
   ↑↓ and ←→, and the position input steps through its options with either pair.

### Selection (§13.5)

7. **`v` still toggles**, as an alias of `ctrl+space`. `ctrl+↑↓` are plain cursor moves.
8. **A plain click in the same list keeps the selection.** It moves the cursor, like ↑↓ do.
   A click in another list drops the selection. The hint line says so in advance:
   `←→ 换列表会取消选择`.
9. **Tagging keeps the selection**, so `#` can be used again. `space` and `t` drop it,
   because the rows leave the list. `J`/`K` and `m` within Enabled keep it.

### Verbs (§13.6, §13.7)

10. **`shift+J`/`shift+K` cannot be told apart from `J`/`K`** in a terminal: `J` is already
    shift+j. Moving by 10 is on `alt+J`/`alt+K` (also `alt+j`/`alt+k`).
11. **After `space` enables, the cursor stays in Disabled**, so several mods can be enabled
    in a row. The status line says `✓ 已放在第 352 位 · m 改位置`. An `m` pressed as the
    very next key moves the mods that `space` just placed. Any other key forgets them, just
    as it clears the status line.
12. **`space` in Staging** puts the mod back where it was, like `t` there and like
    §5.4. Disabling from Staging makes no sense.
13. **The position input** is one list of options, each one line except `最前 · 最后`, which
    share a line. Positions count in the list without the moving mods, which is what
    `MoveBlock` and `Enable` take. `（第 N 位）` beside a name is that mod's current number.
    There are up to 5 name matches, ranked prefix, then substring, then letters in order.
    `tab` makes them "before" and keeps the chosen row. The input sits under the columns,
    which give it their last lines, so a thumbnail never covers it.
14. **The suggested position for mods that are already enabled:** `App.SuggestAt` now
    takes them out of the list first, so `m` can suggest a place for a move too.
15. **`m` from Staging with several mods** enables them at the place and takes them out of
    staging. `Restore` only takes a placement for one mod. This is one undo step; staging
    itself is not on the undo stack, the same as before.
16. **One undo step per verb** comes from one app edit per verb. The pick session's
    `App.BeginBatch` is no longer used by the TUI. It is left in `internal/app` (with its
    test) for the main session to keep or remove.

### Search and position line (§13.3, §13.8)

17. **The "其他区" line is the status line while typing**, not a line under the column title.
    A line there would push every row down.
18. **`tab` while searching** moves the query to the next list to the right (wrapping) that
    has matches, puts the cursor on the first match, and ends the typing. Ending the typing
    is what makes `/` name `tab` `space` work in 3 keys: otherwise `space` would type a space.
    The list it left has its query cleared.
19. **The position line** is on the right of the top bar, before `L 启动`, which is dropped
    first when space runs out. On full-screen, technical, 需要处理 and 最近变化 screens it is
    the breadcrumb. The place counts the visible (searched) rows, and `已筛选` marks a search.
    In the detail, the section comes from the heading above the top line (概要, 简介, 历史,
    技术信息) plus how far down it is.
20. **Popups.** The five of §13.2 are the palette, tag bar, position input, confirm panels and
    help. The `:` command line and the `r` rule prompt are kept as inputs for advanced use,
    and only `?` lists them. Search shows as `› 搜索`, and a pending double press as `› 确认`.
    Confirm panels and help still use the whole body, as before.
21. **esc in the technical pages closes the whole stack** (backspace goes back one page), so
    T20's three presses hold from any depth.
22. **Hint line:** at most 7 pairs, the last being `? 全部按键`. `!` is no longer on the
    hint line (the top bar shows the count), but `!` still works and `?` lists it.
