# Pre-release VM tests

Add a row below after completing a new feature, new key or existing feature whose behavior changed.
Visible UI-only changes should not be added to this list.
Before a release, walk every row in the VM with real data to find potential bugs, following [the 2026-10-27 scenarios 5, 6 and 9](research/2026-10-27_vm-scenarios-5-6-9.md).

- Record findings in that round's research report; fix them or add them to the backlog. Move tested rows into that report; keep only untested rows here.
- **One row is one VM session.** When a new feature is tested with the same setup as an existing row (same staged home, same game round, same agent connection), add it to that row as a labelled part instead of adding a row.
- **Actually enter the game**: every real scenario round must launch → reach the main menu → start a colony and play for a few minutes (pause, speed up, open some windows) → save → load that save → exit normally through the game menu. Then check the game log page (Player.log and ArchoMonitor.log) and "errors from the last run" in can it run; verify errors from loading, save loading and play all match. Reaching only the main menu does not count as testing game-log rows. Run this round with `pwsh scripts/vm/round.ps1`, not screenshot-driven game clicks. It checks steps and phase order and stores `archo problems` and `archo log` output in the evidence directory. Read page text with `cdp.mjs text` for subsequent UI checks.
- VM usage: [scripts/vm/README.md](../scripts/vm/README.md). Scenario writing: [VM automation test plan](research/2026-10-27_vm-automation-test-plan.md) §5, §7; §3 lists all player actions. This table records only additions or changes since then.
- Perform destructive operations only on Mods tagged "I Dont Need It". Restore Steam account changes (subscribe, unsubscribe, SteamCMD login) afterwards: reverting snapshots does not undo account changes.
