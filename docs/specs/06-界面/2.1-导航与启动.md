### 2.2 顶栏、状态行、提示行

**GUI 顶栏**（2026-10-22 改）：只有面包屑（如“库 / 方案 / 主力殖民地”，15px，最后一级加粗）和紧挨着页面名的 chip（环境，如“main  1.7”；能不能跑写“方案  环境”；首页跨环境，不显示）。**顶栏没有按钮**，每一页都一样：收起侧栏的按钮在侧栏顶部（§2.1），启动键只在启动页（§2.3、§2.5）。面包屑的每一级都可点击返回。页面没有另外的大标题（面包屑就是标题）；面包屑下方第一行是**页面头**：左边淡色写这一页此刻的状态或结论（只在有信息时写，例如能不能跑的结论、编辑器的“启用了 34 个”；**不写“这一页是做什么的”**，§7.3），**页面级动作在这一行的右端**（`.page-head` 的 `.page-acts`；没有状态文字的页面动作也在这一行）。页面级动作是安静的“图标 + 文字”按钮，没有边框，只有主操作是实心按钮。方案编辑器也有这一行（§2.5）。

**TUI 顶栏**（已实现）：品牌、当前环境（药丸）、能不能跑 N、未写入 N，用两格空白隔开，右侧是位置行（§3.2）和 `L 启动`（空间不够时先去掉它）。进入二级界面时左侧换成面包屑：`RimArcho › 能不能跑`、`RimArcho › 已启用 › Combat Extended`。游戏运行状态不在顶栏，在状态行右端（§9.1）。

两个界面的底部都是：
- **状态行**：一句话。`✓`（绿）完成、`✗`（红）失败、`…`（次要色）进行中。下一次按键时清除。GUI 在方案编辑器和全屏详情里于状态行左侧显示位置（§3.2）；其他页面不显示（面包屑已经说了在哪），状态行也不再显示“游戏里现在是”（见 §2.5）。能撤销的结果后面带“撤销”链接。
- **提示行**：当前对象此刻能用的动作，`键 说明   键 说明`（每组之间三格，GUI 16px，§7.3），最多 7 项，最后一项是 `? 全部按键`。按键用文字色，说明用次要色，不用分隔点。能不能跑不在提示行上（顶栏或侧栏已经显示数字），用 `shift+2` 去，`?` 会列出它。

“未写入 N”：方案的编辑即时持久化（04 §1），不存在“未保存”。这个数字和行上的 `●` 表示“与上次写入游戏的列表不同、启动或写入游戏时才会写进去”的条目数，只是提示，不阻止启动（08 §2）。界面文字已改为“未写入”。

### 2.3 启动（原首页）

已实现（GUI，`home.js`；2026-10-23 改为瑞士式网格，设计稿见 `docs/design/home-drafts` 的 F）。页面是 12 栏网格，重心是一个大标题；一条粗线下按“01 游戏 → 02 列表 / 整合包 → 03 启动”从左到右三栏。编号就是聚焦键：`1` `2` `3` 把焦点放到这一栏（§3.5 的 `1`–`9`，§7.3 第 8 条）；聚焦的那一栏编号用强调色，不画框（2026-10-23 定）。可以铺背景图（§2.14），图从顶栏下面一直铺到状态行上面。
- 列出**所有环境**的方案和整合包（`view.AddOtherEnvs`：另一个环境的方案用 `app.PlansIn`，不加载那个环境）。没有页面头的文字和页面动作（重新扫描在 Mod 库 › 订阅与更新的变化记录区，新方案 / 导入在方案页）。
- **大标题**是**现在应用的**那一项（`view.PickFeatured`：当前环境的当前方案；在这里应用过整合包、并且此后当前方案没变时，是那个整合包）的名称。上面一行小字：类型（强调色）、环境 chip、Mod 怎么变（“跟着工坊更新” / “版本锁定  自己的存档”）；下面一行：Mod 数（含没写入的数）、能运行的游戏版本（方案写它允许的版本，04 §1.6；整合包是它的 Mod 的 supportedVersions 交集，`view.PackVersions`）、玩过的日期、状态（绿点可以启动 / 琥珀三角有问题 / 空心圈还没检查）。换了应用项时标题从下往上滑入。
- **01 游戏**（`1`）：页面上有方案或整合包的环境，按名称；每行名称和游戏的**完整版本**（`1.6.4871 rev590`，`HomeRow.GameVersion`，02 §2.1；2026-10-24 起，原来只写 `1.6`）。名称在左、可省略号截断，版本在右不换行，悬停写完整版本；版本读不到时空着。点一个游戏就应用它这次会话里上次应用的那一项，没有时应用它最近玩过的那一项（先切换环境）。
- **02 列表 / 整合包**（`2`）：所选游戏的方案（在前）和整合包，各按最近游玩排序（启动记录，08 §2；从没启动过的按名称在后）。每行名称、问题标记（▲ 有问题，○ 还没检查）、右侧淡色“类型  Mod 数”。未选的行退成淡色，选中的行是文字色加粗，行前一个强调色小方块，换选择时小方块滑过去；换游戏时这一栏的行依次进场。
  - **点一行就是应用**：先切换到它的环境（如果不是当前环境），方案成为当前方案，整合包记在 GUI 设置 `ui.gui.home.pack`（环境、包名、当时的当前方案）里。不写任何游戏文件（`API.HomeApply`）。再点已应用的那一行去方案编辑器或整合包页。
  - **切换过程在启动色块上**：页面不清空、不弹“正在切换”的框；01 / 02 的小方块立刻移到所选项，启动色块变成进度：换游戏写“正在切换到 X…”和“正在载入游戏，请稍候…”，换列表写“正在应用 X…”，底边有一条来回的进度条；读完后标题换成新的，色块上的字从下面落进来。切换在后台读数据（§3.1 规则 9），**窗口照常能用**：侧栏能换页，别的页面先显示上次的内容再刷新；只有启动键和会写这个游戏的动作在切换完成前变灰，悬停写“正在切换到 X”。切换中再点另一项，以最后一次为准，前一次的结果丢掉。切换与加入游戏由后台会话准备数据，通过带请求序号的事件返回；扫描和首次分析在后台完成。
- **03 启动**（`3`，焦点在启动键上）：全页唯一的强调色色块“启动游戏”（`L`；右下写“环境 — 名称”和 →；方案和整合包都直接启动，08 §2、§5.3）。按下后写“正在启动…”，游戏的运行状态到了就变成“游戏运行中  N 个错误”（文字色底，禁用，同时只运行一个游戏，08 §4）。
  - 色块下面是**应用项的问题**（细线 + 一两行字）：当前方案先看**最可能出事的问题**（`view.LaunchHint`，`Home.Launch`）：`app.LaunchChecks`（08 §2，按日志语料的观察 / 机会从高到低）里第一种在能不能跑里有计数项的问题，第一行是那一项的标题（多项时“…，另有 N 项同类”），第二行淡色是它的一句原因和语料数字，琥珀色，点击去能不能跑；只挑能不能跑里有的项。没有这一种时写“N 个问题会出错”（同样去能不能跑）；再没有时，整合包的链接还留在 `Mods/` 就写它（中性色，08 §5.3）；再没有时写未载入的外部版本（中性色）；都没有时不出现。它从不阻止启动。
  - 问题右边有 ×：收起后不再显示，直到这一项、它的游戏、它的 Mod 或问题本身有变化（指纹：应用项、环境 chip、Mod 数与没写入数、版本、状态、问题文字与计数、自上次游玩以来的变化；存在 GUI 设置 `ui.gui.home.hidden`，重启后仍然收起）。侧栏“能不能跑”的角标不受影响。
- **右上**两行文字，各是一个链接（只有有内容时才显示那一行）：
  - **上次游戏**：只写结果，“上次游戏  10 月 21 日  3 个错误 →”（没有报错时“没有报错”，去游戏日志；有报错去能不能跑；游戏在运行时写“游戏运行中  N 个错误”）。页面打开或窗口重新得到焦点时，`Player.log` 比上次读过的新就自动读一遍（`app.NewLog`，读一次很便宜）。从没有过游戏记录时这一行不显示。
  - **当前方案**：只说当前方案，“当前方案自上次游玩以来 5 个 Mod 更新，1 个需要处理 →”（`view.ChangeHome`，“需要处理”是会影响启动的行数）。点它打开订阅与更新的变化记录区，范围和时间就是这一句说的（当前方案、上次游玩以来）。没有变化时写“没有变化”；还没玩过时说“自上次扫描以来”；还没扫描过时点它重新扫描。整个库存的变化不再出现在首页。
  - 没玩到（1.1，10 §3）以后加在这里。
- **按键**：`1` `2` `3` 聚焦三栏；焦点在 01 时 `↑` `↓` 换游戏，其他时候 `↑` `↓` 应用所选游戏里的上一个 / 下一个，`←` `→` 换游戏，`Enter` 打开应用项（焦点在启动键上时是启动），`L` 启动，`shift+1–8` 换页。提示行：`1–3 栏  ↑↓ 列表  ←→ 游戏  enter 编辑  L 启动  shift+1–8 页面  ? 全部按键`。
- **颜色与动效**：全部用 §7 的颜色变量和字体，跟随浅色 / 深色主题；问题用琥珀色。系统开启“减少动态效果”时页面没有动画。
- **背景之上的文字**：有图时页面和顶栏用固定的浅色文字（不随浅色主题变），图上压一层暗化（设置里的值）和三处加深：左侧、底部（三栏所在处）、顶栏下方。选“纯色”时没有图，页面跟随主题。窗口窄于 1000 像素时右上两行不显示、03 启动换到下一行；窄于 720 像素时变成一列。
- **内存**（§10）：页面只拿缓存好的 1920 宽 JPEG（`/bg`），从不加载原图；离开启动页就把背景层从页面上拿掉（`setBackdrop` / `dropBackdrop`），WebView2 可以释放解码后的位图。
- 数据：`view.BuildHome`：每个方案和整合包（`view.PackRows`）、启动记录（08 §2）。当前方案的状态用 `BreakCount`，其他方案用 `view.PlanProblems`（读 `view.PlanCheckOf` 的已存结果，从不触发分析；没有结果时写“还没检查”）。整合包行写“编译时检查过”，整合包还没有自己的分析。背景：`API.HomeBackground`。

### 2.4 能不能跑

**游戏 Mod 链接面板**：按游戏分组，小标题显示名称、版本和路径；每个链接一行，显示文件夹名 → 目标路径、简短本地化原因（目标不存在、指向未知位置且归属未确认、重复入口、无法读取），行尾标签写“将删除 / 保留”（恢复操作写对应动作）。长路径从中间省略，悬停显示完整路径。修复确认框复用同样的分组和行；TUI/CLI 使用相同简短原因，终端保留完整路径。健康入口不列入此面板。

链接健康每次取页面数据时现查全部已知游戏，按游戏路径汇总。修复使用一个确认框，复用上述分组行和动作标签；完整路径可悬停查看，技术归属证据留在 CLI 检查中。默认只纳入有凭据且可修复的链接。归属未证实项须用明确的“纳入此链接”动作后再确认；真实目录、未知类型和不可访问项没有删除动作。确认绑定服务端原预览，路径、身份、类型或目标变化须重新检查；游戏运行时拒绝修复。所选游戏的断链阻止方案/包启动，其他游戏的问题只汇总；详见 [08 §3](../08-启动与整合包.md#3-链接部署)。

原名“需要处理”。已实现（GUI 的能不能跑页、TUI 的 `@` 界面）。四个区和凭据在视图模型里（`Need.Section`、`Need.Evidence`），GUI 和 TUI 都按区显示、每项带凭据 chip。
- 数据：`view.BuildNeeds`；游戏运行时把 `view.LiveNeeds` 的“本次运行”项放在“上次运行的报错”分组最前。动作由 `view.Do` 执行。
- 范围：当前方案（GUI 顶栏面包屑和标题写出方案名）。整合包运行时，“本次运行”标明是哪个包（“整合包 X 的报错不是方案的”）。

| 新分组 | 包含（原分组） |
| --- | --- |
| 会让游戏出错 | 原“这个列表”（官方内容顺序、加载顺序、顺序矛盾、同一个 Mod 启用了两份、列表里有但没安装、已启用但无法加载、为旧版本写入的列表、版本不支持的汇总、有维护中的替代品）、原“缺少的前置”（缺失或未启用的依赖、目标未启用的补丁、继承的定义不存在）、原“冲突”（不兼容的 Mod 同时启用）；`Mods/` 里同包名的两份（`pkg.duplicate-mods`，有能移的普通文件夹时第一个动作是“收进锁定库”；以及和本地副本重复的整合包链接，08 §3、§5.3） |
| 上次运行的报错 | 游戏运行时先列“本次运行”（`GroupThisRun`），再列原“上次运行”：当前方案最近一次游戏日志中的错误，按 Mod 归并；旧日志折叠成一行 |
| 要你确认 | 原“需要你确认”：身份待确认项（02 §5.4）、ModsConfig.xml 的外部修改冲突（04 §4.3）、整合包留在 `Mods/` 的链接（08 §5.3，一键“移除链接”）、现在的游戏不在列表允许的版本里（04 §1.6，“加入 1.7” / “去全部列表”） |
| 隐藏的 Mod | 锁定版本上游有更新、退订残留、单独隐藏（08 §6） |

- 每项：一句人话 + 凭据 chip + 一键操作。凭据 chip 有五种：Mod 自己声明（About.xml 的依赖、排序、不兼容）、推断（RimArcho 的分析：补丁落空、继承缺失、排序推断）、日志（Player.log 的证据）、社区数据（社区规则、替代品，04 §6）、社区日志（玩家分享的日志里量出来的，03 §4.3 的日志语料层：来源写实测比例，如“缺了它时 40/50（80%）出错”“一起启用时 30/40（75%）出错，单独时 2/100（2%）”）；排序要求来自玩家自己加的规则时写“你的规则”。chip 后面是具体来源：“About.xml 的 modDependencies”、“log:E3  10 月 19 日 21:04”、“补丁 1.6/Patches/X.xml:4 没有找到目标”。
- 写法、合并、计数和不出现的内容见 §5。计数跟着 03 §4.3.1 的严重度和 04 §5.3 的约束强度：弱的和无害的顺序要求、顺序矛盾（info）淡色列出、不计数；Mod 自己的已知错误是淡色的一行说明，不计数。
- 页面级动作：重新检查文件（`A`）、选择日志（`l`）。分析从没做过时标题旁写“还没检查过 Mod 的文件”；文件在上次检查后变了时写“文件在上次检查后变了”；正在检查时写“正在检查 Mod 的文件…”。
- GUI 的布局：页面头写结论（“主力殖民地还不能放心玩：修好下面 2 个问题就行”），面包屑旁的 chip 写“方案  环境”，页面动作是重新检查、游戏日志。下面是一列，按后果排四个区：会让游戏出错（红色小标题）、上次运行的报错（日志色，标题旁写哪次运行）、要你确认、隐藏的 Mod；小标题后是该区的计数，没有项的区不显示。每个区是一张卡片，卡片里每项一行：粗体一句标题（`Title`，没有时用 `Text`）、一句平实的解释（`Why`）、凭据行（chip + 来源）；右侧是一个主操作按钮，其余动作在 `⋯` 菜单里。光标是一层淡底色加强调色标题（§7.3）；↑↓（`j` `k`、PageUp/PageDown、Home/End）移动，← → 跳到上一个 / 下一个区，动作键直接执行（§3）。侧栏角标 = 页面上的计数项（看板的计数加本次运行的报错）。Archo 面板（1.1）只留了接口（`screens.js` 的 `archo.ask`），还没有面板。
- TUI 的布局（`needs.go`）：同样的四个区和顺序；小标题是区名（会让游戏出错用错误红，其余淡色）加两格空白和计数项数，上次运行的报错后面写哪次运行（“本次运行”、“整合包 X”或 `LastRun`）。每项是状态图标加一句话（`Text`），下一行是淡色的凭据 chip：图标 + 种类 + 两格空白 + 来源，如 `≣ Mod 自己声明  About.xml modDependencies`；光标所在的项再下一行列出它的按键。图标按 §7（完整模式用 Nerd Font，兼容模式用下表的字符）：

  | 凭据 | Nerd Font | 兼容模式 |
  | --- | --- | --- |
  | Mod 自己声明 | file-text-o `U+F0F6` | `≣` U+2263 |
  | 推断 | flask `U+F0C3` | `◊` U+25CA |
  | 日志 | bug `U+F188` | `◍` U+25CD |
  | 社区数据 | users `U+F0C0` | `⬡` U+2B21 |
  | 你的规则 | user `U+F007` | `⌂` U+2302 |
  | 社区日志 | pie-chart `U+F200` | `◔` U+25D4 |

  ↑↓（`j` `k`、PageUp/PageDown、Home/End）移动，← → 跳到上一个 / 下一个区。顶栏的“能不能跑 N”= 页面上的计数项（分析的计数加本次运行的报错），和 GUI 的侧栏角标同一个数。
