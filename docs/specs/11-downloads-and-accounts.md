## 1. Subscriptions: Git, Download Pages, SteamCMD (2026-10-24)

"Subscribe" = install a Mod from an origin, then check/pull updates and remove it later. Steam client still handles Workshop subscriptions (11 §2); add three origins here:

| Origin | Install location | Tracks | Update check | Update |
| --- | --- | --- | --- | --- |
| git: Git repository URL (https, `file://`, or local path) | Subscription directory `<subscribed.dir>/<repository-name>`, entire working tree including `.git` | One of branch (remote default by default), tag, or commit | Read remote refs (ls-remote); branch/tag commit differs from installed = update; tracked commits never have updates | Fetch and check out new commit; refuse dirty working tree (preserve player edits) |
| page: public Mod download page (LoversLab `https://www.loverslab.com/files/file/<id>-<name>/`), login required for download | Subscription directory `<subscribed.dir>/<page-name>` | Page | Read public page version/update time (JSON-LD), changed = update | Player downloads in browser, then updates from zip/extracted folder; RimArcho does not download |
| steamcmd: Workshop ID, explicitly chosen or Steam client unavailable | SteamCMD download directory `<steamcmd-mods.dir>/steamapps/workshop/content/294100/<Workshop-ID>`, registered as shared steamcmd source | Workshop item | Cannot determine offline; record last download time only | Rerun `workshop_download_item` (SteamCMD handles incremental download) |

**Subscribe all choice and later credit** (GUI backend contract: [Steam credit API](../api/steam-credit.md)):

- Before subscribe all on import, following collections, or batch subscribe on needs attention, players choose "subscribe through Steam (slow, but credits authors through subscriptions, managed by Steam)" or "download through SteamCMD (fast, but gives authors no credit, managed by RimArcho)". Client path creates no credit batch. Old calls without `batch:true` keep their semantics.
- Record a batch only for actual execution with explicit `kind=workshop, steamcmd=true, batch=true`; include only items confirmed successful this time, with `About.xml` present and scanned as SteamCMD Instances. Partial failure retains successes; total failure creates no batch. This batch scopes later prompts and differs from SteamCMD runner download batches. Downloads do not create Steam account subscriptions.
- After a normal plan successfully launches and records a Launch, match batches against actually enabled Instances still in live SteamCMD sources; count each Launch once per batch, not games that do not use those `Mods`. Pack runs use fixed copies and do not count as SteamCMD Instance use. After three sessions, change counting to prompt.
- Return `CreditPrompt` only when no registered game runs and the Steam worker is available; merge all due batches, deduplicate count by Workshop ID, and give up to three names. Queries do not consume prompts; frontend must coalesce concurrent queries and open only one dialog at a time; only a persisted answer consumes a prompt. Defer if Steam is unavailable or a game runs. "dismiss" permanently enters dismissed; never ask again for that batch.
- After replacement confirmation, persist replacing before task `steam-credit-replace`. Perform real SubscribeItem calls per recorded Instance; overlapping batches reuse persistently confirmed subscriptions, never unsubscribe/resubscribe to retry; if an earlier batch already replaced the original, later batch records done (already replaced). Persist transient failure counts/backoff; wait for Steam recovery; permanent errors such as explicit invisibility, no access, or removal mark item failed, retain CMD content, original result code and Workshop page, without automatic retry.
- Handover requires client state Subscribed and Installed, without NeedsUpdate, Downloading, or DownloadPending, readable `About.xml`, and scanned workshop Instance with the same Workshop ID. Pause all handover while a game runs. Lists are shared across games: check every environment registry; wherever the old SteamCMD Instance is loadable (including after deployment), the new workshop Instance must also be loadable; otherwise mark whole item retained, change no list/deployment, and name the environment; do not use the list's creation EnvID. Corrupt staging JSON also marks the entire item retained, names the list, and ends without infinite backoff; update existing deployed game projections through registry, game writes, and link lifecycle, changing only this item while preserving other unsaved edits and current plan selection. Persistent deployment obligations ensure completion after interruption.
- After deployed projections hand over, remap current contents, historical versions, undo/redo, staging entries and anchors of all lists to the workshop Instance in one transaction; merge both `instance_note` values (deduplicate text, prefer existing origin); increment `meta.credit.remap` in that transaction to invalidate long-open edit batches. DDS records bind physical directories, file state, and content snapshots; do not migrate texture_mod/texture_file directly or copy DDS; if records exist, prompt to optimize the workshop copy again. The same Mod in one Lineage counts as one item, without an undo step restoring old copy. Do not rewrite fixed packs; beyond cross-environment loadability or corrupt staging above, mark retained with reason if a fixed pack, unfinished other-game deployment, or known inbound link (including actual links in `managed_link` ledger directories) still uses original CMD copy. Only unreferenced copies without inbound links pass allowlist and link lifecycle into recycle bin, never hard deletion. Once all items are done / retained / failed, batch becomes done; per-item reasons remain in task results. done means processing ended, not that all subscriptions succeeded or all copies were recycled.
- Waiting for scans, file tasks, or client scan results uses fixed short waits without increasing failure backoff. RimArcho list read synchronization, save, undo/redo, staging, normal/pack launch, and handover share a cross-process lock; list edits lock before reading, stale snapshot saves reject conflicts, and long-lived TUI edit batches must reload after remapping. Scans run outside the lock; lock only handover, deployment, and recycling; launch wait limit is 16 §2.16.1 W02, with Go supplying "waiting for background replacement" while waiting, error only on timeout. Recheck game processes before writes/recycling; Steam and other external launches ignore the lock, leaving a process-check race window. Session-count failure after successful launch logs only; do not report a launched game as a failed launch. Stopping a task cancels current Steam worker and stops at a handover item boundary; window-close runner wait limit is 16 §2.16.1 W04, retaining completed subscriptions and unfinished obligations. App exit leaves no resident process; next GUI startup resumes from SQLite, or resume on background tasks page. Task history cleanup does not delete obligations. Prompt/replacement authorization covers only recorded batch Instances, without automatic unsubscribe, copying into client directories, or changing client ACF.

**Rules**:
1. **Prefer Steam client for Workshop items**: `subscribe workshop <Workshop-ID>` subscribes through Steam client first (same worker as 11 §2); fall back to SteamCMD only on "Steam unavailable" (`ErrSteamUnavailable`: Steam not running, no `steam_api64.dll` in game directory, API startup fails). Players may explicitly request SteamCMD with `--steamcmd`. If neither path works, report error and Workshop page.

   Before actual subscription, both paths preflight using keyless public `ISteamRemoteStorage/GetPublishedFileDetails` POST, up to 100 IDs/request and three seconds/request; HTTP, decoding, or connection failure stops later preflight requests, leaving unknown items to normal download paths. Explicit `result != 1` or `consumer_app_id != 294100` marks "removed from the Workshop (the author deleted it or made it private)", without Steam / SteamCMD calls, retries, or credit inclusion; missing items remain unknown. Use title as task name and `file_size` as progress weight if present. Previews do not preflight over network.
2. **Settings dependency management locates/installs SteamCMD**; subscriptions request its path through one lookup (`App.FindTool("steamcmd") (path, ok)`, default `SteamCMDPath()`); if absent, say "install SteamCMD in settings"; subscriptions do not download it. Accounts follow 11 §3 (`SteamCMDAccount`): anonymous runs hidden; named accounts log in through SteamCMD's own window; RimArcho never touches passwords.
3. **Subscription directory** (`subscribed.dir`, default `%LOCALAPPDATA%\RimArcho\subscribed`) belongs to RimArcho, registered as shared extra source `src:subscribed`, like Monitor (09 §6): deploy via `_Archo_` links (09 §3), include in managed directories (move, relocate), prohibit `folder remove`. Register SteamCMD download directory (`steamcmd-mods.dir`, default `%LOCALAPPDATA%\RimArcho\steamcmd-mods`) as steamcmd source on first download. Neither may contain/be contained by data directory or source roots.
4. **Origin lives in the Mod folder**: `.rimarcho/source.json` (fingerprints already exclude `.rimarcho`, `.git`, 04 §1.4). No separate table for subscription origin (credit batches persist separately): inventory/details read this file in subscription source folders (mtime-cached), preserving origin after database rebuild or folder moves. Fields:

   ```json
   {"kind": "git|page|steamcmd", "url": "repository URL or download page", "repo": "Git repository linked by download page",
    "workshop_id": "steamcmd Workshop ID", "ref_type": "branch|tag|commit", "ref": "main",
    "installed": "installed commit or page update time at installation", "installed_at": "RFC3339",
    "latest": "commit / page update time from last check", "`checked_at`": "RFC3339", "`check_error`": "last check failure reason"}
   ```
   SteamCMD items without this file (previous player downloads) use `kind=steamcmd` and directory name as Workshop ID.
5. **Install**: install into same-volume temporary `<subscribed.dir>/.archo-tmp-*` first (scan skips `.archo-` directories), require root `About/About.xml`, write `source.json`, then rename to final name; suffix occupied names with `-2`, `-3`, etc.; never overwrite. If repository root is not a Mod (Mod in subdirectory), refuse and list subdirectories with `About/About.xml`. Refuse duplicate URL + tracking target. Scan immediately after install; reconcile new Instance normally (04 §2), joining same Workshop Mod's Lineage through R4.
6. **Check updates** connects only on player request (`subscribe check`, inventory "check updates"); write latest, `checked_at`, `check_error`; "update available" means nonempty latest differs from installed. Offline inventory still shows last result/time.
7. **Update**: `--dry-run` first explains old/new commits; refuse while a game runs (loaded files would change). Git updates in place (same Instance, updated event); download page updates in rule 11.

   - SteamCMD additions and updates share batched downloads: group consecutive updates by real source root and effective account, deduplicate Workshop IDs, limit items per batch with `workshopBatchSize` in `internal/app/subscribeworkshoprun.go`; start one process per batch, create unique temporary script beside SteamCMD exe, pass only ASCII filename to `+runscript`, clean up after process exit. Instances remain mutually exclusive; nonanonymous accounts keep native console.
   - Each item requires success confirmation and `About/About.xml`; exit code 0 or existing directory is insufficient. Report invalid IDs individually before batching, without blocking others; local preparation failures such as script creation retain path/system error. Individual failures retain successes; later batches/source groups continue per next rule; after each group download, verify, publish, write origin; scan/index once at end of subscription update. Update existing sources in their original library; arbitrary layouts still replace via staging, old-directory recycling, and inbound-link lifecycle, preserving identity.
   - After all initial downloads finish, requeue IDs with timeouts, connection failures, abnormal SteamCMD exit, or unconfirmed completion (including bare `Failure` without permanent reason); retry only remaining retryable items, at most two extra rounds, with backoff. Do not automatically retry permissions, invisibility, ownership, authentication, disk-full, or explicit unknown errors. `File Not Found` / `FileNotFound` means "removed from the Workshop", without account advice; suggest checking account only for login, ownership, or access-denied issues. Nonexistent, private, unauthorized, unowned, or disk-write-failed items carry nonretryable markers. If no item in a batch is confirmed and password, Guard, login, or anonymous login fails, stop that source group and mark unrun items with the same failure. Report each failure reason and Workshop page without raw authentication logs.
   - One subscribe-all operation is one task; internal batches/retry rounds create no task rows or steps. Within the existing account lock, SteamCMD records starting `console_log.txt` offset and reads this run's output incrementally; each Success / ERROR updates task, but final per-item parsing and `About.xml` validation remain authoritative. Progress/cancellation UI contract: 16 §2.16.
   - Cancellation terminates only this task's SteamCMD process tree (Windows Job Object, assigned before process resumes), removes temporary script, releases account lock; confirmed successes still validate, register source, scan into database, and enter credit batch; unfinished items become canceled. Resume keeps original task/progress, submitting only remaining items. Steam client path stops later calls after current call returns, retaining subscriptions already made. Closing window also cancels current task runner.
   - Only Git items split SteamCMD groups; skipped download-page items during update-all do not split groups, and returned items retain selection order. Git failure still stops later operations, scanning earlier successes. SteamCMD failures aggregate at operation end, continuing later Git updates and preserving their results.

8. **Remove** (`subscribe remove`) = recycle folder (02 §3 allowlist includes subscription/download directory folders with `source.json` or in SteamCMD sources), never permanently delete; warn only if plans use it (same as 16 §2.9 deletion). SteamCMD items have no account subscription to cancel; deletion is removal.
9. **Commands**: `archo subscribe git <URL> [--branch <name> | --tag <name> | --commit <sha>] [--dry-run]`, `archo subscribe page <download-page> [--git | --from <zip-or-folder>] [--dry-run]`, `archo subscribe workshop <Workshop-ID…> [--steamcmd] [--dry-run]`, `archo subscribe list`, `archo subscribe check [<reference>…]`, `archo subscribe update <references…> | --all [--dry-run]`, `archo subscribe remove <references…> [--dry-run]`. check without references checks all subscriptions; update requires references or `--all`, refusing neither (13 §3.3).
10. **Pure-Go Git** (go-git, 17 §1), no installed Git or system git calls; only repositories requiring no login (public https, local paths); no submodules or LFS (pointer files are downloaded, warn after install). Shallow clone branches/tags (depth 1); full fetch then checkout for tracked commits.
11. **Download pages and LoversLab**: `subscribe.ReadPage` fetches public metadata with one HTTPS GET, no cookies, redirects, or download-button reading. Public pages may also challenge; 403 does not mean not logged in. Authenticated LoversLab download is a separate player entry point:
   - Read JSON-LD (schema.org `SoftwareApplication`: name, `softwareVersion`, `dateModified`; fall back to `og:title`, `og:updated_time`), and body links to Git repositories (gitgud.io, GitHub, GitLab root URLs, stripping `/-/tree/…`, `/-/blob/…`, etc.).
   - If page links one repository (for example RimJobWorld to gitgud.io), `subscribe page <page>` suggests a Git subscription (with several repositories, choose the one most linked into files via `/-/tree/…`, `/-/blob/…`, `/tree/…`, `/blob/…`; homepage/release-only links are usually dependencies, such as Harmony on RimJobWorld's page; if ambiguous, ask player to choose using `subscribe git`), recording page in `source.json` url (kind remains git, repo is repository); `--git` does this directly. gitgud.io is GitLab, anonymous https clone with or without `.git`.
   - Without a repository, or if player wants page releases: `subscribe page <page> --from <zip-or-folder>`. Player downloads in browser first (UI "open download page"); RimArcho installs zip (standard `archive/zip`; extract 7z/rar first) or folder into subscription directory: Mod at archive root or sole first-level subdirectory; refuse without `About/About.xml`. installed records page version/update time (`1.4.1 @ 2026-10-23T15:16:59Z`). Examples: RimJobWorld links a gitgud.io repository (Git); RJW Industrial Milk Management has only a download button (zip).
   - Update check rereads page; changed version or newer update time means update; update = `subscribe update <reference> --from <new-zip-or-folder>`, install in temporary directory, recycle original, rename into same location (R1, same Instance).
   - Page read failures (Cloudflare block, changed page layout) only record `check_error`, without retry or bypass.
   - After first login in settings › accounts, accepting site notice and logging in personally in isolated window, players can read downloadable files on subscribed pages without Git repositories; list multiple files by actual filename, size, date, falling back to button text only without metadata; player selection required. Authenticated `subscribe.LoversLab` does not change public reader contract. Updates use the same file selection flow.
   - Download using actual links/forms from this request, never guessed attachment IDs or CSRF parameters. Show site declarations verbatim and submit only after player agreement; hidden fields and temporary links stay in memory, never `source.json` or tasks. Download managed temporary zip, then reuse `subscribe.Import`, `About.xml` validation, install preview, and old-directory recycling; if public metadata is blocked, local installation records `player download`.
   - Missing/expired sessions, login redirects, 403, Cloudflare/captcha, or unrecognized pages explain the reason and return to "open download page → choose zip". No automatic challenge solving, login loops, or retries.
   - Save session encrypted with current Windows user DPAPI; cookies and non-secret status only, no passwords; do not invent persistent expiry for session cookies. Preserve site's Remember me in login window. Show expiry of longest-lived authentication cookie (member/login/device key, etc.), not earliest short session cookie; session-only means N/A. Merge Set-Cookie (rotation, expiry, deletion) from every HTTPS response in validation, file reading, download, and authenticated update checks into encrypted storage, surviving restarts. Public `ReadPage` stays cookie-free; logged-in GUI update checks reuse authenticated client.
   - Serialize per service; request spacing and 429 Retry-After cooldown in 16 §2.16.1 S11; refuse retries during long cooldowns. HTTPS only, exact `loverslab.com` / `www.loverslab.com` file flows; unregistered external CDNs not observed in practice fall back to manual download; never forward site cookies to CDNs.
   - No general "Mod index" `source:` no existing index to connect.

## 2. Steam client calls (subscribe and unsubscribe)

This is implemented for unsubscribe and resubscribe in the mod library (16 §2.9). Like RimCrow, RimArcho subscribes to and unsubscribes from Workshop items through the player's running Steam client:

- **Bounded child process.** RimArcho launches `archo steam-worker subscribe|unsubscribe|state|download|watch <Workshop IDs…>`, which is not listed in help. Its working directory is `%LOCALAPPDATA%\RimArcho\steam`. This contains `steam_api64.dll` copied from the game installation and `steam_appid.txt` containing `294100`. The local 1.7 DLL is in the game root; also search the Unity layout at `RimWorldWin64_Data\Plugins\x86_64`. Recopy the DLL if the game's copy changes. Never write to the game directory. The child exits after its calls, but `watch` stays alive while waiting for downloads. Steam then shows "playing RimWorld", so downloads must be requested explicitly rather than left to Steam's background updates. A DLL failure cannot crash the window.
- **Calls.** Use `syscall`, without cgo, to invoke the flat Steamworks C API. Call `SteamAPI_InitFlat` (SDK 1.58 and later), falling back to `SteamAPI_Init` if it is absent. Select the highest available versions of `SteamAPI_SteamUGC_v0NN` and `SteamAPI_SteamUtils_v0NN` in the DLL. Issue `SteamAPI_ISteamUGC_SubscribeItem` or `UnsubscribeItem` for each item, then loop `SteamAPI_RunCallbacks`. Read each call's `EResult` through `ISteamUtils_IsAPICallCompleted` and `GetAPICallResult` until all calls have results or time out. For unanswered calls, use the subscribed bit from `GetItemState`. Before the operation, process the subscription-list refresh triggered by initialization. Afterward, continue processing callbacks and watch for confirmed-success items whose state reverts; retry each reverted item once. See 16 §2.16.1 S05 for the initialization, reply and compensation-observation intervals and deadlines. Finally, call `SteamAPI_Shutdown` and exit. The local game's 1.7.4982 DLL provides `SteamAPI_Init`, `SteamUGC_v016` and `SteamUtils_v010`.
- **Output** is line-oriented text parsed by the parent (`steamworks.Parse`): `ITEM <ID> ok|failed:<EResult>|timeout <state bits>`, `STATE <ID> <state bits>`, and `DONE`. If Steam is unavailable, the only line is `ERROR <reason>`. `watch` adds `PROGRESS <ID> <downloaded bytes> <total bytes> <state bits>`, emitted only when a sample changes. The parent consumes each line through `App.runSteamStreaming` and calls `BatchCalls.Progress` or `Done`, without waiting for the child to exit. A batch has at most 50 items. Ordinary calls time out after 40 seconds; download waits use the limits below.
- **Steam unavailable.** Steam not running, not being logged in, a missing or unloadable DLL, or a timeout produces `app.ErrSteamUnavailable`. The window opens the items' Workshop pages and explains the reason; the CLI error includes their page links. A Steam failure (`failed:<EResult>`) is reported as returned, without opening pages. The wording is in `app.WorkshopResultText`. Result 3 (no connection) says "the Steam client is offline", and task details suggest restarting Steam. A common cause is SteamCMD logging into the same account and displacing the client (16 §2.9).
- **Unsubscription lets Steam delete Workshop folders**, so it is destructive like recycling. The UI first shows `--dry-run` with the folder to be deleted, then asks for confirmation; MCP `manage_library` marks it as destructive. An enabled Mod or one used by plans in any environment only warns, listing the plans in `warning:`, and unsubscription proceeds. Those plan entries become missing. Refuse if a game is running (09 §4). Unsubscribed residue cannot be unsubscribed again (use `trash`), and an already subscribed item cannot be subscribed again.
- **Resubscribing subscribed Workshop originals.** `App.Workshop("resubscribe", refs, dryRun)` previews and then confirms that RimArcho will recycle the folder before Steam downloads it again, losing any local changes. Accept only Workshop originals with numeric Workshop IDs that are not themselves links and carry no locked marker. Enabled Mods and Mods used by any list are allowed; refuse if a game runs. First unsubscribe through the existing worker. Only for items whose unsubscription Steam confirms, recycle the entire original `…/workshop/content/294100/<Workshop ID>` directory, including extra files and `.git`, through the existing recycle backend and path allowlist. Never follow the copy's own symbolic link or junction to clean its target, and never delete permanently. Subscribe only after `Lstat` confirms that the original path is absent. If Steam has concurrently deleted it, count that as success. Briefly retry transient failures such as sharing conflicts under 16 §2.16.1 S10. If a directory still exists after the deadline, or its absence cannot be confirmed, report that item's cleanup failure and do not subscribe it; other successful items continue. Do not clean up or subscribe items whose unsubscription was not confirmed. Unsubscribed residue skips unsubscription and cleanup and subscribes directly. The GUI uses the existing Steam background-task queue, with at most 50 items per batch; the CLI and MCP execute in the foreground. In between, do not remove Instances, change lists or detach game links to the original path. Scan rule R1 (same source and relative path, 04 §2.1) reuses the original ID and Lineage when the folder returns, even if a scan marked it missing during the gap. Confirmed subscriptions, including residue, go to `watch`. For each item, call `ISteamUGC::DownloadItem(id, true)`, pump `SteamAPI_RunCallbacks` at the intervals in 16 §2.16.1 S08, read `GetItemState` and the byte counts from `GetItemDownloadInfo`, and obtain the install path through `GetItemInstallInfo`. An item succeeds only when its directory exists and is nonempty, Installed is set, and neither Downloading nor DownloadPending is set. Installed alone may refer to an old manifest and does not prove completion. See 16 §2.16.1 S08 for the per-item no-growth stall threshold and total wait limit. On expiry, report "Steam did not download; please check Steam" or a download timeout. `BatchCalls.Stopped` cancels the operation: the parent closes the input pipe, and the worker exits and calls Shutdown. If the DLL hangs, force-terminate and reap the child. Parent exit also causes pipe EOF, preventing orphan workers. See 16 §2.16 for task-page phases, per-item text and JSON. The CLI reports progress about every 10% and at each item's completion; the command returns only after the download completes or fails.
- **Anonymous local state.** If Steam is unavailable, `workshop state` and MCP `steam_state` return whether the local folder exists, explicitly marked `Local` with the reason retained. Subscription, update and download progress are unknown; state bits 0 must not be interpreted as "unsubscribed". Subscription and unsubscription still require an account, and failures must not be disguised as success.
- **Commands.** Use `archo workshop unsubscribe <refs…> [--dry-run]`, `archo workshop subscribe <refs…> [--dry-run]`, `archo workshop resubscribe <refs…> [--dry-run]`, and `archo workshop state <refs…>` (subscribed, installed, needs update, downloading). The MCP `manage_library` actions are `unsubscribe`, `subscribe`, `resubscribe` and `steam_state`. Do not rescan immediately after a call. Resubscription waits for the download to complete; ordinary subscription and unsubscription leave Steam to download or delete in the background, and the next scan sees the result.
- **Tests** use fake child processes (`App.SteamWorker` for ordinary calls and `App.SteamWorkerStream` for streaming waits), never real Steam. Real calls occur only after player confirmation. Manual development checks stop at the preview.

## 3. Downloading game versions with SteamCMD

**Account management.** Settings › accounts offers only login, relogin and logout. The one-line availability status is defined in 16 §2.14. After the player enters an account name, open the native SteamCMD console with `+login <name>`; the player enters the password and Guard response there and quits. After the window closes, run `+login <name> +licenses_print +quit` hidden to verify automatically with cached authentication, without passing a password. Confirm login only if both the login steps and subsequent user info are OK; support step and result messages on separate lines. RimWorld ownership requires app 294100 in a license's Apps/AppID list. Store only the ownership boolean and check time, not the license list. Anonymous users can download Workshop Mods but cannot own or download the game. Do not claim credentials have expired on a network failure, or reuse records from another tool path or account.

Logout runs `+logout +quit`. If it fails, is unconfirmed or is offline, automatically clear the managed copy's known local authentication cache (02 §1). Explain the scope beforehand in the confirmation text. Do not read tokens, back up authentication files or log out other devices. Copies at external paths or on `PATH` manage their own login; they do not get managed-account buttons or cleanup.

Workshop fallback, game downloads and account operations share the resolution of the actual tool instance and account. The instance lock covers the process lifetime. Public branch lists always use anonymous access; reading branches does not establish a game license. SteamCMD owns its console output. RimArcho adds no prompts or window titles containing untranslated text. Externally reported progress and errors contain only the permitted phases, counts and reasons, never raw authentication or license logs.

Game-version download is implemented (`archo env branches`, `archo env download`, and "download a version" in first-run step 1, 16 §2.15). It serves a player who owns RimWorld and wants an older version, such as 1.5, as another environment.

- **SteamCMD location.** Search in order: `steamcmd.path`, `%LOCALAPPDATA%\RimArcho\steamcmd\steamcmd.exe`, then `PATH`. If none is found, ask the player first, showing the source and size. Obtain `Content-Length` with a HEAD request to `https://steamcdn-a.akamaihd.net/client/installer/steamcmd.zip`. After consent (CLI `--install-steamcmd`), download and extract it to `%LOCALAPPDATA%\RimArcho\steamcmd`. SteamCMD updates itself on first run, downloading about 30 MB.
- **Branches.** Run `steamcmd +login anonymous +app_info_update 1 +app_info_print 294100 +quit`. Anonymous access can read RimWorld's app information without ownership. Read `depots/branches`, omit password-required branches (`pwdrequired`), and sort as follows: `public`, `unstable`, `version-*` from newest to oldest, then the others (`alpha*`, `beta*`). Never guess branch names. The list measured on 2026-10-22 (`testdata/steamcmd/app_info_print_294100.txt`) was `public`, `unstable` (Public testing), `version-1.6.4633`, `version-1.5`, `version-1.4.3901`, `version-1.4.3563`, `version-1.4.3542`, `version-1.3-latest`, `version-1.3.3287`, `version-1.2.3005`, `version-1.2`, `version-1.1`, `version-1.0`, `beta19`, `beta18`, `alpha17`…`alpha13`, `alpha4`. There is no `version-1.6`; the version of `public` is known only after downloading and reading Version.txt.
- **Branch cache.** Cache public branches in-process by appID and SteamCMD tool identity (normalized real path, file size and modification time). See 16 §2.16.1 C02 (`internal/app/gamebranches.go`) for validity and retry gates after failure. Concurrent queries for the same key run only once. When the cache expires, show the old list immediately, refresh anonymously in the background, and update the UI on completion. On failure, retain the old list and show the error; allow retry after a short backoff. The actual query still holds `accounts.Lock`, sharing instance exclusion with downloads and account operations. Reread tool identity after success to support SteamCMD self-updates. Cancel branch queries when the window closes. The UI shows a lightweight refresh notice. See 16 §2.16.1 G05 for status-polling backoff and the stop deadline; reentering the page allows another read. Download-log polling and waits for descendant processes follow S01 and S12.
- **Destination.** The directory must neither be inside nor contain the RimArcho data directory. It must not contain or be contained by any source, including any game's `Data` or `Mods` and any Mod folder, and must not be an existing environment's game directory. Create it if it does not exist.
- **Login.** Use the account in settings by default. Anonymous access can download only Workshop Mods; a game download asks the player to log into an account that owns RimWorld. The `steamcmd.account` setting may be empty (anonymous), `anonymous`, or an account name. The download form and CLI `--account` override it only for this run, with precedence: explicit account → settings → anonymous. Explicit `anonymous` overrides a saved account; clearing the setting restores anonymous access. Public branch lists always use anonymous access. RimArcho stores only the account name and does not receive passwords or Steam tokens. The player enters them in SteamCMD's **own console** (`CREATE_NEW_CONSOLE`) or the CLI's current terminal.
- **Download.** Run `+force_install_dir <directory> +login <account> +app_update 294100 [-beta <branch>] validate +quit`, omitting `-beta` for `public`. RimArcho does not read the SteamCMD console. It follows the tool's `<steamcmd>/logs/console_log.txt`, starting at the prelaunch file length and restarting from the beginning if the file becomes shorter. Convert `Update state (0x..) downloading|verifying update, progress: P (done / total)` into progress; `Success! App '294100' fully installed.` indicates success. Then confirm that the directory contains a game and register it through the existing-game flow. Name it after the version, such as `1.5`, use `direct` launch, and default to shared saves (CLI may use `--saves own`). Scan only its `Data` and `Mods`.
- **Plain-language failures.** Explain login, Guard, network, license, disk and branch failures using the permitted reasons in `DownloadError.Why`. For an unrecognized result, say that completion was not confirmed. Do not append raw SteamCMD output to external messages. A final `fully installed` overrides earlier errors because SteamCMD reconnects itself: `steamcmd has been disconnected from steam with result 3 (No Connection)` may be followed by `Retrying...`. In a 2026-10-28 VM test, a 16 GB download disconnected once but still completed. - **Unverified items.** Development did not use real login or download. ## 4. Account storage and login window isolation

`internal/deps` still only discovers tools; `internal/accounts` manages account boundaries. Secrets live only in `%LOCALAPPDATA%\RimArcho\accounts\loverslab.session`, protected with current-user CryptProtectData from `golang.org/x/sys/windows`, never machine scope. A protected DACL grants only the current user and propagates to children. Store necessary site cookie attributes, including session-only cookies used by the API after the login window exits; expiry and logout belong to the site. Store no passwords or browser databases. `.session.new` is also ciphertext only; atomically replace the single authoritative file. Exclude it from DB backups, exports, packs, diagnostics, logs and tasks.

Login runs in a separate native `account-login-helper` process with an STA message loop and independent WebView2 environment. Delete temporary `accounts/webview-profile` after closing; never restore an old profile next time. Dispatch this process before CLI / main UI initialization. It exposes no Wails services, host objects, web messages, DevTools, remote debugging, script injection, screenshots, request-body diagnostics or agent interface. Disable password saving, ordinary form autofill and browser debug shortcuts. Use only CookieManager to retrieve cookies for the allowed domains. The host can run local processes; do not claim protection from arbitrary code running as the same user.

`accounts/downloads` holds managed temporary authenticated downloads; delete on installation or forgetting the account, and clear crash residue when forgetting. Ordinary session reads are offline; verification is one GET; downloads are restricted to real file pages and observed site links. Raw responses, CSRF and temporary signed URLs never enter errors or tasks. Uninstall first performs account forgetting from 02 §2; preserve retry conditions on failure.

Automatic renewal reuses the single original-site settings-page GET in `subscribe.LoversLab.Verify` (canonical `/settings/`; the old query URL redirects there with 301, but this GET does not follow redirects, falsely classifying a logged-in session as needing verification). Accept server Set-Cookie and save through the same encrypted file. Do not launch a browser or submit passwords; do not promise server-side extension. Schedule from the earliest persistent authentication-cookie expiry in `accounts.Session.RenewalExpiry`, ignoring short session cookies, and check ahead near expiry. If verification still leaves imminent expiry, login or browser verification is needed, show this in settings › accounts and quiet notifications. Advance-check formula, notification thresholds and intervals: 16 §2.16.1 A02; authorization and notification rules: 16 §2.16. Offline, retain known sessions and pending status; do not loop requests on failure. File pages read during automatic Mod checks are also guest-visible. Mark a session usable only if a page contains the logged-in user's logout link (the same evidence as verification); a guest view does not change the session-check conclusion.
