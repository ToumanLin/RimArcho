# 11 · Downloads, subscriptions and accounts

> Status: implemented: Git, download-page and SteamCMD subscriptions with SteamCMD credit replacement, Steam client subscribe, unsubscribe and resubscribe calls, game-version downloads with SteamCMD, and LoversLab login with encrypted session storage. Parts of the real SteamCMD login and download flow are unverified (§3).
> Basis: 00, 00a, 02 §1 / §2 / §3, 03 §2 / §4.1, 04 §1.4 / §2, 09 §3 / 19 §6, 13 §3.3, 16 §2.9 / §2.14 / §2.16, 17 §1.

This specification covers how Mods and game versions arrive from outside RimArcho: subscriptions to Git repositories, download pages and SteamCMD (§1), subscribe and unsubscribe calls through the player's Steam client (§2), downloading game versions with SteamCMD (§3), and how account sessions are stored and login windows isolated (§4).

## 1. Subscriptions: Git, download pages, SteamCMD

A subscription installs a Mod from an origin, then checks for and pulls updates, and can remove it later. The Steam client handles Workshop subscriptions (11 §2); this section adds three origins:

| Origin | Install location | Tracks | Update check | Update |
| --- | --- | --- | --- | --- |
| git: Git repository URL (https, `file://`, or local path) | Subscription directory `<subscribed.dir>/<repository-name>`, the entire working tree including `.git` | A branch (by default the remote default), a tag, or a commit | Read remote refs (ls-remote); a branch or tag commit that differs from the installed one is an update; a tracked commit never has updates | Fetch and check out the new commit; refuse a dirty working tree (to preserve the player's edits) |
| page: public Mod download page (LoversLab `https://www.loverslab.com/files/file/<id>-<name>/`), where downloading requires login | Subscription directory `<subscribed.dir>/<page-name>` | The page | Read the public page's version and update time (JSON-LD); a change is an update | The player downloads in the browser, then updates from the zip or extracted folder; RimArcho does not download (except with a LoversLab login, rule 11) |
| steamcmd: Workshop ID, chosen explicitly or when the Steam client is unavailable | SteamCMD download directory `<steamcmd-mods.dir>/steamapps/workshop/content/294100/<Workshop-ID>`, registered as a shared steamcmd source | The Workshop item | Cannot be determined offline; only the last download time is recorded | Rerun `workshop_download_item` (SteamCMD downloads incrementally) |

**Subscribe-all choice and later credit** (GUI backend contract: [Steam credit API](../api/steam-credit.md)):

- Before "subscribe all" on import, when following collections, or for a batch subscription on Can it run, the player chooses "from Steam (slow, but credits the modder with a subscription; Steam manages it)" or "from SteamCMD (fast, but does not credit the modder; RimArcho manages it)". The Steam client path creates no credit batch. Calls without `batch:true` create no batch either.
- Record a batch only when a download actually runs with explicit `kind=workshop, steamcmd=true, batch=true`. Include only items confirmed successful in this run, with `About.xml` present and scanned as SteamCMD Instances. A partial failure keeps the successes; a total failure creates no batch. This batch scopes later prompts and is distinct from the SteamCMD runner's download batches. Downloads create no Steam account subscriptions.
- After a normal plan launches and its launch is recorded, match batches against the Instances actually enabled that are still in live SteamCMD sources. Count each launch once per batch, and do not count games that do not use those Mods. Pack runs use fixed copies and do not count as use of SteamCMD Instances. After three sessions, the batch moves from counting to prompt.
- Return `CreditPrompt` only when no registered game runs and the Steam worker is available. Merge all due batches, count Mods once per Workshop ID, and give up to three names. Queries do not consume prompts: the frontend must coalesce concurrent queries and open only one dialog at a time, and only a persisted answer consumes a prompt. Defer if Steam is unavailable or a game runs. "dismiss" moves the batch to dismissed for good; RimArcho never asks again for that batch.
- After the player confirms replacement, persist `replacing` before starting the task `steam-credit-replace`. Make a real SubscribeItem call for each recorded Instance. Overlapping batches reuse subscriptions already confirmed and persisted, and never unsubscribe and resubscribe to retry. If an earlier batch already replaced the original, the later batch records the item as done (already replaced). Persist transient failure counts and backoff, and wait for Steam to recover. A permanent error, such as an item explicitly invisible, without access, or removed, marks the item failed and keeps the SteamCMD content, the original result code and the Workshop page, without automatic retry.
- Handover requires the client state Subscribed and Installed, without NeedsUpdate, Downloading or DownloadPending, a readable `About.xml`, and a scanned Workshop Instance with the same Workshop ID. Pause all handover while a game runs. Plans are shared across games, so check every environment's registry: wherever the old SteamCMD Instance is loadable (including after deployment), the new Workshop Instance must be loadable too. Otherwise mark the whole item retained, change no plan or deployment, and name the environment; do not use the plan's creation EnvID. Corrupt staging JSON also marks the whole item retained, names the plan, and ends without endless backoff. Update existing deployed game projections through the registry, game writes and the link lifecycle, changing only this item and preserving other unsaved edits and the current plan selection. Persistent deployment obligations ensure completion after an interruption.
- Once the deployed projections are handed over, remap the current contents, historical versions, undo/redo, staging entries and anchors of all plans to the Workshop Instance in one transaction. Merge both `instance_note` values (deduplicate the text, prefer the existing origin). DDS records are bound to physical directories, file state and content snapshots: do not migrate `texture_mod` / `texture_file` directly or copy DDS files; if records exist, prompt to optimize the Workshop copy again. The same Mod in one Lineage counts as one item, with no undo step that restores the old copy. Do not rewrite fixed packs. Beyond the cross-environment loadability and corrupt staging above, mark the item retained, with the reason, if a fixed pack, an unfinished deployment in another game, or a known inbound link (including actual links in `managed_link` ledger directories) still uses the original SteamCMD copy. Only unreferenced copies without inbound links go through the allowlist and the link lifecycle into the recycle bin; never delete permanently. Once all items are done, retained or failed, the batch becomes done, and per-item reasons remain in the task results. Done means processing ended, not that all subscriptions succeeded or all copies were recycled.
- Waits for scans, file tasks or client scan results use fixed short intervals and do not increase failure backoff. Reading plans for synchronization, save, undo/redo, staging, normal and pack launch, and handover share a cross-process lock. Plan edits take the lock before reading, saves from a stale snapshot are refused as conflicts, and long-lived TUI edit batches must reload after remapping. Scans run outside the lock; only handover, deployment and recycling take it. The launch wait limit is 16 §2.16.1 W02; while waiting, Go supplies "waiting for background replacement", with an error only on timeout. Recheck game processes before writes and recycling; Steam and other external launches ignore the lock, which leaves a race window for the process check. If counting the session fails after a successful launch, only log it; do not report a launched game as a failed launch. Stopping a task cancels the current Steam worker and stops at a handover item boundary; the runner's wait limit on window close is 16 §2.16.1 W04, and completed subscriptions and unfinished obligations are kept. Exiting RimArcho leaves no resident process: the next GUI start resumes from SQLite, or the player resumes on the Background tasks page. Cleaning up task history does not delete obligations. Authorization from the prompt and replacement covers only the batch's recorded Instances, with no automatic unsubscribing, no copying into client directories and no changes to the client's ACF.

**Rules**:
1. **Prefer the Steam client for Workshop items**: `subscribe workshop <Workshop-ID>` subscribes through the Steam client first (the same worker as 11 §2). It falls back to SteamCMD only when Steam is unavailable (`ErrSteamUnavailable`: Steam not running, no `steam_api64.dll` in the game directory, or the API fails to start). The player may request SteamCMD explicitly with `--steamcmd`. If neither path works, report the error and the Workshop page.

   Before subscribing, both paths run a preflight with the keyless public `ISteamRemoteStorage/GetPublishedFileDetails` POST: up to 100 IDs and three seconds per request. An HTTP, decoding or connection failure stops later preflight requests and leaves the remaining items unknown, for the normal download paths. An explicit `result != 1` or `consumer_app_id != 294100` marks an item "removed from the Workshop (the author deleted it or made it private)", with no Steam or SteamCMD calls, retries or credit batch; items missing from the reply stay unknown. Use the title as the task name and `file_size` as the progress weight when present. Previews do not run the network preflight.
2. **Settings' dependency management locates and installs SteamCMD**. Subscriptions get its path through one lookup (`App.FindTool("steamcmd") (path, ok)`, by default `SteamCMDPath()`); if it is absent, they say "install SteamCMD in settings" and do not download it themselves. Accounts follow 11 §3 (`SteamCMDAccount`): anonymous runs are hidden; named accounts log in through SteamCMD's own window; RimArcho never touches passwords.
3. **The subscription directory** (`subscribed.dir`, default `%LOCALAPPDATA%\RimArcho\subscribed`) belongs to RimArcho and is registered as the shared extra source `src:subscribed`, like Monitor (19 §6): it is deployed through `_Archo_` links (09 §3), counts as a managed directory (move, relocate), and cannot be removed with `folder remove`. The SteamCMD download directory (`steamcmd-mods.dir`, default `%LOCALAPPDATA%\RimArcho\steamcmd-mods`) is registered as a steamcmd source on the first download. Neither may contain or be contained by the data directory or a source root.
4. **The origin lives in the Mod folder**: `.rimarcho/source.json` (fingerprints already exclude `.rimarcho` and `.git`, 04 §1.4). There is no separate table for subscription origins (credit batches are stored separately): the Mod library and details read this file in subscription source folders (cached by mtime), so the origin survives a database rebuild or a folder move. Fields:

   ```json
   {"kind": "git|page|steamcmd", "url": "repository URL or download page", "repo": "Git repository linked by download page",
    "workshop_id": "steamcmd Workshop ID", "ref_type": "branch|tag|commit", "ref": "main",
    "installed": "installed commit or page update time at installation", "installed_at": "RFC3339",
    "latest": "commit / page update time from last check", "checked_at": "RFC3339", "check_error": "last check failure reason"}
   ```
   SteamCMD items without this file (downloaded without a record) use `kind=steamcmd` and their directory name as the Workshop ID.
5. **Install**: install into a temporary `<subscribed.dir>/.archo-tmp-*` on the same volume first (scans skip `.archo-` directories), require `About/About.xml` at the root, write `source.json`, then rename to the final name. Suffix occupied names with `-2`, `-3` and so on; never overwrite. If the repository root is not a Mod (the Mod is in a subdirectory), refuse and list the subdirectories with `About/About.xml`. Refuse a duplicate URL with the same tracking target. Scan immediately after installing; the new Instance is reconciled normally (04 §2) and joins the Lineage of the same Workshop Mod through R4.
6. **Checking for updates** connects only on the player's request (`subscribe check`, "check for updates" in the Mod library) or during automatic checks when they are on (16 §2.16). It writes `latest`, `checked_at` and `check_error`; "update available" means a nonempty `latest` that differs from `installed`. Offline, the Mod library still shows the last result and its time.
7. **Update**: `--dry-run` first explains the old and new commits; refuse while a game runs (loaded files would change). Git updates in place (same Instance, an updated event); download pages update as in rule 11.

   - SteamCMD additions and updates share batched downloads. Group consecutive updates by real source root and effective account, deduplicate Workshop IDs, and limit the items per batch with `workshopBatchSize` in `internal/app/subscribeworkshoprun.go`. Start one process per batch, create a unique temporary script beside the SteamCMD exe, pass only an ASCII file name to `+runscript`, and clean up after the process exits. SteamCMD instances stay mutually exclusive; named accounts keep the native console.
   - Each item needs a success confirmation and `About/About.xml`; exit code 0 or an existing directory is not enough. Report invalid IDs individually before batching, without blocking the others; local preparation failures, such as creating the script, keep the path and system error. Individual failures keep the successes, and later batches and source groups continue as the next rule says. After each group's download, verify, publish and write the origin; scan and index once at the end of the subscription update. Existing sources are updated in their original library; arbitrary layouts are still replaced through staging, recycling of the old directory and the inbound-link lifecycle, preserving identity.
   - After all initial downloads finish, requeue the IDs with timeouts, connection failures, an abnormal SteamCMD exit or unconfirmed completion (including a bare `Failure` without a permanent reason). Retry only the remaining retryable items, for at most two extra rounds, with backoff. Do not automatically retry permission, invisibility, ownership, authentication, disk-full or explicit unknown errors. `File Not Found` / `FileNotFound` means "removed from the Workshop", without account advice; suggest checking the account only for login, ownership or access-denied problems. Nonexistent, private, unauthorized, unowned or disk-write-failed items carry nonretryable markers. If no item in a batch is confirmed and the password, Guard, login or anonymous login fails, stop that source group and mark its items not yet run with the same failure. Report each failure's reason and Workshop page, without raw authentication logs.
   - One subscribe-all operation is one task; internal batches and retry rounds create no task rows or steps. Within the existing account lock, the SteamCMD run records the starting offset of `console_log.txt` and reads this run's output incrementally. Each Success / ERROR line updates the task, but the final per-item parsing and `About.xml` validation remain authoritative. Progress and cancellation UI contract: 16 §2.16.
   - Cancelling terminates only this task's SteamCMD process tree (a Windows Job Object, assigned before the process resumes), removes the temporary script and releases the account lock. Confirmed successes are still validated, registered as a source, scanned into the database and added to the credit batch; unfinished items become cancelled. Resuming keeps the original task and progress and submits only the remaining items. The Steam client path stops later calls after the current call returns and keeps the subscriptions already made. Closing the window also cancels the current task runner.
   - Only Git items split SteamCMD groups; download-page items skipped during "update all" do not, and returned items keep the selection order. A Git failure still stops later operations, and earlier successes are scanned. SteamCMD failures are collected at the end of the operation; later Git updates continue and keep their results.
   - "Update all" and a multi-selection update in the window and the TUI are one files-lane task for all Git and SteamCMD items, run as one update operation, so its SteamCMD items share the batches above. The task reports each item: SteamCMD items start when their group's batch starts and end with that group's per-item result; a Git failure ends that item and leaves the later ones skipped. Steam client copies are one more task that asks Steam to download every listed Workshop ID in one call; the error names the items Steam refused. The confirmation is one dry run on one session (16 §2.9).

8. **Remove** (`subscribe remove`) recycles the folder (the 02 §3 allowlist includes subscription and download-directory folders with `source.json` or in SteamCMD sources) and never deletes permanently. It only warns if plans use the Mod (as deletion does, 16 §2.9). SteamCMD items have no account subscription to cancel; removing the folder is the whole removal.
9. **Commands**: `archo subscribe git <URL> [--branch <name> | --tag <name> | --commit <sha>] [--dry-run]`, `archo subscribe page <download-page> [--git | --from <zip-or-folder>] [--dry-run]`, `archo subscribe workshop <Workshop-ID…> [--steamcmd] [--dry-run]`, `archo subscribe list`, `archo subscribe check [<reference>…]`, `archo subscribe update <references…> | --all [--dry-run]`, `archo subscribe remove <references…> [--dry-run]`. `check` without references checks all subscriptions; `update` requires references or `--all` and refuses when given neither (13 §3.3).
10. **Pure-Go Git** (go-git, 17 §1): no installed Git and no calls to a system git. Only repositories that need no login (public https, local paths). No submodules or LFS (pointer files are downloaded, with a warning after install). Branches and tags are shallow clones (depth 1); a tracked commit gets a full fetch, then a checkout.
11. **Download pages and LoversLab**: `subscribe.ReadPage` fetches public metadata with one HTTPS GET, without cookies, redirects or reading the download button. Public pages may also present a challenge; a 403 does not mean the player is not logged in. Authenticated LoversLab download is a separate entry point for the player:
   - Read JSON-LD (schema.org `SoftwareApplication`: name, `softwareVersion`, `dateModified`; falling back to `og:title`, `og:updated_time`) and links in the body to Git repositories (gitgud.io, GitHub, GitLab root URLs, stripping `/-/tree/…`, `/-/blob/…` and similar).
   - If the page links one repository (for example RimJobWorld to gitgud.io), `subscribe page <page>` suggests a Git subscription. With several repositories, choose the one linked most often into files via `/-/tree/…`, `/-/blob/…`, `/tree/…`, `/blob/…`; links only to a homepage or releases are usually dependencies, such as Harmony on RimJobWorld's page; if it is ambiguous, ask the player to choose with `subscribe git`. The page is recorded in the `url` of `source.json` (`kind` stays `git`, `repo` is the repository); `--git` does this directly. gitgud.io is GitLab and allows anonymous https clones with or without `.git`.
   - Without a repository, or if the player wants the page's releases: `subscribe page <page> --from <zip-or-folder>`. The player downloads in the browser first (UI "open download page"); RimArcho installs the zip (standard `archive/zip`; extract 7z or rar first) or folder into the subscription directory. The Mod must be at the archive root or in its only first-level subdirectory; refuse without `About/About.xml`. `installed` records the page's version and update time (`1.4.1 @ 2026-10-23T15:16:59Z`). Examples: RimJobWorld links a gitgud.io repository (Git); RJW Industrial Milk Management has only a download button (zip).
   - An update check rereads the page; a changed version or a newer update time is an update. Updating is `subscribe update <reference> --from <new-zip-or-folder>`: install in a temporary directory, recycle the original, and rename into the same location (R1, same Instance).
   - Page read failures (a Cloudflare block, a changed page layout) only record `check_error`, without retry or bypass.
   - After the first login in settings › "accounts", in which the player accepts the site's notice and logs in personally in an isolated window, the player can read the downloadable files on subscribed pages without Git repositories. Several files are listed by actual file name, size and date, falling back to the button text only without metadata; the player must choose. The authenticated `subscribe.LoversLab` does not change the public reader's contract. Updates use the same file selection.
   - Download with the actual links and forms from this request, never with guessed attachment IDs or CSRF parameters. Show the site's declarations verbatim and submit only after the player agrees; hidden fields and temporary links stay in memory and never enter `source.json` or tasks. Download to a managed temporary zip, then reuse `subscribe.Import`, the `About.xml` validation, the install preview and the recycling of the old directory; if the public metadata is blocked, the local installation records `player download`.
   - A missing or expired session, a login redirect, a 403, a Cloudflare challenge or captcha, or an unrecognized page is explained, and the player returns to "open download page → choose zip". No automatic challenge solving, login loops or retries.
   - Save the session encrypted with the current Windows user's DPAPI: cookies and non-secret status only, no passwords; do not invent a persistent expiry for session cookies. Keep the site's Remember me in the login window. Show the expiry of the longest-lived authentication cookie (member, login, device key and similar), not of the earliest short session cookie; session-only means N/A. Merge Set-Cookie (rotation, expiry, deletion) from every HTTPS response during validation, file reading, download and authenticated update checks into the encrypted storage, so it survives restarts. The public `ReadPage` stays cookie-free; logged-in GUI update checks reuse the authenticated client.
   - Requests are serialized per service; request spacing and the 429 Retry-After cooldown are in 16 §2.16.1 S11; refuse retries during long cooldowns. HTTPS only, and only the exact `loverslab.com` / `www.loverslab.com` file flows; external CDNs not registered (none observed in practice) fall back to manual download; never forward site cookies to a CDN.
   - There is no general "Mod index" `source:`: no index exists to connect to.

## 2. Steam client calls (subscribe and unsubscribe)

Like RimCrow, RimArcho subscribes to and unsubscribes from Workshop items through the player's running Steam client. The Mod library uses these calls to unsubscribe and resubscribe (16 §2.9).

- **Bounded child process.** RimArcho launches `archo steam-worker subscribe|unsubscribe|state|download|watch <Workshop IDs…>`, which is not listed in help. Its working directory is `%LOCALAPPDATA%\RimArcho\steam`. This contains `steam_api64.dll` copied from the game installation and `steam_appid.txt` containing `294100`. In 1.7 the DLL is in the game root; also search the Unity layout at `RimWorldWin64_Data\Plugins\x86_64`. Recopy the DLL if the game's copy changes. Never write to the game directory. The child exits after its calls, but `watch` stays alive while waiting for downloads. Steam then shows "playing RimWorld", so downloads must be requested explicitly rather than left to Steam's background updates. A DLL failure cannot crash the window.
- **Calls.** Use `syscall`, without cgo, to invoke the flat Steamworks C API. Call `SteamAPI_InitFlat` (SDK 1.58 and later), falling back to `SteamAPI_Init` if it is absent. Select the highest available versions of `SteamAPI_SteamUGC_v0NN` and `SteamAPI_SteamUtils_v0NN` in the DLL. Issue `SteamAPI_ISteamUGC_SubscribeItem` or `UnsubscribeItem` for each item, then loop `SteamAPI_RunCallbacks`. Read each call's `EResult` through `ISteamUtils_IsAPICallCompleted` and `GetAPICallResult` until all calls have results or time out. For unanswered calls, use the subscribed bit from `GetItemState`. Before the operation, process the subscription-list refresh triggered by initialization. Afterward, continue processing callbacks and watch for confirmed-success items whose state reverts; retry each reverted item once. See 16 §2.16.1 S05 for the initialization, reply and compensation-observation intervals and deadlines. Finally, call `SteamAPI_Shutdown` and exit. The DLL of game build 1.7.4982 provides `SteamAPI_Init`, `SteamUGC_v016` and `SteamUtils_v010`.
- **Output** is line-oriented text parsed by the parent (`steamworks.Parse`): `ITEM <ID> ok|failed:<EResult>|timeout <state bits>`, `STATE <ID> <state bits>`, and `DONE`. If Steam is unavailable, the only line is `ERROR <reason>`. `watch` adds `PROGRESS <ID> <downloaded bytes> <total bytes> <state bits>`, emitted only when a sample changes. The parent consumes each line through `App.runSteamStreaming` and calls `BatchCalls.Progress` or `Done`, without waiting for the child to exit. A batch has at most 50 items. Ordinary calls time out after 40 seconds; download waits use the limits below.
- **Steam unavailable.** Steam not running, not being logged in, a missing or unloadable DLL, or a timeout produces `app.ErrSteamUnavailable`. The window opens the items' Workshop pages and explains the reason; the CLI error includes their page links. A Steam failure (`failed:<EResult>`) is reported as returned, without opening pages. The wording is in `app.WorkshopResultText`. Result 3 (no connection) says "the Steam client is offline", and task details suggest restarting Steam. A common cause is SteamCMD logging into the same account and displacing the client (16 §2.9).
- **Unsubscription lets Steam delete Workshop folders**, so it is destructive like recycling. The UI first shows `--dry-run` with the folder to be deleted, then asks for confirmation; MCP `manage_library` marks it as destructive. An enabled Mod or one used by plans in any environment only warns, listing the plans in `warning:`, and unsubscription proceeds. Those plan entries become missing. Refuse if a game is running (09 §4). Unsubscribed residue cannot be unsubscribed again (use `trash`), and an already subscribed item cannot be subscribed again.
- **Resubscribing subscribed Workshop originals.** `App.Workshop("resubscribe", refs, dryRun)` previews and then confirms that RimArcho will recycle the folder before Steam downloads it again, losing any local changes. Accept only Workshop originals with numeric Workshop IDs that are not themselves links and carry no locked marker. Enabled Mods and Mods used by any plan are allowed; refuse if a game runs. First unsubscribe through the existing worker. Only for items whose unsubscription Steam confirms, recycle the entire original `…/workshop/content/294100/<Workshop ID>` directory, including extra files and `.git`, through the existing recycle backend and path allowlist. Never follow the copy's own symbolic link or junction to clean its target, and never delete permanently. Subscribe only after `Lstat` confirms that the original path is absent. If Steam has concurrently deleted it, count that as success. Briefly retry transient failures such as sharing conflicts under 16 §2.16.1 S10. If a directory still exists after the deadline, or its absence cannot be confirmed, report that item's cleanup failure and do not subscribe it; other successful items continue. Do not clean up or subscribe items whose unsubscription was not confirmed. Unsubscribed residue skips unsubscription and cleanup and subscribes directly. Unsubscribing and subscribing again are one unit: `BatchCalls.Stopped` is honoured before the unsubscribe and once the subscribe is sent (the download), never between them. Before the unsubscribe, the items are recorded in `meta[workshop:resubscribe-pending]` (Workshop ID → name); Steam's confirmation of a subscription (any Subscribe call, `runSteamContext`) or a refusal to unsubscribe removes an item. Items still recorded after a crash, a lost Steam connection or a failed folder cleanup, and not subscribed since (no live, non-residue copy in the Workshop folder), appear in can it run as "a resubscribe was cut short" with "subscribe again" (`App.ResubscribePending`, `view.resubscribeNeeds`). The GUI uses the existing Steam background-task queue, with at most 50 items per batch; the CLI and MCP execute in the foreground. In between, do not remove Instances, change plans or detach game links to the original path. Scan rule R1 (same source and relative path, 04 §2.1) reuses the original ID and Lineage when the folder returns, even if a scan marked it missing during the gap. Confirmed subscriptions, including residue, go to `watch`. For each item, call `ISteamUGC::DownloadItem(id, true)`, pump `SteamAPI_RunCallbacks` at the intervals in 16 §2.16.1 S08, read `GetItemState` and the byte counts from `GetItemDownloadInfo`, and obtain the install path through `GetItemInstallInfo`. An item succeeds only when its directory exists and is nonempty, Installed is set, and neither Downloading nor DownloadPending is set. Installed alone may refer to an old manifest and does not prove completion. See 16 §2.16.1 S08 for the per-item no-growth stall threshold and total wait limit. On expiry, report "Steam did not download; please check Steam" or a download timeout. `BatchCalls.Stopped` cancels the operation: the parent closes the input pipe, and the worker exits and calls Shutdown. If the DLL hangs, force-terminate and reap the child. Parent exit also causes pipe EOF, preventing orphan workers. See 16 §2.16 for task-page phases, per-item text and JSON. The CLI reports progress about every 10% and at each item's completion; the command returns only after the download completes or fails.
- **Anonymous local state.** If Steam is unavailable, `workshop state` and MCP `steam_state` return whether the local folder exists, explicitly marked `Local` with the reason retained. Subscription, update and download progress are unknown; state bits 0 must not be interpreted as "unsubscribed". Subscription and unsubscription still require an account, and failures must not be disguised as success.
- **Commands.** Use `archo workshop unsubscribe <refs…> [--dry-run]`, `archo workshop subscribe <refs…> [--dry-run]`, `archo workshop resubscribe <refs…> [--dry-run]`, and `archo workshop state <refs…>` (subscribed, installed, needs update, downloading). The MCP `manage_library` actions are `unsubscribe`, `subscribe`, `resubscribe` and `steam_state`. Do not rescan immediately after a call. Resubscription waits for the download to complete; ordinary subscription and unsubscription leave Steam to download or delete in the background, and the next scan sees the result.
- **Tests** use fake child processes (`App.SteamWorker` for ordinary calls and `App.SteamWorkerStream` for streaming waits), never real Steam. Real calls occur only after player confirmation. Manual development checks stop at the preview.

## 3. Downloading game versions with SteamCMD

**Account management.** Settings › "accounts" offers only "log in", "log in again" and "log out". The one-line availability status is defined in 16 §2.14. After the player enters an account name, open the native SteamCMD console with `+login <name>`; the player enters the password and Guard response there and quits. After the window closes, run `+login <name> +licenses_print +quit` hidden to verify automatically with the cached authentication, without passing a password. Confirm the login only if both the login steps and the user info that follows are OK; step and result messages may be on separate lines. RimWorld ownership requires app 294100 in a license's Apps/AppID list. Store only the ownership boolean and the check time, not the license list. Anonymous users can download Workshop Mods but cannot own or download the game. Do not claim that credentials have expired on a network failure, and do not reuse records from another tool path or account.

Logout runs `+logout +quit`. If it fails, is unconfirmed or is offline, automatically clear the managed copy's known local authentication cache (02 §1). Explain the scope beforehand in the confirmation text. Do not read tokens, back up authentication files or log out other devices. Copies at external paths or on `PATH` manage their own login; they do not get managed-account buttons or cleanup.

Workshop fallback, game downloads and account operations share the resolution of the actual tool instance and account. The instance lock covers the process lifetime. Public branch lists always use anonymous access; reading branches does not establish a game license. SteamCMD owns its console output. RimArcho adds no prompts or window titles containing untranslated text. Externally reported progress and errors contain only the permitted phases, counts and reasons, never raw authentication or license logs.

Game-version download (`archo env branches`, `archo env download`, and "download a version" in step 1 of the first-run guide, 16 §2.15) serves a player who owns RimWorld and wants an older version, such as 1.5, as another environment.

- **SteamCMD location.** Search in order: `steamcmd.path`, `%LOCALAPPDATA%\RimArcho\steamcmd\steamcmd.exe`, then `PATH`. If none is found, ask the player first, showing the source and size. Obtain `Content-Length` with a HEAD request to `https://steamcdn-a.akamaihd.net/client/installer/steamcmd.zip`. After consent (CLI `--install-steamcmd`), download and extract it to `%LOCALAPPDATA%\RimArcho\steamcmd`. SteamCMD updates itself on first run, downloading about 30 MB.
- **Branches.** Run `steamcmd +login anonymous +app_info_update 1 +app_info_print 294100 +quit`. Anonymous access can read RimWorld's app information without ownership. Read `depots/branches`, omit password-required branches (`pwdrequired`), and sort as follows: `public`, `unstable`, `version-*` from newest to oldest, then the others (`alpha*`, `beta*`). Never guess branch names. The recorded list (`testdata/steamcmd/app_info_print_294100.txt`) is `public`, `unstable` (Public testing), `version-1.6.4633`, `version-1.5`, `version-1.4.3901`, `version-1.4.3563`, `version-1.4.3542`, `version-1.3-latest`, `version-1.3.3287`, `version-1.2.3005`, `version-1.2`, `version-1.1`, `version-1.0`, `beta19`, `beta18`, `alpha17`…`alpha13`, `alpha4`. There is no `version-1.6`; the version of `public` is known only after downloading and reading Version.txt.
- **Branch cache.** Cache public branches in-process by appID and SteamCMD tool identity (normalized real path, file size and modification time). See 16 §2.16.1 C02 (`internal/app/gamebranches.go`) for validity and retry gates after failure. Concurrent queries for the same key run only once. When the cache expires, show the old list immediately, refresh anonymously in the background, and update the UI on completion. On failure, retain the old list and show the error; allow retry after a short backoff. The actual query still holds `accounts.Lock`, sharing instance exclusion with downloads and account operations. Reread tool identity after success to support SteamCMD self-updates. Cancel branch queries when the window closes. The UI shows a lightweight refresh notice. See 16 §2.16.1 G05 for status-polling backoff and the stop deadline; reentering the page allows another read. Download-log polling and waits for descendant processes follow S01 and S12.
- **Destination.** The directory must neither be inside nor contain the RimArcho data directory. It must not contain or be contained by any source, including any game's `Data` or `Mods` and any Mod folder, and must not be an existing environment's game directory. Create it if it does not exist.
- **Login.** Use the account in settings by default. Anonymous access can download only Workshop Mods; a game download asks the player to log into an account that owns RimWorld. The `steamcmd.account` setting may be empty (anonymous), `anonymous`, or an account name. The download form and CLI `--account` override it only for this run, with precedence: explicit account → settings → anonymous. Explicit `anonymous` overrides a saved account; clearing the setting restores anonymous access. Public branch lists always use anonymous access. RimArcho stores only the account name and does not receive passwords or Steam tokens. The player enters them in SteamCMD's **own console** (`CREATE_NEW_CONSOLE`) or the CLI's current terminal.
- **Download.** Run `+force_install_dir <directory> +login <account> +app_update 294100 [-beta <branch>] validate +quit`, omitting `-beta` for `public`. RimArcho does not read the SteamCMD console. It follows the tool's `<steamcmd>/logs/console_log.txt`, starting at the prelaunch file length and restarting from the beginning if the file becomes shorter. Convert `Update state (0x..) downloading|verifying update, progress: P (done / total)` into progress; `Success! App '294100' fully installed.` indicates success. Then confirm that the directory contains a game and register it through the existing-game flow. Name it after the version, such as `1.5`, use `direct` launch, and default to shared saves (CLI may use `--saves own`). Scan only its `Data` and `Mods`.
- **Plain-language failures.** Explain login, Guard, network, license, disk and branch failures using the permitted reasons in `DownloadError.Why`. For an unrecognized result, say that completion was not confirmed. Do not append raw SteamCMD output to external messages. A final `fully installed` overrides earlier errors because SteamCMD reconnects itself: `steamcmd has been disconnected from steam with result 3 (No Connection)` may be followed by `Retrying...`; in a VM test, a 16 GB download disconnected once and still completed (`TestSteamDownloadRecoversFromDisconnect`).
- **Unverified items.** A VM test with a cached login downloaded `unstable` (16.4 GB, 37 minutes) and verified the progress-line format and the disconnect text. Still unverified are the real login window and prompts, the wording of failures (only the `No subscription` and login `FAILED (...)` formats are certain), whether a nonexistent branch produces an error or installs `public`, and the contents of the completed directory. Tests use a fake SteamCMD (`App.SteamCMDStart` / `SteamCMDRun`) that writes log lines.

## 4. Account storage and login window isolation

`internal/deps` only discovers tools; `internal/accounts` manages account boundaries. Secrets live only in `%LOCALAPPDATA%\RimArcho\accounts\loverslab.session`, protected with current-user CryptProtectData from `golang.org/x/sys/windows`, never with machine scope. A protected DACL grants access only to the current user and propagates to children. Store the site cookie attributes that are needed, including session-only cookies the API uses after the login window exits; expiry and logout belong to the site. Store no passwords or browser databases. `.session.new` is also ciphertext only and atomically replaces the single authoritative file. Exclude the file from DB backups, exports, packs, diagnostics, logs and tasks.

Login runs in a separate native `account-login-helper` process with an STA message loop and its own WebView2 environment. Delete the temporary `accounts/webview-profile` after closing; never restore an old profile next time. Dispatch to this process before the CLI or main UI initializes. It exposes no Wails services, host objects, web messages, DevTools, remote debugging, script injection, screenshots, request-body diagnostics or agent interface. Disable password saving, ordinary form autofill and browser debug shortcuts. Use only CookieManager to retrieve cookies for the allowed domains. The host can run local processes; do not claim protection from arbitrary code running as the same user.

`accounts/downloads` holds managed temporary authenticated downloads; they are deleted on installation or when the account is forgotten, and forgetting also clears crash residue. Ordinary session reads are offline; verification is one GET; downloads are restricted to real file pages and observed site links. Raw responses, CSRF tokens and temporary signed URLs never enter errors or tasks. Uninstall first forgets accounts (02 §2) and keeps what is needed to retry on failure.

Automatic renewal reuses the single GET of the site's own settings page in `subscribe.LoversLab.Verify`, at the canonical `/settings/`: the GET does not follow redirects, and the query URL that redirects there with 301 would classify a logged-in session as needing verification. Accept the server's Set-Cookie and save it through the same encrypted file. Do not launch a browser or submit passwords; do not promise that the server extends the session. Schedule from the earliest persistent authentication-cookie expiry in `accounts.Session.RenewalExpiry`, ignoring short session cookies, and check ahead of expiry. If expiry is still imminent after verification, a login or browser verification is needed: show this in settings › "accounts" and in quiet notifications. Advance-check formula, notification thresholds and intervals: 16 §2.16.1 A02; authorization and notification rules: 16 §2.16. Offline, retain known sessions and pending status; do not loop requests on failure. File pages read during automatic Mod checks are also guest-visible. Mark a session usable only if a page contains the logged-in user's logout link (the same evidence as verification); a guest view does not change the session-check conclusion.
