# 20 · Game test runs

> Status: implemented: test runs and probe runs (§2, §3) for 1.6 and 1.7; probe runs through RimArcho are tested on real 1.6 only. The `rimworld-probe` skill (§4) is tested on real 1.6 and 1.7.
> Basis: 02 §1, 06, 09 §3, 14 §3, 17 §4

This specification covers the two ways to start the real game for a test: RimArcho's test runs, which check whether a plan loads and which errors it logs (§2), with probe runs that add a small test Mod reporting what it observed (§3); and the repository's `rimworld-probe` agent skill, which runs such a probe Mod in a sandbox of its own (§4). Neither touches the player's saves, configuration or logs.

## 1. Overview

| | Test run (§2, §3) | `rimworld-probe` skill (§4) |
| --- | --- | --- |
| Part of | RimArcho: `archo test run`, MCP `test_run` | The repository's `skills/`, packed into the release zip (17 §5); RimArcho does not depend on it (14 §3) |
| Tests | A plan of an environment, in that environment's game | The Mods named on the command line, against any game folder |
| Game folder | The environment's own, with temporary `_Archo_` links | A sandbox of junctions and hard links in a work folder |
| Answers | Does the plan load, which errors occur, which Mods they come from, compared with the player's log and the previous run; with `--probe`, what the probe observed | What the probe observed, its errors per step, and a screenshot |

Both read the probe line contract (§3), so a probe built with the skill runs under either.

## 2. Test runs

A test run (`internal/gametest`, `App.TestRun`, `archo test run`, MCP `test_run`) launches a plan in an environment's game, checks whether it reaches the main menu or a test map and which errors occur, then closes the game and reports. Research and measurements: `docs/research/2026-10-24_game-test-runs-rimdevtools.md`. A test run does not touch the player's saves, configuration or logs. Its only write to the game directory is the temporary links below, removed when the run ends.

Before preparing isolated data or starting a process, a test run performs the read-only link inspection from 09 §3. If the tested game's links are broken or the inspection fails, it returns a structured report with `status: links-blocked`, paths, targets, reasons and evidence. It then creates no test data, changes no Mods and does not launch the game. The low-level `internal/gametest.Run` also performs a read-only precheck.

- **Isolated user data.** Use `<data directory>/tests/<environment ID>/userdata`, passed to the game as `-savedatafolder=`. Reuse it across runs; 1.7 stores shader and texture caches here, so reuse makes a substantial difference. Before each run, write `Config/ModsConfig.xml` (`loadout.Render`, with known DLC as in 10 §3). Copy the environment's other `Config/` `*.xml` files to preserve Mod settings, except `ModsConfig.xml`, `Knowledge.xml`, `Prefs.xml` and `KeyPrefs.xml`. Then copy Mod settings as 09 §3 "Settings follow the Mod" would for the folders this run's game sees (`testRunSeen`: its folder in `Data/`, `Mods/` or the Workshop, or an existing link's name), checking the environment's `Config/` for present files and writing only the isolated one, where a previous run's copy is refreshed. Delete `Config/Knowledge.xml`. Also remove old Prefs and KeyPrefs from the isolated directory on each run, letting the target game generate default language, window and key preferences to avoid incompatibilities from sharing player configuration across versions. Retain the caches. The directory cannot be inside the game directory; `gametest` checks this.
- **Logs.** Each run gets `<data directory>/tests/<environment ID>/runs/<UTC time>/`, using `20060102-150405`. If a directory for that second exists, advance to the next second. It contains `Player.log`, merged stdout and stderr in `stdout.log`, the process result in `result.json`, and the attribution report in `report.json`. Keep only the latest 10 run directories per environment, retaining the `userdata` cache. For Unity 1.6 and earlier, add `-logfile <run directory>/Player.log`. From 1.7 onward, identified by `Waylith.dll` in the game directory, the file-log location is hardcoded to the player's LocalLow. Add `-NoFileLog` instead, and let RimArcho capture stdout and stderr. As it reads the console format (`HH:MM:SS  LEVEL message`), convert it to the file format in `Player.log` so that `internal/logs` can parse it normally. Launch without a console (`DETACHED_PROCESS`); terminal Ctrl+C reaches only RimArcho, which kills the game. Cancelling the MCP `test_run` call kills it too; the call sends progress every 10 seconds so that clients with a request timeout keep waiting (14 §1). A known limitation is that the 1.7 console uses the system ANSI code page. Characters it cannot represent, such as Chinese Mod names on an English system, become `?` in the log. Package and type names are unaffected, so attribution still works.
- **Launch.** Always start the executable directly, with the game directory as the working directory. Do not use Steam, which cannot provide a process handle. For Unity versions, also add `-popupwindow`. Refuse if a game is already running (`checkNoGame`).
- **Decision.** At the main menu, `MainMenuDrawer.Init()` writes `Config/Knowledge.xml`. Its appearance after launch marks arrival at the menu; then wait for `--settle` to collect late errors. For a test map (`--map`), add `quicktest`. After `Initializing new game with mods` appears, count arrival when the log has been quiet for the required threshold. See 16 §2.16.1 V01–V04 for sampling intervals, the settle wait and default time limits. An early game exit is `exited`; reaching the `--timeout` deadline is `timeout`. Kill the process at the end.
- **Game-invisible Mods** (temporary links, `app/testrunlinks.go`). The game can find plan Mods only in its `Data/`, `Mods/` (including existing links), or the environment's Workshop directory. Before preparing the test data, link each listed deployable Instance (09 §3: pinned copies in the lock library, SteamCMD and extra folders, another game's `Mods/`) that the game does not see into `Mods/` under its 09 §3 link name, journaled like a save's links (`App.applyLinks`), and list the names in the report's `linked`. So after `pin_mod` (07 §5.2) and an edit of the copy, a test run tests the copy without a save: the test `ModsConfig.xml` names the unsuffixed packageId, which the game resolves to the `Mods/` copy before a same-package Workshop copy. Link nothing that would change what is already in `Mods/`: if an entry with the link's name exists, or another `Mods/` entry (a folder or any link) has the same packageId (the game loads only one, 09 §3), the Mod stays in `missing` with that `reason`. Without a `Mods/` folder every such Mod is missing with a reason. Invisible Mods that are not deployable (not installed, or residue) are listed in `missing` too, and the game launches anyway. **Removal.** The links are recorded in `tests/<environment ID>/links.json` before they are made and removed as soon as the game has exited (also when preparing the test data fails or the call is cancelled), then the record is deleted. A link is removed only while it is still a link to the recorded folder; nothing else in `Mods/` is touched. An interrupted run (RimArcho killed during it) leaves its links and record: the next test run removes them first, and the next save or launch removes them anyway when the plan does not list those Mods (09 §3).
- **Consequences.** Clusters that follow from a def file that failed to load (06 §3) are counted in `counts` and `clusters_total` but not listed; their root has `consequences: N`. In `fixed`, too, only the root is listed, with the same count; `player_log.fixed` still counts every cluster.
- **Report.** Include the status (`menu` / `map` / `timeout` / `exited`), loading seconds from launch to the marker, total seconds, peak memory (the process's `PeakWorkingSetSize`), the requested Mod count and `missing`, the log's error clusters (`testRunLog`, attributed against the tested plan), and counts by category. Text output is for people; `--json` is for MCP and scripts. Exit with 0 only if the target was reached without error clusters; otherwise, exit with 1 (MCP `isError` follows). Informational clusters (`mod-report`, `other`, `noise`) are listed under `info` (up to 30; class, message cut to 100 characters, count and `before`; never counted as errors) and in a text `informational: N` section, so a run's own warnings are visible without reading the log. `args` is saved only in `report.json` (the next run's baseline needs the map mode) and is left out of `--json` and the MCP result. The messages in `fixed` and `gone` are cut to 100 characters (`shortMessage`); gone clusters still find the earlier report's attribution by their first line.
- **Analysis before attribution.** Assembly types and Harmony IDs come only from the analysis (06 §2), and a test run is often the first command after a scan. After the game exits, and before attributing its log, bring the tested plan's analysis up to date (`ensureTestAnalysis`; it waits for one still running from an earlier MCP call and has no MCP time bound). Running it after the game keeps the measured load unaffected; a fresh analysis costs nothing. If it fails, attribute with what is stored and put the error in `analysis_error`.
- **Comparison with the player's log** (`comparePlayerLog`). The player's log is the one `archo log` (MCP `analyze_log`) reads by default: the environment's current `Player.log`, else `Player-prev.log` (`LogPaths`, 06 §4). Whenever it exists, compare with it, so the first run of a plan and the first map run get a comparison too. Attribute it as `archo log` does (`AnalyzeLog`, cached, against the current plan) and compare cluster keys. `player_log` gives `path` and the counts `present` and `absent` (this run's clusters with and without the same key in the player's log) and `fixed` (the player's non-informational clusters, preference errors excluded, that this run no longer has), over all clusters. Each listed cluster has `before: present` or `absent`. `fixed` lists up to 30 of them with their attribution there (class, first message line, count, mods, confidence). A cluster this run could not show is counted in `unreached` instead of `fixed`: every cluster when the run did not reach its target (status other than `menu` / `map`), and a cluster whose observed phases (19 §4) are all after loading: a save load or play, or a new game for a run without `--map` (`testRunReaches`); clusters without observed phases count as reachable. If attributing the player's log fails, `player_log.error` says why and nothing is compared. Without a player's log these fields are absent and the text says `compared with the player's log: none found`.
- **Comparison with the previous run** (`compareTestRun`). The baseline is the newest earlier run directory of this environment whose `report.json` has the same `plan`, a status other than `links-blocked` and the same map mode (`args` contains `quicktest`), and whose `Player.log` is readable; older reports without comparison fields qualify too. Reparse that log (`logs.Clusters`, no attribution) and compare cluster keys over the non-informational clusters (preference errors as `settings`). `baseline` gives `run_dir`, `status` and the counts `new`, `present`, `gone` over all clusters, including those beyond the 30 listed; each listed cluster has `delta: new` or `present`; `gone` lists up to 30 baseline clusters missing now (class, first message line, count, mods, confidence). A gone cluster keeps the mods and confidence of the baseline report's entry with the same class, first line and count; failing that (beyond its 30 listed, or a report without attribution), those of the player's log's cluster with the same key; otherwise `mods: []` and an empty confidence. Without a baseline these fields are absent and the text says `compared with: no earlier run of this plan`. **Neither comparison changes the exit code.** The previous run is not a known-good reference: usually it is the faulty run being fixed, so passing on "no new clusters" would pass an unchanged faulty list. The player's log is not one either: it is the faulty run. `fixed` and `gone` show that a fix worked; success still means no error clusters.

XML errors in PrefsData or KeyPrefs are classified as `settings` (environment configuration), without listing suspected Mods. They still count as errors and produce a failing exit code.

## 3. Probe runs

A probe is a small test Mod: on a test map it sets up a situation, lets the game run, logs what happens and quits. A probe run (`archo test run --probe <folder>`, MCP `test_run` `probe`) is a test run as in §2 that adds one probe to the tested list and waits for its result (`checkProbe`, `finishProbe`, `gametest.Options.Probe`). Any Mod folder that follows the line contract works. RimArcho does not depend on `skills/rimworld-probe` (14 §3); its template is one way to build a probe.

- **Line contract.** A probe logs messages that start with `[Probe] ` (`Verse.Log.Message`) and ends with exactly one `[Probe] RESULT <summary>` or `[Probe] EXCEPTION <text>` line (`gametest.ProbeLine`). When `-probequit` is on the command line, it quits the game itself after that line. In `Player.log` the line is the message itself (Unity), or the message after the time and level (the converted 1.7 console log). Test runs delete `Prefs.xml` (§2), so the game starts with dev mode off and `runInBackground` off: unfocused, it stops updating. A probe sets what it needs itself; the skill's template turns on `Prefs.RunInBackground` when `-probequit` is given and runs at Superfast without dev mode.
- **Folder.** The folder needs `About/About.xml` with a packageId that is neither official content nor in the tested plan, and `Mods/` must hold no other entry with that packageId (the game loads only one, 09 §3). If `Mods/` already holds the folder itself (a folder or link with the same real path), nothing is linked. Otherwise the folder is linked into `Mods/` as `_Archo_probe_<packageId>` (characters other than letters, digits, `.` and `-` become `_`), recorded and removed together with the run's other links ("Game-invisible Mods" in §2), and listed in `linked`. These checks run after the links of an interrupted run are removed and before this run links anything or writes its test data; a failed check is an error with no report.
- **Position.** `--probe-after <packageId>` or `--probe-before <packageId>` (MCP `probe_after`, `probe_before`) put the probe next to a Mod of the tested list, official content included; the default is last. A packageId the list does not have, or both options, is an error, and so is either option without `--probe`. Only the test `ModsConfig.xml` lists the probe; the plan is not changed and `requested` does not count it.
- **Launch and arrival.** A probe run is a map run (`quicktest`; `--map` is implied) with `-probequit`. Arrival is the RESULT or EXCEPTION line, not the quiet log. After it, wait up to `--settle` (default 15 s in a probe run) for the game to quit by itself, then kill it; the status is `probe` either way. A game that exits before the line is `exited`; `--timeout` still bounds the run (`timeout`). `load_seconds` is the time from launch to the line.
- **Report.** `probe` gives `folder`, `package_id`, `position` (1-based in the tested load order, official content included), `outcome` (`result`, `exception`, or `none` when no line arrived), `result` (the text after `RESULT `, up to 2,000 characters), `exception` (the text after `EXCEPTION ` with up to 8 following stack lines), `lines` (every `[Probe]` message's first line without the prefix, cut to 300 characters; beyond 40 messages, the first 10 and the last 30) and `lines_total`, `screenshot`, and `missing_dependencies` (the About.xml `modDependencies` the tested list lacks). A probe may save `probe.png` in its save data folder (`GenFilePaths.SaveDataFolderPath`, the isolated user data): RimArcho deletes an earlier one before the launch and moves the new one into the run directory, whose path is `screenshot`. Error clusters, attribution, `info` and both comparisons are as in §2, except that `info` leaves out the probe's own `[Probe]` messages (the game files them as Mod reports; they are in `lines`). The probe has no analysis, so a cluster from the probe's own code names no Mod. Success needs `outcome: result` and no error clusters: a probe run of a conflict usually fails on the conflict's errors, and its RESULT still says what happened. The text output adds a `probe:` section.
- **Comparisons.** The previous run of a probe run is the newest one with the same plan and the same probe packageId; plain runs and probe runs never compare with each other. Against the player's log, a probe run reaches what a map run reaches. It plays only minutes of a fresh test map, so clusters seen only in play count as `unreached`.
- **1.7.** The contract works unchanged: the game runs with `-NoFileLog`, and the converted console log carries the `[Probe]` lines. The probe must be built for that game: .NET 10 (`net10.0`) against the game folder's `Assembly-CSharp.dll`, `UnityStubs.dll` (UnityEngine names) and a 1.7 Harmony. The skill's `build` against a 1.7 game does this and puts the DLL in `1.7/Assemblies` (its `LoadFolders.xml` picks the folder); with the skill's own runner on 1.7.5000 its screenshot, error hook and quit work. A probe run of 1.7 through RimArcho has not been tried yet. If the quit does nothing, the run still ends after the settle wait.

## 4. The rimworld-probe skill

`skills/rimworld-probe` gives an agent a probe Mod skeleton (`template/`) and a runner (`scripts/probe.mjs`: `new`, `build`, `run`, `clean`). `SKILL.md` is the agent's guide to writing scenarios and stays the place for those details. The runner never writes the game folder, the Mods it is given, Steam, or `%APPDATA%\RimArcho`.

- **Build.** `build` reads the game's `Version.txt` and builds for that version: 1.6 as `net472` against `RimWorldWin64_Data/Managed`; 1.7 (`Waylith.dll` in the game folder) as `net10.0` against the game folder's `Assembly-CSharp.dll` and `UnityStubs.dll`. Harmony comes from `<Harmony>/<version>/Assemblies`, else `Current/Assemblies`. The DLL goes to `<version>/Assemblies`; the template's `LoadFolders.xml` loads the folder of the running game, so one probe folder serves both versions.
- **Sandbox.** `run` builds `<work>/game-<version>`: a junction for each folder of the game, a hard link for each top-level file (a copy when the work folder is on another volume), and a junction in `Mods/` for each given Mod. The game's own `Mods/` and `steamapps/` are left out, and so is `steam_appid.txt`, so the game does not attach to a running Steam client. Attached, it scanned every subscribed Workshop Mod, and 1.6 changed the player's `Prefs.xml` in LocalLow at startup. The work folder must be outside the game folder. `clean` unlinks the junctions before deleting the sandbox and refuses while a link remains; user data and run folders stay.
- **User data.** `<work>/userdata-<version>`, passed as `-savedatafolder=`, is reused between runs, so 1.7 keeps its shader and texture caches. Before each run the runner writes `Config/ModsConfig.xml` (Harmony first, then official content in release order without the `--no-dlc` ones, then the given Mods in order) and a minimal `Prefs.xml` (a 1280x720 window, dev mode, `runInBackground`, no automatic pause, English, sound off). It deletes `Saves/` (dev mode would load a save named `autostart` instead of the test map) and an earlier `probe.png`.
- **Launch and end.** The game starts directly with `-quicktest -probequit`: on 1.6 with `-logFile <run>/Player.log`; on 1.7 with `-NoFileLog`, its console written unconverted (`HH:MM:SS  LEVEL message`) to `<run>/Player.log`. The run ends at the `[Probe] RESULT` or `EXCEPTION` line, after which the game has 8 seconds to quit before it is killed; when the game exits; or after `--seconds` (default 600). The runner writes the `[Probe]` lines to `<run>/probe-lines.txt`, copies `probe.png` into the run folder, prints error lines of either log format, and warns when the player's `Prefs.xml` changed during the run (its hash before and after). The warning is for the agent to report, not to repair.
- **Template.** `ProbeRunner.cs` keeps the line contract (§3). A scenario class overrides `OnStartup` (at `[StaticConstructorOnStartup]`, in load order), `Setup` (once the map is ready), `OnFrame` (every frame, paused or not), `Observe`, `Done` and `Finish`. `Step(name)` files every error the game logs from then on under that step (`Application.logMessageReceived`), and the RESULT line ends with the count per step. At the end it pauses, closes the debug log window, selects `ScreenshotTarget`, saves `probe.png` in the save data folder, logs the result and quits under `-probequit`. It runs at Ultrafast in dev mode and Superfast otherwise. Under `-probequit` it turns on `Application.runInBackground`, since a test run (§2) starts the game with default preferences. The same source builds for 1.6 and 1.7; `RW_UNITY` and `RW_WAYLITH` are defined for code that differs.

## 5. Acceptance

### Test runs and probe runs

- `go test ./internal/gametest/` uses fake processes to cover the main menu, map, timeout and early exit. After console-log conversion, `logs.Parse` must still recognize the Waylith format.
- On a real machine, run `archo test run` for a small plan on 1.6 or 1.7. The modification times of `Logs/` and `Config/` under the player's LocalLow must remain unchanged, the game directory must be unchanged, and the report status must be `menu`.
- Probe runs (§3): `go test ./internal/gametest/` covers the RESULT and EXCEPTION lines in both log formats, the probe quitting by itself and being killed after the settle wait, and a game that exits without a line; `go test ./internal/app/ -run Probe` covers the folder checks, the position in the test `ModsConfig.xml`, the link and its removal, the screenshot move, the report fields and the baseline rule, all with synthetic data.
- On a real machine (the VM), run `archo test run --probe <folder>` with the skill's unchanged smoke probe and Harmony in the plan on 1.6: status `probe`, `outcome: result`, `result` starting `smoke ok`, a `screenshot` in the run directory, no `_Archo_probe_` link left in `Mods/`, and the player's LocalLow unchanged.

### The rimworld-probe skill

- The unchanged template builds with 0 errors against a 1.6 and a 1.7 game into `1.6/Assemblies` and `1.7/Assemblies` of the same probe folder.
- On a machine with both games, `run` with Harmony and the unchanged template ends on each with `[Probe] RESULT smoke ok … errors=[startup:0 setup:0 spawn-wall:0 watch:0]`. The game quits by itself, `probe.png` in the run folder shows the selected wall, the log has `SteamAPI.Init() failed` (not attached to Steam), and the player's `Prefs.xml` and LocalLow `Logs/` are unchanged. A paused scenario that opens an info card and logs one deliberate error ends with 0 ticks passed and that error under its own step.
- `clean` removes the sandbox without touching a file of the game or the Mods.
