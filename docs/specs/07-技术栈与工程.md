# 07 · 技术栈与工程

> 本文定义：语言与依赖、代码结构、数据位置、测试与发布，以及 M0 技术验证的通过标准。
> 依赖库均为**候选**，要等 M0 验证通过后才定下来。

## 1. 技术栈

| 用途 | 选择 | 理由 / 待验证点 |
| --- | --- | --- |
| 语言 | Go（当前稳定版） | 单二进制、内存可控、并发简单 |
| TUI | Bubble Tea + Lip Gloss + Bubbles | 生态成熟；需验证 500 行列表的渲染性能与中文宽度 |
| 存储 | SQLite，纯 Go 实现（modernc.org/sqlite） | 不依赖 cgo；需验证内存占用与写入速度 |
| XML 读取 | 标准库 `encoding/xml` 流式解析 | Def 层只抽字段，不建 DOM |
| XPath 模拟 | antchfx/xmlquery + xpath | 需验证与 .NET XPath 1.0 的兼容率（03 §5.2） |
| .NET 元数据 | 候选：saferwall/pe 的 CLR 元数据解析；不满足时自研 ECMA-335 读取器 | 需验证能否读出 CustomAttribute 参数 |
| MCP | 官方 Go SDK（modelcontextprotocol/go-sdk） | 需验证 stdio 与工具注解的支持 |
| KeyValues | andygrunwald/vdf 或自研 | 用于 `libraryfolders.vdf` 和 ACF |
| 哈希 | xxh3-128 | 快 |
| 字符宽度 | mattn/go-runewidth | 中文对齐 |
| 反编译 | ilspycmd（外部，可选） | 不随程序分发 |

不引入：Web 框架、前端构建工具、LLM SDK、ORM。

## 2. 代码结构

```
cmd/archo/                 入口：无参数启动 TUI，有参数走 CLI，`mcp` 子命令走 MCP
internal/
  env/                     环境、路径探测、Player.log 定位
  source/                  来源、重新绑定、链接解析
  scan/                    目录遍历、观测、内容指纹
  identity/                对账、Lineage、墓碑、变更事件、待确认项
  store/                   SQLite 访问与迁移
  content/                 生效内容解析（LoadFolders、版本目录）
  analyze/
    decl/                  声明层问题
    defs/                  Def 索引
    patches/               PatchOperation 模拟
    harmony/               Harmony 事实
    logs/                  日志解析与归因
  dotnet/                  .NET 元数据读取
  loadout/                 工作区、历史、ModsConfig 读写
  order/                   约束图与排序
  rules/                   用户规则、社区数据
  playerdata/              别名、标签、备注、RimCrow 导入
  cmds/                    命令注册表：参数定义、执行、文本输出
  render/                  大纲文本渲染（05 §2）
  surface/
    cli/
    mcp/
    tui/
testdata/                  合成的小型 Mod 样本
```

- 所有表面只依赖 `cmds/`。业务包之间不允许反向依赖表面层。
- `analyze/` 下的分析器以 `archo analyze <层>` 子进程方式运行（03 §3）。

### 6.1 M0 结论（2026-10-19）

**测量环境：** Windows 11，RTX 4090 主机，SSD，Go 1.27.2。使用玩家真实的 RimWorld 环境：ModsConfig 中启用 485 个 Mod，可解析 482 个；工坊目录下有 1274 个文件夹。游戏本体刚更新到 1.7.4982（unstable 分支），但 `ModsConfig.xml` 和 `Player.log` 都来自 1.6.4871（2026-09-29）。全部验证只读，没有改动工坊目录、`Mods/` 和 ModsConfig。

代码在 `spikes/<名称>/`，模块为 `github.com/rimarcho/rimarcho`，每项的原始输出见同目录下的 `RESULT*.txt`。游戏行为依据 ilspycmd 反编译当前的 `Assembly-CSharp.dll`（1.7.4982）得出，涉及 `Verse.ModsConfig`、`ModLister`、`ModMetaData`、`ModContentPack`、`LoadedModManager`、`PatchOperation*` 和 `DirectXmlLoader`。

| 验证项 | 结果 | 关键数字 |
| --- | --- | --- |
| .NET 元数据 | **通过** | 用 saferwall/pe 读表和堆，加上约 450 行自写的 CustomAttribute blob 解码。从启用的 Mod 中按大小均匀抽取 20 个 DLL：读出 560 个 HarmonyPatch 特性，与 ilspycmd 对照一致 560/560（100%）。扩大到 60 个 DLL：920/920（100%）。读取全部 575 个引用 HarmonyPatch 的 DLL：6943 个特性，解码错误 0 个，用时 0.12 秒（约 0.2 毫秒/DLL）；ilspycmd 处理 20 个 DLL 要 14 秒。能读出的内容包括：`typeof` 参数（含嵌套、泛型、`Nullable<T>`）、字符串、`MethodType` / `ArgumentType` 枚举、`Type[]` 与枚举数组，以及对 `HarmonyLib.Harmony::Patch` 的 MemberRef 引用（即手动补丁）。 |
| XPath 兼容 | **兼容性通过；性能有条件通过；内存未通过** | 482 个 Mod，4592 个 Def 文件（35257 个顶层 Def），1155 个 Patch 文件，5433 个顶层操作（另有 269 个 Mod 自定义的操作类，无法模拟），7044 次 XPath 求值，0 个编译错误。模拟出 9 个失败，日志报告 7 个，其中 7 个吻合。不一致 2 个，**不一致率 0.037%**（标准是 < 0.5%）。这 2 个都不是 XPath 引擎造成的：被补丁的 Mod（sbz Neat Storage）在日志之后的 10 月 3–6 日更新，把 `sbzSmallDisplayShelfBase` 改名为 `sbzDisplayShelfBase`。在这套环境中，antchfx/xpath 与 .NET XPath 没有观察到任何差异。耗时：直接用 xmlquery 时总计 58–70 秒（`NodeNavigator.MoveToNext` 占 54% 的 CPU，原因是每次求值都要线性扫描 3.5 万个顶层 Def）；加上 defName/@Name 索引快速路径后为 **7.8 秒**（索引命中 6729 次，重建 66 次），结果完全相同。内存：合并后的文档有 267 万个节点，文本只有 43 MB，但每个节点约占 225 字节，常驻堆 560–640 MB，**峰值工作集 0.8–1.0 GB**，超过 400 MB 的目标。 |
| TUI 渲染 | **通过** | Bubble Tea v1.3.10 + Lip Gloss + go-runewidth。500 行：滚动时每次按键（Update+View）平均 0.02 毫秒，最大 1.2 毫秒；中文增量搜索最大 0.5 毫秒。5000 行：滚动最大 1.7 毫秒，搜索最大 1.5 毫秒。用真实渲染器测得按键到画面平均 16.7 毫秒，这是渲染器 60 fps 的固定刷新间隔，不是计算耗时。中文对齐：5.3 万行渲染结果的显示宽度全部一致。内存：工作集 16 MB。 |
| SQLite 内存 | **通过** | modernc.org/sqlite v1.60.1，WAL 模式，默认缓存。写入 500 个 Mod 的实例、快照和文件清单（137003 行，对应 8.2 GB 的 Mod 文件；哈希用随机值代替），用时 1.8 秒（约 7.5 万行/秒）。写完后工作集 **21.5 MB**（重复 3 次一致），数据库文件 15.5 MB。注意“私有提交”约 59 MB，其中约 33 MB 是 modernc 的 libc 在启动时预留的，没有实际驻留。空 Go 程序的工作集是 6 MB。 |
| `_steam` 令牌 | **规则已确认（依据反编译），尚无游戏内实测** | 玩家当前环境中没有本地与工坊同包名的 Mod，也没有 `_steam` 条目，因此没法在不改文件的前提下实测。规则已写入 04 §2.2 和 §2.4。 |

**各项要点与后续动作：**

1. **.NET 元数据**：确定采用 saferwall/pe，不需要自研 ECMA-335 读取器。注意 saferwall 返回的是原始编码索引，标签位要自己解码；它把堆映射到文件上，Close 之前要先复制出来。HarmonyPatch 的枚举都按 int32 处理，Harmony 的枚举确实都是 int32。
2. **XPath**：确定采用 antchfx/xpath。xmlquery 只用来解析；Patch 层要换成自己的紧凑节点表示：以 arena 保存节点，用 int32 记录相互链接，名字做字符串驻留，然后实现 `xpath.NodeNavigator` 接口。按 267 万节点、每节点约 40 字节加 43 MB 文本估算，峰值可以控制在 200 MB 左右。defName/@Name 索引快速路径是必须的；缓存失效规则见 `spikes/xpathcompat/index.go`。模拟时还需要注意这些游戏行为：
   - 解析时忽略注释和空白（`IgnoreComments` / `IgnoreWhitespace`）。
   - 选中属性节点后做树操作会抛异常，该操作记为失败。
   - 只有 `Sequence` 列表里的 `li` 才认 `MayRequire`；顶层 `Operation` 上的不起作用。
   - `PatchOperationFindMod` 按 Mod 的**显示名**匹配。官方 DLC 的 About.xml 没有 `<name>`，显示名取 ExpansionDef 的标签（即文件夹名，例如 “Royalty”）。最初的模拟漏掉了这一点，导致 2 个误报。
   - 日志里的失败描述就是 `ToString()` 的输出，例如 `Verse.PatchOperationAdd(xpath)`、`...Sequence(count=N, lastFailedOperation=...)`；比对以“文件路径 + 描述”为键。
3. **TUI**：确定采用 Bubble Tea，不需要分页渲染。依赖要锁定 `charmbracelet/x/ansi v0.10.1`，因为 v0.11.9 与 bubbletea v1.3.10 的 cellbuf 不兼容。还有两点注意：
   - 东亚“模糊宽度”字符（`–`、`…`、`·`）在 Windows Terminal 中占 1 格。如果 runewidth 的 `EastAsianWidth` 被语言环境或 `RUNEWIDTH_EASTASIAN` 开启，对齐就会错位，所以宽度设置要与终端保持一致，并在设置中提供开关。
   - 管道输入下 bubbletea 会把 UTF-8 字节逐个解码，所以端到端测试中的中文按键是用 `p.Send` 注入的；在真实控制台里输入中文还需要人工验证（06 §8 T4）。
4. **SQLite**：确定采用 modernc.org/sqlite，开启 WAL 和 `synchronous=NORMAL`，缓存用默认值，不需要换 cgo 版本。
5. **`_steam`（游戏 1.7.4982 的逻辑）**：
   - `ModLister.RebuildModList` 按官方 `Data/` → `Mods/` → **已订阅**的工坊条目的顺序调用 `TryAddMod`。packageId 重复、来源不同、而新加入的是工坊副本时，给工坊副本设置 `appendPackageIdSteamPostfix`，它的 ID 变成 `<pkg>_steam`。来源相同的重复副本会报错并被忽略。
   - 保存时写入的就是这个带后缀的 ID。
   - 读取时：先按完整 ID 匹配；不中再按文件夹名匹配；还不中而带 `_steam` 时，去掉后缀再匹配；同一个无后缀 ID 被启用两次时，后一个会被停用。
   - 另外两个发现：`ModsConfig.version` 的主次版本与当前游戏不同时，**整个列表会被重置**（玩家当前就是这种情况：配置文件是 1.6，游戏已是 1.7）；游戏只枚举**已订阅**的工坊条目，取消订阅后残留在工坊目录里的文件夹不会被加载（本机有一批这样的残留文件夹，没有 About.xml）。这两点已写入 04，02 的扫描规则也需要相应补充，留作后续工作。
   - 还缺一次游戏内实测：在可以改动文件的测试环境中，做一个本地副本与工坊版同名的场景，观察游戏实际写入的内容。

**缩略图与 bubbletea 的配合方法（V3 照此实现）：**

1. **包装输出。** `tea.WithOutput` 传入一个包装 stdout 的 writer。bubbletea v1.3 每帧只调用一次 `Write`，包装层在这次写入中，把整帧放进同步输出（`CSI ?2026h` … `CSI ?2026l`），并在帧后追加图片操作。这样图片和帧是同一次写入，不会被下一帧插到中间。
2. **清除。** 选中项变化时立即清除：`ESC 7`，对矩形的每一行执行 `CUP` + `ECH 18`，然后 `ESC 8`。图片不在 bubbletea 的帧缓冲中，它不会替我们擦。
3. **停留。** 选中项变化时把“代数”加 1，并 `tea.Tick(150ms)`；到期且代数没变才异步解码，结果回到 Update 时代数仍一致才记下图片序列。快速滚动时几乎不会画图（619 帧只画 3 次）。
4. **绘制。** `ESC 7`、`CSI ?25h`、`CUP 矩形左上角`、`OSC 1337;File=inline=1;size=N;width=18;height=<行数>;preserveAspectRatio=0;doNotMoveCursor=1:<base64> BEL`、`CSI ?25l`、`ESC 8`。图片事先按第 6 点补成恰好 18×行数 格的比例。图片显示期间每帧都重画一次，这样不必推断 bubbletea 这一帧动了哪几行。
5. **关键坑：光标必须可见。** WezTerm 在 Windows 上通过 ConPTY 运行子进程。ConPTY 自己重新生成光标移动，把 OSC 1337 原样转发；但光标隐藏（`?25l`，bubbletea 默认如此）时，它不会把图片前的 `CUP` 发出去，图片就会画在 ConPTY 上次留下光标的地方（实测在第 13 行最右侧，按原图尺寸）。只在写图片的那一刻 `?25h`，写完立即 `?25l`，图片就落在正确位置。用 `imgtest -alt -hide` / `-hide -show` 可以复现和验证。同步输出、`ESC 7/8` 和备用屏幕都与这个问题无关（逐项排除过）。
6. **尺寸（修正后的规则）。** 不能让 WezTerm 决定图片的大小。`preserveAspectRatio=1` 时它并不把图片放进 width×height 的框里：实测它保持宽度、按比例推算高度（1:3 的图在 `width=18;height=9` 下画成 18 格 × 约 23 行），有的图又被压进 9 行，行为不一致。所以 RimArcho 自己算：先把图按比例缩放到 18×9 格以内，取能放下它的最少行数 N（≤ 9），再用透明像素把画布补到恰好 18×N 格的像素比例，最后以 `width=18;height=N;preserveAspectRatio=0` 发送。这样 WezTerm 覆盖的正好是这 18×N 格。格子的宽高比按自带字体取 13:30（11 号字、150% 缩放下实测 13×30 像素；这个比例由字体决定，换 DPI 只差 1 像素的取整），它只影响长宽比是否精确，不影响覆盖哪些格子。16:9 的预览图占 5 行，正方形 8 行，竖图 9 行。
7. **清除规则。** 对 18×9 的整个预留矩形逐行执行 `CUP` + `ECH 18`（`CSI 18 X`）。因为第 6 点保证图片不会超出矩形，这就清掉了图片的全部像素。不要依赖“文字覆盖”或 bubbletea 的整行重写来擦图：实测图片格子被文字重写 7 次后仍然可见，只有 ECH 清得掉。

**观察与限制：**

- **残影（初版的问题，已修正）：** 初版用 `width=18;height=9;preserveAspectRatio=1`，并只清除 18×9。慢速滚动经过第 468 行（Guarding Pawns，预览图 839×1004，高宽比 1.20）时，图片被画成 18 格 × 约 9.3 行，底部约 9 像素落进矩形下方的第 12 行。之后的清除只覆盖 3–11 行，于是第 12 行留下一条棕色细条（`thumbs-2-after-slow-scroll.png`，y 381–389）。复现与验证：
  - `ghost.exe` 用纯品红的 8 种比例测试图逐张绘制和清除，`run-ghost.ps1` 按截图测品红像素的范围。初版下 1:3 的图覆盖 y 111–812（23 行），清除后残留 y 381–812；修正后 8 种比例全部落在 y 111–380、x 726–957（正好 18×9 格以内，正方形 232×234 像素，16:9 是 232×132），每次清除后品红像素为 0。
  - 用真实数据重放原来的滚动（`run-thumbs.ps1 -OldFit` 与修正版），统计第 12 行顶部 6 像素（y 381–386，没有字形）的非背景像素：初版在慢速滚动后是 1398（与原截图完全相同），修正版 10 张截图全部为 0。
  - `run-thumbs.ps1 -Ghost`：最高的预览图 → 16:9 → 无预览 → 最高 → 无预览，修正版截图中矩形和第 12 行都干净。
- **闪烁：** 截图（含快速滚动中的 3 张）没有出现撕裂或半张图；每次换行都是先清除再在 150 毫秒后画出，这个“空一下再出现”是设计行为。肉眼的闪烁判断需要人在 V3 的 T6 中确认。
- **兼容模式：** Windows Terminal 中 Nerd Font 图标显示为替换字符（Cascadia 没有这些字形），所以兼容模式必须用 06 §3 的右栏。
- **WezTerm 会写用户目录：** 即使用 `--config-file`，它也会在 `%USERPROFILE%\.local\share\wezterm\` 下创建 GUI 套接字（`gui-sock-<pid>`）和日志（`wezterm-gui.exe-log-<pid>.txt`）。Windows 上这个位置不能改。V0 之前这个目录不存在，现在由 V0 创建，保留未删。06 §1.4 已注明。`~/.config/wezterm` 和 `~/.wezterm.lua` 没有被创建。
- **archo 的内存（复查后更正）：** V0 第一次测量时 archo 是 78–80 MB，比 M5 的 tuimem（47 MB）高得多。复查结果：
  - 7 次重测，换了 3 种启动方式（直接启动、经 `cmd /c`、原来的 `measure.ps1` 原样重跑），刚启动后空闲都是 30–32 MB，峰值 ≤ 32 MB；gctrace 显示 Go 堆只有 5–8 MB，私有提交约 67 MB（主要是 modernc libc 的预留）。
  - 在真实 WezTerm 中用 `wezterm cli send-text` 走一遍 tuimem 的整套操作（扫描、浏览、搜索、问题视图、分析日志，再空闲 2 分钟），用的是数据目录的副本：空闲时 44 MB，峰值 53 MB，与 tuimem 的 47 MB 一致。宿主终端和启动路径都没有带来额外开销。
  - `TuneProcess`（40 MB 软上限、GOGC 50、256 KiB 页缓存）在 CLI 启动路径上是生效的（`tui.Run` 第一行）。
  - 78–80 MB 那一次复现不出来。当时的输入与现在相同：archo.db 最后写入是 11:30，那次运行之后没有扫描、也没有写库。还排除了“上次被强制结束后 SQLite 恢复 WAL”：在副本上强制结束 3 次，WAL 都是 0 字节，内存都是 31 MB。原因未查明，代码不需要修改。
  - 后续：V3 加入缩略图缓存后，用 `archosession.ps1` 在 WezTerm 中复测，并记录峰值。
- **字体回退：** 不能用 `font_locator = 'ConfigDirsOnly'`，否则 Maple 没有的字形（如 `⬥`、`⇣`）会变成方框；回退链为 Symbols Nerd Font Mono → Cascadia Mono → Segoe UI Symbol。
