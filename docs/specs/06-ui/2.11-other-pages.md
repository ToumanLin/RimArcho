- **Save management**: group saves by colony and identify the corresponding plan and environment for each group. Put old saves that match no plan in a separate group. Show the list first and fill in the sizes row by row. While counting, disable both dropdowns and replace the button with “stop counting”; stopping restores the previous result. Changing the scope or scale does not recalculate the statistics: retain the previous figures and say “Options changed… click count the textures to recalculate”. After conversion or restoring all textures, say “Textures have changed since…”. Conversion is available without statistics because it converts only new or changed PNGs; state this in the confirmation. If statistics have been collected and there is nothing to convert, disable “convert.” Cache each Mod's summary using the fingerprint of its texture paths, sizes, and modification times, together with the options. On reopening the page, check the metadata first and fill in unchanged figures directly. Changes to files that have not been scanned also invalidate the cache. Batch result polling at the interval in §2.16.1 G06; retain the original nodes and shimmer for unchanged rows. Settings retains only the location of the todds encoder.

### 2.14 Settings

The settings page is implemented in the GUI. In the TUI, “Settings” in the command palette displays text with commands. Each item consists of a value and the command that changes it; the UI only invokes that command. The UI runs only commands allowed by `view.SettingCommand`: `env set`, `env rebind`, `folder add`, `folder remove`, `folder set`, `folder move`, `config set`, `db backup`, `db vacuum`, `cache clear`, `data update`, `gc`, `deps install`, `deps remove`, `source clean`, `source decompile`, `update`, and `update --check`. The data comes from `view.SettingsPage`. Choices may have display labels (`choiceLabels`). Address display, native path selection, and URL editing follow §3.1 rule 12. Relocating and moving folders retain the existing command semantics. To move a folder, first select the destination parent directory, then show the preview and ask for confirmation.

**Order**: show About first, followed by common settings, with maintenance settings last. The GUI and TUI follow the order in `view.SettingsPage`; the TUI adds “Current game,” containing the environment-page content, after About. The first 9 group headings have focus keys `1`–`9` (§3.5). Resize it to two JPEGs, 1920 pixels wide for the launch page and 480 pixels wide for the thumbnail and preview, in `cache/backgrounds/`. Ordinary images are named using the path, size, and modification time. Game menu pairs use the first 12 bytes of the SHA-256 of the lowercase packageId plus the format version: `menu-shared-v1-<hash>-1920.jpg` / `-480.jpg`. These names are independent of the installation path, game version, ZIP or Unity fingerprint, and UI language. Store only one pair per package. Validate the JPEG size, dimensions, and full decode. Within a process, memoize validation by path, size, and modification time; when these are unchanged, perform only file status checks. Re-extract only the package with a missing, corrupt, or dimensionally mismatched pair. Ignore and retain old `menu-<stamp hash>-*.jpg` files; never delete player files. Game updates do not automatically invalidate the shared cache. To refresh the artwork, close RimArcho, delete only `cache/backgrounds/menu-shared-v1-*.jpg` (or just the target package's pair), and reopen the app. External browsers require a hard refresh. During extraction, validate the source fingerprints. If the source changes or the operation is cancelled, discard the temporary files without replacing existing members. Replace JPEGs atomically through temporary files. Game ZIP reading supports zstd method 93 and deflate and verifies the full entry size and CRC-32. DDS and Unity decoding support BC7, BC1, and BC3; Unity also supports RGBA32. Decode only 4 rows at a time, directly into box scaling. ZIP entries are capped at 128 MiB. For split data, validate the DDS dimensions (each side ≤ 16384 and ≤ 40 million pixels), mip count, and payload bounds derived from block counts before allocating one split buffer of the declared length. The command table references that buffer directly. After validating the ZIP size and CRC-32, reconstruct 16-byte blocks as needed, without allocating a fully restored DDS or full-size pixels. After completing the thumbnail, still traverse the remaining mip records to validate their fields; do not publish a JPEG if validation fails. Ordinary DDS uses no whole-entry buffer. Unity metadata has a size limit; read pixel ranges without loading the entire `.resS`. Never allocate or store full-size RGBA, a restored DDS, or PNG, and release the memory after each image. Scale other images directly from the decoder output without copying another full-size bitmap. Debounce memory release after batches (§2.16.1 M03). Load thumbnails only when they enter view. `/bg` serves only images listed for the current environment, never arbitrary paths. The URL includes the image-path version. **Task definition**: a task is work that takes time after one player action and must not block the UI. Each task belongs to a queue:

| Queue | Tasks | Execution |
| --- | --- | --- |
| Files | Inventory actions that mutate files: recycle, move into the lock library, unhide, pin a version, update a pinned version, and unpin (§2.9) | Run one task at a time in submission order. | Steam | Unsubscribe and resubscribe through the Steam client (08 §10) | Run one task at a time. Precheck each item, then submit batches of 50 to Steam. |
| RimArcho | Scan, readiness analysis, pack creation, texture conversion and restoration, game download through SteamCMD, SteamCMD and todds download, community update, cache clear, database backup and vacuum, tombstone cleanup, and self check and install (07 §5.1) | Use the existing subprocess or goroutine mechanism for each kind (§8.4). Run one task per kind at a time; different kinds may run concurrently. |

- **Speed** (2026-10-23): previously, every folder move scanned the whole inventory and each unsubscribe launched Steam, making hundreds of items slow to process. A resubscribe download wait can stop within a batch by closing the worker.
- **Resubscribe download progress**: after subscription confirmation, actively request the download and wait for the files (08 §10). **Records**: each task has a record containing its kind, object (14 Mods or Main colony 10-22), state, start time, duration, and a one-sentence result. **Multiple windows** (a GUI and TUI, or two GUIs, using the same data directory, 2026-10-30): each task's `owner` stores the initiating process, process start time, and sequence. **Loading cost**: between Game versions and Follow Steam collections, show Estimated loading cost. Display resident RAM and VRAM including Core and DLC, and the loading RAM budget. Resident means stable main-menu private bytes; loading means peak private bytes from startup to the main menu. Neither means working set. What is included expands the categories, the top five Mods for RAM and for VRAM, and the estimate boundaries. Measure in the background after rendering the page; discard stale results when the list or game changes. Data comes from `app.PlanLoadCost`, `loadcost.Estimate` / `Baseline` / `LoadingBudget` / `Spill`, and `view.PlanLoadCost`; the CLI command is `archo plan cost [<list>] [--mods] [--json]`. The model code is the sole source of coefficients. Unity 1.6 estimates use the vanilla baseline, per-Mod overhead and texture curve calibrated in the 2026-10-31 and 2026-11-01 VM measurements. Combined texture and DDS payloads were measured up to 7.5 GiB; larger payloads remain extrapolated. The VM's graphics adapter has no dedicated VRAM, so those private bytes include the driver's copy of every texture: 1.2 bytes per payload byte (`Coef.TextureGPU16`) and 0.66 GiB for vanilla. The model reports that share as VRAM and the rest of the curve as RAM. `loadcost.Spill` returns to RAM the 1.6 VRAM beyond `Coef.UsableVRAM` (90%) of the dedicated capacity, or all of it when no dedicated VRAM is reported (VM, integrated GPU, unreadable adapter); resident RAM, the loading budget and the §2.4 comparison include it and say how much it is. Without dedicated VRAM every estimate equals the VM curve; on a real graphics card the split is inferred, not measured. Loading budgets estimate startup peak private bytes from the payload and follow the same curve. Coefficients are owned by `loadcost.Coef`, `Baseline` and `LoadingBudget`; see [Unity 1.6 heavy-texture memory](../../research/2026-11-01_unity16-heavy-texture-memory.md) and [Unity 1.6 texture memory breakdown](../../research/2026-11-01_unity16-texture-memory-breakdown.md) for evidence and limits. The 1.7 loading reserve remains uncalibrated. Saves, maps, AssetBundles, and Mod allocations may exceed the scope. Changes to the per-Mod raw measurement format invalidate the file-fingerprint cache; model changes invalidate estimate totals. All lists use the selected game environment, or an explicit version override, to choose coefficients and LoadFolders, rather than the version saved in list history. An unknown version prompts a rescan. See §2.4 for hardware comparisons and levels.
