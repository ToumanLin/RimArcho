# 06 · UI · Information architecture; sidebar, top bar, launch, can it run (§2–2.4)

> Part of [06 · UI](README.md). Section numbers run throughout 06 and remain unchanged after splitting. References still use `06 §x.y`.

## 2. Information architecture and pages

The GUI uses the sidebar below (`shell.js`, `view.Nav` and `NavPath`). Only the Playing group is currently shown. Unplayed, Worth Playing, and Archo have no pages yet and remain hidden. Plans contains each plan and + New plan. The `shift+1`–`shift+8` shortcuts follow the sidebar order. The TUI consists of a four-area plan editor and secondary screens; `P` opens plan switching and management (§9.1). Each page description identifies the implemented parts and the view functions it uses.

### 2.1 Sidebar

Settings uses the same six-tooth gear outline in the side and top navigation (`icons.js`, `settings`). See §2.2 for the style and position of the window buttons, and §3.5 for the command panel.

The left sidebar has groups and expands only the children of the current entry. This grouping was defined on 2026-10-21: Playing covers what the player wants to play or handle now; Library covers what the player has.

| Library | Lists (plans in the spec, §7.2) | All lists first (§2.17), followed by at most 4 lists: the current list, the list open in the editor, then the most recently edited or launched lists. Only Can it run displays a number. Its amber badge counts the items that need the player's attention; it excludes advisory hints and hidden or locked Mods, which have been outside this page since 2026-10-29 (§2.4). No other entry or child displays a count. The sidebar does not show the RimArcho name or icon. The navigation toggle occupies the top row, level with the breadcrumbs; the first group heading follows it directly.

The dimensions follow the magpie sidebar. The default width is 212px, or 184px when the window is narrower than 860px. Dragging the right edge changes the width within 168–360px and saves it in `ui.gui.side`; double-clicking the edge restores the default. Horizontal padding is 10px. Group headings use muted 12px text with .04em tracking and a 14px gap from the previous group. Entries are 30px high, with 13px text and 14px icons. The icon, name, and right-side count align to the same edges on every row. The current entry has a raised-card background that slides between entries like the thumb of a view switch. A small arrow follows the name of an entry with children and points down when it is open. Children are indented 16px along a muted hairline tree guide, which does not indicate selection (§7.3). Child rows are 26px high with 12px text; the current child is bold with a soft background that also slides between children. When the player changes entries, the old children collapse while the new children expand (§7.1). Opening the Mod inventory opens its first child, All Mods (§2.9). Since 2026-10-25, Lists opens the current list; it previously opened All lists. All lists became the first child on 2026-10-26. Clicking a list child only opens that list and does not change the current list (04 §1.3), so browsing the sidebar does not change the list used for the next launch. When the current list changes, the children slide from their old positions to the new order with `motion.slideFrom` and `--t-layout`, as editor rows do. With reduced motion, the order changes immediately.

The bottom of the sidebar contains the following entries:
- **Archo** opens right panel from any page (§2.13).
- **Settings** opens settings (§2.14).
- **Background tasks** (§2.16, 2026-10-23) is a permanent row above Settings. The player requested that it remain visible on 2026-10-23; it no longer appears only when there is work. Normally, it shows an icon and its name. When tasks are running or queued, an overall-progress ring replaces the icon, the text becomes Background N, and the percentage appears on the right. Unseen failures add a red badge on the right. The row has the raised current-entry background when its page is open. Clicking it or pressing `ctrl+j` opens the page.
- **The game runtime status is outside the sidebar.** The row above Settings was removed on 2026-10-30 because the player described it as a second Can it run entry. It previously showed the running-since time, such as 14:05, and the current error count, or Analyze this log after exit. Both opened Can it run, whose entry directly above already counted those errors. Now polling through `view.LiveTracker.Update` (§2.16.1 G01) updates the current-run findings and the badge without a dialog. The running status appears in the launch block and the top-right Last game link (§2.3), and in Current run on Can it run. **New logs are read automatically:** when `view.Live.NewLog` first appears after exit, or when opening RimArcho reveals a run launched externally, the GUI reads `Player.log` once in the background through `API.ReadNewLog`. It uses the same read as Can it run, marks the log as seen, starts no analysis, and then releases memory normally. The sidebar badge and any open Can it run or Launch page refresh without a click. The TUI retains a hint at the right of the status line (§9.1).

**Navigation can be at the side or the top.** This player requirement was adopted on 2026-10-22 and replaced the expanded, compact, and hidden modes implemented that day. The toggle switches between the two positions and saves the choice in `ui.gui.nav`: `top` selects the top, and an empty value selects the side.
- **Side:** the sidebar described above has Playing and Library group headings and tree children. Its right edge can be dragged within 168–360px (`ui.gui.side`).
- **Top:** following magpie since 2026-10-22, the same entries occupy a centered, text-only row without icons in a 46px bar at the top of the window. A thin rule runs below it. There are no groups, group headings, or separators. If the current entry has children, such as the inventory's All and updates pages, plans, or packs, those children become switch buttons in the former breadcrumb position, like magpie's second row. A deeper detail or build page appends / name. Pages without children show the page name without the group name. Plan buttons retain the same context menu as the sidebar. The Settings gear is at the right. The raised selection background and the Can it run badge remain. The bar scrolls horizontally when its contents do not fit.
- The toggle is at the top of the sidebar, level with the top bar, or at the left end of the top navigation. Its shortcut is `ctrl+b` (§3.5). The top bar still has no page action buttons; the navigation bar provides navigation.
- Switching moves the navigation and page to their new positions with a view transition using `--t-enter`. Under `prefers-reduced-motion`, the change is immediate.
- The `tab` key reaches every navigation button. Within navigation, `↑↓` moves between side entries, `←→` moves between top entries, `enter` opens an entry, and `esc` leaves navigation. The `shift+1–8` shortcuts and subpage `tab` / `shift+tab` navigation continue to work.
- Magpie also switches between side and top navigation, with centered text entries at the top and subpages in the row below.
- The implementation uses `navLayout`, `toggleNav`, `navKey`, and `kidOwner` in `shell.js`. Child buttons are rendered by `renderCrumbs`; `#app` carries `nav-side` or `nav-top`.

### 2.2 Top bar, status line, hint line

The Windows controls are flat buttons with square corners, separated by hairlines. The close button uses the theme's danger color on hover; the other states use the navigation theme variables. See §2.1 for the Settings icon.

**The GUI top bar** was changed on 2026-10-22. It shows breadcrumbs, such as Library / Lists / Main colony, in 15px text with the last level bold. An adjacent chip identifies the environment, such as main 1.7; on Can it run it identifies the plan and environment. The cross-environment home page has no chip. Since 2026-10-28, Launch has no breadcrumbs (§2.3): it is a root page whose large headline supplies the title. The subpage switches in this position remain in top navigation. **No page has page action buttons in the top bar.** The sidebar toggle is at the top of the sidebar (§2.1), and launch is available only on the Launch page (§2.3, §2.5). The Windows controls occupy the right end of the topmost row: the top bar in side navigation, or the navigation bar in top navigation (§8.2). Each breadcrumb level can be clicked to return to it. There is no separate large page title. The first line below the breadcrumbs is the **page heading**. Its left side shows a muted current status or conclusion only when informative, such as the Can it run conclusion or 34 enabled in the editor; it never explains the page's purpose (§7.3). **Page actions occupy the right side** of `.page-head`, in `.page-acts`, even when there is no status text. They are quiet, borderless buttons with an icon and text; only the primary action is solid. The plan editor also has this row (§2.5).

**The implemented TUI top bar** shows the brand, an environment pill, Can it run N, and N unsaved, separated by two spaces. The position (§3.2) and `L Launch` are on the right; launch is dropped first when space is short. On secondary screens, breadcrumbs replace the left side, for example `RimArcho › Can it run` or `RimArcho › Enabled › Combat Extended`. The runtime status is at the bottom right (§9.1).

Both interfaces have the following lines at the bottom:
- **Status:** a single sentence uses a green `✓` for completion, a red `✗` for failure, or a secondary-color `…` for progress. The next key clears it. In the GUI editor and full-screen details, the position appears on the left (§3.2); other pages omit it because the breadcrumbs already identify the location. The status line no longer says which list the game currently uses (§2.5). Undoable results include an Undo link.
- **Hints:** the line shows actions currently available for the current object as `key description   key description`, with three spaces between groups, or 16px in the GUI (§7.3). It contains at most 7 items, ending with `? All keys`. Keys use the text color and descriptions use the secondary color, with no dot separators. Can it run is omitted because its count is already in the top bar or sidebar; `shift+2` opens it and the help lists the shortcut.

N unsaved means that edits have been persisted immediately (04 §1) but have not been written to the game. The count and the row's `●` identify entries that differ from the last saved list and will be written to ModsConfig.xml only on save or launch. They are informational and never block launch (08 §2).

### 2.3 Launch (formerly Home)

The TUI Launch page uses a simple column (§9.1).

The GUI page is implemented in `home.js`. A Swiss grid was introduced on 2026-10-23 in commit `04f745e`. Draft F from that design was not stored; `docs/design/home-drafts` contains only the earlier A/B/C drafts. The layout was tightened on 2026-10-28: the headline is not truncated on one line, 03 has one problem line, amber marks only the applied item, a flat floor sits below the thick rule, and duplicate text was removed. A twelve-column grid centers the large headline. Below a thick rule, three areas run from left to right: 01 Game → 02 List / pack → 03 Launch. The numbers `1`, `2`, and `3` focus their columns (§3.5 `1`–`9`, §7.3 rule 8). Since the 2026-10-23 decision, the focused number uses the accent color without a frame. The background (§2.14) extends from below the top bar to above the status line. This root page has had no breadcrumbs since 2026-10-28 (§2.2).
- **Four font sizes** have been used since 2026-10-28: 12px for column headings, counts, versions, problems, the top-right links, and small launch-block text; 17px for row names and the subtitle; 26px for the launch-block heading; and the responsive headline size described below. This is an exception to §7.3 rule 4.
- The page lists plans and packs from **all environments**. `view.AddOtherEnvs` uses `app.PlansIn` without loading the other environment. Plans are shared across games (04 §1.7), so every game lists all plans and marks its own current plan. There is no page-heading text or page action row. Rescan is in the change-history area of library subscriptions; new and import actions are on the plans page.
- **The headline** names the applied item. `view.PickFeatured` selects the current environment's current plan, or the last pack applied here if the current plan has not changed since. A trailing `[…]` Workshop tag, such as `[UPDATED 1.7]`, moves from the name to the start of the subtitle; parentheses remain in the title. **A headline is never truncated on a single line** (2026-10-28, `fitHeadline`). It uses the maximum size, `clamp(48px, 7.6vw, 124px)`, if it fits; otherwise it shrinks to 64px, then wraps to two lines and shrinks from 64px to 48px. Only if two lines at 48px still do not fit is the second line ellipsized. Hover shows the full name, and resizing recomputes the fit. There has been no eyebrow above the title since the type, environment, and changes line was removed on 2026-10-26. The subtitle contains the tag, Mod count, and play date. Supported versions and status were removed on 2026-10-26; status is now in the 02 markers and the 03 problem line. A new headline slides in from below.
- **01 Game** (`1`) lists the environments that have plans or packs on the page. The game of the applied item comes first and slides into that position when changed; the others follow by name. Each row shows the name and a short version chip, such as `1.7`, omitted if the version is already in the name, as in `1.6`. Hover shows the full version, such as `1.6.4871 rev590` (`HomeRow.GameVersion`, 02 §2.1). Full versions appeared on rows from 2026-10-24 through 10-27; the short form returned on 2026-10-28 because full versions made a one- or two-row column look like a data table. The name is on the left and may be ellipsized; the version is on the right without wrapping and is blank if unknown. Clicking a game first switches the environment, then applies the item last applied in this session, or otherwise its most recently played item.
- **02 List / pack** (`2`) lists the selected game's plans before its packs. Within each group, items follow last-played order from the launch records (08 §2), with never-played items afterward by name. The applied item slides to the first position; the column scrolls beyond 6 rows. Each row shows the name and a muted Mod count on the right. Packs say pack N; since 2026-10-28, plans show only the count, whereas every row previously named the type. **Only the applied row has problem markers:** ▲ for problems and ○ for unchecked; 03 explains the problem. Other rows put their status in the first hover line. This changed on 2026-10-28 because five rows all showing ▲ conveyed no information. Unselected rows are muted; the selected row uses bold text color and a small accent square that slides with selection. When the game changes, these rows enter in sequence.
  - **Clicking a row applies it.** The environment switches first if needed. A plan becomes current; a pack is saved in `ui.gui.home.pack` with the environment, pack name, and then-current plan. `API.HomeApply` writes no game files. Clicking the applied row again opens its editor or pack page.
  - **Switching progress appears in the launch block.** The page stays visible without a switching dialog. The 01 and 02 squares move immediately. For a game switch, the block shows Switching to X… and Loading game, please wait; for a list switch, it shows Applying X…. An indeterminate progress bar runs along the bottom edge. On completion, the headline changes and the block text enters from below. Reads happen in the background (§3.1 rule 9), and **the window remains usable**: sidebar navigation works, and other pages display their previous content before refreshing. Only launch and actions that write to this game are disabled until completion, with a switching-to-X tooltip. If another item is selected, the latest selection wins and previous results are discarded. Background sessions prepare data for switching or adding a game and return it through events carrying request sequence numbers. Scanning and the first analysis run in the background.
- **03 Launch** (`3`, which focuses the button) is the page's sole accent block, labeled launch the game (`L`), with only → at the bottom right. The environment and name were removed on 2026-10-28 because 01 and 02 already identify the target. Both plans and packs launch directly (08 §2, §5.3). An unsaved current plan adds an outlined Save N changes w button at the bottom left (2026-10-30; previously this was only a count requiring an editor visit). Clicking it or pressing `w` writes without launching, using the editor's `ui.run("save")`; hover explains that launch also saves. This is a separate button overlapping the corner, outside the launch button. It has square corners and uses the block's text color for its outline and text, like the upper-right L badge. Only this button brightens on hover, and the launch block remains the sole accent block. The save button is hidden while running, switching, or launching, or when a pack or another plan is applied; only the current plan has unsaved changes. The hint line has no room for an eighth action, so `w` appears on the button and in help. Before 2026-10-28, a separate unsaved line below the block opened the editor; now clicking the 02 row again or pressing `Enter` opens it. Pressing launch shows Launching…, then Game running N errors when the runtime status arrives. The running button is disabled and has a text-colored background; only one game runs at a time (08 §4).
  - **The applied item's problem** appears below the block as a thin rule and one line of text. For the current plan, `view.LaunchHint` and `Home.Launch` first chooses the likeliest problem: the first kind in `app.LaunchChecks` (08 §2, ordered from highest to lowest corpus observations/opportunities) that has a counted item on Can it run. It shows that item's title, with N more of the same kind when applicable. The text is amber, the rule is neutral, and overflow is ellipsized. Since 2026-10-28, the reason and corpus figures have been in the tooltip; previously the reason occupied a second muted line and the rule was amber. Clicking opens Can it run, and only items present there are chosen. If no such kind exists, the line says N problems breaks the game and still opens Can it run. Otherwise it shows remaining pack links in `Mods/` in neutral text (08 §5.3), then an unloaded external version in neutral text. With none of these, the line is absent. It never blocks launch.
  - An × on the right appears only when the problem is hovered or has keyboard focus. Dismissing it hides the line until the applied item, its game, its Mods, or the problem changes. The fingerprint includes the applied item, environment chip, Mod and unwritten counts, version, state, problem text and count, and changes since last play. The `ui.gui.home.hidden` setting preserves dismissal across restarts. The Can it run badge is unaffected.
- **The top-right area** has two links, or three when a new RimArcho version is available. Each line appears only when it has content. Since 2026-10-28, their left edge has aligned with 03 in grid columns 9–12; previously they were right-aligned in a 380px area whose left edge was off the grid. If a label and its text do not fit on one line, the text wraps below the label:
  - **Last game** shows only the result, such as Oct 21, 3 errors →. No errors opens the game log; an error result opens Can it run. While running, it says Game running N errors. Opening the page or refocusing the window rereads `Player.log` if it is newer than the last read (`app.NewLog`; a single read is cheap). The line is hidden if there has never been a game record.
  - **Current plan** describes only the current plan, for example 5 Mods updated since last play, 1 needs attention → (`view.ChangeHome`; needs attention counts rows affecting launch). Clicking opens the subscriptions change history with exactly that plan and time range. Since 2026-10-28, the line is hidden when nothing changed; it previously said No changes. If the plan has never been played, the range is since last scan. If it has never been scanned, clicking rescans. Whole-inventory changes no longer appear on home.
  - **New RimArcho version** (2026-10-31, 07 §5.1) adds a line such as RimArcho 0.9.1 available → below the other two when a newer version exists. It opens the RimArcho row in Settings › About, with install update focused. The line is hidden without a newer version and in development builds. `view.Home.Update` (`view.SelfUpdateHome`) reads a single check record.
  - Untouched content (1.1, 10 §3) will be added here later.
- **Keys:** `1`, `2`, and `3` focus the three columns. With focus in 01, `↑` and `↓` change the game; elsewhere they apply the previous or next item in the selected game. The `←` and `→` keys change the game. `Enter` opens the applied item, or launches when the launch button is focused. `L` launches; `w` saves unsaved changes to the current plan (03); `shift+1–8` changes pages. The hint line lists areas, ↑↓ lists, ←→ games, enter edit, L launch, shift+1–8 pages, and ? all keys.
- **Color and motion:** the page uses the §7 color variables and fonts and follows the light or dark theme. Problems are amber. The page has no animations when the system requests reduced motion.
- **Text over a background:** when an image is present, the page and top bar use fixed light text even in the light theme. The image has the configured dimming layer and extra shading on the left, at the bottom behind the three columns, and below the top bar. A flat `.hm-floor` was added below the thick rule on 2026-10-28. Its gradient starts 64px above the rule and reaches an 80% mask, black in the dark theme and white in the light theme. It extends to the page's sides and bottom so the three columns sit on a flat base and the image remains visible only in the headline half. It is omitted below 720px. Solid color has neither an image nor this floor and follows the theme. Below 1000px, the top-right links disappear and 03 moves to the next row; below 720px, the layout becomes one column.
- **Memory** (§10): the page uses only the cached 1920-wide JPEG at `/bg` and never loads the original. Leaving Launch removes the background layer with `setBackdrop` and `dropBackdrop` so WebView2 can release the decoded bitmap.
- The data comes from `view.BuildHome`: each plan and pack (`view.PackRows`) and the launch records (08 §2). The current plan's status uses `BreakCount`. Other plans use `view.PlanProblems`, which reads saved `view.PlanCheckOf` results and never triggers analysis; absent results say Not checked yet. **Memory hints at launch** use the RAM levels in §2.4. At the severe level, the entire launch button turns red and says Insufficient memory, launch game. Cancel has the default focus; Enter activates the focused button and Esc cancels. At the warning level, the whole button turns yellow and says Memory is tight, launch game; it launches directly. Normal and unknown levels retain the ordinary button. VRAM does not affect it. Confirmation binds to the environment and current-list snapshot; changing the environment, list, or scan version invalidates it. Packs have no corresponding loading estimate yet and retain their existing launch interaction.

### 2.4 Can it run

**The Game Mod links panel** groups links by game, with a heading showing the name, version, and path. Each row shows the folder name → target path, a short localized reason (target missing, unknown target with unconfirmed ownership, duplicate entry, or unreadable), and a final Will remove / Keep label, or the corresponding restoration action. Long paths are ellipsized in the middle, with the full path on hover. The repair confirmation reuses these groups and rows. The TUI and CLI use the same short reasons and retain full paths in the terminal. Healthy entries are omitted. The current game comes first. Other games collapse to an expandable line such as Game “1.5 test” also has 1 link needing attention; repair still handles all games together.

Each page read checks link health afresh across all known games and groups the results by game path. A single repair confirmation reuses the grouped rows and action labels, with full paths on hover; technical ownership evidence remains in the CLI inspection. By default, the repair includes only links with ownership evidence that can be repaired. A link with unproven ownership requires the explicit Include this link action before confirmation. Real directories, unknown types, and inaccessible entries have no delete action. Confirmation binds to the original server preview; a change to the path, identity, type, or target requires a new check. Repair is refused while the game runs. Broken links in the selected game block plan or pack launch; problems in other games are only summarized. See [08 §3](../08-launch-and-packs.md#3-link-deployment).

This page was formerly called Needs attention. It is implemented as a GUI page and the TUI `@` screen. The view model provides sections and evidence through `Need.Section` and `Need.Evidence`; both interfaces group the items by section and attach an evidence chip to each item. The GUI has used two columns since 2026-10-29 (draft `docs/design/canitrun-drafts/a.html`, decision 00 §6 D22).
- See §5 for focused finding views and action buttons. Providers query only existing caches when details open (03 §4.3), without adding Def file scans to page loading.
- **RAM and VRAM:** `view.MemoryNeed` and `Needs.Memory` separately compare the current list's loading RAM budget and VRAM estimate with the machine's capacity. See §2.17 for resident and loading metrics and calibration. The budget is not a promised peak upper bound and excludes saves, maps, and allocations made by Mods. RAM uses currently available physical memory (`app.RAMBudget`): below the budget's lower bound is severe (`severe` / `StatusErr`), within the interval is warning (`warning` / `StatusWarn`), and reaching the upper bound is normal (`ok`). VRAM below the estimated upper bound produces only an ordinary warning. A physical-memory shortage does not guarantee a crash; commit headroom and paging also affect the result.
  - The page shows existing data first. The GUI and TUI measure in the background, cache results by each Mod's file fingerprint, and reject stale results after a list switch. An absent estimate, unreadable hardware, or an integrated GPU without dedicated VRAM is unknown, never zero or a pass. Normal and unknown items appear in worth knowing; shortages appear in breaks the game and count as one item. Only shortage items append the exclusion of saves and Mod allocations. Re-estimate memory refreshes the result. CLI `plan cost` and MCP `estimate_memory` use the same assessment.
  - `internal/machine` reads machine information. Native probing does not block the page and is cached for 30 seconds. It reports total and currently available physical RAM and dedicated VRAM capacity. DXGI selects candidate GPUs in Windows high-performance order, or by dedicated VRAM on older systems. The display explicitly says that the game's actual GPU choice is unconfirmed. It neither sums multiple GPUs' VRAM nor treats shared memory as dedicated. Unsupported platforms and read failures show unknown.
  - The page reads only compact estimated totals from SQLite. A change to the list, game version, scan snapshot, or model invalidates them. Totals older than one hour still display and determine the level while a background re-estimate runs, so the button does not first revert to normal and then change color. The cache stores no hardware snapshot. Unscanned file changes may leave the old totals in use; an explicit re-estimate revalidates the file fingerprints.
  - See §2.3 for the launch interaction. CLI `plan cost` and MCP `estimate_memory` also report normal, warning, severe, or `unknown` when comparison is unavailable.
- The data comes from `view.BuildNeeds`. While the game runs, Current run items from `view.LiveNeeds` appear first in the errors from the last run group. `view.Do` executes the actions.
- The last run groups actual error kinds by Mod. Open game log opens that run's Player.log and locates the corresponding cluster (§2.10); see §5 for wording.
- When a run has explicit phase records (03 §6.7.3–4), its log card has muted headings for Loading game, Loading save, Starting new colony, Playing, and Main menu for nonempty groups only. A Mod with errors in two phases appears once in each, with that phase's counts and kinds. Counts whose phase cannot be recovered appear under Phase not recorded. Headings have no cursor and add no item count; individual items no longer repeat the phase words. Current run uses the same grouping and remains before the last run. Older logs without markers retain the flat list.
- The scope is the current plan, named in the GUI breadcrumbs and title. During a pack run, Current run identifies the pack, for example errors from pack X, not this plan.
