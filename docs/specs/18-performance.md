# 18 · Performance targets and baselines

> Status: current baselines for 1.0, measured on the host with real data (read-only or a data-directory copy) and with synthetic data. Checks that still need real data or a native window in the VM are in [release VM tests](../../UserGuide/release-vm-tests.md).
> Basis: 00a §3 (few resources by default); 16 §10 (resource targets); 17 §7.3–§7.4 (memory measures, analysis implementation).

This specification holds the measured values that other specifications reference (`18 §2`, `18 §3`). They state the targets; this one records what was measured, where and how. A row's date says when it was measured; a measurement without its own environment uses §1.

## 1. Measurement environment and conventions

- **Machine**: Windows 11, RTX 4090 host, SSD, Go 1.27.2.
- **Real environment** (player's machine, read-only measurements or data directory copies): RimWorld 1.7.4982 rev1280 (Steam, `D:\SteamLibrary`). 1354 Mod folders: 6 official, 74 local, 1274 Workshop (64 Workshop folders have only `About.xml.disabled`, 5 are unsubscribed residue; `Mods/` has 23 RimCrow `_Link_*` junctions). ModsConfig.xml is a 1.6.4871 list, 485 entries (482 resolvable, 3 missing). 261,448 files, 20.9 GB; 48,033 semantic files. Player.log is from 1.6, 5814 lines, 8.7 MB (2026-09-29, before the 1.7 update).
- **Research environment**: separate data directory for log corpus research, about 3500 Instances (1.6 game + downloaded research Mod library).
- **Conventions**: memory means working set (Task Manager "Memory" = private working set). Record private committed memory but do not use it as a threshold: modernc's libc reserves about 33–49 MB of private commit at startup, mostly nonresident. Unqualified times are wall-clock.
- **cgo threshold**: consider cgo SQLite (mattn/go-sqlite3) only if the TUI idle working set exceeds 65 MB (expected private commit 25–35 MB). It would need mingw-w64 for every build and lose simple cross-compilation.

## 2. Summary table

**GUI memory with 6,574 copies** (native Wails window on the host; synthetic `internal/testkit` home sized like the real library: 5,184 Lineages, 6,574 Instances, 601 enabled; 1440×880 at 150%, GPU on; process-tree private working set, Task Manager's Memory; single runs, about ±10 MB between runs; each script starts RimArcho, makes one pass over the pages, then returns to the Launch page):

- 2026-11-02: Go 52 MB at start (heap 34), 74 MB after the page pass (heap 50), 64–69 MB once page readers expire (heap 39–44): within the 80 MB target at this size. Window in front with the focus (activated from outside) and no input: the page process stays at 95 MB until 105 seconds and falls to 15 MB by 120 (idle low target, 16 §2.16.1 M08); GPU and browser processes 73 → 12 MB by 150 seconds; total 250 → 106 MB at 2.5 minutes. In the page, `api.PageInput` resolves (an unknown method fails), so input reaches the policy.
- 2026-11-01: total 180 MB at start, 289 MB after the page pass (page process 88 MB). With another window holding the focus: 162 MB after 75 seconds in the background (page, GPU and browser processes 39 MB; M08) and 137 MB once readers expire. Minimizing alone takes the page process from 78 to 44 MB. Part of the background saving is working-set trimming, which comes back as pages are used. The script could not give the window the focus again (Windows foreground lock), so the return to normal on activation is covered only by `TestMemoryTargetFollowsWindow` and minimize/restore.
- 2026-11-01: Launch page idle 3 minutes, 208 → 212 MB (Go 84 → 89); one `HomeMemory` call 3–4 ms and 0.2 MB allocated. With a 1,354-Mod synthetic home, 220–235 MB after the page pass; retained page DOM is one copy per page, about 3,750 nodes, and keeping only Can it run's drawing (`pageCache`) saves 3–4 MB. Neither `GOGC=50` nor a forced WebView2 GC changes the totals beyond run variance.

Real data and the 10-minute acceptance (16 §10) remain VM checks.

**GUI CPU at rest** (2026-11-06, native Wails window on the host, sandboxed offline host, the 6,574-copy synthetic home, 60 Hz display; process-tree CPU time over 20-second windows, as % of one core, and `document.getAnimations()`): Launch, Mod library, Can it run and Settings at rest 0.2–1.1%, no running animation. Before the fix, the plan page's problems button stayed `updating` for as long as it was measured (111 s, no work running) and its pulse cost 12.6%; the running-game dot's endless blink 5.4% (gpu-process 3.8, renderer 1.4); as `steps(2)` 2.0%; three blinks then still 0.7%; static 0.3%. After the fix (same setup, fresh copy of the home): the plan page never says `updating` in 48 s and rests at 1.9% (Go 1.0, gpu-process 0.1; the window includes the first A08 maintenance check); the Launch page 0.7%; the dot's first 20 seconds with its three blinks 1.7%, then 1.2% with gpu-process 0. Go's pprof CPU profile on Windows counts the main thread blocked in `GetMessage` as busy; use the OS counters. 144 Hz displays and the real home remain VM checks.

**Image scaling memory** (2026-11-06, Windows / Go 1.27.2, synthetic 3840×2160 picture, `runtime.MemStats.TotalAlloc`): decoding allocates 33.3 MB for a PNG and 12.5 MB for a JPEG. Scaling to 360 px used to convert the whole picture to RGBA first, another 33.5 MB; it now converts the rows under one target row at a time, 0.64 MB. A 4K picture's peak is about 34 MB as a PNG (was 67) and 13 MB as a JPEG (was 46), and at most two are decoded at once (16 §4.4). `TestScaleBoxNeedsNoFullCopy` fails above 2 MB for a 2000×2000 PNG.

**Search files** (2026-11-01, Windows / Go 1.27.2; `internal/testkit`, 1,354 installed Mods including Core, the current list contains all copies, one searchable XML file per Mod, pattern `Thing`): page information from the database **20.74 ms**, first streamed result **33.84 ms**, full run **1.982 s**, retained heap **14.03 MiB**, sampled peak heap **16.86 MiB**, cumulative allocation **69.94 MiB**. The stream keeps all 1,354 matching Mods, and opening the page includes building it from the stored inventory. The walk is sequential and resolves filesystem links within each Mod: it trades total throughput for early results and bounded retained state. Reproduce with `GOFLAGS=-buildvcs=false ARCHO_FILESEARCH_BENCH=1 go test ./internal/view -run TestFileSearch1354Measurement -count=1 -v`; it samples incremental deltas, not replayed history. Single measurements, not medians; heap is not the native process working set. Chromium tests exercise the production frontend with synthetic API replies, including a 1,354-Mod tree and 10,000-line viewer virtualization. Native WebView2 memory and real ilspycmd latency remain VM acceptance checks.

**Source library size in Settings** (2026-11-01, Windows / Ryzen 9 7950X, synthetic 300 assemblies and 6,000 generated files, `BenchmarkSourceLibrarySize -benchtime=200ms -count=3 -benchmem`, median of three): **0.021 ms / 592 B allocated** per lookup, read from stored accounting; Settings does not walk generated code. **Database maintenance** (2026-10-29, Windows / Go 1.27.2, `RIMARCHO_MAINTENANCE_BENCH=1 go test ./internal/app -run '^TestMaintenanceMedium$' -count=1 -v`): `internal/testkit.MaintenanceHistory` creates 40 versions of 15,000 files each, with longer paths to control the database size. Not representative of real path distributions, cold disks or native windows; no player database was read and no VM run made.
