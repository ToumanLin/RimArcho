# 04 · 方案与排序

> 状态：2026-10-21。方案编辑、多个方案、历史、写入规则、启动时写入、排序、规则、社区数据、锁定版本（锁定库）、列表交换、玩家数据与 RimCrow 导入、外部修改按写入者归属已实现。2026-10-23 加允许的游戏版本（§1.6）、跟着 Steam 合集（§9.6）、导出格式“工坊链接”（§9.3），已实现（CLI、MCP、GUI）。2026-10-25 方案改为所有游戏共用（§1.1、§1.7），已实现（schema v19）。
> 依据：00、00a、01、02 §5–§6、03 §4、05 §4、06 §2.5、07 §6–§7、08 §2–§7。

方案就是一份有序的启用列表。本文讲方案怎么存、怎么改、怎么回退，怎么写进游戏的 `ModsConfig.xml`，怎么自动排序，以及锁定版本、玩家数据和列表交换。启动流程在 08 §2，界面在 06 §2.5。

## 1. 方案模型

### 1.1 方案是什么

- 方案**所有游戏（环境）共用**（2026-10-25 定，§1.7）：在哪个游戏里都看得到全部方案，切换游戏不会让列表“消失”。第一个方案叫 `default`。方案名不区分大小写。
- 方案的内容：有序的条目列表。每个条目是一个 Instance，或者一个**缺失条目**（解析不到 Instance 的 packageId，原样保留，见 §4.2）。
- 方案里存的是 Instance，不是 packageId：玩家选的是“这一份”（00a §4）。
- 所有方案共用游戏默认的存档和设置，方案不提供独立存档。需要独立存档时编译成整合包（08 §5）。
- 方案的编辑**即时持久化**：每一步编辑立即写进 RimArcho 的数据库，关掉程序也不丢；每一步都可以撤销（§2.1）。“保存”是另一回事，只在启动方案（08 §2）或执行 `archo save` 时发生（§4.1）。
- 方案名在所有方案里唯一。命名列表就是方案；不再有“给某个版本起名”的做法（`loadout tag` 已删除）。
- 每个环境记住自己的一个**当前方案**（可以是任何方案）：编辑器打开的、CLI 和 MCP 命令默认作用的方案。两个游戏可以同时以同一个方案为当前方案。
- 用户规则（§6.1）和玩家数据（别名、标签、备注，§8.1）挂在 Lineage 上，所有方案共享；方案只决定启用哪些、什么顺序。

### 1.2 每个方案拥有的数据

工作区、撤销栈、版本历史、暂存都挂在方案上（schema v11）。身份确认合并 Mod 时，这些记录一起跟随保留的 ID，规则见 02 §5.4。

| 数据 | 内容 | v10 的存储 | v11 的存储 |
| --- | --- | --- | --- |
| 方案 | 名字、创建时所在的环境、创建时间、上次修改、上次启动 | 无 | 新表 `plan`（`id`、`environment_id`、`name`、`created_at`、`updated_at`）。v19 起 `environment_id` 只表示“在哪个游戏里建的”，不限制在哪里用；名字全局唯一（由程序检查） |
| 工作区 | 当前列表；它是从哪个版本来的（`origin_version`、`origin_kind`：`import`、`external`、`checkout`、`edited`、`save`）；未载入的外部版本（`conflict_version`，§4.3） | `workspace`，按环境一行 | 按方案一行 |
| 撤销栈 | `undo` 与 `redo` 两个栈，各最多 100 步，每步存编辑前的完整列表、暂存（条目、顺序、原位置和锚点）和操作名 | `workspace_undo`，按环境 | 按方案 |
| 版本历史 | `v<n>`：时间、来源（§3.1）、完整列表、游戏版本字符串、备注 | `loadout_version`，按环境编号 | 按方案编号 |
| 暂存 | 暂存的 Mod 和各自的原位置（§2.2） | `meta` 中的 `stage:<环境 ID>` | `stage:<方案 ID>` |
| 当前方案 | 每个环境一个 | 无 | 环境上记一项 |

不挂在方案上的：

| 数据 | 挂在 | 说明 |
| --- | --- | --- |
| ModsConfig.xml 写入记录 | **用户数据目录** | 上次写入的哈希、上次看到的哈希、写入者（哪个方案、哪个版本）、写入时间（§4.3）。`modsconfig_state` 按用户数据目录一行，带写入者（方案、版本号）。写入者指“文件现在装的是什么”：写入游戏时是写入的那个版本；外部修改载入或记录后，改为那个 `external` 版本（否则下一次外部修改会被误判为冲突） |
| 启动记录 | 环境 | `launch` 表记环境、时间、方式、命令行，以及方案、列表指纹和版本号三列（整合包的方案为空）；启动时填写（08 §2） |
| 用户规则 | Lineage（按环境存） | `user_rule`，§6.1 |
| 玩家数据 | Lineage | `lineage_data`、`lineage_tag`，§8.1 |

### 1.3 方案的管理

| 动作 | 规则 |
| --- | --- |
| 新建 | 可以从：空列表、复制当前方案、复制某个历史版本、导入的列表（§9.1）、一份存档的 Mod 列表（10 §4）。新方案的第一个版本来源为 `import`，备注写出处（复制得来的写“复制自 <方案> v<n>”） |
| 切换 | 只改环境的当前方案，不写游戏文件。当前方案是启动和写入游戏用的那个，CLI / MCP 的方案命令也作用于它。**打开不等于切换**（2026-10-25 定）：GUI 从侧栏、命令面板或全部列表打开一个方案，只是在这个窗口里查看和编辑它（会话里的“打开的方案”，`App.OpenPlan`），当前方案不变；在启动页选它、点“设为当前”、从它的编辑器保存或点启动游戏时，它才成为当前方案。新建的方案也只是打开。CLI 的 `--open-plan <名称>` 让一条命令作用于另一个方案而不切换（GUI 的分析、编译整合包子进程用它）。游戏里实际是哪个方案，以用户数据目录的写入记录为准，界面上标出“游戏里现在是：<方案> v<n>”（GUI：有多个方案时，那个方案的侧栏子项上的绿色小点，06 §2.5；TUI：状态栏） |
| 改名 | 只改名字，历史不变 |
| 删除 | 要玩家确认；不能删除最后一个方案。删除后该方案的工作区、撤销栈、版本和暂存一起删除；以它为当前方案的游戏改用最早的另一个方案 |

GUI 里这些动作集中在全部列表页（06 §2.17）。命令：`archo plan list`、`archo plan new <名字> [--from current|v<n>|<文件>]`、`archo plan use <名字>`、`archo plan rename <旧> <新>`、`archo plan remove <名字>`。CLI 和 MCP 的其他方案命令（`enable`、`sort`、`loadout log` 等）作用于当前方案（05 §4）。

### 1.4 首次使用与迁移

- 环境第一次被读取、还没有当前方案时（`environment.current_plan = 0`）：
  - ModsConfig.xml 还是某个方案上次写进去的样子（哈希等于写入记录）：那个方案成为这个游戏的当前方案，不新建。
  - 没有 ModsConfig.xml（例如独立存档的新游戏），而已经有方案：最近改过的方案成为当前方案，不新建。
  - 否则读取 ModsConfig.xml，建立一个新方案，v1 来源 `import`，备注 `ModsConfig.xml`（文件不存在时是空列表，备注 `no ModsConfig.xml`）。名字是 `default`；已被占用时用环境名，再占用时加编号（`1.6 2`）。首次引导里玩家也可以改选“从 RimSort、RimCrow 搬过来”或“打开整合包或 Steam 合集”（06 §2.15）。
- 迁移现有数据库（v10 → v11）：每个环境现有的工作区、撤销栈、版本和暂存成为这个环境的第一个方案 `default`；`loadout_tag` 里的每个名字成为一个新方案，列表等于那个版本，历史从一个 `import` 版本开始；然后删除 `loadout_tag`。`modsconfig_state` 按环境的用户数据目录改写，写入者记为该环境的第一个方案；几个环境共用一个目录时取最新的那次写入。名为 `default` 的标签改名为 `default (tag)`，指向不存在版本的标签丢弃。

### 1.5 Archo Monitor 默认加入

Archo Monitor 是 RimArcho 自带的游戏内辅助 Mod（03 §6.7，安装与更新见 08 §9）。**默认开着**，意思是 RimArcho 把它加进方案；加进来以后它就是普通 Mod。

- **设置**：`monitor.default`（`on` / `off`，默认 `on`）：`archo config set monitor.default off`，或设置页“游戏日志”分组（06 §2.14）。它只管自动加入，不管更新（08 §9）。
- **对哪些方案**：新建的方案（任何来源：空列表、复制当前方案、历史版本、导入的列表或存档），以及 RimArcho 第一次装好 Monitor 时环境里已有的每个方案（升级）。检查的时机见 08 §9“何时检查”，新建方案时紧接在创建之后。
- **每个方案只加一次**：处理过的方案记在 meta `monitor.added:<方案 ID>`（加了，或方案里本来就有）。之后玩家停用、移动、暂存都照常，RimArcho 不会自己加回来；只有排序会（下一条）。
- **排序也加**（2026-10-28）：设置开着、方案里没有 Monitor、已经装好时，每次排序（`archo sort`、编辑器和能不能跑里的排序）把最新版本放到 Harmony 后面，和排序是同一步撤销；玩家拿掉过也加回来，不想要就关掉设置。加不了时（方案里没有 Harmony、`Mods/` 不能建链接）排序照常完成，结果里写一句原因（`SortResult.MonitorSkipped`，GUI 的提示和 `archo sort` 都写）。测试：`TestSortAddsMonitor`。
- **加在哪**：紧跟在 Harmony（`brrainz.harmony`）后面。Monitor 的 About.xml 写 `loadAfter brrainz.harmony`、`loadBefore Ludeon.RimWorld`，所以排序（§5）也把它留在 Harmony 之后、Core 之前，能看到 Core 和所有 Mod 的加载。
- **不加、也不标记**（下次检查再看）的情况：设置是 `off`；方案里没有 Harmony（Monitor 依赖它）；`Mods/` 不能建链接（FAT、exFAT，08 §9）；没有装好的 Monitor。
- **一步可撤销的编辑**，名为 `add Archo Monitor after Harmony (default; archo config set monitor.default off)`。不是当前方案也一样：这一步记在那个方案自己的撤销栈里，`archo undo` 在那个方案里撤回它。编辑结果的说明（CLI 输出、界面提示）写出加入了哪些方案。测试：`TestMonitorInstallAndDefault`、`TestMonitorDefaultOff`。

### 1.6 允许的游戏版本

2026-10-23 定，已实现。每个方案记一组**允许的游戏版本**（主次版本，如 1.5、1.6、1.7），回答“这个列表打算在哪些版本上玩”。界面在全部列表页（06 §2.17）。

- **默认值**：方案里所有 Mod 都写了支持的版本（`supportedVersions` 的交集），加上创建方案时游戏的主次版本，取从最低到最高的连续一段。例：交集是 1.5、1.6，创建时是 1.7，默认就是 1.5–1.7。
  - 求交集时不算官方内容（Core、DLC 只写自己那一版）、缺失条目和没写 `supportedVersions` 的 Mod。
  - 交集为空时，只取创建时的版本。
  - 默认值不存储，每次读取时按当前列表算，所以启用、停用 Mod 后默认值会跟着变。
- **玩家改过**：存下玩家选的那组版本，可以不连续。之后不再跟着 Mod 变，直到玩家恢复默认。
- **存储**：`plan` 表加两列，`created_game`（创建时游戏的主次版本）和 `versions`（玩家选的版本，逗号分隔，空表示默认）。迁移时，已有方案的 `created_game` 取所在环境当时的游戏版本。
- **复制方案**时连同玩家的选择一起复制。**导入**时，RimArcho 列表带 `versions` 的就用它（§9.3），其余按默认值算，`created_game` 取当前环境的版本。
- **用在哪**：
  - 启动页和全部列表页上写方案的版本（06 §2.3、§2.17）。
  - 当前游戏不在允许的版本里时，“能不能跑”的“要你确认”里有一项：“<列表> 允许 1.5–1.6，现在的游戏是 1.7”，动作是“加入 1.7”和“去全部列表”。它不阻止启动。
  - 导出的 RimArcho 列表写 `versions`（§9.3）。
  - `version.unsupported`（03 §4.3）仍按当前游戏版本检查，不受这项影响。
- **命令**：`archo plan versions [<名字>]` 显示允许的版本和每个版本有几个 Mod 没写支持；`archo plan versions <名字> <版本…>` 设置，例如 `1.5 1.6 1.7` 或 `1.5-1.7`；`archo plan versions <名字> default` 恢复默认。设置版本不是列表编辑，不进撤销栈；界面的状态行带“撤销”，撤销就是把原来的值设回去。MCP 有同名工具。
- **提醒数量**：`PlanVersions.Missing` 及全部列表里版本选项的提示排除已忽略的版本提醒，另列 `Muted` 数量（03 §4.2）；全部忽略时写“没有版本提醒”，不声称“每个 Mod 都支持”。`Common`、默认值、允许的版本及玩家的选择仍依据实际声明，不把忽略提醒当作支持。

### 1.7 所有游戏共用方案

2026-10-25 定，已实现。玩家反馈：在 1.7 建了三个列表，切到 1.6 只剩 `default`，以为列表丢了。方案只是“启用哪些、什么顺序”，与游戏目录无关；允许的游戏版本（§1.6）已经说明一个方案打算在哪些版本上玩，所以方案不再按环境分。

- **列表页、侧栏、启动页**列出全部方案，不按游戏分组；方案上照常写允许的版本，当前游戏不在其中时由“能不能跑”提示（§1.6），不隐藏。
- **条目怎么在另一个游戏里读**：方案存的是 Instance。共用文件夹（工坊、SteamCMD、额外文件夹、锁定库、Monitor）的 Instance 是全局的，各游戏都认得。另一个游戏自己的 Instance（它的 `Data/` 里的 Core、DLC，它的 `Mods/`）在这个游戏里读成缺失条目（packageId），再按 §4.2 解析到这个游戏自己的那份（`app.localizer` + `Registry.Heal`）；这里没有的，就是缺失条目。只是读取，不改存储；在这里编辑后存下的是这个游戏的 Instance，回到原来的游戏时同样按 packageId 读回去。
- **切换游戏补链接**（02 §0 第 14 项）：当前方案里属于上一个游戏 `Mods/` 的 Mod 也照常经 `_Archo_env_<Instance ID>` 链接进目标游戏。
- **其他游戏的 `Mods/` 在任何游戏里都能用**（2026-10-25 定）：每个游戏的索引另外载入其他游戏 `Mods/` 里活着的 Mod（不含 `_Archo_*` 链接），内存里的来源类型是 `elsewhere`（`source.Elsewhere`，不存库；来源标签 `local-<环境名>`，`app.withElsewhere`）。它们出现在 Mod 库（来源值 `local-<环境名>`，位置是那个游戏的 `Mods/` 路径，02 §0 第 11 项）和编辑器的未启用列表里；启用后和 SteamCMD、额外文件夹的 Mod 一样是“部署”的：写入游戏时链接进本游戏 `Mods/`，名字是 `_Archo_env_<Instance ID>`（`DeployName`），保存或停用时不删（与切换游戏建的链接相同）。本游戏已有同一文件夹的 Instance（以前建的链接扫描成的本地 Instance）时只列本游戏那份；本游戏自己的 `Mods/` 有同包名的 Mod 时，列表里另一个游戏的那份读作本游戏的那份（`Index.Elsewhere`，02 §0 第 14 项“目标已有同包名副本时保留”）。只读 Data/ 不跨游戏。测试：`TestOtherGamesModsUsableAnywhere`。
- **写入记录**多记写入的游戏（`modsconfig_state.writer_env`）：外部修改按写入的那个游戏解析（§4.3），“游戏里现在是”在另一个共用目录的游戏写入时带那个游戏的名字。
- **删除环境**不删方案：先把各方案（工作区、版本、撤销步骤）里指向该环境自己 Instance 的条目改写成 packageId，再删 Instance（`store.keepLists`）。
- **迁移 v19**：`modsconfig_state` 加 `writer_env`，取写入者方案当时的环境；不同环境里重名的方案，最早建的保留原名，其余改为 `<名字> (<环境名>)`，仍冲突时加编号；当前方案指向不存在的方案时改指本环境最早的方案。测试：`TestPlansSharedAcrossGames`、`TestPlanStore`、迁移测试。

## 2. 编辑

### 2.1 操作

每个操作都是一条命令，GUI、TUI、CLI、MCP 共用（05 §1）。每个改变列表或暂存的操作是撤销栈里的一步；两者都没变就不记。

| 操作 | 命令 | 规则 |
| --- | --- | --- |
| 启用 | `archo enable <引用…> [--at <n>\|--before <引用>\|--after <引用>]` | 先检查可加载性（§2.3），不能启用时说明原因。已经启用的给出提示并跳过。给了位置时多个 Mod 按给出的顺序连续插入。没给位置时，列表里有同 packageId 的缺失条目就原地替换它；否则逐个按排序约束放（`order.Place`，与编辑器的建议位置 `App.SuggestAt` 同一规则，06 §3）：紧跟在它必须排在其后的最后一个已启用 Mod 之后（不早于官方内容）；只有已启用的 Mod 要求排在它后面时，放在其中第一个之前（库、前置、DLC——后启用的 Odyssey 因此直接回到官方顺序）；没有约束时放末尾；有 `attach` 目标的紧跟目标。2026-10-26 用日志语料回放定的：每份日志拿掉 DLC 和 3 个随机 Mod 再启用，这条规则让 95% 的 DLC 和 17% 的其他 Mod 回到玩家原来的位置（中位距离 31），“约束允许的最晚位置”是 15%（中位距离 35），一律放末尾是 0% / 2%，并且其他 Mod 违反了 8.3 万条强约束（这条规则 739 条） |
| 停用 | `archo disable <引用…>` | 引用可以是 `pkg:<packageId>`，用来去掉缺失条目（带不带 `_steam` 都算）。本来就没启用的给出提示 |
| 移动 | `archo move <引用> --to <n>\|--before <引用>\|--after <引用>\|--up\|--down` | 必须给出一种位置；没启用的报错并提示 `archo enable` |
| 替换实例 | `archo swap <引用> [<引用>]` | 用同一 Lineage 的另一个 Instance 替换已启用的那个，位置不变。两个引用顺序随意。只给一个时，Lineage 里只有一个别的可加载 Instance 就用它，有多个就列出来让玩家选。不同 Lineage 报错，提示 `archo lineage merge` 或先停用再启用 |
| 排序 | `archo sort [--dry-run]` | §5。`--dry-run` 只显示结果 |
| 暂存 | `archo stage add/drop/restore/list` | §2.2 |
| 撤销 / 重做 | `archo undo [<n>]`、`archo redo [<n>]` | 每个栈最多 100 步，所有界面共用同一个栈。新的编辑清空 `redo` 栈。`checkout`（§3.2）和导入替换（§9.1）也是可撤销的编辑 |
| 历史 | `archo history [--all]` | 未保存的编辑步骤和版本列表（§3.3），默认只列最新 10 个版本 |

- 同一个 RimArcho 数据目录（`%APPDATA%\RimArcho`，07 §3）可以被两个进程同时使用（例如 GUI 和 MCP）。数据库的变化键（`data_version` + `total_changes`）一变，下一次读取就看到对方的修改；在旧视图上做的编辑不会覆盖对方。测试：`TestTwoProcessesShareTheWorkspace`。
- 撤销 / 重做快照保留列表原来存储的 Instance 绑定（包括 Core、DLC 和各游戏自己的 Mod），不把当前游戏解析后的副本写进快照；还原时按原样存回，再按当前游戏解析用于显示。编辑批次遵循同一规则。
- 读取方案的结果会缓存，直到数据库或 ModsConfig.xml（大小、修改时间）变化。

**SteamCMD 批次交接**：玩家接受 credit 替换（02 §3.4）后，只在游戏未运行、且所有能加载旧副本的环境均能加载新副本时，将列表中的原 Instance 替成对应 workshop Instance，位置不变；当前内容、历史版本、撤销/重做、暂存项和位置锚点在同一事务中跟随。交接不产生会恢复旧副本的撤销步；历史引用本身不保留旧副本。任一环境不满足即整项保留、所有共享列表不切换；暂存数据损坏也整项结束并保留。固定整合包、尚未交接的游戏部署和入链仍保留原身份与副本，并注明原因。游戏中已有的投影复用 §4 的写入器与 registry 处理 `_steam`，只替换该项、摘除该项的自有部署链接，不提交其它未保存编辑，不切换玩家当前列表。备注在重映射事务内合并；DDS 台账不跨物理目录迁移，结果提示重新优化。列表编辑与交接共用启动锁，读后保存需仍持锁；晚到快照或长期编辑批次遇到交接冲突须重读，不能写回旧 ID。部署义务先落 SQLite，退出后可以续完。完整流程与回收条件以 02 §3.4 为准。

### 2.2 暂存

暂存是每个方案一个、持久保存、**从不写入游戏**的列表。两种用途：

- **准备区**：新订阅的 Mod 先放进来，想好了再启用。
- **排查区**：把一批 Mod 从“已启用”移到暂存来排查问题，排查完一键放回原位置。

规则：

- 暂存里只有**没有启用**的 Mod。暂存的 Mod 被重新启用（启用、撤销、checkout、导入都算）时，在同一事务中持久移出暂存，之后停用也不会重新出现。
- 从已启用里暂存的 Mod 记住原位置：当时的序号（从 1 开始）和它前面那个 Instance（锚点；在第一位或前面是缺失条目时锚点为空，退回用序号）。如果锚点本身是更早暂存、原来夹在中间的 Mod，锚点顺延到它，这样放回时它们按原顺序回到中间。
- 从未启用里暂存的 Mod 没有原位置（序号为 0）。
- 放回：跟在锚点后面；锚点还在暂存里就沿着锚点链继续找；都找不到时回到原序号。一次放回多个时，锚点在同一批里的先放；其余按原序号；没有原位置的放到末尾，按暂存顺序。沿锚点找的步数有上限，防止编辑后锚点成环。
- 带位置参数（`--at`、`--before`、`--after`）时只能放回一个 Mod，放到指定位置。
- 放回前检查可加载性（§2.3）。
- 暂存 add / drop / restore 各是一步可撤销的编辑；从未启用里暂存、只移出暂存也一样。每步同时记录 entries 与暂存的完整状态（条目、顺序、原位置和锚点），撤销 / 重做在同一事务中还原。其他列表编辑也记录暂存，因启用、载入版本或导入而移出的项可以随撤销恢复。批量编辑合并成的一步遵循同一规则。
- 旧撤销步骤没有暂存快照时，只恢复 entries，保留无关的暂存项，并持久清除当前或目标列表中已启用的暂存项；不推测旧位置与锚点。此后的反向步骤保存完整快照。

| 命令 | 含义 |
| --- | --- |
| `archo stage list` | 暂存的 Mod 和各自的原位置 |
| `archo stage add <引用…>` | 放入暂存；已启用的离开列表并记住位置。一步可撤销的编辑 |
| `archo stage drop <引用…>` | 移出暂存，不启用。一步可撤销的编辑 |
| `archo stage restore <引用…> \| --all [--at\|--before\|--after]` | 放回；`--all` 全部放回，引用和 `--all` 都没写时拒绝（05 §3.3）。一步可撤销的编辑 |

测试：`TestStageRestoreAllKeepsPositions`、`TestStageRestoreOneFollowsAnchor`、`TestStageRestoreAllRandomBatches`。界面上的暂存栏和按键见 06 §2.5。

### 2.3 可加载性

能进方案的 Instance 必须：活着、不是残留、不是 `unloadable`，并且游戏能看到它或 RimArcho 能把它部署给游戏：

- 位于 `Data/`、`Mods/` 或已订阅的工坊中；经别名出现在这些位置也算（例如 SteamCMD 目录经 junction 出现在 `Mods/` 下）。RimArcho 自己建的 `_Archo_` 链接不算在这里；
- 或者是**可部署**的：来源是 `steamcmd` 或 `extra`，写入游戏时用 `_Archo_` 链接放进 `Mods/`（08 §3）。

`enable`、`swap`、`stage restore` 拒绝时的说明：

| 情况 | 说明 |
| --- | --- |
| 墓碑 | 已经不在磁盘上 |
| `unloadable: about-disabled` | About.xml 被改了名，游戏读不到（处理见 08 §6） |
| 残留 | 工坊文件夹已不在订阅里，游戏会忽略 |
| 来源游戏不读，也不可部署 | 游戏不从 `src:<标签>` 读 Mod；把它链接或复制进 `Mods/` |
| 同一位置有同 packageId 的另一份 | `pkg.duplicate-installed`：按文件夹名排在前面的那份赢，这一份被游戏忽略（03 §4.3） |
| 同 packageId 的工坊版和非工坊版 | 不能同时启用（游戏只保留不带后缀的那份，§4.1 第 4 条）；提示 `archo swap <已启用的> <这一份>` |

## 3. 历史

### 3.1 版本

方案的每个版本 `v<n>` 记录：时间、来源、完整列表、游戏版本字符串、备注。编号在方案内递增。

| 来源 | 含义 |
| --- | --- |
| `import` | 方案的初始列表来自外部：首次读取 ModsConfig.xml（§1.4），或从列表文件、分享码、合集、存档、复制建立新方案（§1.3、§9.1）。备注写出处 |
| `external` | 外部修改：ModsConfig.xml 被游戏的 Mod 菜单或别的工具改过，归到上次写入它的方案（§4.3）。备注 `ModsConfig.xml changed outside RimArcho`。这也是“启动快照”：RimArcho 启动时发现的外部修改就是这种版本，不另设来源 |
| `user` | `archo save`（界面上叫“保存”）写入游戏时的列表 |
| `undo` | checkout 某个历史版本后没有再编辑，直接写入游戏。备注 `restored v<n>` |
| `launch` | 启动方案时写入游戏的列表（08 §2）。列表与该方案最新的版本相同时不新增版本，启动记录直接指向那个版本；checkout 后没再编辑就启动的，新版本的备注写 `restored v<n>` |

撤销栈里的步骤不是版本：版本是“写进游戏或从游戏读来”的列表，撤销步骤只在 RimArcho 里。

方案的**未保存修改** = 最新版本与工作区之间的差异。它只是提示，不阻止任何事：启动时会写入当前列表（08 §2）。

### 3.2 命令

| 命令 | 含义 |
| --- | --- |
| `archo loadout log [--all]` | 列出当前方案的版本：编号、时间、来源、条目数、备注；有未载入的外部版本时标出 |
| `archo loadout diff [<v>] [<v>]` | 差异，分“新增 / 移除 / 移动 / 实例替换”四类。默认对比最新版本与工作区。版本写 `v3` 或 `3`；工作区写 `workspace`、`ws` 或 `current` |
| `archo loadout checkout <v>` | 把某个版本载入工作区，是一步可撤销的编辑；不写游戏。之后直接写入游戏，版本来源为 `undo` |

载入的版本按当前游戏解析后，与工作区列表完全相同时是无操作：不改来源、冲突标记、暂存或撤销 / 重做栈，界面只写“没有变化”，不提示可撤销。

差异的算法：同一 Lineage 换了 Instance 算“实例替换”；其余共同条目求最长公共子序列，子序列以外的才算“移动”，所以挪动一个 Mod 只报一次移动，位置没变的条目不显示为移动。

### 3.3 历史区的逻辑

界面在方案编辑器的第三栏（06 §2.5）。这里定义它背后的数据和行为：

- **未保存的步骤**：撤销栈，一行一步，最新在上；光标所在即当前状态，`u` / `ctrl+r` 移动光标。选中较早的一步并确认，等于连续撤销到那一步（`StepTo`）；栈不够时停在栈底。点一个未保存的步骤立即生效，仍可 `u` / `ctrl+r` 回去。
- 每步的标题由这一步前后两份列表算出（例如“启用 Harmony · 第 2 位”），不另外存储。
- **版本**：版本列表，一行一个，标注来源。选中显示与工作区的差异，确认后 `loadout checkout`。载入版本先确认。
- 未载入的外部版本（§4.3）在这里也可以看差异、载入或忽略。

## 4. 写入游戏

### 4.1 ModsConfig.xml 写入规则

两处共用这套规则：**启动方案**（08 §2）和 **`archo save`**（写入游戏但不启动，给从 Steam 等其他途径开游戏的玩家；界面上叫“保存”）。

1. **先同步**：写入前先做一次外部修改检查（§4.3），文件里已有的外部内容先记成版本，不会被悄悄覆盖。**有未载入的外部版本时拒绝。** 要写入的方案有未载入的外部版本，或者文件里装的是另一个方案尚未载入的外部内容时，`save`、`launch`（含 `--dry-run`）拒绝，什么都不写，并给出看差异 / 载入 / 忽略三条命令（05 I8）。理由：接着写下去会覆盖一份玩家还没看过的修改。
2. **前置检查**：环境没有用户数据目录时拒绝，提示 `archo env set --user-data <目录>`；现有文件读不了时拒绝，提示先修好或移走它。写入路径要通过安全底线检查（01 §4）。
3. **同步链接**：写 ModsConfig.xml 之前同步 `_Archo_` 链接并移除整合包的 `!ArchoPack_` 链接（08 §3）。
4. **`activeMods`**：按方案顺序写小写 packageId。同一 packageId 同时有工坊版和非工坊版时，方案选的是工坊版就写 `<packageId>_steam`，选的是非工坊版就写不带后缀的 `<packageId>`。原因：游戏按“官方 → `Mods/` → 已订阅的工坊”登记 Mod，各组内按文件夹名排序；工坊副本与已登记的非工坊副本重名时，给工坊副本加 `_steam` 后缀；其他重名一律拒绝（07 §7）。两份同时启用时游戏只保留不带后缀的那份，所以方案不能同时包含这两个 Instance（§2.3）。
5. **缺失条目**原样写回。已在方案里、但现在游戏登记不到的 Instance（被删除、被停用），写成它的 packageId，避免它从游戏列表里悄悄消失；以后能解析到时自动恢复为 Instance 条目（§4.2）。
6. **`version`**：写环境当前的游戏版本，即 `Version.txt` 里的完整字符串，与游戏自己保存时一致；环境没有记录游戏版本时保留原值。游戏读取时，如果 `version` 的主次版本与当前游戏不同，会**丢弃整个列表**并重置（07 §7），所以每次写入都按当前版本写。
7. **其余内容**：只替换 `<version>` 和 `<activeMods>` 两段，`knownExpansions`、未知元素、BOM、换行风格原样保留，文本按 XML 转义。文件不存在时按游戏自己的格式新建，`knownExpansions` 写已安装的官方 DLC（活着的官方 Instance，Core 除外）。
8. **备份与原子替换**：原文件先备份到 `<用户数据目录>/Config/ModsConfig.xml.rimarcho.bak`，只留最近一份（完整历史在 RimArcho 的数据库里）；新内容写进同目录的临时文件、刷盘，再改名覆盖原文件。
9. **记录**：在方案里记一个版本（`archo save` 来源 `user` 或 `undo`，启动来源 `launch`，§3.1）；在用户数据目录的写入记录里写入哈希、写入者（方案和版本号）和时间（§4.3）；工作区的来源改为这个版本，清除未载入的外部版本标记。

预览与执行：

- `archo save --dry-run` 和界面命令面板的“预览保存”显示：与最新版本的差异、版本改写（“将从 1.6 改写为 1.7”）、缺失条目数、要建和要删的链接。预览只读，不带“继续”。
- 界面的“保存”（`w`）和 CLI 的 `archo save` 一样直接执行，状态行写“已保存（vN）”；上面第 1、2 条拒绝时写原因和命令，不弹确认（06 §6）。MCP 那边是否放行由宿主决定（05 §5）。

读到的 `version` 主次版本与游戏不同时，在状态栏和 `archo status` 中提示：“这份列表是为 X 版本保存的，游戏启动时会重置它；从 RimArcho 启动或保存一次，就会按当前版本保存。”它不阻止任何操作（启动时总会按当前版本写入，08 §2）。

### 4.2 读取时的实例解析

读 ModsConfig.xml（以及导入的列表，§9）时，每个条目按游戏的解析顺序找 Instance（07 §7）：

1. 先按完整 ID 匹配。`<pkg>_steam` 对应工坊来源的 Instance，前提是同时存在非工坊的同名副本。
2. 没有匹配时，按**文件夹名**匹配，并把条目改写为该 Mod 的 packageId。
3. 还没有匹配，而条目以 `_steam` 结尾时，去掉后缀再匹配。这种情况是本地副本已经删除，只剩工坊版。
4. 普通 packageId 有多个 Instance 时，非工坊版优先。两份来源相同（例如 `Mods/` 下有两个副本）时，游戏只接受按文件夹名排序靠前的那一份，其余报错后忽略。两种情况都给出 `pkg.duplicate-installed`（03 §4.3）。

- 同一个 Instance 在列表里出现两次时，只保留第一个位置（游戏会停用后面那个）。
- 找不到 Instance 的条目保留为**缺失条目**，显示在列表里并产生 `dep.missing` 风格的问题（03 §4.3），不静默丢弃。
- **自愈**：之后扫描到能解析它的 Instance 时，缺失条目自动变成 Instance 条目，不需要手动修复（除非那个 Instance 已经在列表里）。
- **已有可部署副本**：未绑定的 packageId 不自动选取游戏注册表以外的副本（例如另一个游戏的 `Mods/`）。`App.UseInstalled(packageIDs)` 使用 `MissingMods` 中 `CanEnable` 的副本原位绑定，一批为一步可撤销编辑；重复条目保留第一个位置。执行时重新核对缺失状态、可加载性及同包名已启用冲突；任一请求不可用则整批拒绝。绑定不创建链接，保存／启动时按 08 §3 部署。界面合同见 06 §8.7。

以上规则只有反编译依据，还没有在游戏里实测同包名的本地版与工坊版同时存在、以及 `_steam` 条目（01 §5）。

### 4.3 外部修改

ModsConfig.xml 被多个方案、多个环境共用（共用游戏默认的用户数据目录，02 §2.4）。RimArcho 按**用户数据目录**记录上次写入的哈希、上次看到的哈希和写入者（哪个环境写的、哪个方案、哪个版本；方案所有游戏共用，所以环境单独记，§1.7）。

**何时检查**：每次扫描、GUI 和 TUI 启动，以及每条读取方案的命令执行时。

**判断**：

1. 文件哈希等于上次看到的：没有变化。
2. 等于 RimArcho 上次写入的：只更新“已看到”。
3. 都不等，但解析出的列表和 `version` 与写入者记下的那个版本相同（只是格式不同，例如游戏重写了文件）：不算外部修改，只更新“已看到”。
4. 否则是**外部修改**（例如玩家在游戏内的 Mod 菜单里改了列表）。归到**上次写入它的方案**（条目按那个方案所在环境解析，§4.2）：
   - 那个方案在那次写入之后**没改过**（工作区仍等于写入的版本）：把文件内容载入为该方案的一个 `external` 版本，并载入工作区；可以撤销。提示“ModsConfig.xml 在 RimArcho 之外被修改：已载入为 <方案> v<n>”。这次修改让列表少了 Mod 时（游戏在 Mod 加载失败后会把列表重置成本体和 DLC），提示后加“；N 个 Mod 不在列表里了（v<m> 里有）”，“能不能跑”页“需要你确认”里多一张卡：列出少了的 Mod，操作“看改了什么”（`loadout diff v<m> v<n>`）、“恢复 v<m>”（一步，可撤销）、“保留这次修改”。卡在玩家回答、或工作区之后改过、检出过别的版本时消失。
   - 那个方案在那次写入之后**改过**：文件内容只记为该方案的 `external` 版本，不载入，方案标记“有未载入的外部版本”，提示冲突。玩家可以：
     - **看差异**：`archo loadout diff v<n> workspace`；
     - **载入**：`archo loadout checkout v<n>`（可撤销的编辑），标记清除；
     - **忽略**：`archo loadout ignore-external`，清除标记，版本留在历史里。（有标记时写入游戏会被拒绝，§4.1 第 1 条，所以写入不会走到“清除标记”这一步。）
   - 标记显示在 `archo status`、`archo loadout log`、状态栏和方案页。

- 没有写入记录时（新的用户数据目录、记录丢失），把外部修改归到当前环境的当前方案，按上面两种情况处理；之后这个方案就是写入者。写入者方案已被删除时同样处理。
- 第一次读取（还没有方案）走 §1.4 的导入，不算外部修改；导入不把文件记为“已看到”，所以另一个环境的方案写过、之后又被改过的文件，那次修改仍归到那个方案。

实现：`internal/app/external.go`，在每次读取方案的同步里调用。标记显示在 `archo status`、`loadout log`、“能不能跑”（带“看差异”动作）、侧栏和方案页；其他方案上的标记也列出，提示里附 `plan use <名字>` 或 `--env <名字>`。测试：`TestExternalChangeAndConflict` 和 V6–V8。

## 5. 自动排序

### 5.1 约束

| 约束 | 来源 | 强度 |
| --- | --- | --- |
| Core 在最前，DLC 按官方顺序紧随其后 | 内置 | 硬 |
| 依赖在被依赖方之前 | About.xml `modDependencies`（含 `ByVersion`） | 硬 |
| `loadBefore` / `loadAfter`（含 `ByVersion`）、`forceLoadBefore` / `forceLoadAfter` | About.xml | 硬 |
| 社区排序规则 | 社区数据（§6.3） | 硬 |
| 用户规则 | 玩家（§6.1） | 硬，且可以屏蔽上面任意一条约束 |
| 尽量保持当前相对顺序 | 当前列表 | 软 |

- 排序前，已安装且可加载的原版 Core 缺席时自动补入；`monitor.default` 开着时 Archo Monitor 缺席也补入（§1.5）；再对完整列表建图；DLC 沿用玩家的启用选择。预览不改工作区，补入与排序一起支持撤销。排序结果按名字写出补入了什么（“已排序：加入了 Archo Monitor，移动 3 个”）。
- 编辑器的“未启用”栏默认把 Core、DLC 按官方顺序置顶，其余按名称排列；“已启用”栏显示实际加载顺序。
- `ByVersion` 取当前游戏主次版本那一项（`v1.6` 这样的键）。
- **官方顺序**：Core → Royalty → Ideology → Biotech → Anomaly → Odyssey；未知的 `ludeon.rimworld.*` 排在已知 DLC 之后；其余 Mod 在全部官方内容之后。
- **豁免**：声明了 `loadBefore`（含 `ByVersion`）或 `forceLoadBefore` 某个官方包的 Mod（例如 Harmony）不受“官方内容最先”约束，与游戏和 Harmony 的设计一致；不豁免的话几乎每个列表都有环。
- **缺失条目**也是节点：它没有 About.xml 声明，但“官方最先”、别的 Mod 指向它 packageId 的声明和社区规则照常生效，所以基本保持原位。
- `incompatible` 用户规则不参与排序，只用于问题分析（03 §4.3）。
- **无法满足的约束**不进图，在 `archo sort` 的 “not used” 里列出原因（日志语料 G2）：

| 情况 | 原因 |
| --- | --- |
| 两个官方包之间的声明或社区规则，与官方顺序相反 | contradicts the official order |
| 把某个 Mod 排到 Core 或 DLC 之前的规则（About.xml 的 loadBefore / forceLoadBefore、社区规则），而它的其他约束又要求它在官方内容之后，与内置顺序成环 | would put the mod before official content … |

  没有成环的“排在 Core 之前”（Harmony 的惯例）照常满足（上面的豁免）。

### 5.2 算法

1. 建有向图。每条边记录来源：哪个 Mod 的哪条声明、哪条社区规则、哪条用户规则，以及它的可屏蔽引用（§6.2）。重复的边只算一次；被 `ignore` 规则屏蔽的边不加，计数报告。
2. 求强连通分量（Tarjan）。环里同时有内置官方边和“排在官方内容之前”的规则时，去掉后者（§5.1 无法满足的约束）再求一次。仍有环时**不屏蔽任何约束**：产出 `order.cycle`（info，03 §4.3.1；“能不能跑”淡色列出、不计数），列出环上每条边及其来源，其余部分照常排序。环内成员这样排：同一对 Mod 之间的约束取最强的一条代表这一对，按“放弃顺序”从强到弱逐对保留，会和已保留的对形成环的就放弃；再按保留的约束排环内成员，约束允许时保持当前顺序。被放弃的约束在 `archo sort` 里标 `[broken]`。（2026-10-26 改：以前环内整体保持当前顺序，当前顺序碰巧违反依赖时依赖也跟着违反；语料回放里 RimArcho 的强约束违反因此比 RimCrow 多约 5%。）
3. 每个环给出一条**建议屏蔽**的边：上一步放弃的约束里最弱的一条（都不能屏蔽时取环上最弱的一条）。**放弃顺序**从弱到强：
   1. 约束强度（§5.3，含 `observed.json` 的单条判定）：无害、弱、强；
   2. 同强度里按种类：社区规则、`loadAfter`、`loadBefore` / `force*`、依赖、内置官方顺序、用户规则；
   3. 再同等时，先放弃当前列表已经违反的那条（From 在 To 之后）。

   用户规则从不建议：处理办法是 `archo rule remove`。建议屏蔽的引用保留给 CLI；界面自动采用排序器的取舍，在“能不能跑”里不计数地说明具体放弃的要求（并进“自动排序”那一项，06 §5），不要求玩家手动屏蔽，也不弹错误。取舍只用于这次排序，不写入忽略规则。
4. 在分量之间做拓扑排序（Kahn）：多个分量同时可选时，依次比较：附着在刚输出节点后面的优先（第 5 步）；档位靠前的优先（置顶、普通、置底，§5.5）；第一个成员在当前列表里最靠前的优先。所以没有置顶、置底时结果与原列表差异最小。
5. `attach` 规则：刚输出的节点有 Mod 附着在它后面时，优先输出那个 Mod，前提是不违反硬约束。
6. 输出新顺序和差异。界面直接写进方案（一步可撤销的编辑），不写游戏。`archo sort --dry-run` 只显示。排序返回缺失必需依赖、未解析条目、推荐替代与自动解环信息；API 合同见 06 §6.1。

为什么成环不阻止：游戏本身不排序，遇到违反声明的顺序只打警告，所以成环的列表在游戏里通常能跑。例：Ferny 的 Progression 系列里，Production `loadAfter` Furniture，Better Architect 系列之间互相声明 `loadAfter` 和依赖，形成一个 3 个 Mod 的真实环；RimArcho 报告 `order.cycle`、列出各条证据和屏蔽引用，排序时放弃其中最弱的约束。`order.cycle` 不阻止写入游戏、启动和编译整合包（08 §5.2）。

### 5.3 违反声明的严重程度

日志语料的结论（数字见 07 §6）：

- **声明约束的违反很常见，而且多数无害。** 大约一半的日志违反了依赖或加载顺序声明，接近一半违反社区规则；Mod 数超过 100 时，有违反和没有违反的日志出错的比例差不多；最常被违反的约束很少涉及报错指向的 Mod；有一条（`modoptionssort` 排在 Core 之前）根本无法满足。所以 `order.violated` 最高是 warning，不是 error（03 §4.3），排序结果和问题文字要区分“会出错”和“声明了但游戏不强制”。

**约束强度**（`internal/order/strength.go`，日志语料 P1：6,734 份 1.6 的 HugsLib 日志，docs/research/decisions-corpus.md）。对每条被某些日志违反的约束，比较违反它的日志与保持它的日志（两个 Mod 都启用、列表规模同档）中，任一方被问题归因为来源（source）的比例：

| 约束 | 违反次数 | 来源比例 观察/期望 | 强度 | 严重度 |
| --- | --- | --- | --- | --- |
| Mod 需要 Core/DLC 先加载（依赖、loadAfter、forceLoadAfter 指向官方包） | 192 | 3–4.5 | 强 | 并入 `official.order` |
| 依赖（Mod 之间） | 2,903 | 1.41 | 强 | warning |
| loadBefore（Mod 之间） | 395 | 1.34 | 强 | warning |
| forceLoad*、用户规则 | 少 | — | 强 | warning |
| loadAfter（Mod 之间） | 5,430 | 1.14 | 弱 | info |
| 社区规则（Mod 之间） | 6,541 | 1.13 | 弱 | info |
| 声明排在 Core/DLC 之前 | 451 | 1.05 | 无害 | info |

- 1.3 以上为强。弱和无害的违反只出现在技术信息里，不进入“能不能跑”的计数（06 §5）；方案编辑 › 排序里的解释和顺序问题写明强 / 弱，强的在前（06 §2.5）。
- 单条规则：语料中违反次数足够、能单独判断的规则随程序发布（`internal/order/observed.json`，只有汇总计数，不含日志编号）。“无害”：违反 ≥ 30 次，违反时来源比例不高于保持时（保持的日志不足 30 份时，违反 ≥ 100 次且比例 ≤ 2%）；“有害”：违反 ≥ 20 次，比例 ≥ 20%，是保持时的两倍以上，z ≥ 3。表中有的按表，表中没有的按类型。无害的违反在说明里写出语料计数，第一条建议是 `ignore` 规则。
- `archo data update` 只拉取第三方数据集（§6.3），RimArcho 没有自己的数据仓库，所以这份表嵌在程序里，随版本更新。
- **Odyssey 排得太晚**是最常见的官方顺序违反（语料中 23% 的日志）：列表建好之后才启用的 DLC 被追加到列表末尾。`official.order`（warning）给出最省的移动——把排在 Mod 之后的官方包移回前一个官方包之后，或把排在官方内容之前的少数 Mod 移到最后一个官方包之后，取步数少的（不超过 3 步，否则建议排序）。从官方包指向 Mod 的约束不单独报告；其中强约束（Mod 需要这个 DLC）作为 `official.order` 的证据列出。自动排序也会把它放回官方顺序（03 §4.3）。
- 没有声明 `loadBefore` 官方包的 Mod 会被排到全部 DLC 之后，即使它原来排在 Core 前面（例如 RimCrow Companion）。

### 5.4 其他细节

- 社区规则只读 `<数据目录>/cache/communityRules.json`（§6.3）。
- 差异里位置没变的条目不显示为移动（§3.2）。
- 性能目标：500 个 Mod 排序 ≤ 1 秒（S5）；实测见 07 §6。

### 5.5 置顶与置底（档位）

2026-10-26 加入。来源：社区规则的 `loadTop` / `loadBottom`（`{"value": true}`），用户规则 `top` / `bottom`（§6.1），RimCrow 导入（§8.2）。同一个 Mod 两边都有时用户规则为准。

- **档位只是偏好，不是约束**：只在拓扑排序“多个分量同时可选”时比较（§5.2 第 4 步），从不违反任何约束，也不进入问题分析（不报“没排在最后”）。官方内容不受档位影响，仍按 §5.1 排在最前；置顶的 Mod 没声明 loadBefore 官方包时，排在全部 DLC 之后的最前面。
- **带上相关的 Mod**：置顶的 Mod 把它需要的（所有沿约束排在它前面的 Mod）一起带到置顶档；置底的 Mod 把需要它的（所有沿约束排在它后面的 Mod）一起带到置底档。只有这样置顶才真的靠前：否则它要等前面的依赖按原位置慢慢输出。官方顺序是硬约束，所以这种“带上”不会把 Mod 排到 DLC 前面（RimCrow 用位置权重做同样的传播，没有官方约束兜底，回放中 4.8% 的列表有 Mod 被带到 DLC 之前）。
- 一个 Mod 同时被带向两端（例如它依赖置底的 Mod，又被置顶的 Mod 需要）时留在普通档；被要求置顶/置底的 Mod 本身保持自己的档位。约束照常满足。
- 档位内部仍按当前顺序。
- 社区规则里的置顶/置底可以用 `archo rule add ignore community:<pkg>:loadtop`（或 `loadbottom`）屏蔽；用户规则用 `archo rule remove`。
- `archo sort` 在 “ends” 一节列出每个置顶/置底的 Mod、来源、屏蔽方法、带上了几个 Mod，被带向两端的标 `[also pulled to the other end]`。
- 不做 RimCrow 那样的位置权重、按名称排的平局、按 Mod 类型（语言包、贴图）猜的位置：没有语料证据，而且会让每次排序都大量移动。

## 6. 规则与社区数据

### 6.1 用户规则

挂在 Lineage 上（按环境存储，所有方案共享），所以原版和锁定版本共享，作者改了包名也不会丢。

| 规则 | 含义 |
| --- | --- |
| `after A B` | A 在 B 之后 |
| `before A B` | A 在 B 之前 |
| `incompatible A B` | A 和 B 不能同时启用（问题分析用，不参与排序） |
| `attach A B` | A 紧跟在 B 之后（语言包、补丁包） |
| `top A` / `bottom A` | A 在约束允许的范围内尽量靠前 / 靠后（§5.5；偏好，不是约束） |
| `ignore <约束引用>` | 屏蔽一条声明、社区规则或内置官方顺序 |

| 命令 | 说明 |
| --- | --- |
| `archo rule add after\|before\|incompatible\|attach <A> <B> [--note <文字>]` | 引用解析到 Lineage；两个引用在同一 Lineage 时拒绝 |
| `archo rule add top\|bottom <A> [--note <文字>]` | 只有一个引用 |
| `archo rule add ignore <约束引用> [--note <文字>]` | 约束引用照 `archo sort` 打印的写法 |
| `archo rule list` | 列出规则：`r:<n>`、种类、对象、备注、创建时间 |
| `archo rule remove <r:n>` | 删除一条 |

- 每条规则可以加备注，记录创建时间。
- 规则 ID 单调递增（`meta` 里的 `rule_seq`），删除后也不复用，所以 `r:<n>` 在备注和脚本里始终指同一条规则。

### 6.2 可屏蔽的约束引用

| 打印的写法 | 指什么 | 存储的写法 |
| --- | --- | --- |
| `decl:<#实例>:<字段>:<pkg>` | 某个 Mod 的 About.xml 声明。字段为小写的 `loadafter`、`loadbefore`、`forceloadafter`、`forceloadbefore`、`dependency` | `decl:<Lineage>:<字段>:<pkg>` |
| `official:<#实例>` | 这个 Mod 受到的内置官方顺序约束 | `official:<Lineage>` |
| `community:<pkg>:<字段>:<pkg>` | 一条社区规则，字段为 `loadafter` 或 `loadbefore` | 同左 |
| `community:<pkg>:loadtop`、`community:<pkg>:loadbottom` | 社区规则里这个 Mod 的置顶 / 置底（§5.5） | 末尾多一个 `:` |

打印时用 Lineage 的主 Instance 引用，存储时换成 Lineage，所以 Mod 换了副本、改了包名之后屏蔽仍然有效。打印出来的引用可以原样用于 `rule add ignore`（测试 `TestPrintedIgnoreRefsRoundTrip`）。

### 6.3 社区数据

| 数据集 | 文件（`<数据目录>/cache/`） | 用途 | 默认来源 |
| --- | --- | --- | --- |
| 社区排序规则 `rules` | `communityRules.json` | loadBefore/After 补充（§5.1） | `https://raw.githubusercontent.com/RimSort/Community-Rules-Database/main/communityRules.json` |
| 工坊元数据库 `steamdb` | `steamDB.json` | packageId 与工坊 ID 对照：缺失条目给出工坊链接；依赖补全（作者没写 `modDependencies` 时，待实现） | `https://raw.githubusercontent.com/RimSort/Steam-Workshop-Database/main/steamDB.json` |
| 替代规则 `replacements` | `replacements.json.gz` | “建议改用某 Mod”：`mod.replaced`（03 §4.3）；导入预览里未安装的条目也给出替代 | `https://raw.githubusercontent.com/emipa606/UseThisInstead/main/replacements.json.gz` |

- 可由 `archo data update`、设置页“立即更新”或自动检查（06 §2.16）联网更新；普通页面读取不联网。
- `archo data update [<数据集>…] [--dry-run]`：
  - 按顺序下载（不给名字时三份都更新）；`--dry-run` 只列来源。
  - 先写临时文件，校验 JSON 结构（规则要有 `rules`、steamDB 要有 `database`、替代规则要有 `rules`），记下数据集自己的版本或时间戳和条目数。
  - **全部准备好才替换**：数据、来源记录和 steamDB 紧凑索引先全部写入临时文件并检查写入 / 关闭错误。任何一份下载、校验或暂存失败，已有文件不变。替换时暂存旧文件，重命名或数据库代数写入失败就恢复整套旧文件；首次安装失败则移除部分新文件。恢复也失败时保留备份目录并在错误中给出位置。实现见 `internal/app/datareplace.go`；不承诺进程被杀或断电时的跨文件原子性。
  - 来源未变且本地文件仍在时，带上次的 ETag / Last-Modified 发 `If-None-Match` / `If-Modified-Since`，未修改就不下载。单个文件上限 512 MB，超时 10 分钟（steamDB 约 50 MB）。gzip 内容自动解压，UTF-8 BOM 去掉。
  - 每份数据旁边写 `<文件>.source.json`，与数据同批替换和回滚：数据集、来源、ETag、Last-Modified、版本、下载时间、检查时间、条目数、字节数。304 只推进检查时间，保留下载时间。旧 sidecar 没有检查时间时用下载时间。
  - steamDB 下载后压成 packageId 索引 `steamDB.index.json`（packageId → [工坊 ID, 名称]；同一 packageId 有多条时取工坊 ID 最小的；跳过 `appid` 条目），之后不再解析 50 MB 的原文件。
- `archo data status`：每份数据的来源、版本、下载及检查时间、条目数；超过 30 天标“较旧”；自动检查状态见 05 §4.2。
- 手动与自动更新共用锁，下载或校验失败不替换已有文件；成功后以数据库 `community:generation` 让其他连接的紧凑索引失效，GUI / TUI 丢弃页面分析缓存。自动失败的通知规则见 06 §2.16。
- 来源可以改：`config set data.rules.url`、`data.steamdb.url`、`data.replacements.url`；也可以是本地路径。
- 社区数据按 packageId 存储，使用时解析到 Lineage。

## 7. 锁定版本

锁定版本是**单个 Mod** 的概念：把一个 Mod 固定在某一份内容上，工坊更新不影响它。它不是新的身份概念，是同一 Lineage 下的另一个 Instance（02 §6）。玩家文案一律叫“锁定版本”；`pin` 是创建它的命令，`copy-local` 保留为别名。

### 7.1 两种形态

| 形态 | 样子 | 识别 |
| --- | --- | --- |
| RimArcho 创建 | **锁定库**里的副本目录，带 `.rimarcho/origin.json`；工坊那份不动。锁定库是设置项 `lock.dir`，默认 `%LOCALAPPDATA%\RimArcho\locked`，所有环境共用一个（02 §0），作为共用的 `extra` 类来源登记（标签 `src:locked`）：副本和它的上游一样是一条全局记录，哪个游戏的方案都能用它。0.9.0 之前按环境分的子目录 `<lock.dir>/<环境>` 迁移后是共用文件夹 `src:locked-<环境>`，文件不动，里面的副本照样是锁定版本。游戏只通过 `_Archo_` 链接看到它（08 §3） | 扫描读到 `origin.json`，按对账规则 R5 并入同一 Lineage，标“确认”（02 §5.1）。`origin_instance` 是它的上游。以前建在 `Mods/` 里、带 `origin.json` 的副本照样识别为锁定版本 |
| RimCrow 风格 | 工坊那份的 `About/About.xml` 被改名为 `About.xml.disabled`（游戏看不到），`Mods/` 里有一份本地副本（常见目录名 `_<工坊ID>_`） | 同一 Lineage 里，有一个 about-disabled 的工坊 Instance，另有一个活着、可加载、不在工坊的 Instance（RimCrow 副本、`Mods/` 里的副本、部署进 `Mods/` 的副本都算；有多个时优先已启用的）。工坊那份是上游 |

- 锁定版本给出 `mod.pinned`（info，03 §4.3），**不再**报 `mod.unloadable`。列表里显示为“已锁定”：生效的是副本，工坊那份是“上游”。
- 分类每次分析时计算，不入库。没有副本的 about-disabled 工坊目录不是锁定版本，属于“隐藏的 Mod”（08 §6）。
- 整合包里的副本也写 `origin.json`，但扫描跳过整合包的链接，不算锁定版本（08 §5）。

**为什么放在锁定库，不放进 `Mods/`。** 游戏对同一 packageId 在 `Mods/` 里只登记按文件夹名排在前面的一份（07 §7）。副本放在 `Mods/` 时，同一个 Mod 的两份锁定版本不能并存，更新锁定版本就得移走旧副本或改名 About.xml。放在锁定库里，写入游戏时只把当前方案用的那一份链接进 `Mods/`：新旧副本可以并存，每个方案各用各的，不改 About.xml，也不用玩家手动操作。代价：`Mods/` 所在的卷不支持 junction（FAT、exFAT）时，用到锁定版本的方案不能写入游戏，按 08 §3 拒绝并说明原因。

### 7.2 创建

`archo pin <实例> [--name <目录名>] [--git] [--dry-run]`（`copy-local` 是别名）。

1. 第一次使用时登记锁定库来源（检查它与数据目录、各来源根目录互不包含，01 §4）。把 Instance 复制到锁定库，默认目录名 `<原目录名>_local`；名字已被占用时加后缀（`_local2`、`_local3` …），**从不覆盖**。`--name` 必须是普通的目录名（不能含路径分隔、`.`、`..`、`<>:"|?*`）。
2. 复制细节：
   - 先复制源的真实路径（链接解析掉）。
   - Mod 目录内的链接按内容复制；指向 Mod 目录以外的链接和成环的链接跳过，在输出里列出。
   - 上游的 `.git` 和已有的 `.rimarcho/` 不复制。
   - 文件保留原修改时间。
   - 先组装在 `<目标>.archo-tmp`，完成后改名到位；失败时删除临时目录，不留残骸。
3. 写 `.rimarcho/origin.json`：

   ```json
   {"origin_instance": "<ID>", "origin_lineage": "<ID>", "workshop_id": "<ID>", "origin_snapshot": "<hash>", "copied_at": "<ISO 时间>"}
   ```

   `origin_snapshot` 是复制时源的快照哈希（十六进制），`copied_at` 是 UTC 时间。
4. 带 `--git` 时：在副本里 `git init`，`git add --all --force`（被忽略的文件也提交，基线必须是完整副本），用固定身份（`RimArcho` / `rimarcho@localhost`）、`core.autocrlf=false`、`commit.gpgsign=false`、`--no-verify` 提交一次，消息 `Baseline: copy of <名称> (#<实例 ID>)`。找不到 git 时副本照常完成，报告 git 失败。
5. 重新扫描，副本并入原 Lineage。
6. **只在当前方案里**把原 Instance 换成副本（`swap`，一步可撤销的编辑；原 Instance 没启用时不改方案）。其他方案不动：它们继续用工坊那份。启动或写入游戏时，副本通过 `_Archo_` 链接进入 `Mods/`，工坊那份写成 `<packageId>_steam`（§4.1 第 4 条）。`Mods/` 里已经有同包名的另一份（不是工坊版）时不建这条链接（08 §3：同一来源的两份游戏会报错）：那一份是普通文件夹时，提议一次确认后把它也收进锁定库（`--move-duplicates`，用它的方案照样用它，经链接进入游戏），再链接这一份；是链接或被别的工具的链接指着时不移动，拒绝并说明，改用那一份或自己移走。不改名任何 About.xml。
7. 输出副本的引用、路径、文件数、字节数、跳过的链接。

### 7.3 上游有更新

- **RimCrow 风格**：工坊 Instance 的快照与副本不同（快照 ID 和语义哈希都不同），并且工坊 ACF 的 `timeupdated` 晚于副本首次出现的时间。
- **RimArcho 创建**：上游 Instance 当前的快照哈希与 `origin.json` 的 `origin_snapshot` 不同。

此时 `mod.pinned` 升为 warning，文字为“上游有更新”，动作是“查看差异”和“更新锁定版本”：

`archo mod <实例> --diff <实例>`：列出两个 Instance 之间不同的语义文件，`+ 只在后者`、`~ 有改动`、`- 只在前者`，按路径排序。about-disabled 那份的 `About/About.xml.disabled` 当作 `About/About.xml` 比较。不写任何文件。

### 7.4 更新锁定版本

收进锁定库的原确认/CLI dry-run 同时列出每个受影响游戏、链接路径、原目标及摘除/重建去向。实体搬移前摘全游戏自有入链，更新 Instance 后回接；每实例每游戏只留一个有效入口，不能同时保留 env 和 locked 双入口。外来入链及运行中游戏拒绝，失败/恢复契约见 08 §3。

`archo pin --update <实例> [--name <目录名>] [--dry-run]`：引用可以指副本，也可以指上游。先显示差异；按 §7.2 在锁定库里复制出一份新副本（新目录名），在当前方案里换上；旧副本留在锁定库里，不删除（副本里可能有玩家自己的改动，`--git` 基线就是为此）。

**`Mods/` 里的旧副本。** 锁定库出现之前，RimArcho 把副本建在 `Mods/` 里。这样的副本（只认带 `origin.json` 的）在第一次 `pin --update` 时，或用 `archo pin <副本> --move-to-library [--dry-run]` 时，移进锁定库：同一个卷上直接改名；跨卷时先复制（含 `.git` 和 `.rimarcho/`）、逐个文件核对，再把原目录移到回收站。副本里有指向它外面的链接时拒绝。没有 `origin.json` 的目录（包括 RimCrow 的副本）从不经这条命令移动；`Mods/` 里其他备用副本由 Mod 库存的“收进锁定库”（`archo library move-to-locked`，06 §2.9）处理。两者是同一个移动：RimArcho 把 Instance 指到新位置再扫描，所以 ID 和所有方案的引用都不变（以前只在当前方案里换成新 Instance）。CLI 不带 `--dry-run` 就执行；界面先预览再确认。

### 7.5 解除锁定

`archo unpin <实例> [--dry-run]`：引用可以指副本，也可以指上游。

- **RimCrow 风格**：把工坊目录的 `About/About.xml.disabled` 改回 `About/About.xml`（`About.xml` 已存在时拒绝，不改任何文件），立即重扫；如果副本在当前方案里，换成工坊版（等于 `swap`）。副本留在原处。
- **RimArcho 创建**：如果副本在当前方案里，换回上游；副本留在锁定库里。
- 只改当前方案，其他方案不动。
- CLI 不带 `--dry-run` 就执行（与 `save` 相同）；界面先预览再确认。

把 Mod 文件夹移到回收站由 08 §6–§7 负责。

## 8. 玩家数据与 RimCrow 导入

### 8.1 玩家数据

| 数据 | 挂在 | 说明 | 命令 |
| --- | --- | --- | --- |
| 别名 | Lineage | 在所有界面里作为显示名称，`find` 和搜索也匹配它。日志归因仍然按 About.xml 的名称匹配，因为游戏打印的是 `[Name]`，不是别名 | `archo alias <引用> [<名字>] [--clear]` |
| 标签 | Lineage | 多个，不分大小写；RimCrow 的“分组”导入为标签 | `archo tag add\|remove <引用> <标签…> [--mod <引用>]…`、`archo tag list`；筛选 `list --filter tag:<标签>` |
| 备注 | Lineage | 纯文本 | `archo note <引用> [<文字>] [--clear]` |

存储：`lineage_data`（环境、Lineage、别名、备注）、`lineage_tag`（环境、Lineage、标签）。挂在 Lineage 上，所以原版和锁定版本共享，所有方案共享。

### 8.2 RimCrow 一次性导入

`archo import rimcrow --db <路径> [--rules <路径>] [--dry-run] [--include-disabled-rules] [--all]`

1. `--db` 必填：RimCrow 把数据库放在 `<安装目录>/data/mod_manager.db`，没有注册表或设置项可以找到它。`--rules` 默认是数据库旁边的 `data\rules\user_rules.json`。
2. 数据库和它的 WAL 先复制到 RimArcho 数据目录下的临时目录（`rimcrow-*`），从副本只读打开，结束后删除副本。RimCrow 的原文件从不以写方式打开。
3. RimCrow 的玩家数据按 packageId 存。每条记录先按 RimCrow 记录的资源路径（绝对路径换算成“来源 + 相对路径”）映射到 Instance，失败时再按 packageId；一个 packageId 对应多个 Lineage 时不导入，列入报告。
4. 映射：

   | RimCrow | RimArcho |
   | --- | --- |
   | 别名、备注 | 别名、备注；不覆盖 RimArcho 里已有的不同值，列为冲突 |
   | 分组、标签 | 标签 |
   | 互锁（interlock） | `attach` 规则 |
   | `user_rules.json` 的 loadAfter / loadBefore / incompatibleWith | `after` / `before` / `incompatible` 规则 |
   | `user_rules.json` 的 loadTop / loadBottom（`value` 为真） | `top` / `bottom` 规则（§5.5） |
   | sign_color、user_mod_type、ignored_issues | 没有对应，只计数 |

5. RimCrow 里**关闭了**的用户规则默认不导入，除非给 `--include-disabled-rules`：悄悄导入会改变排序结果。
6. 报告：映射了多少条（按路径、按 packageId）、成功、已存在、冲突各多少，逐条列出未映射项和冲突；RimCrow 标记停用的资源数；只有 `About.xml.disabled` 的目录按来源分别计数，并给出处理指引（改回文件名或在 RimCrow 里重新启用后 `archo scan`；或者退订、删除；RimArcho 自己的处理见 08 §6）。
7. 可以重复执行，结果相同：值相同就跳过，规则按“种类 + Lineage”去重。不需要导入日志表。
8. `--dry-run` 只出报告，不写任何东西。报告里每类明细默认列 6 条，`--all` 全部列出。

本机已执行过一次导入，结果见 07 §6。

## 9. 列表交换

### 9.1 导入的去向

任何导入的列表（文件、粘贴的文本、分享码、Rentry 链接、Steam 合集、存档的 Mod 列表）都先预览，再三选一：

- **导入为新方案**：新建一个方案，列表就是导入的列表，v1 来源 `import`，备注写出处（文件名、`share code`、`collection ws:<ID>`、`rentry <ID>`）。默认名取列表自己的名字（分享码、合集的标题），没有时取文件名。命令 `loadout import --new`（05 §4.2），MCP `manage_plans action=import`。
- **替换当前方案**：当前方案的列表整体换成导入的列表，是一步可撤销的编辑，不写游戏。
- **只加入缺少的 Mod**（合并）：把导入列表里有、当前方案里没有的 Mod 按排序约束建议的位置加进当前方案，已有的不动；一步可撤销的编辑。

三种去向都不写 ModsConfig.xml。

导入的是 Steam 合集时，预览下面多一个勾选框“以后跟着这个合集”（默认勾上）：导入后把合集关联到新的或当前的方案（§9.6）。

命令：`archo loadout import <文件|分享码> [--new [<名字>]]`，不带 `--new` 时替换当前方案。

预览内容：格式、来源、列表自己的名字、游戏版本（与环境的主次版本不同时提示“这份列表是给 RimWorld X 的，当前环境是 Y”）、总数、已安装和未安装各多少；未安装的给出工坊链接（列表自带工坊 ID，或从 steamDB 查到）和替代建议（§6.3）；“替换当前方案”会新增、移除、移动、换副本各多少。RimArcho 列表（§9.3）带着每个 Mod 的版本：已安装的条目里，本地没有那个版本的标“版本不同”，总数后面加“N 个版本不同”，已安装那一组默认展开。

解析：packageId 一律小写；带 `_steam` 的保留为令牌，按 §4.2 解析；解析不到的成为缺失条目。只有工坊 ID 的条目按已安装 Instance 的工坊 ID 换成 packageId（有多个时优先可加载的）；本地没有的不成为缺失条目（没有 packageId），在预览和结果里列出工坊链接。名称和工坊 ID 只用于缺失项的显示和工坊链接。RimArcho 列表还带语义哈希：packageId 解析到的那份内容不同、而另一份活着且可加载的 Instance 正是这个哈希时，换成那一份（同一份已在列表里时不换）。

### 9.2 导入格式

按内容识别，不看扩展名（`.rws` 除外，按存档读）。

| 格式 | 识别 | 读取 |
| --- | --- | --- |
| RimArcho 列表（`.archolist.json`） | `{` 开头，有 `entries` 数组和数字 `format` | 就是 `pack.json` 的格式（08 §5.1）：`name` 是列表名，`game`，`entries[]` 的 `package_id`、`name`、`workshop_id`、`hash`；`format` 高于本版本时拒绝。整合包目录里的 `pack.json` 也这样读 |
| 文本列表 | 其余文本 | 每行一个 packageId（形如 `作者.名字`），`#` 后是注释，标题和散文行跳过 |
| ModsConfig.xml / RimSort 导出的列表 | 根元素 `ModsConfigData` | `version`、`activeMods/li` |
| 存档 | 扩展名 `.rws`，或前 4096 字节含 `<savegame` | `<meta>` 里的 `gameVersion`、`modIds`、`modNames`；读到 `</meta>` 就停（存档有几十 MB）；名称用来标注缺失条目 |
| RimWorld 的 `.rml`（游戏内“保存 Mod 列表”，RimCrow 也写） | 根元素 `savedModList` | 优先 `modList/ids` 与 `names`，否则 `meta/modIds`、`modNames`；工坊 ID 取 `meta/modSteamIds` 中对应项 |
| RimCrow `ModList.xml` | 根元素 `ModList` | 平行的 `modIds`、`modNames`、`modSteamWorkshopIds`（`0` 表示没有） |
| RimSort JSON | 以 `{` 开头 | `version`；列表取 `activeMods`、`active_mods`、`mods`、`mod_list`、`modList` 中第一个存在的 |
| RimCrow JSON | `{"format":"rimcrow_json", …}` 或纯数组 | 优先 `modlist`（`{package_id, name, workshop_id}`），否则 `package_ids` |
| RimSort 剪贴板文本 | 每行 `名称 [packageId][链接]` | 链接里的 `?id=` 是工坊 ID |
| Rentry markdown | 行内含 `{packageid: x}` 或 `packageid: x` | packageId；`?id=数字` 取工坊 ID；最后一个 `[名称](` 取名称 |
| 工坊 ID 列表 | 每行 7 位以上数字，或含 `id=` 的 steamcommunity 链接 | 工坊 ID |
| RimCrow 分享码 | 见 §9.4 | |

- JSON 条目可以是字符串，或带 `packageId` / `package_id` / `packageid` / `id`、`name`、`workshopId` / `workshop_id` / `publishedFileId` 的对象。
- 同一 packageId 重复出现只取第一次。文件按 UTF-16 / UTF-8 BOM 识别后统一转 UTF-8；小于 16 MB 的文件整份读入。
- 读不出任何 Mod 时报错：“没有找到 Mod：可以是 RimSort、RimCrow 或 RimWorld 的列表、分享码、packageId 或工坊链接”。
- 界面里粘贴单行文本时：是存在的文件路径就按文件读；是 Rentry 链接就联网读取 `https://rentry.co/<id>/raw`（上限 4 MB；失败时提示打开页面复制列表再粘贴）；是工坊链接或 6 位以上的纯数字就按 Steam 合集读（§9.5）。只有后两种联网。
- 整合包（`.archopack`）的导入见 08 §5.4；它导出的列表就是 RimArcho 列表，在这里导入。

### 9.3 导出

`archo loadout export [--format <格式>] [--out <文件>]`，导出当前方案。不给 `--out` 时输出到标准输出；`--out` 指向已存在的文件时拒绝，不覆盖。

| 格式 | 内容 |
| --- | --- |
| `archo` | RimArcho 列表（`.archolist.json`）：`pack.json` 的格式（08 §5.1），`light` 为 true，`name` 是方案名；每个条目带 `lineage`、`instance`、`workshop_id` 和语义哈希 `hash`（Core 和 DLC 只写 `official`），缺失条目只写 `package_id`。导入的一方由此看出哪些和自己的是同一版本（§9.1）。界面的导出里排第一个，叫“RimArcho 列表” |
| `text`（默认） | 两行 `#` 注释头（环境、Mod 数、时间；导入方法），然后每行 `<packageId>  # <名称>`，缺失条目名称写 `missing` |
| `modsconfig` / `rimsort` | ModsConfig XML（`ModsConfigData`：`version`、`activeMods/li`、`knownExpansions/li`）；同包名的工坊版写 `_steam`。RimSort 的导出列表就是这个格式，`rimsort` 是别名 |
| `rml` | RimWorld 的 `savedModList`：`meta` 下 `gameVersion`、`modIds`、`modSteamIds`（没有写 `0`）、`modNames`，`modList` 下 `ids`、`names`；游戏可以直接在 Mod 菜单里载入 |
| `rimcrow` | 分享码，一行文本（§9.4） |
| `rimcrow-xml` | RimCrow 的 `ModList.xml`：`modIds`、`modNames`、`modSteamWorkshopIds`（没有写 `0`） |
| `workshop` | 工坊链接（2026-10-23 加）：一行 `#` 注释头（列表名、Mod 数、其中几个在工坊），然后每行一个 `- [<名称>](https://steamcommunity.com/sharedfiles/filedetails/?id=<工坊 ID>)`，按加载顺序；最后注释列出不在工坊的条目（Core、DLC、本地 Mod、缺失条目）。给没装的人照着订阅；导入时按“工坊 ID 列表”读（§9.2） |

`archo` 格式加一个字段 `versions`：方案允许的游戏版本（§1.6），如 `["1.5","1.6","1.7"]`。旧版本的 RimArcho 读到它时忽略。

界面上导出是列表的子页（06 §2.17），每种格式先显示内容，再保存为文件或复制；分享码只能复制。

条目写法与写入游戏时相同（§4.1 第 4、5 条）；游戏版本取环境的游戏版本，没有时取 ModsConfig.xml 里的。

### 9.4 RimCrow 分享码

- 格式：`RC-<8 位大写 CRC32>-<无填充的 url-safe base64>`。旧前缀 `RMM1-` 也接受；`share://RC/` 前缀去掉。
- base64 解出 zlib 压缩的 JSON：`[1, 列表名, 游戏版本, 条目]`。条目是 `"pkg"`、`["pkg","工坊ID"]` 或 `["pkg","工坊ID","名称"]`。
- CRC32 按压缩后的字节计算，不符时拒绝（“分享码损坏或不完整”）；第一个元素不是 1 时拒绝（不支持的版本）。
- 导出时用最高压缩级别；有名称的条目写三元组，只有工坊 ID 的写二元组，否则写字符串。列表名是方案名。

### 9.5 Steam 合集

- 接口：`POST https://api.steampowered.com/ISteamRemoteStorage/GetCollectionDetails/v1/`，表单 `collectioncount=1&publishedfileids[0]=<ID>`，不需要 API key。`children[]` 按 `sortorder` 排序（序号有空缺）；`filetype` 0 是 Mod，2 是子合集。ID 不是合集（或合集私有）时 `result` 不为 1、没有 `children`，报“这不是合集”。
- 合集和条目的标题用工坊详情接口补全，每次请求 100 个；取标题失败不影响对照。
- 合集链接或 ID：取 `?id=` 或开头 6 位以上数字。
- `archo collection <链接或ID>`：读取合集，与本地对照，分三组：已安装（列出对应 Instance，同一工坊 ID 有多个时优先可加载的）、未安装（给工坊链接）、子合集（列出，不递归）。只在执行时联网。
- `archo collection <链接或ID> --import`：按合集顺序导入已安装的 Mod，去向按 §9.1（现在是替换当前方案）。未安装的条目列出工坊链接，不成为缺失条目。
- “能不能跑”里的缺失项给“在工坊订阅”的链接；一键订阅和退订在 1.2（01 §1）。

### 9.6 跟着 Steam 合集

2026-10-23 定，已实现（检查合集在打开全部列表页时进行，超过 10 分钟才联网；后台任务里定时检查待做）。方案可以**关联**一个或多个 Steam 合集。合集变了以后，RimArcho 告诉玩家变了什么；跟不跟上由玩家决定，RimArcho 从不自己改方案。

- **数据**：新表 `plan_collection`，列有方案、工坊 ID、标题、跟上方式（`add` / `follow`）、上次检查的时间，以及**快照**（上次关联或跟上时，合集里的条目和顺序）。
- **关联**：玩家粘贴合集链接，或在导入合集时勾选“以后跟着这个合集”（§9.1）。关联时读一次合集，把当前内容记成快照，所以刚关联时没有变化。同一个合集在同一个方案里只关联一次。
- **检查**：只在打开全部列表页（每个关联的合集最多每 10 分钟一次）或执行 `archo plan sync --check` 时联网，接口同 §9.5。启动游戏不检查，也没有后台轮询。
- **变化**：现在的合集和快照比，分成新增（合集里有、快照里没有）和移除（快照里有、合集里没有）。玩家自己在方案里停用过的合集 Mod 不算变化，因为比的是快照，不是方案。
- **跟上合集**：一步可撤销的编辑，名为 `sync collection <标题>`，做完把快照更新为现在的合集。
  - `add`（默认，界面叫“只加入新增的”）：新增的 Mod 里已经装了的，按排序约束建议的位置加进方案，同“只加入缺少的”（§9.1）。合集移除的 Mod 留在方案里。
  - `follow`（界面叫“也停用移除的”）：另外停用合集移除、而且还在方案里的 Mod。只是停用，不退订、不删文件。
  - 新增但没装的，列出工坊链接，不成为缺失条目（同 §9.5）。
- **没装几个**：合集里本地没有任何一份的条目数，带“在工坊订阅”的链接。
- **取消关联**：删掉这条关联和它的快照，方案不变。删除方案时，它的关联一起删除。
- **命令**：`archo plan follow <名字> <合集链接或 ID> [--mode add|follow]`、`archo plan unfollow <名字> <合集>`、`archo plan sync <名字> [<合集>] [--check|--dry-run]`。`--check` 只检查、列出变化；`--dry-run` 显示跟上后会启用、停用哪些。MCP 有同名工具，`sync`（不带 `--check`、`--dry-run`）标为会改动方案。
