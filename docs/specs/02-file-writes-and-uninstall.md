# 02 · File writes and uninstall

> Status: implemented (`internal/app/uninstall.go`, `internal/app/trash.go`).
> Basis: 00 §4 (principle 4: respect your files), 09 §3 (link deployment), 17 §3 (data locations).

This specification is RimArcho's safety boundary: every file RimArcho writes (§1), how uninstall reverses each write (§2), and the recycle bin, through which all removal of the player's content goes (§3).

## 1. File write list (safety boundary)

RimArcho writes only to the locations below and touches nothing else. Every action that writes to disk has a preview (CLI `--dry-run`, an interface preview), needs the player's confirmation (interface) or explicit execution (CLI without `--dry-run`), and is reversible or says why it cannot be reversed.

Automatic checks (16 §2.16) are the one exception to per-action confirmation: when their master switch is on, they may write check records (including RimArcho version checks), metadata of existing subscriptions, renewed encrypted sessions of enabled accounts, and community data caches. They never install Mods, update external tools or RimArcho, or change game configuration.

Moving or removing a physical Mod directory first detaches RimArcho's links into it in every known game. It is refused when an affected game is running, a foreign inbound link would break, or a link's state is unknown; the confirmation preview lists the affected links. Link inspection is read-only, link repair runs only after confirmation (CLI `links repair --yes`), and startup never changes the disk on its own, except to finish the previously confirmed release relocation or update cleanup listed below. Scanning, opening the problems page, launch checks and test runs never authorize deletion. The shared link lifecycle, recovery after an interruption and repair rules are in [09 §3](09-launch.md#3-link-deployment).

Maintainer-only release writes: `archo workshop publish` assembles local staging folders and saves a newly created Workshop item ID in the repository (17 §5.1); it does not modify an installed Workshop Mod. These build artifacts and source metadata are outside player uninstall scope.

Never do the following:
- Never change existing files in Workshop items. Only three changes may happen in Workshop directories, each after the player confirms: restoring `About.xml.disabled` to `About.xml`, recycling a whole item folder, and creating `.dds` beside PNG files during texture optimization (Steam updates or verification may delete these; RimArcho notices this from its records and offers to regenerate them).
- Never write marker files into Workshop directories (Steam verification or updates would delete them). Texture optimization records the files it writes in the database, not in Mod folders.
- Never follow links out of a Mod directory for writes; prevent path traversal.
- Network access is limited to actions the player starts and, when their master switch is on, automatic checks (16 §2.16): community data updates (08 §2), Workshop descriptions and images (can be turned off in settings, 16 §4.3), reading Steam collections (07 §7), subscribing to Git repositories, reading the Mod metadata of download pages and checking for and pulling updates, logging in to LoversLab and validating its session after the player opts in, and downloading selected site files (11 §1), SteamCMD Workshop downloads without a Steam client (11 §1), subscribing and unsubscribing through the Steam client (11 §2), resumable credit replacement subscriptions after the player accepts (11 §1), downloading SteamCMD and using it to read branches and download game versions (11 §3), checking external tools' versions and downloading them (17 §2.1), checking for new RimArcho versions and downloading one after confirmation (GitHub Releases, 17 §5.1), sending a feedback report through the feedback relay (16 §2.14), and model calls (with consent, 15 §3).
- Never ask for, receive, save or pass on passwords, verification codes, Steam Guard codes, recovery codes or TOTP secrets for any service. SteamCMD interacts only in its own console; LoversLab only in an isolated window of the original site. Session cookies are used only in the secret storage and restricted HTTP client of 11 §4, never in ordinary data or by agents.

## 2. Uninstall

Implemented in `internal/app/uninstall.go`. Uninstall reverses each row of §1's table as its last column says: the column names the step (`accounts`, `links`, `modsconfig`, `textures`, `locked`, `monitor`, `packs`, `saves`, `games`, `steamcmd`, `source`, `data`, `program`), or says after "None:" why no step applies. `TestUninstallCoversWriteList` checks that every row has this column, that every step it names exists, and that every step appears in §1.

The first step, "forget account sessions" (`accounts`), deactivates in-memory sessions, deletes the encrypted cookies, temporary login profiles and download leftovers, and clears the known authentication caches of the managed SteamCMD. It is independent of tool deletion and still runs when Mods are kept; it leaves system browsers and external SteamCMD caches untouched. When cleanup fails, uninstall stops without deleting tools or data and without claiming everything was forgotten; the player can close login windows and retry. Local forgetting cannot be undone and does not sign out other devices.

The link ledger stays with the data until the uninstall steps finish. Owned links are detached across all known games before the lock library, packs and subscriptions are handled. Foreign links, unknown types and real directories are left untouched; uninstall refuses a plan whose later deletions would break foreign inbound links.

- **Entry points**: GUI Settings › uninstall RimArcho (16 §2.14); the TUI command panel's "uninstall RimArcho"; CLI `archo uninstall` (without `--yes` it only shows the plan, 13 §4.2). MCP has only the read-only `preview_uninstall`. **No AI uninstall tool**: uninstall removes the program the player installed and all its records (plans, history, notes), and one tool call should not make RimArcho disappear from the player's computer. AI may explain what will happen; only the player can run it.
- **Preview the plan first**: folders, sizes and destinations per step, with the choices in the corresponding rows (GUI checkboxes and folder pickers, not a series of dialogs). Defaults: recycle lock library copies, keep packs, move own saves out, keep downloaded games, and keep the current ModsConfig.xml list while removing RimArcho's entries.
- **Preview sizes**: the GUI marks estimates with `≈` and reuses byte counts for the same path for at most 60 seconds; changing an option still rechecks paths, processes and ownership and never reuses deletion eligibility. The full plan is regenerated before uninstalling, without the preview's size cache or recursive directory size counting; the execution report omits directory sizes.
- **One confirmation**: GUI and TUI confirmation and summary are in 16 §2.14; the CLI uses `--yes`.
- **Refuse** when a game is running; when another RimArcho from the same program folder (window, `archo mcp`, scan subprocess) has the database open; or when choices conflict (kept copies go into a game that is to be deleted, or kept saves or packs go into a folder that is to be deleted). Refusing changes nothing.
- **Order**: accounts → links → ModsConfig.xml → texture optimization DDS → lock library → Monitor → packs → own saves → downloaded games → SteamCMD → source library → data → program. If one item fails (for example, no recycle bin, §3), the others continue but the final two steps are skipped: the data and database stay, so uninstall can be retried after fixing the problem.
- **The final two steps run after RimArcho closes**: Windows cannot delete a running program or an open database, so uninstall writes a cmd script to a temporary folder and starts it detached. The script waits for this process to exit (up to 5 minutes), deletes the data directory and the managed root resolved by `app.LocalDir()` (17 §3), then deletes the release zip files in the program folder (§1's release row, plus `fonts/` if present) and the update leftovers in `.archo-update/` (17 §5.1); it deletes the program folder only if it is then empty, logs failures to `%TEMP%\RimArcho-uninstall.log`, and finally deletes itself. The script calls the System32 `tasklist`, `find` and `ping` by full path (with Git's `usr/bin` in PATH, `find` would otherwise resolve to GNU find). `rd /s` does not enter links. Development builds (`go run`, `guidev`) do not delete the program. Other systems delete directly in-process.
- **No installer**: releases are zip files (17 §5), and uninstall deletes the files itself. If an installer is added, the `program` step will run its uninstaller.
- **Never touch**: the Mods themselves (Workshop, SteamCMD sources, other folders, the player's own folders in `Mods/`; DDS written by texture optimization are the exception, removed by `textures`), Workshop subscriptions, saves in the game's default user data directory, and Mods restored to the game by `unhide`.
- After uninstalling, this process rejects every command ("RimArcho was uninstalled; close it"); the GUI shows only the report and "close RimArcho"; the TUI exits on Enter.

## 3. Recycle bin

RimArcho never permanently deletes the player's content. It always moves it to the system recycle bin, and refuses when the recycle bin is unavailable.

Before a target is recycled, RimArcho's links into it are detached (09 §3). Removing a link deletes only the link itself; it creates no recycle bin entry and does not widen this section's allowlist.

**Allowlist.** Accept only these four categories; reject every other path:

| Category | Conditions | Callers |
| --- | --- | --- |
| Mod folder | An Instance's real directory inside, but not equal to, its source root: a hidden or unsubscribed Workshop or SteamCMD copy (Steam downloads subscribed ones again), or the player's own copy in `Mods/` or the lock library (refused when the copy itself is a link). Enabled Mods and Mods used by plans only warn | `trash` (09 §5), Mod library "delete" (16 §2.9), 1.2 unsubscribe |
| Pack directory | `<pack name>/` in the pack directory | `pack remove` (10 §4) |
| Save file | A save in the environment's user data `Saves/` or a pack's `userdata/Saves/` (product rules in 12 §4) | Save management (`app.TrashSaves`, 12 §4.4) |
| Player content during uninstall | Lock library copies (selected by default), packs, own save directories, `<data directory>/backups/saves/` and games downloaded with SteamCMD, only when the player chooses deletion. RimArcho's own folders (data, Monitor and the downloaded SteamCMD) are deleted directly rather than recycled | Uninstall (§2) |

The single entry point `App.ToTrash` (`internal/app/trash.go`) enforces the path allowlist whoever the caller is; caller-specific rules for enabled Mods, plan use and subscription are checked before it. The path allowlist (links are resolved first, but a path that is itself a link is rejected):
- A path inside, but not equal to, any source root (Workshop, SteamCMD, `Mods/`, the lock library or another Mod folder, in any environment), or inside any `<game directory>/Mods/`.
- A direct child `<pack name>/` of the pack directory; not the root itself and not folders inside packs.
- A path inside any environment's user data `Saves/` (the game's default user data folder when the environment names none), a pack's `userdata/Saves/`, an own save directory `<data directory>/userdata/<environment name>`, or the save backups `<data directory>/backups/saves` and below.
- An environment's game directory itself, only if it was downloaded with SteamCMD (`steamapps/appmanifest_294100.acf` exists).

Other paths are refused (`ErrNotInTrashList`, `TestTrashAllowList`).

**Platforms:**

- **Windows** uses `SHFileOperationW` with `FO_DELETE` and the flags `FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT | FOF_NOERRORUI | FOF_WANTNUKEWARNING`. The last flag makes a volume without a recycle bin, such as a network drive, return an error instead of deleting permanently. A nonzero return value or a cancelled operation is reported as an error with the shell code.
- **macOS** renames the item into `~/.Trash`, adding `.2`, `.3` on name collisions.
- **Other systems** follow freedesktop: on the data directory's volume use `$XDG_DATA_HOME/Trash` (default `~/.local/share/Trash`); on other volumes use `<mount>/.Trash-<uid>`. The volume trash and its `files/` and `info/` directories must be owned by the current user, have mode 0700 and be real directories, not links. Move the item into `files/` and write `info/<name>.trashinfo` with URL-escaped `Path` and local `DeletionDate`; `Path` is absolute for the home trash and relative to the mount for volume trash. Reserve metadata exclusively and finish writing it before moving the item; existing files or metadata get `.2`, `.3` suffixes. An unavailable or unsafe trash, metadata failure or failed rename leaves the original in place; remove this attempt's metadata when the move fails.
- Trash never falls back to copying and permanently deleting. macOS still refuses a rename across volumes.
