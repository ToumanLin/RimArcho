## 1. UTF-16 About.xml

- 读取 About.xml、LoadFolders.xml 和 Defs/Patches 时，按 BOM 识别 UTF-16 LE/BE 和 UTF-8 BOM，统一转成 UTF-8 再解析。没有 BOM 但 XML 声明写 `encoding="utf-16"` 时也按 UTF-16 读。
- 夹具测试：UTF-16 LE 带 BOM、UTF-16 BE 带 BOM、UTF-8 BOM、声明 utf-16 但实际 UTF-8（按实际内容读）。

## 2. 隐藏与固定（09 §7）

### 2.1 分类

扫描已经把只有 `About/About.xml.disabled` 的目录建成 `unloadable: about-disabled` 的 Instance（02 §4.1）。分析时再按下面的规则分类，结果不入库，每次分析时计算：

| 类别 | 条件 | 发现 |
| --- | --- | --- |
| 固定副本 | 同一 Lineage 里有另一个活着、可加载、不在工坊的 Instance（RimCrow 的 `_<工坊ID>_` 副本、copy-local 副本、部署进 `Mods/` 的副本都算） | `mod.pinned`，info |
| 退订残留 | 工坊来源，且不在 ACF 的已订阅列表里 | `mod.hidden-residue`，warning |
| 单独隐藏 | 其余 | `mod.hidden`，warning |

- 固定副本**不再**报 `mod.unloadable`。它在列表里显示为“已固定”：生效的是副本，工坊那份是“上游”。
- **上游有更新**：工坊 Instance 的语义哈希与副本不同，且工坊的 ACF `timeupdated` 晚于副本首次出现的时间。此时 `mod.pinned` 升为 warning，文字为“上游有更新”，动作是“查看差异”。差异用现有的文件级对比（`view.FileDiff` 的两份快照版本）。
- 更新固定副本属于整合包的范围（§8），1.0 只提示和显示差异。

### 2.2 动作

| 类别 | 动作 | 命令 | 写什么 |
| --- | --- | --- | --- |
| 固定副本 | 查看差异 | `archo mod <实例> --diff <实例>` | 不写 |
| 固定副本 | 取消固定 | `archo unpin <实例> [--dry-run]` | 把工坊目录的 `About.xml.disabled` 改回 `About.xml`；工作区里把副本换成工坊版（等于 `swap`），副本留在原处 |
| 退订残留 | 删除 | `archo trash <实例> [--dry-run]` | 整个文件夹移进回收站 |
| 单独隐藏 | 保持隐藏 | `archo problems ignore <p:ref>` | 只写 RimArcho 的数据库（现有忽略机制，Mod 变化后自动失效） |
| 单独隐藏 | 恢复 | `archo unhide <实例> [--dry-run]` | 把 `About.xml.disabled` 改回 `About.xml` |
| 单独隐藏 | 删除 | `archo trash <实例> [--dry-run]` | 整个文件夹移进回收站 |

- 所有动作都要确认：CLI 不带 `--dry-run` 就执行（与 `save` 相同，D6）；TUI 和 GUI 先显示预览再确认。
- 改名前检查：`About.xml` 已存在则拒绝；改名后立即重扫该目录。
- 需要处理（08 §8）新增分组“隐藏的 Mod”，按上表给动作。

### 2.3 安全底线修订（01 §5.3）

在 09 §3.1 的修订之外新增：“玩家确认后，RimArcho 可以把 `About.xml.disabled` 改回 `About.xml`（撤销其他管理器的隐藏），也可以把未订阅或被隐藏的工坊文件夹整体移进回收站。”除此之外仍不修改工坊条目里的文件。

### 2.4 回收站

- Windows：`SHFileOperationW`，`FO_DELETE | FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT | FOF_NOERRORUI`。回收站不可用（例如网络盘）时拒绝，不做永久删除。
- 其他系统：移到 `~/.local/share/Trash`（freedesktop 规范）；macOS 移到 `~/.Trash`。不支持时拒绝。
- 只删除 Instance 的真实目录，且必须在工坊或 SteamCMD 来源之内；链接只删链接。

## 3. 游戏日志实时追踪（09 §4）

### 3.1 游戏运行检测

- 由 RimArcho 启动时记下进程号（Steam 方式启动时按可执行文件名在 30 秒内找到进程）。
- 其他方式启动时，每 3 秒检查一次进程表（Windows：`CreateToolhelp32Snapshot`），可执行文件路径在当前环境的游戏目录下即为本环境的游戏。
- 状态：`stopped`、`running`（带开始时间和进程号）。`archo status` 显示“游戏运行中，已运行 12 分钟”。

### 3.2 实时读取

- `app.LogFollower`：记住 Player.log 的路径、文件标识（大小缩小或创建时间变化视为新文件）和已读字节偏移。每秒检查一次，只读新增的字节。
- 新内容按行切分，最后一行没有换行时留到下次。完整的条目交给现有解析器（`logs.Parse` 的增量版本：解析器状态跨批次保留，条目在下一个非续行出现或游戏退出时结束）。
- 内存上限：只保留聚类，不保留原文。每个聚类保留前 3 个样本条目和计数；聚类数超过 2000 时丢弃最旧的 info 级聚类。
- 每批新聚类用现有归因（03 §6）处理，结果进入“需要处理”的“本次运行”组，按首次出现时间排序。
- 游戏退出后停止追踪，做一次完整分析（现有 `archo log`），结果替换“本次运行”组。

### 3.3 RimCrow 辅助模组的日志

- 位置：用户数据目录下的 `RimCrow_Realtime.log`（以及旧名 `RMM_Realtime*.log`，只读，不改名）。
- 每行一条 JSON，读取 `timestamp`、`level`、`message`、`context`。只用来补时间戳和级别；`context.relatedModIds` 非空时作为“被提及”证据加入归因，不覆盖 RimArcho 的结论。
- 无效行跳过并计数。

### 3.4 接口

- CLI：`archo log --follow`：持续输出新聚类，直到游戏退出或 Ctrl+C；`--json` 每个聚类一行。
- MCP：`get_log` 增加 `since`（上次返回的游标），agent 可以轮询。
- TUI/GUI：游戏运行时顶栏显示“游戏运行中”和本次运行的错误数；新错误到来时需要处理的计数更新，不弹窗。

### 3.5 验收

| # | 场景 | 期望 |
| --- | --- | --- |
| L1 | 向夹具 Player.log 追加一个异常 | 1 秒内出现 1 个新聚类，归因与完整分析一致 |
| L2 | 一个条目分两次写入（续行在第二批） | 合成一个条目 |
| L3 | 文件被截断并重写（游戏重启） | 偏移归零，旧聚类清空 |
| L4 | 追加 50 万行同一错误 | 1 个聚类，计数 50 万，常驻内存增长 < 20 MB |
| L5 | RimCrow_Realtime.log 有 JSON 与坏行 | 时间戳补上，坏行计数 |

## 4. 列表交换（09 §3.2）

现有：文本列表（每行一个 packageId）、ModsConfig.xml、存档（`.rws` 的 `<meta>`）。导入按内容识别格式，不看扩展名。

### 4.1 RimSort

- **导出列表**就是 ModsConfig XML（`ModsConfigData`：`version`、`activeMods/li`、`knownExpansions/li`），同包名的工坊版写作 `_steam`。现有 `--format modsconfig` 已兼容；`--format rimsort` 作为别名。
- **导入**新增：
  - RimSort JSON：以 `{` 开头，含 `version` 和 `activeMods`。
  - 剪贴板文本：每行 `名称 [packageId][链接]`。
  - Rentry markdown：按 `{packageid: x}` 或 `packageid: x` 取 packageId，按 `?id=数字` 取工坊 ID。

### 4.2 RimCrow 与 RimWorld 自己的列表

- **导入**新增：
  - `.rml`（RimWorld 游戏内“保存 Mod 列表”的格式，RimCrow 也写）：`savedModList` 下优先读 `modList/ids` 与 `names`，否则读 `meta/modIds`、`modSteamIds`、`modNames`。
  - RimCrow `ModList.xml`：`<ModList>` 下平行的 `modIds`、`modNames`、`modSteamWorkshopIds`（`0` 表示没有）。
  - RimCrow JSON：`{"format":"rimcrow_json", "package_ids":[...], "modlist":[{package_id, name, workshop_id}]}`，或纯数组。
  - RimCrow 分享码：`RC-<8 位大写 CRC32>-<无填充 url-safe base64>`（旧前缀 `RMM1-` 也接受，`share://RC/` 前缀去掉）。base64 解出 zlib 压缩的 JSON `[1, 列表名, 游戏版本, 条目]`，条目是 `"pkg"`、`["pkg","工坊ID"]` 或 `["pkg","工坊ID","名称"]`；CRC 按压缩后的字节计算，不符则拒绝。
  - 工坊 ID 列表：每行 7 位以上数字或含 `id=` 的链接。
- **导出**新增：`--format rml`（游戏可以直接在 Mod 菜单里载入）、`--format rimcrow`（分享码，输出一行文本）。
- packageId 一律小写；带 `_steam` 的保留为令牌，按 04 §2.4 解析。名称和工坊 ID 只用于缺失项的显示和工坊链接。

### 4.3 Steam 合集

- 接口：`POST https://api.steampowered.com/ISteamRemoteStorage/GetCollectionDetails/v1/`，表单 `collectioncount=1&publishedfileids[0]=<ID>`，不需要 API key。`children[]` 按 `sortorder` 排序（序号有空缺）；`filetype` 0 是 Mod，2 是子合集。ID 不是合集时该项 `result` 不为 1、没有 `children`，报“这不是合集”。条目的名称用现有的工坊详情缓存补全。
- `archo collection <链接或ID>`：读取合集条目，与本地对照，分三组：已安装（列出对应 Instance）、未安装（给工坊链接）、合集里的子合集（列出，不递归）。只在执行时访问网络。
- `archo collection <链接或ID> --import`：按合集顺序导入为工作区（等同 `loadout import`，未安装的条目成为缺失项）。
- 需要处理里的“缺失项”给“在工坊订阅”的链接（订阅本身在 1.2）。

### 4.4 验收

| # | 场景 | 期望 |
| --- | --- | --- |
| X1 | RimSort 导出的 XML、RimSort JSON、剪贴板文本分别导入 | 与原列表顺序一致，缺失项保留 |
| X2 | RimArcho 导出为 RimSort 格式，再导入 | 往返一致 |
| X3 | `.rml`、ModList.xml、分享码导入；导出 rml 与分享码再导入 | 往返一致；分享码 CRC 错一位时拒绝 |

## 5. 社区数据通道（04 §5.2）

- `archo data update [--dry-run]`：下载三份数据到 `<数据目录>/cache/`，先写临时文件，校验 JSON 能解析再原子替换；失败时保留旧文件。
- `archo data status`：每份数据的来源、版本（提交号或 ETag）、下载时间、条目数。
- 来源可配置：`config set data.rules.url`、`data.steamdb.url`、`data.replacements.url`；也可以是本地路径。默认值在实现时核实后写进代码和本节。
- 只在玩家执行时访问网络（04 §5.2）。`status` 在数据超过 30 天时提示“社区数据较旧”。
- steamDB 用于：packageId 与工坊 ID 对照（缺失项给出工坊链接）、依赖补全（作者没写 modDependencies 时）。replacements 用于需要处理里的“建议改用”。

| # | 场景 | 期望 |
| --- | --- | --- |
| D1 | 本地 HTTP 夹具提供三份数据 | 下载、解析、`data status` 显示条目数 |
| D2 | 第二份是坏 JSON | 整体失败，旧文件不变 |
| D3 | replacements 里有已启用的 Mod | 需要处理出现“建议改用 X” |

## 6. 历史区与启动快照（08 §14）

- 版本表新增来源类型 `snapshot`。
- **启动快照**：RimArcho 启动（CLI 的任何会读工作区的命令、TUI、GUI）时读取 ModsConfig.xml；如果与最新版本不同，并且不是 RimArcho 自己写的，就记为 `snapshot` 版本。现有的“外部修改”流程（04 §2.3）已经记录 `external` 版本，这里合并为一套：外部修改即快照，不重复记录。第一次使用时的导入版本就是首个快照。
- **历史区**（TUI 第 3 列、GUI 第 3 区）：
  - 暂存为空时自动折叠为标题行，`z` 或点击标题切换。
  - “未保存”段：撤销栈，一行一步，最新在上；光标所在即当前状态。`u` / `ctrl+r` 移动光标；选中较早的一步并确认，等于连续撤销到那一步。
  - “已保存”段：版本列表（保存、外部修改、撤销、启动快照），一行一个，标注来源。选中显示与工作区的差异，确认后 `loadout checkout`。
- 撤销栈每一步需要可读的标题：`workspace_undo` 增加 `label` 列（“启用 Harmony · 第 2 位”），旧记录显示为操作名。

| # | 场景 | 期望 |
| --- | --- | --- |
| V1 | 外部修改 ModsConfig.xml 后启动 | 多一个快照版本；未修改时不新增 |
| V2 | 三步编辑后在历史区选第一步 | 工作区回到第一步之后的状态，可 `ctrl+r` 前进 |
| V3 | 历史区选 v1 | 显示差异，确认后工作区等于 v1 |

## 8. 整合包 v1（09 §2）

### 8.1 数据

- 存放：`<pack.dir>`（默认 `<数据目录>/packs`）`/<包名>/`，内含 `pack.json` 和 `mods/<目录名>/`。
- `pack.json`：格式版本、包名、创建时间、游戏版本、来源环境、条目列表（顺序、packageId、lineage、实例 ID、工坊 ID、语义哈希、目录名、是否随包携带文件）、清洗记录。
- 轻包：只有 `pack.json`，扩展名 `.archopack.json`。完整包：目录打成 zip，扩展名 `.archopack`。

### 8.2 编译 `archo pack build <包名> [--light] [--dry-run]`

1. 需要处理里列表、依赖分组的 error 必须清零，否则拒绝并列出。
2. 排序（等于 `archo sort`，结果只用于包，不改工作区）。
3. 复制每个 Mod 到包内 `mods/`，复制时清洗：
   - 只保留当前游戏版本会加载的目录：有 LoadFolders.xml 时按其中对应版本的条目；否则保留公共目录和不高于当前版本的最高版本目录（03 §1.1）。其余版本目录不复制。
   - PNG 转 DDS：1.0 先不做，留接口（`--textures` 报“未实现”）。原因：需要下载外部转换工具，等工具来源确定后再做。
4. 写 `pack.json`，记录每个目录省掉的字节数。

### 8.3 启动 `archo pack launch <包名>`

1. 把包内 `mods/<目录>` 链接进 `Mods/`，链接名 `_ArchoPack_<包名>_<目录>`（链接部署的同一套代码，前缀不同）；移除其他包的链接。
2. 包的 ModsConfig.xml 写到包自己的用户数据目录 `<包>/userdata/Config/`，启动参数 `-savedatafolder=<包>/userdata`。这样包的列表、存档、设置都独立，原环境的 ModsConfig.xml 不变。
3. 包内副本与原环境的工坊版同包名时，按 04 §2.4 包内副本（`Mods/`）拿原名，工坊版成为 `_steam`；包的列表只写包内副本。
4. 游戏退出后保留链接（下次启动同一包不必重建），切换到其他包或回到普通方案时清理。

### 8.4 其他命令

- `archo pack list`：包名、Mod 数、大小、游戏版本、上次游玩时间。
- `archo pack export <包名> <文件>`、`archo pack import <文件>`：导入轻包时按 lineage 和语义哈希匹配本地实例，列出匹配、版本不同、缺失三组，再决定导入为方案或补齐后编译。
- `archo pack remove <包名>`：移进回收站。
- 每个副本写 `.rimarcho/origin.json`，扫描时归入原 lineage（与 copy-local 相同）。

### 8.5 验收
