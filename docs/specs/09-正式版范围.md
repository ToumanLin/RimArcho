# 09 · 正式版范围（1.0–1.2）

> 状态：2026-10-20 与玩家讨论后确定的方向。细节进入各功能自己的规格后，以那份规格为准。
> 依据：MVP 验收（mvp-acceptance）、backlog、08 §13–§14，以及本页 §0 的裁定。
> 一页式说明：`.archify/explainer-rimarcho-release-scope-20261020-0145/rimarcho-release-scope.html`。

设计原则（00 §2 第 5 条，06 §13）：不让玩家沿着复杂路径操作，而是让玩家**随时知道自己在哪里、可以去哪里、怎么回去**，并以最少的步骤完成任务。

## 2. 整合包（1.0）

整合包把一份方案**编译**成固定产物：每个 Mod 锁定到实例和内容快照，并记住它属于哪个 lineage。原因：一份没有错误的列表，其中的 Mod 更新以后会不会出错，事先说不准。

### 2.1 编译步骤

1. **检查**：“需要处理”清零才能编译（缺失项、不可加载项、顺序问题、缺前置）。自动排序。
2. **清洗**：
   - 去掉**不属于当前游戏版本**的内容。按游戏的加载规则（03 §1.1：有 `LoadFolders.xml` 时取对应版本标签，否则取公共目录加不高于当前版本的最高版本目录），只保留本环境会加载的目录，例如 1.7 环境只留 `1.7/` 和公共目录，丢掉 `1.5/`、`1.6/`。
   - **纹理优化**：PNG 转 DDS（参照 RimCrow 使用 todds 的做法）。只作用于整合包里的副本，从不改原 Mod。转换工具需玩家同意后下载。这修订了 00 §5 的“不做贴图优化”：只在编译整合包时做。
3. **固定**：每个 Mod 记录实例 ID、lineage、语义哈希（02 §4）和来源工坊 ID。
4. **打包**：完整包是清单加清洗后的 Mod 文件；轻包只有清单，用于分享，导入时按 lineage 和哈希匹配本地实例。

### 2.2 放置与启动

- 整合包解压到 `<数据目录>/packs/<包名>/`，再用**目录链接**放进 `Mods/`（Windows 用 junction，不需要管理员权限；不支持时退回复制）。链接目标在 RimArcho 的数据目录里，从不写工坊目录。扫描已经会把联接点解析成真实路径（00 §6.4）。
- 每个放进去的副本写 `.rimarcho/origin.json`，挂回原 lineage（与 copy-local 相同）。
- 启动时写 ModsConfig.xml，用 `_steam` 令牌选中包内副本（需先完成 1.0 的 `_steam` 实测）；用 `-savedatafolder` 给每个整合包单独的存档和配置目录，切换整合包不影响原来的列表和存档。
- 启动整合包像 PCL 启动器选版本：整合包列表、启动按钮、上次游玩时间。

## 3. 订阅与列表交换

### 3.1 订阅、退订、下载（1.0 读取，1.2 订阅）

- **读取合集**（1.0）：用 Steam 公开接口取合集的条目，对照本地已有、缺少、版本不同。
- **订阅**（1.2）：交给 Steam（Steamworks `SubscribeItem` 或 `steam://` 链接），需技术验证。
- **退订**（1.2）：向 Steam 发退订请求，然后由 RimArcho 删除本地文件夹，不等 Steam 慢慢清理。删除进回收站，先列出要删的文件夹并确认。
- **安全底线修订**（01 §5.3 第 1 条）：原文“不修改工坊目录下的任何文件”改为“不修改工坊条目里的文件；只在玩家退订时整体删除该条目的文件夹，进回收站”。

### 3.2 导入导出（1.0）

现有：文本列表、ModsConfig.xml、存档。新增：RimSort 列表、RimCrow 列表、整合包（完整包和轻包）、Steam 合集（导入为方案）。

## 4. 游戏日志实时追踪（1.0）

参照 RimCrow 的 `game-logs` 与 `game-monitor`（inventory/backend-files-logs.md §game-logs）：

- **游戏运行检测**：从 RimArcho 启动时直接知道；从别处启动时检测游戏进程。
- **运行中实时读取** `Player.log`：新出现的错误立即进入“需要处理”的“本次运行”组，用现有的日志归因（03 §6）。
- **兼容 RimCrow 辅助模组**：玩家启用了 RimCrow Companion 时，同时读取 `RimCrow_Realtime.log`（每行一条 JSON，带时间戳和级别）。本机实测：这份日志 819 行，`relatedModIds` 一条都没填，只有 44 条标了错误类型；所以它的价值是实时和精确时间，归因仍以 RimArcho 自己的引擎为准。
- **内存**：只增量读取新内容，不缓存整份日志（RimCrow 这里没有上限，是已知风险）。
- **RimArcho 自己的辅助模组**（1.x）：游戏内用 Harmony 记录结构化日志和加载阶段，格式可兼容 RimCrow 的 JSON 行。

## 5. AI（1.1–1.2）

### 5.1 形态

- 内置一个轻量 harness（例如 Pi），默认开启，可以关闭。
- 工具与 MCP 是同一套（05 的工具 + view 的动作）。外部 agent 继续用 `archo mcp`。
- 写操作全部走现有动作，进撤销历史；写游戏文件仍要玩家确认保存。
- 模型来源：玩家自带 API key，或调用本机已装的 Claude Code、Codex。发给模型的内容（简介、日志、源码片段）每类任务首次使用前征得同意。

### 5.2 任务

聊天（回答管理器问题，例如 lineage、instance 是什么），以及一键任务：修排序自循环、名称与简介翻译、标签分类、管理器与排序错误分析修复、结合日志与本地反编译修 Mod 报错、简介图片识字。

**OCR 的依据**（修订 06 §6.4 第 7 条）：2026-10-20 用 Steam 公开接口取了本机已装的 127 个 “Vanilla … Expanded” 条目。最大的作者账号有 96 个，**全部带 3 张以上图片，中位数 27 张**；去掉各 Mod 共用的段落后，独有文字中位数约 2700 字。图片夹在段落之间，像是章节标题和功能展示（未逐张核实）。所以 OCR 的作用是读出这些图片里的标题和展示内容，而不只是补全没有文字的简介。旧结论“只靠图片写简介的只有 1 个”只统计了纯图片的情况，低估了图片的作用。

### 5.3 存档分析

- **使用度**（1.1，确定性分析，不需要 AI）：读取全部存档（只读），把存档里的 Def 引用映射回提供它的 Mod，回答“哪些 Mod 多局都没用到”“哪些 Mod 大部分内容没玩到”。本机实测：202 个存档，每个 15–28 MB；最新存档中不同的 `<def>` 有 1382 个，提取 0.11 秒；存档开头列出了当时启用的 packageId。
- 口径：Def 引用只说明“出现过”。界面、性能这类纯功能 Mod 不进存档，要单独标出，避免误判为没用。
- **本局主题与内容冲突**（1.2）：例如米莉拉与 Deadman's Switch 技术上不冲突，但强度差太多，一起玩时后者没有意义。由 AI 给建议，社区数据积累后再做规则。

## 6. 设置页（1.0）

关键路径（游戏、用户数据、工坊，修改后重新绑定来源）、启动方式与参数、语言、数据库（大小、备份、导出、压缩、`gc`）、缓存（缩略图、工坊简介、图片、反编译缓存，分别显示大小并可清除）、AI（模型来源、各任务的同意状态）、整合包存放位置。历史区见 08 §14。

## 7. about-disabled 的 68 个 Mod（1.0）

RimCrow 通过把 `About.xml` 改名为 `About.xml.disabled` 让游戏看不到某份 Mod。本机 68 个（64 个工坊、4 个本地）分三类：

| 类别 | 数量 | 实际含义 | 处理 |
| --- | --- | --- | --- |
| 固定副本 | 56 | 同一 lineage 有一份已启用的本地副本 `_<工坊ID>_`，工坊那份被藏起来：玩家用它**固定版本**，防止工坊更新弄坏列表 | 不再当作“不可加载”，显示为“已固定”：本地副本是生效的那份，工坊那份是上游。工坊更新后提示“上游有更新”，可查看差异后“更新固定副本”。以后由整合包承担这件事 |
| 退订残留 | 5 | 已退订，文件夹还在 | 按 §3.1 的规则，确认后删除（进回收站） |
| 单独隐藏 | 7 | 没有副本，玩家直接藏起来 | 进“需要处理 · 需要你确认”：保持隐藏、恢复（改回 About.xml），或删除 |

恢复和删除都要玩家确认。在 §3.1 的安全底线修订生效前，RimArcho 不做这两件事，只列出。
