# 14 · MCP

> Status: implemented: the stdio server and every tool in §2, served in two groups (§1). Not implemented: `list_unplayed` (12 §3).
> Basis: 00 (§3.2, §6 D23), 00a, 13.

`archo mcp` serves RimArcho's tool layer (13 §1) to external agents over the Model Context Protocol. Each tool runs a CLI command and returns its text unchanged, so agents and players receive the same facts. Archo uses the same tools (15 §2.1).

## 1. Transport and lifecycle

- Only stdio is supported (`StdioTransport`); no network ports are opened. stdout carries only protocol messages.
- **Tool groups.** There are 45 tools, `guide` included. `archo mcp` serves the core group (§2): the 29 tools for diagnosis (Mod settings and saves included), plan edits, saving, launching, test runs, locking, rules and ignoring problems. `archo mcp --tools all` (or `--tools=all`) serves all 45, adding the player's management tools (13 §1.2). `--tools core` is the default. The core group is the default because each listed tool costs agent context on every turn; a new tool joins it only when agents need it to diagnose, edit, save, launch or test a plan. Another value, an unknown flag or a positional argument is a usage error (exit 2) before the data folder is opened; `archo mcp --help` shows the flag. A tool outside the served group is an unknown tool to the client. Each tool's group is part of its row in `Tools()`; `Tools()`, `Catalog()` and `ArgvFor()` still cover every tool for harnesses (`spikes/agenteval`), and `ToolDoc.Group` names its group. On synthetic data, the core `tools/list` is about 30 KB and all tools about 47 KB, close to the 48 KB limit (§3).
- The server is named `rimarcho` and reports the release version. It sends the `Instructions` from §3 during initialization.
- The server is not resident: the process exits when the harness closes the session.
- The server starts in the current environment. A tool's `env` parameter switches the environment for that call and restores the previous one afterward.
- Calls within a process run one at a time and share one App.
- Each tool builds a CLI argv and returns the text from `cmds.ExecuteContext` unchanged, run with `cmds.ForMCP` so that a reference matching nothing names `find_mods` (13 §3.3). Exit codes 1 and 2 set `isError`. Exit code 3, an ambiguous reference, is a normal result because the text lists the candidates.
- Calls that need the analysis wait as 16 §2.16.1 W01 says; the CLI has no time limit. If the analysis subprocess takes longer than the wait, the call returns the declaration-level findings and says the rest is `still computing in the background`. The subprocess continues, and the next call gets its results. Meanwhile, `get_def`, `get_patches`, and `get_harmony` use the previous, stale analysis if there is one.
- A `read_source` call with `search` has a default budget of 10 seconds. It reports how many assemblies remain to be decompiled and says `still computing; run again`.
- **Progress.** When a tool call carries a progress token, the server sends `notifications/progress` every 10 seconds until the result. Each one has a count that rises by 1 and a message: the command's latest progress line (`test_run`: preparing test data, waiting for the game to load, analysing the log, comparing with the player's log), or `running`, then the elapsed seconds. Nothing is sent after the result, and a call without a token gets none. Clients that restart their request timeout on progress therefore wait for `test_run` instead of cancelling it. Pi 1.4 asks for progress on every call and cancels after 60 s without any. A cancelled `test_run` stops the game (20 §2). A client whose timeout ignores progress still needs a limit above the run's length.

## 2. Tool table

For link health, the read-only `check_links` maps to `archo links check [--all] --json`. The destructive `repair_links` only previews when `dry_run=true`; to repair, it needs an explicit `confirm=true`. Links without evidence of who owns them also need their full paths in `include`. The CLI equivalents are `links repair [--all] --dry-run` / `--yes [--include <link-path>…]`, with JSON also supported. Without `all`, the current game and its local source are checked. The output includes the full paths, targets, reasons, evidence, and actions. A dangling link or a failed check makes `links check` exit with code 1. [09 §3](09-launch.md#3-link-deployment) sets what the actions may touch.

Annotations follow the MCP specification; the external harness decides whether to permit an action. Archo uses the tiers in 15 §2.2. `openWorldHint: true` applies to `get_description` (the public Steam API), `exchange_list` (Steam collections), `maintenance` (community downloads), `manage_subscriptions` (Git hosts, download pages, and Steam), and `manage_saves` (a fix's Workshop subscriptions: the Steam Web API and Steam). It is false for the other tools.

## 3. Progressive disclosure: Instructions, tool descriptions and guide

On connection, the agent reads only `Instructions`, each tool's short description, and the parameter schemas. This is enough to choose the right tool. Details live in the read-only `guide` tool and are fetched as needed. It maps to the CLI `archo guide [<topic>]` and returns identical text (13 §1.1). Other tools return the CLI text with its suggested commands (`next:`, `fix:`) written as tool calls, so an agent can use them as they are (13 §1.1). 00 §6 D23 gives the reasons.

- The reader is an agent. With no skills loaded, `Instructions`, tool descriptions, and on-demand guide topics must be enough to complete the error-debugging and assembly-inspection workflows (I4). Archo uses the same content (15 §2.1).
- The repository's `skills/rimworld-probe` is separate from this surface. It gives an agent a probe-mod skeleton and a sandbox runner for checking behavior in the real game (1.6 and 1.7). Archo's tools and guide topics must not depend on it. `test_run` `probe` takes any folder that follows the `[Probe]` line contract (20 §3), whether or not it came from the skill.
- The context has a budget (`TestInitialContextBudget`, I13). For the default core group: `Instructions` ≤2000 characters, each description ≤320 characters, and the combined total ≤12000 characters. The `tools/list` JSON of all tools (`--tools all`), schemas included, is limited to 48 KB. Keep new descriptions as short as the existing ones and put details in the guide topic. If a budget must grow, explain why in the commit. Keep parameter descriptions short too; `env` always reads "environment name (default: current)".
- With no topic, `guide` lists all topics. Its tool list puts the tools that only `--tools all` serves on a separate line, `only with archo mcp --tools all: …`, so the text is the same on every surface and in either group (I1; `cmds.AllOnlyTools`, kept in step with `Tools()` by `TestToolGroups`). Their guide topics are still available to a core session. An unknown topic is a usage error (exit 2 and `isError`), with text listing the workflow topics. Topic text is returned verbatim, bypassing `ShellSafe`, so that `#` references in example JSON are kept.
- No tools are merged, and no tool has an alias: `copy_local` and `add_rule` are unknown tools (13 §5).
- Every MCP tool except `guide` itself needs a guide topic of the same name containing `Example: <tool-name> {` (`TestToolsAndAnnotations`).

The tool schema's `game_version` and `env` must be **direct fields**. The SDK does not expand embedded structs when inferring the schema, so embedded fields are rejected as unknown properties. Tools without `env` (`guide` and `preview_uninstall`) run in the current environment.

**`guide topic=diagnose`** contains the following diagnosis workflow. Use the evidence verbatim rather than paraphrasing it:

1. **Start with the error.** If the user pasted a log, call `analyze_log text=…`; otherwise, call `analyze_log` for the current Player.log, then `analyze_log cluster=E<n>` for the relevant cluster. For each cluster, list the candidate Mods and their roles: source (its own code or data produced the error), patcher (it only has a Harmony patch on a frame), dependency (what it provides is missing or disabled), or mentioned (it appears in the message or a lower frame). Never call a patcher or mentioned Mod the cause without further evidence. Evidence belonging to the Mod itself keeps it as the source. A framework that only provides a type, or a Mod that invokes code generically (a static-constructor runner, a type lister, a log uploader), is not the cause. A Mod whose own call passes the arguments (a constructor call, an event, a Def it builds) can be: compare what the callee dereferences with what the call passes (the `trace:` lines of `analyze_log cluster=` and the callers view of `read_source`, when shown); a caller is not acquitted because the exception is thrown in someone else's code. If the cluster names no source and no tool result identifies a Mod's own faulty files or code, say that the cause is undetermined.
2. **Confirm the identity and state with `get_mod`**: the exact Instance, whether it is enabled and its position, its path, and other copies in the same Lineage.
3. **Classify the error**:
   - For XML errors (a failed PatchOperation, missing cross-reference, duplicate or missing parent Def, or malformed XML), use `get_patches failed=true`, `get_def`, and `search_files`. The reasons include target-inactive, target-missing, target-later, wrong-version-route, stale-name, unguarded-optional, and node-absent; explain what each means for the player.
   - For a material or icon error (`_MainTex` or `ResolveIcon`), check XML first. In the named Mods, use `search_files` to find `uiIconColor` without `uiIconPath` or `texPath`.
   - For an assembly error (a C# exception, `Pawn.Tick`, `ThingWithComps.Tick`, or world tick), use `get_harmony` with target=<method> for each patched frame, then `read_source` with type=<patch class> or search=<pattern>. For a tick crash, check AllComps mutations in the cluster's candidates: `read_source search="AllComps.Remove(" in=[…]`, also checking `"AllComps.Add("`, `"InitializeComps"`, and `"PostExposeData"`. When the top frame is a Harmony patch of a game method, also read the caller frame's source and the callee's vanilla contract (`read_source game=true type=<callee> all=true` shows its guards; what vanilla's own call sites pass is the norm): a patch that assumes vanilla's contract is not the owner of a caller that breaks it.
   - For assembly loading errors (ReflectionTypeLoadException, TypeLoadException, or a static constructor failure), inspect the assembly named in the message or adjacent lines. `analyze_log` identifies which enabled Mod loaded that DLL.
   - For a mixed error, first confirm that the XML side loaded successfully with get_patches failed=true, then investigate the code.
   - For other errors (save loading, configuration checks, missing assets, or noise), use `guide topic=errors`.
4. Use `list_problems` for the static overview: dependencies, incompatibilities, load order, Def overrides, patches with no match, and Harmony conflicts. Use `explain_relation` to explain two specific Mods.
5. **Report** the failure phase, whether it is XML, assembly, or mixed, the exact Mod Instances and paths, the file and line or class and method, why it failed, whether each named Mod is a cause, dependency, or bystander, and the smallest fix. When two Mods are involved in one error, the one that threw and the one whose action made it throw (it passed a null, removed an item from a list the other enumerates, changed state the other relies on), report both and list both fix places: a guard or a different loop in the thrower hides the error, removing the action in the other removes it. A cluster with two source candidates says so in a `fixes:` line (06 §3).
6. If it worked before, use `list_changes` to find changed Mods and `plan_history action=diff` to find plan changes.
