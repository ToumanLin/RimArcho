# 16 · Interface · Background tasks (§2.16)

> Part of [16 · Interface](README.md). Section numbers run through all of 16 and stay unchanged when split across files.

### 2.16 Background tasks

**Automatic checks and data updates**: while the GUI or the interactive TUI is open, `app.AutomaticLoop` uses one timer to schedule the session, mods, tools, data and self checks. Startup timing, wake frequency, interval tiers and due conditions: [§2.16.1](2.16.1-scheduled-behavior.md) A01–A03, A06–A07 and A15. Closing the app cancels requests; there is no resident service. Self only checks for new RimArcho versions; installing one needs the player's confirmation (17 §5.1). Each round uses its own connection, runs its checks one after another, and releases the inventory and data indexes afterwards. Network access holds no page lock. While GUI tasks are running or queued, the player's actions go first.

- Settings has only the master switch `updates.auto` and `updates.interval` (normal / half / double). Defaults and durations: §2.16.1. The intervals are described in plain words, such as daily and weekly.
- SQLite meta `automatic:<category>` records the check attempt before going online, then the result, completion time and pending count. Windows that share a database claim a check through a conditional update, so only one of them runs it. Neither a restart nor a failure causes an immediate retry. A manual community-data update or account verification also counts for its interval. The CLI and MCP read the status without starting the timer (13 §4.2).
- Mod checks read only public SteamCMD Workshop metadata, tracked Git refs and download-page versions. LoversLab uses an enabled session to read file pages. Checks never download Mods or check out new Git commits. Results appear in the Mod library's updates (§2.9). An update needs the player's confirmation and is refused while any registered game is running. Steam-client subscriptions update through Steam and are not checked. Known updates are kept while offline.
- Tool checks: 17 §2.1. The LoversLab session protocol: 11 §4. Community-data downloads, conditional requests and replacement: 08 §2.3. RimArcho version checks, download, verification and replacement: 17 §5.1.
- **New RimArcho version**: the result appears in three places, without a dialog (§3.1 rule 7): the RimArcho row in Settings › About (§2.14), the top right of the launch page (§2.3), and one quiet notification when the version is found (“RimArcho 1.0.1 can be updated; see Settings”). The notification comes once per version, and again for a newer version. CLI and MCP `status` show `RimArcho 1.0.1 available` on the automatic-checks line. Checking and installing are tasks in the RimArcho queue (`self-check`, `self-update`). The installation stages say that it is downloading (for example 3.2 MB of 12 MB), checking the download, waiting for other RimArcho processes to close, replacing the program files and starting the new version. Downloading and waiting can be stopped without changing files; the download is kept for reuse. On success, the result is written to the record before the window closes and the new version opens.
- When the pending count changes and is not zero, one quiet notification is sent, not repeated for the same count. LoversLab sign-in warnings use ⚠ in the GUI or `!` in the TUI; update counts use the completion marker. A failed community-data update keeps the old files and sends no failure notification. The GUI records each check as a task, but automatic failures do not create unread red badges. The TUI shows quiet notifications. Results appear in subscriptions and in the Settings groups for tools, community data and accounts (§2.14). Successful subscription and task results say “everything is up to date” or how many updates are available, not that the check is complete. The reasons for failures are kept.

**Steam credit prompt**: “subscribe all” on import, followed collections and bulk subscribe on Can it run first ask the player to choose Steam subscription (slower, counts toward the authors' subscriptions, managed by Steam) or SteamCMD download (faster, does not count toward the authors' subscriptions, managed by RimArcho). Both requests pass `batch:true`. After a SteamCMD batch has been in three game sessions, query `CreditPrompt()` when the window is ready, a game exits, or the window comes back to the foreground (`assets/js/credit.js`, `checkCredit`). A non-empty result opens one prompt asking whether to subscribe on Steam to credit the authors. The choices are to replace this SteamCMD batch with Steam subscriptions gradually in the background, or No thanks. The prompt shows the merged Mod count and a few names, and the answer covers all of `batchIDs`. Concurrent frontend queries are coalesced. If another dialog is open, the prompt waits for a later query. Esc or a failed answer request does not count as an answer, so a later query asks again. `null` defers the prompt without marking it as read; there is no third, implicit Dismiss action. Batch rules: 11 §1. Signatures, JSON, events and text keys: the [API contract](../../api/steam-credit.md).

**Gradual replacement task**: accepting the prompt queues a `steam-credit-replace` task in the RimArcho queue, which uses the existing `tasks` change and end events. It shows the processed count and the total; each item shows waiting, replaced, the reason its copy was kept, or an unrecoverable subscription error. The task can be stopped while it waits for Steam or for the game to exit. Stopping keeps finished subscriptions and the outstanding obligations; “continue replacement” continues the task from the task page, also after a restart. Clearing the displayed history must not discard the SQLite obligations. Handover, the reasons a copy is kept (each item names the environment, list, pack or link that kept it), notes and the handoff lock are defined in 11 §1. When the old copy had DDS records, the task result suggests optimizing the Workshop copy again. While a launch waits for the handoff lock (bound: §2.16.1 W02), Go emits “waiting for background replacement” (`launch-wait`) and reports an error only on timeout. For an item already handed over by an overlapping batch, say that another batch replaced it with the Workshop copy. Closing the window cancels the Steam worker (the wait for the replacement runner: §2.16.1 W04); the task continues the next time the app opens. A `done` result may include copies that were kept. `part` or `fail` means unrecoverable failures, which are never retried automatically.

The background tasks page explains what RimArcho did in the background, how far it has got, which items failed, and why. It is a **page** at the same level as the other pages, **not a dialog** (§3.1 rule 7). The player can go elsewhere while a task runs and come back later.

**Task definition**: a task is work that takes time after one player action and must not block the interface. Each task belongs to a queue:

| Queue | Tasks | Execution |
| --- | --- | --- |
| Files | Mod library actions that change files: recycle, move into the lock library, unhide, pin a version, update a pinned version and unpin (§2.9) | One task at a time, in submission order. Recycle and unhide check each item first, then move 8 folders at a time and scan once at the end. Pin and move-to-library stay sequential per item, because a scan must recognize each new copy. |
| Steam | Unsubscribe and resubscribe through the Steam client (11 §2) | One task at a time. Check each item first, then submit batches of 50 to Steam. |
| RimArcho | Scan, can-it-run analysis, reading the saves in full (§2.11), pack creation, texture conversion and restoration, game download through SteamCMD, SteamCMD and todds download, community-data update, cache clear, database backup and compaction, tombstone cleanup, and the self check and install (17 §5.1) | Each kind uses its existing subprocess or goroutine mechanism (§8.4). One task per kind at a time; different kinds may run at the same time. |

- **Speed**: folder moves and unsubscribes run in batches, so hundreds of items are processed quickly; for these tasks, speed takes priority over memory. Stopping takes effect during the checks, between folders or between Steam batches. Waiting for a resubscribe download can stop within a batch by closing the worker.
- **Resubscribe download progress**: after Steam confirms the subscription, request the download and wait for the files (11 §2). The task stage says “Steam downloading 3 / 14”; each item says waiting for Steam or “downloading 45%”. The overall percentage includes the byte fraction of the running item; the finished count goes up only when an item ends. Changes are coalesced and throttled as in §2.16.1 Q01, but end events are sent at once. In the persistent `app.TaskItem`, `got` and `size` are the downloaded and total bytes. `view.TaskItemRow` uses the `got` and `downloadSize` numbers and a localized `stateText`, and keeps the formatted `size` and the file-size `bytes`. Stopping or closing the window ends the wait and leaves unfinished items to continue later. Steam itself may go on downloading.
- **Subscribe-all download task**: one task and one overall progress per action, without showing internal batches or retry rounds. Preflight, batches and failure classes: 11 §1. Show the processed count, the total and the current Mod. Each SteamCMD Success or ERROR updates the record at once; progress only moves forward, across batches and retries. Items are weighted by the public `file_size`. Unknown sizes take the mean known size; if no size is known, count items. While running, the percentage stops at 99%; successful completion reaches 100%. Transient failures are retried within the same task. Those items do not count as finished until the retries are used up; then the final failure is shown.
- **Subscription results**: the first line at the left says Subscribe N Mods, or Subscribe and the Mod's name for one Mod. The second line is one summary, such as 36 complete, 4 failed: no longer on Workshop. The summary at the right groups the reasons, one line each, such as 4 Mods removed or private, without repeating individual reasons or URLs. Item names use the preflight title and fall back to the Workshop ID. Reasons are short phrases without a `failed:` prefix. The “open the Workshop page” menu item stays. `failureKind` and `permanent` are stored; rows with a permanent failure have no retry action.
- **Cancel and resume subscriptions**: while the task runs, “cancel” is the stop action. Finished items are kept and the rest are marked cancelled. Afterwards, “continue N items” reuses the original task row, total, finished items and progress, and submits only the rest. Transient failures left after the automatic retries offer “retry N items”; permanent failures are excluded. When no item can be retried, there is no retry, and the primary button becomes “go to updates”. Internals and process ownership: 11 §1.
- In the Files and Steam queues, a failed item does not stop the task: it goes on to the next item and records every result. File changes that RimArcho cannot undo still need a preview and confirmation before they are submitted (§6); after confirmation they become background tasks. The status says, for example, that 14 Mods are queued for recycling in the file queue; at the end it reports the counts, such as 12 complete and 2 failed, with a link to the task page.
- Some background work is not a task: size calculation on the build and texture pages, data reads when switching games, and page reads. This work does not block the interface (§3.1 rule 9). Its progress appears only where it happens, not on the task page.
- Plan edits (enable, disable, stage, change version, disable in all lists) are not tasks. They finish at once and can be undone in one step (§3.1 rule 2). Save and launch are not tasks either (§6).
- The file queue and scanning exclude each other. File tasks wait while a scan runs; a scan waits for the current file item to finish.
- In the TUI, the subscription actions (subscribe, check a source, check for updates, update, remove a subscription) and decompiling the current list's Mods use the shared `app.Tasks` and `tasks.json`, with the same kinds and queues as the GUI. The status first says that the action is queued, then gives the result (`view.TaskStatus`). The TUI has no task page: “background tasks” in the command panel shows the records as text. Other Mod library file actions still run synchronously in the TUI.
- A task is started by the player or by the automatic checks above. Tasks started by Archo (1.1, 15) will carry its portrait, and their details will say started by Archo, confirmed by you.

**Records**: each task has a record with its kind, object (14 Mods, or Main colony 10-22), state, start time, duration and a one-sentence result. Where it applies, the record also has each item's name, Instance reference, result, reason and size. Running tasks live in memory. When a task ends or stops, or a record is removed, all records, including running and queued tasks, are written to `<data directory>/tasks.json`. The latest 200 tasks are kept; the oldest finished tasks go first, and failures and partial results are kept longer. Records survive a window restart. Closing the window marks queued and running tasks Stopped (window closed) and stops their work; there is no resident service (00 §4 principle 6). The exception is a pack build, which runs in its own process and goes on (10 §2): closing does not stop it, and its record says it went on in the background (`Task.Detached`). The Packs page shows how it ended.

**Multiple windows** (a GUI and a TUI, or two GUIs, on the same data directory): each task's `owner` stores the process that started it, the process start time and a sequence number. Each window runs and stops only its own tasks. Before writing, a window reads the file again, keeps other owners' records as they are, applies its own removals (`Del`, `C`, and records beyond 200), then writes it back. Reads and writes use a cross-process lock (a Windows named mutex; the write goes ahead after a timeout; bound: §2.16.1 Q04). Other owners' running tasks are hidden. Their finished tasks appear after the file changes and is read again; the reread window after a recent write is in §2.16.1 Q04. On opening, only unfinished tasks whose owner is gone become Stopped (window closed) and move to this window. Removing a record in one window removes it in the others too; the original owner never brings it back. Undo or continue moves ownership to the window that acts. Failures already seen and items moved to retry tasks stay so across windows. The implementation is in `internal/app/taskfile.go`.

**States**: a task can be running, queued, failed, partially complete (with successes and failures), stopped or complete. An item can be complete, failed, running, waiting, or untouched after a stop.

**Entries**:
- A permanent sidebar row above Settings (§2.1) normally says “background tasks”. While tasks are running or queued, it shows a ring that fills with the overall progress, and the number of tasks with the percentage, such as 2 background tasks 54%. Unread failures and partial results have a red count badge. Opening the page marks failures that have already finished as seen.
- `ctrl+j` opens the page from anywhere; pressing it again returns to the previous page. “background tasks” in the command panel also opens it.
- The status after a task result includes a link to background tasks.
- With top navigation, the icon, ring and badge sit at the right, beside the settings gear.

**Layout**: the same pattern as the Mod library, with filters at the top left and a list below (§2.9). The breadcrumb is “background tasks”. The page heading has no description and only one action, “take the done ones off the record” (`C`).
- **Left**: the default width is `clamp(270px, 25%, 380px)`. A draggable divider changes it; the value is stored in `ui.gui.tasks.side`. A double-click resets it.
  - `1` **Filters** uses the shared §2.5 component. Search covers task names, objects, results and item names. The filter groups are state, queue and time (now / today / yesterday / earlier).
  - `2` **Tasks** groups tasks under Running / Queued / Today / Yesterday / Earlier, with muted counts in the group headings. The newest come first, except that queued tasks follow the execution order. Each task has two lines. The first shows the kind in bold, the object in muted text and the start time at the right. For a running task, the second line shows a small progress bar, 10 / 14 and the current action, such as moving RocketMan, waiting for Steam batch 2, or step 4 pin version. A queued task says why it is waiting. A finished task shows its state (red failure, amber partial, green ✓ complete, or muted stopped) and a result sentence. Complete and stopped tasks do not have bold names.
- **Right**: two cards with a gap that can be dragged up and down. The split is stored in `ui.gui.tasks.split`; a double-click resets it:
  - **Summary** shows the kind and object at 15px and one sentence on the state, progress or result. Running, stopped and partially complete tasks have a bar. Tasks with several steps show ✓, an accent dot for the current step and muted numbers for the waiting steps (§2.6). Action buttons show their keys. The last, muted row shows the queue and how it runs tasks, the start time and the elapsed time.
  - `3` **Items** is a table (§3.9) of the items the task touched. Its columns are Item (the name, always visible), Result, Reason (made readable by `view.Humanize`) and Size. The heading menu also offers Location (the folder or Workshop ID). It is sorted by result by default, failures first. The heading shows the completed and failed counts at the right. Tasks without item results (scan, check, game download) show one result and where to look, such as press o for subscriptions.
- Below 900px, only the left column shows. `enter` opens the right column full-screen over it and `esc` returns, as in the Mod library.

**Actions**: only applicable actions appear. Buttons, context menus and keys use one table. Actions apply to the selected tasks, or to the task under the cursor if none is selected:

| Key | Action | When |
| --- | --- | --- |
| `x` | “stop the rest”: stop after the current item, keep the finished items and mark the rest untouched. For a queued task, “cancel the wait” leaves everything unchanged. | Running or queued |
| `r` | “retry N items”: retry the failures that can be retried, in a new task with only those items. For a stopped task, “do the N left” processes only the untouched items. Without item results, “try again”. | Failures that can be retried, partial completion, or stopped tasks |
| `J` `K` | “later” / “sooner”: move one place back or forward in the queue; rows can also be dragged. | Queued |
| `o` | Open the page concerned: the Mod library filtered to the touched items, subscriptions, can it run, the pack, or texture optimisation. | Always |
| `ctrl+o` | Open the folder; on an item row, that item's folder. | File tasks or items |
| `Del` | “take off the record”: remove only the record; files are not touched. The status offers Undo, also `ctrl+z`. | Finished |
| `C` | Remove only complete tasks from the record. Failed, partially complete and stopped tasks stay. Undoable. | Page action |

- Stop, retry and remove need **no confirmation**. Stop only skips later items; retry creates a new task from failed items that were not changed; removing a record can be undone (§6).
- On an item, `o` focuses that copy in the Mod library, `ctrl+o` opens its folder, `r` retries only this item if its failure can be retried, and `ctrl+c` copies its name.
- Restoring recycled items is **not implemented**. It needs restoring from the recycle bin to the original path (02 §3).

**Keys**: `1`, `2` and `3` focus the three areas (§3.5). `↑↓`, `PgUp`, `PgDn`, `Home` and `End` move. On a task, `enter` or `→` enters its items, and `←` returns. `shift+↑↓`, `ctrl+space` and `ctrl+a` select several tasks. `s` opens the item table's heading menu; `<`, `>` and `=` change widths. The Menu key or `shift+F10` opens the row menu. `/` or `ctrl+f` searches, `\` opens the filters, and `?` shows all keys. The hint follows the actions available for the task under the cursor: move, enter items, x stop, r retry failures, o Mod library, and ? all keys.

**Motion**: running progress bars and the sidebar ring advance smoothly with `--t-layout`. The bar's shimmer follows §7.1 Loading. When a task changes groups, its row moves with a FLIP transition. These animations are off under `prefers-reduced-motion`.

**Data and implementation**: `internal/app/tasks.go` owns tasks, queues and the record file. The Files and Steam queues call the single-item Mod library actions. `internal/view/tasks.go` provides `BuildTasks` for groups, rows, summary, items and actions, with the wording in `view.Text`. The GUI uses `API.Tasks`, `TaskAct`, the `tasks` event (changes coalesced as in §2.16.1 Q01; end events sent at once) and `js/tasks.js`. The progress events for scans, analysis, packs, textures and game downloads stay as they are; each of these also records one task. The CLI and MCP do not read the history, because their commands finish in the foreground (13). The TUI has no task page (see above).
