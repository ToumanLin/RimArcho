### 2.16 Background tasks

**Automatic checks and data updates**: while the GUI or interactive TUI is open, `app.AutomaticLoop` uses one timer to schedule session, mods, tools, data, and self work. See [§2.16.1 Scheduled behavior](2.16.1-scheduled-behavior.md) A01–A03, A06–A07, and A15 for startup timing, wake frequency, interval tiers, and due conditions. Closing the app cancels requests; there is no resident service. Self only checks for new RimArcho versions; installation requires the player's confirmation (17 §5.1). Each round uses an independent connection, runs sequentially, and releases the inventory and data indexes afterward. Networking holds no page lock. When GUI tasks are running or queued, give the player's operations priority.

- Settings contains only the master `updates.auto` switch and `updates.interval` (normal / half / double). See §2.16.1 for the defaults and durations. Describe the intervals naturally, using daily, weekly, and corresponding English terms.
- SQLite meta `automatic:<category>` records the check attempt before networking, then records the result, completion time, and pending count. Windows sharing a database claim the same check through a conditional update. Neither a restart nor a failure causes an immediate retry. A manual community update or account verification also satisfies its corresponding interval. The CLI and MCP read the status without starting the timer (13 §4.2).
- Mod checks read only public SteamCMD Workshop metadata, tracked Git refs, and download-page versions. LoversLab uses an enabled session to read file pages. Checks neither download Mods nor check out new Git commits. Results reuse waiting for you to update (§2.9). An update requires the player's confirmation and is refused while any registered game is running. Steam-client subscriptions update through Steam and are excluded from automatic checks. Retain known updates while offline.
- Tool checks and the LoversLab session protocol are defined in 17 §2.1 and 11 §4 respectively. Community downloads, conditional requests, and replacement are defined in 08 §2.3. RimArcho version checking, downloading, verification, and replacement are defined in 17 §5.1.
- **New RimArcho version** (2026-10-31): show the result in three places without opening a dialog (§3.1 rule 7): the RimArcho row in Settings › About (§2.14), the top-right of the launch page (§2.3), and one quiet notification when the update is discovered, saying that RimArcho 0.9.1 is available in settings. Notify only once per version, and notify again for a newer version. CLI and MCP `status` shows `RimArcho 0.9.1 available` on the automatic checks line. Check and install are tasks in the RimArcho queue (`self-check`, `self-update`). The installation stages describe downloading 3.2 MB / 12 MB, verifying the downloaded files, waiting for 2 other instances to close, replacing the program files, and launching the new version. Downloading and waiting can be stopped without changing files; retain the download for reuse. On success, write the result to the record before closing the window and opening the new version.
- When the pending count changes and is nonzero, send one quiet notification. Do not repeat it for the same count. LoversLab sign-in warnings use GUI ⚠ or TUI `!`; update counts use the completion marker. Community failures retain the old files without failure notifications. The GUI records each check as a task, but automatic failures do not create unread red badges. The TUI shows quiet notifications and has no task page yet. Results appear in subscriptions and in the settings areas for tools, community data, and accounts (§2.14). Successful subscription and task results say up to date or N updates available rather than Check complete. Retain the reasons for failures.

**Steam credit prompt**: Subscribe all on import, followed collections, and bulk subscribe on Needs attention first ask the player to choose Steam subscription (slower, counts toward the authors' subscriptions, managed by Steam) or SteamCMD download (faster, does not count toward authors' subscriptions, managed by RimArcho). Both requests pass `batch:true`. After a SteamCMD batch reaches three game sessions, query `CreditPrompt()` when the window is ready, a game exits, or the window returns to the foreground (`assets/js/credit.js`, `checkCredit`). A nonempty result opens one prompt asking whether to subscribe on Steam to credit the authors. The choices are to gradually replace this SteamCMD batch with Steam subscriptions in the background, or No thanks. Show the merged Mod count and a few names, and answer for the entire `batchIDs`. Coalesce concurrent frontend queries. If another dialog is open, defer the prompt until a later query. Esc or a failed answer request does not count as an answer, so a later query prompts again. `null` means defer without marking the prompt read; there is no third implicit Dismiss action. Batch rules are defined in 11 §1. See the [API contract](../../api/steam-credit.md) for signatures, JSON, events, and text keys.

**Gradual replacement task**: accepting the prompt queues a `steam-credit-replace` task in the RimArcho queue, using the existing `tasks` change and end events. Show the processed count and total; each item shows waiting, replaced, the reason its copy was retained, or an unrecoverable subscription error. The task can be stopped while waiting for Steam or game exit. Stopping retains completed subscriptions and outstanding obligations; the task can continue from the task page and across restarts. Clearing the displayed history must not discard the SQLite obligations. History and undo follow the client copy without creating duplicates. Retain the entire item if any environment that can load the old copy cannot load the new one, and name the environment. Other retention reasons are corrupted staging data (name the list), a fixed pack, an inbound link, or game deployment that has not been handed over. Merge notes into the new copy. Do not migrate the DDS ledger directly; instead, suggest optimizing the Workshop copy again in the task result. A launch waits for the handoff lock up to the bound in §2.16.1 W02. Go emits Waiting for background replacement (`launch-wait`) and reports an error only on timeout. Scanning does not hold the handoff lock. For an item already handed over by an overlapping batch, show that another batch replaced it with the Workshop copy. Waiting for scans or file tasks does not increase the failure count. Closing the window cancels the Steam worker; see §2.16.1 W04 for the bound on waiting for the replacement runner. Continue on the next opening. A `done` result may include copies retained for the reasons above. `part` or `fail` means there are unrecoverable failures, which are never retried automatically.

This page was defined on 2026-10-23, when the player chose tasks and their individual items from three candidates (prototype `spikes/bgtasks-v2/c.html`). It explains what RimArcho did in the background, how far it has progressed, which items failed, and why. It is a **page** at the same level as other pages, **not a dialog** (§3.1 rule 7). The player can navigate elsewhere while a task runs and return later.

**Task definition**: a task is work that takes time after one player action and must not block the UI. Each task belongs to a queue:

| Queue | Tasks | Execution |
| --- | --- | --- |
| Files | Inventory actions that mutate files: recycle, move into the lock library, unhide, pin a version, update a pinned version, and unpin (§2.9) | Run one task at a time in submission order. Recycle and unhide precheck each item, then move 8 folders concurrently and scan once at the end. Pin and move-to-library remain sequential per item because a scan must recognize each new copy. |
| Steam | Unsubscribe and resubscribe through the Steam client (11 §2) | Run one task at a time. Precheck each item, then submit batches of 50 to Steam. |
| RimArcho | Scan, readiness analysis, reading the saves in full (§2.11), pack creation, texture conversion and restoration, game download through SteamCMD, SteamCMD and todds download, community update, cache clear, database backup and vacuum, tombstone cleanup, and self check and install (17 §5.1) | Use the existing subprocess or goroutine mechanism for each kind (§8.4). Run one task per kind at a time; different kinds may run concurrently. |

- **Speed** (2026-10-23): previously, every folder move scanned the whole inventory and each unsubscribe launched Steam, making hundreds of items slow to process. These operations now run in batches; speed takes priority over memory for these tasks. Stopping takes effect during checks, between folders, or between Steam batches. A resubscribe download wait can stop within a batch by closing the worker.
- **Resubscribe download progress**: after subscription confirmation, actively request the download and wait for the files (11 §2). The task stage says Steam downloading 3 / 14; each item says waiting for Steam or Downloading 45%. The overall percentage includes the byte fraction of the running item; the completed count increases only when an item ends. Coalesce and throttle changes per §2.16.1 Q01, but send end events immediately. In the persistent `app.TaskItem`, `got` and `size` are the downloaded and total bytes. `view.TaskItemRow` uses the `got` and `downloadSize` numbers and localized `stateText`, retaining the existing formatted `size` and file-size `bytes`. Stopping or closing the window ends the wait and leaves unfinished items available to continue. Steam itself may continue downloading.
- **Subscribe-all download task**: show one task and one overall progress indicator per action, without exposing internal batches or retry rounds. See 11 §1 for preflight, batches, and failure classes. Show the processed count, total, and current Mod. Each SteamCMD Success or ERROR updates the record immediately; progress advances monotonically across batches and retries. Weight items by the public `file_size`. Unknown sizes use the mean known size; if all sizes are unknown, use item counts. The running percentage is capped at 99%, and successful completion reaches 100%. Retry transient failures within the same task. Do not count those items complete until retries are exhausted, then show the final failure.
- **Subscription results**: the first line at the left says Subscribe N Mods, or Subscribe Mod name for one Mod. The second line is a single summary, such as 36 complete, 4 failed: no longer on Workshop. The right summary groups reasons, one line each, such as 4 Mods removed or private, without repeating individual reasons or URLs. Item names use the preflight title and fall back to the Workshop ID. Reasons are short phrases without a `failed:` prefix. Retain the Open Workshop page menu item. Persist `failureKind` and `permanent`; permanent-failure rows have no retry action.
- **Cancel and resume subscriptions**: while running, Cancel uses the stop action. Keep completed items and mark the remainder Cancelled. Afterward, Continue N reuses the original task row, total, completed items, and progress, submitting only the remainder. Transient failures that remain after automatic retries show Retry N; permanent failures are excluded. Hide retry when no items are retryable. The primary button then becomes Go to updates. See 11 §1 for internals and process ownership.
- The Files and Steam queues are new. Previously, these inventory actions ran synchronously and stopped on the first failure, for example, after completing 2 items. They now continue to the next item after each failure and record every result. File changes that RimArcho cannot undo still require a preview and confirmation before submission (§6). After confirmation, they become background tasks. The status says 14 Mods queued for recycling in the file queue; completion reports the success and failure counts, such as 12 complete and 2 failed, with a task-page link.
- Some background work is not a task: size calculation on build and texture pages, data reads when switching games, and page reads. This work does not block the UI (§3.1 rule 9). Its progress appears only where it occurs, and it is absent from the task page.
- Plan edits (enable, disable, stage, change version, and disable in all lists) are not tasks. They finish immediately and can be undone in one step (§3.1 rule 2). Save and launch are not tasks either (§6).
- The file queue and scanning exclude each other. File tasks wait while a scan is running; a scan waits for the current file item to finish.
- In the TUI (2026-10-30), subscription, update, and add actions (subscribe, check a source, update, and remove a subscription) use the shared `app.Tasks` and `tasks.json`, with the same kinds and queues as the GUI. The status first reports that the action is queued, then reports the result (`view.TaskStatus`). The task page is pending; other inventory file actions still run synchronously in the TUI.
- The initiator is the player or the automatic checker described above. Future tasks initiated by Archo (1.1, 09) will carry its portrait, with details saying initiated by Archo, confirmed by you.

**Records**: each task has a record containing its kind, object (14 Mods or Main colony 10-22), state, start time, duration, and a one-sentence result. Where applicable, it also contains each item's name, instance reference, result, reason, and size. Running tasks live in memory. When a task ends, stops, or has its record removed, write all records, including running and queued tasks, to `<data directory>/tasks.json`. Keep the latest 200 tasks; evict the oldest completed tasks first and retain failures and partially completed tasks longer. Records survive a window restart. Closing the window marks queued and running tasks Stopped (window closed); there is no resident service (00 §4 principle 6).

**Multiple windows** (a GUI and TUI, or two GUIs, using the same data directory, 2026-10-30): each task's `owner` stores the initiating process, process start time, and sequence. Each window runs and stops only its own tasks. Before writing, reread the file, retain other owners' records as stored, apply this window's removals (`Del`, `C`, and records beyond 200), then write back. Reading and writing use a cross-process lock (a Windows named mutex; write even after timeout; see §2.16.1 Q04 for the bound). Hide other owners' running tasks. Their finished tasks appear after a file-change reread; see §2.16.1 Q04 for the recent-write reread window. On opening, only unfinished tasks whose owner is gone become Stopped (window closed) and transfer to this window. Removing a record in one window also removes it in the others; the original owner never resurrects it. Undo or Continue transfers ownership to the acting window. Seen failures and items transferred to retry tasks persist across windows. The implementation is in `internal/app/taskfile.go`.

**States**: a task can be running, queued, failed, partially complete (with successes and failures), stopped, or complete. An item can be complete, failed, running, waiting, or untouched after a stop.

**Entries**:
- A permanent sidebar row above Settings (§2.1) normally says Background tasks. While tasks are running or queued, it shows a ring that fills with overall progress and “2 background tasks 54%”. Unread failures and partial results have a red count badge. Opening the page marks failures that have already finished as seen.
- `ctrl+j` opens the page from anywhere; pressing it again returns to the previous page. Background tasks in the command palette also opens it.
- The task-result status includes a link to background tasks.
- With top navigation, the icon, ring, and badge appear at the right, beside the settings gear.

**Layout**: use the inventory pattern, with filters at the top-left and a list below (§2.9). The breadcrumb is Background tasks. The page heading has no description and only the Clear completed action (`C`).
- **Left**: the default width is `clamp(270px, 25%, 380px)`. A draggable divider changes it; store the value in `ui.gui.tasks.side`. Double-clicking resets it.
  - `1` **Filters** uses the shared §2.5 component. Search task names, objects, results, and item names. Filter groups are state, queue, and time (now / today / yesterday / earlier).
  - `2` **Tasks** groups tasks under Running / Queued / Today / Yesterday / Earlier, with muted counts in the group headings. Show the newest first, except that queued tasks follow execution order. Each task has two lines. The first shows the kind in bold, the object in muted text, and the start time at the right. For a running task, the second shows a small progress bar, 10 / 14, and the current action, such as moving RocketMan, waiting for Steam batch 2, or step 4 pin version. A queued task shows why it is waiting. A finished task shows its state (red failure, amber partial, green ✓ complete, or muted stopped) and a result sentence. Complete and stopped names are not bold.
- **Right**: show two cards with a vertically draggable gap. Store the split in `ui.gui.tasks.split`; double-clicking resets it:
  - **Summary** shows the kind and object at 15px and one sentence for the state, progress, or result. Show a bar for running, stopped, and partially complete tasks. Multistep tasks show ✓, an accent dot for the current step, and muted waiting numbers (§2.6). Action buttons include their keys. The final muted row shows the queue and its execution semantics, start time, and elapsed time.
  - `3` **Items** is a table (§3.9) of the items touched by the task. Its columns are Item (the name, always visible), Result, Reason (humanized through `view.Humanize`), and Size. The heading menu also offers Location (the folder or Workshop ID). Sort by result by default, with failures first. Show completed and failed counts at the right of the heading. For tasks without item results (scan, check, and game download), show one result and a destination, such as press o for subscriptions.
- Below 900px, show only the left column. `enter` overlays the right column in full screen, and `esc` returns, as in the inventory.

**Actions**: show only applicable actions. Buttons, context menus, and keys use one table. Actions apply to the selected tasks, or to the task under the cursor if none are selected:

| Key | Action | When |
| --- | --- | --- |
| `x` | Stop after the current item; retain completed items and mark the remainder untouched. For a queued task, Cancel queue leaves everything unchanged. | Running or queued |
| `r` | Retry retryable failures in a new task containing only those items. For a stopped task, Continue processes only the remaining untouched items. Without item results, offer Try again. | Retryable failures, partial completion, or stopped tasks |
| `J` `K` | Move one queue position back or forward; row dragging is also supported. | Queued |
| `o` | Open the affected page: inventory filtered to touched items, subscriptions, readiness, the pack, or textures. | Always |
| `ctrl+o` | Open the folder; on an item row, open that item's folder. | File tasks or items |
| `Del` | Remove only the record, leaving files unaffected. The status offers Undo, also available through `ctrl+z`. | Finished |
| `C` | Clear only complete tasks. Retain failed, partially complete, and stopped tasks. This action is undoable. | Page action |

- Stop, retry, and remove require **no confirmation**. Stop only skips later items; retry creates a new task from failed items that were not changed; record removal is undoable (§6).
- On an item, `o` focuses this copy in the inventory, `ctrl+o` opens its folder, `r` retries only this item if the failure is retryable, and `ctrl+c` copies its name.
- Restoring recycled items is **pending**. It requires restoration from the Recycle Bin to the original path in 02 §3.

**Keys**: `1`, `2`, and `3` focus the three areas (§3.5). `↑↓`, `PgUp`, `PgDn`, `Home`, and `End` navigate. On a task, `enter` or `→` enters its items, and `←` returns. `shift+↑↓`, `ctrl+space`, and `ctrl+a` select multiple tasks. `s` opens the item-table heading menu; `<`, `>`, and `=` adjust widths. Menu or `shift+F10` opens the row menu. `/` or `ctrl+f` searches, `\` opens filters, and `?` shows all keys. The hint adapts to the actions available for the task under the cursor: move, enter items, x stop, r retry failures, o inventory, and ? all keys.

**Motion**: running progress bars and the sidebar ring advance smoothly with `--t-layout`. The bar shimmer follows §7.1 Loading. When a task changes groups, use a FLIP row transition. Disable these animations under `prefers-reduced-motion`.

**Data and implementation**: `internal/app/tasks.go` owns tasks, queues, and the record file. The Files and Steam queues call the original single-item inventory actions. `internal/view/tasks.go` provides `BuildTasks` for groups, rows, summary, items, and actions, with wording in `view.Text`. The GUI uses `API.Tasks`, `TaskAct`, the `tasks` event (changes coalesced per §2.16.1 Q01; end events sent immediately), and `js/tasks.js`. Existing progress events for scans, analysis, packs, textures, and game downloads are unchanged; each also records one task. The CLI and MCP do not read the history because their commands already finish in the foreground (05). The TUI page is **pending**.
