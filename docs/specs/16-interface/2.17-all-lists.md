# 16 · Interface · All lists (§2.17)

> Part of [16 · Interface](README.md). Section numbers run through all of 16 and stay unchanged when split across files.

### 2.17 All lists

All lists is implemented in the GUI; the prototype is `docs/design/all-lists-drafts/`. The page shows which plans exist, which game versions each allows, which collections each follows, and how to share them. Editing a plan's content stays in the editor (§2.5).

**Entry and location**: “all lists” is the first child under Lists in the sidebar, above the recent lists. The sidebar shows at most 4 lists; the rest appear only here. Clicking Lists itself opens the current list (§2.1). The breadcrumb is “library / lists / all lists”. With top navigation, all lists is the last subpage button.

**Heading**: no description (§7.3), only the primary “new / import” button at the right (`n`). Creating and importing share one form, so they have no separate entries; `i` still opens import mode directly. If a draft exists, the button resumes it. While a list is being created, the button is not solid.

**Left card**: by default, the left card takes 38% of the page width and the right card 62%, with a minimum width of 270px. The gap between them is draggable; the split is stored in `ui.gui.plans.side` and a double-click resets it (§7). Plans are shared across games (07 §1.7), so there are no game groups. The current game's current list comes first, then the others in creation order. When a list is made current, its row moves from the old position to the new one with an animation, as in the sidebar (§2.1). Lists whose allowed versions exclude the current game stay visible; their muted version text already explains this (07 §1.6). Each row has two lines:
- The top line shows the name in bold and the markers: a green dot if the list is the one written in the game, or an amber dot for outside changes not yet adopted. These follow the sidebar rules (§2.5).
- The muted bottom line shows the allowed versions, N Mods and the last-play date, or never played.
- At the right, the current list has a “current” pill. Other lists show “make current” on hover or selection. This sets the list to launch without writing game files (07 §1.3).
- The row under the cursor has the selected background and an accent-colored name.

**Right card**: the selected list's details:
- **Header**: the name and markers. A muted facts line below shows the Mod count, last-play date, creation date and origin (the v1 note, such as copied from default v4). “in the game now: v18” appears in green only when it applies. Four buttons appear directly, without an overflow menu: “rename” (`F2`), “duplicate” (`D`), “delete” (`Delete`, with confirmation; disabled for the last list), and the primary “edit” ↵, which opens the editor.
  - **Inline rename**: double-clicking the name, pressing `F2` or clicking “rename” turns the name into an input with all text selected. Duplicate names are checked while typing. `enter` or leaving the input saves; `esc` cancels. No dialog opens.
  - **Duplicate**: immediately copies the current load order and allowed versions into a new plan with its own history. The copy is named `<name> copy`, with a suffix if that name exists. The copy is selected and rename starts. Undo in the status deletes the copy. Duplicate in the sidebar's context menu does the same.
- **“game versions”** (07 §1.6): small buttons from 1.0 up to the current game version, showing only the version numbers. Allowed versions are raised and use the accent color; the current version has a dot. The hover text says, for example, that N Mods do not declare 1.7 support, or that all Mods declare 1.6 support. A click adds or removes the version; at least one stays. If the player has changed the defaults, “reset to default” appears at the right, with the defaults in its hover text; otherwise nothing is added. No explanatory prose here. Can it run points out Mods that do not support the current game. After a change, the status says, for example, Main colony allows 1.5–1.7, and offers Undo.
- **“follows Steam collections”** (07 §7.6): the number of followed collections at the right of the heading. Each collection has a card:
  - The first line shows the Steam icon, the title and the muted item count. At the right are “open in Steam” and “stop following”.
  - A muted second line shows the last check (such as Today 14:02), 4 not installed, and “subscribe in the Workshop”. The URL itself is not shown.
  - If the collection has changed, an amber-tinted line shows the change (3 added and 1 removed) with “see the changes”, and “catch up” at the right. The changes expand inline, with a green `+` or red `−` and one Mod per line. If nothing changed, show ✓ “same as the collection”.
  - The last row says “when catching up:” and has two segments: “add new only” / “also disable dropped”.
  - Below the cards are an input for pasting a collection link and “follow”. If the list follows no collection, a muted “no collection yet” appears above the input.
  - Catching up is one undoable edit. The status says, for example, Main colony caught up with the Vanilla Expanded collection: 3 enabled, and offers Undo.
- **“share”**: the last pack created from the list, in one row with its name, size and date; “open” at the right goes to the pack page. Below are “export…” (`e`, opens a subpage) and “create a pack…” (`B`, §2.6).

**Export subpage**: the breadcrumb is “library / lists / <list> / export”. The sidebar stays on all lists, or on the list it was opened from in the editor. The heading has no description. “cancel” at the right (`esc`) returns to where the player came from. The left card has one radio choice per format (07 §7.3), with a name, an extension and a sentence: RimArcho list (recommended), RimCrow share code, text list, ModsConfig.xml, RimWorld Mod list (.rml), RimCrow ModList.xml and Workshop links. The right card shows N Mods and the allowed versions, then the full export in monospace (`loadout export --format`). Below it are “save as a file…” (a save dialog that never overwrites an existing file) and “copy”. A share code has only “copy the share code”. The chosen format is stored in `ui.gui.export.format`.

**New / import** (`n`): no dialog (§3.1 rule 7). The breadcrumb is “library / lists / all lists / new list”. A Draft row appears at the top of the left card and does not count as a real list. The form at the right first asks for the “new list name”, checks for duplicates as the player types, and defaults to New list. Then “start from” offers “an empty list” (the default), “copy a list”, “from a save” and “import”. An empty list explains that Mods are added in the editor. Copy a list offers “source list” (any list for the current game) and “based on which version”. The default is “current editing content (including unsaved changes)”; the other choices are all history entries that can be copied, with version, date, time and Mod count. Changing the source list resets the version to the current content; a stale read cannot overwrite a later choice. The copy takes the current load order and allowed versions and starts its own history.

The form has only one primary button, fixed at the bottom of the visible area. Its hover text says that no game files are written. Even a long preview must not push it out of view. In import mode, the button says “preview” before a preview exists and “create and edit” afterwards; the other modes always say “create and edit”. Creating opens the editor without making the new list current (07 §1.3). `enter` in the name field or `ctrl+enter` in the text area presses the button; `enter` in the text area inserts a line break. Duplicate-name, read and submission failures keep the input. The form is disabled during submission to prevent duplicates. There are no Back to management, Continue later or Create only actions. The player leaves through the sidebar, another list or `esc`, which closes the form. Asynchronous reads of suggested names or source lists update inline; they never redraw the form or swallow a click in progress.

**Drafts**: drafts are kept per game while the app stays open. On leaving the form (`esc`, another list or page, or back), drafts whose names are still the default or an unchanged import suggestion are discarded, because an unchanged name shows no intent to create. Renamed drafts stay in the left card. Clicking the draft or “new / import” restores its name and all source inputs. When `esc` leaves a kept draft, the status says “draft kept; continue it from the list”. The form of a kept draft adds a quiet “discard draft” link; discarding can be undone. Drafts are not restored after a restart.

**Import within creation**: switching modes stays in the same form and keeps the name. If the player has not edited the name, suggest the source's title or file name. A muted guide lists the supported imports (RimSort, RimCrow, RimWorld and RimArcho lists, saves, share codes and Steam collections) and says that the player sees installed and missing Mods before anything is created. The dashed area has “choose a file…”, which opens the native dialog and reads and previews the file at once; in development, it falls back to the browser picker. The chosen path and “clear” follow §3.1 rule 12; with nothing chosen, a drop hint appears. There is no manual path field. Dropping a file anywhere on the form switches to import and reads it. Below, an “or paste” text area accepts a share code, a collection link, a Rentry link or a copied list. This input is read only on preview; links use the network. Import analysis shows the source, version differences, installed Mods and missing Mods. Steam collections offer “follow this collection from now on”. Changing the input invalidates the preview, and the button says “preview” again. Submission checks the preview's identity and game. A preview alone changes no list.

**Missing Mods**: below “not installed: N”, explain that subscribed Mods take their place in the list once downloaded. “subscribe all N” (`M`) at the right first asks the player to choose Steam subscription or SteamCMD download, then queues the Mods with known Workshop pages as one task (`subscribe workshop <id…>`, §2.16). For the others, say that N Mods have no Workshop page and must be found by hand. Each row keeps “subscribe” or “not on the Workshop list”. After download and scanning, `loadout.Registry.Heal` replaces the missing entries with the installed Mods in place. The editor's import subpage shares this block. Can it run gathers a list's uninstalled Mods into one item (§5).

**Import subpage** (editor `i`, onboarding, or a file dropped outside the import area; no dialog): on All lists, `i` uses the import inside creation described above; the editor keeps a separate flow with a choice of destination. The breadcrumb is “library / lists / import”, the sidebar stays on all lists, and “cancel” (`esc`) is at the right. A text input accepts a share code, a Steam collection link, a Rentry link or a package name, with “choose a file…” beside it. After reading, the preview (07 §7.1) shows the name, the source, the game version (amber if it differs from the current game), the installed and missing Mod counts with Workshop subscription for the missing ones, and the suggested allowed versions. Below are three destinations: a new list, replacing the selected list (with added, removed and moved counts), or adding only the missing Mods. A Steam collection adds “follow this collection from now on”, checked by default. The Import button's hover text says that no game files are written. After the import, the page returns to All lists with the imported list selected.

**Keys**: `↑↓` selects a list; `enter` opens the editor; `n` opens new / import (there are no Mods on this page, so it does not mean note, §3.5); `i` opens import mode; `F2` renames inline; `D` duplicates; `Delete` deletes after confirmation; `e` exports; `B` creates a pack; and `tab` moves into the right-side controls. In the form, `esc` closes it. The hint shows “pick a list”, edit, new / import, rename, duplicate, export and all keys. The form's hint shows enter with preview or create and edit, and esc close.

**Loading cost**: between game versions and the followed collections, show “Loaded memory (estimate)”: resident RAM and VRAM including Core and DLC, and the loading RAM budget. Resident means stable main-menu private bytes; loading means peak private bytes from startup to the main menu. Neither means working set. “what is counted” expands the categories, the five largest contributors by RAM and by VRAM, and the limits of the estimate. The measurement runs in the background after the page renders; stale results are discarded when the list or game changes. Data comes from `app.PlanLoadCost`, `loadcost.Estimate` / `Baseline` / `LoadingBudget` / `Spill` and `view.PlanLoadCost`; the CLI command is `archo plan cost [<list>] [--mods] [--json]`. The model code is the only source of coefficients. Unity 1.6 estimates use the vanilla baseline, the per-Mod overhead and the texture curve calibrated in VM measurements. Combined texture and DDS payloads were measured up to 7.5 GiB; larger payloads are extrapolated. The VM's graphics adapter has no dedicated VRAM, so its private bytes include the driver's copy of every texture: 1.2 bytes per payload byte (`Coef.TextureGPU16`) and 0.66 GiB for vanilla. The model reports that share as VRAM and the rest of the curve as RAM. `loadcost.Spill` moves back to RAM the 1.6 VRAM beyond `Coef.UsableVRAM` (90%) of the dedicated capacity, or all of it when no dedicated VRAM is reported (VM, integrated GPU, unreadable adapter); resident RAM, the loading budget and the §2.4 comparison include it and say how much it is. Without dedicated VRAM, every estimate equals the VM curve; on a real graphics card the split is inferred, not measured. Loading budgets estimate the startup peak private bytes from the payload and follow the same curve. Coefficients are owned by `loadcost.Coef`, `Baseline` and `LoadingBudget`; evidence and limits: [Unity 1.6 heavy-texture memory](../../research/2026-11-01_unity16-heavy-texture-memory.md) and [Unity 1.6 texture memory breakdown](../../research/2026-11-01_unity16-texture-memory-breakdown.md). 1.7 coefficients come from one RTX 4090 (24 GB) run (research 2026-10-24 §4); there the VRAM upper bound was the engine's upload watermark, not the textures' size. 1.7 uploads textures on demand and, above `loadcost.Watermark17` of the card (Waylith 1.7.5000 `TextureResidency.HighWatermark` of a driver budget taken as `Coef.Tex17Budget` × dedicated VRAM), evicts least-recently-used ones to its disk cache. `loadcost.Cap17` therefore caps texture and DDS VRAM at the watermark less the vanilla baseline, and their RAM at `Coef.Tex17RAMPerVRAMLow` / `High` × that room (mod RAM measured 1.1–2.1× the resident mod VRAM). `app.LoadCost.FitTo` applies it together with `Spill` to the shown and compared totals; the per-category rows stay uncapped. Without a readable dedicated card nothing is capped. The capped totals on smaller cards are inferred from the engine code, not measured. The 1.7 loading reserve is not calibrated. Saves, maps, AssetBundles and Mod allocations may go beyond the estimate. A change to the per-Mod raw measurement format invalidates the file-fingerprint cache; a model change invalidates the estimate totals. All lists uses the selected game environment, or an explicit version override, to choose coefficients and LoadFolders, not the version saved in the plan's history. An unknown version asks for a rescan. Hardware comparisons and levels: §2.4.

**Data**: `view.BuildPlanManage` provides the rows, the selected details, the allowed versions and, for each version, the number of Mods that do not declare support for it. `view.PlanCollections` provides the followed collections and their changes from the cache; network checks are queued as background tasks (§2.16). `view.ExportPreview` provides the full export. The GUI APIs `PlanVersions`, `PlanFollow`, `PlanUnfollow`, `PlanSync` and `PlanExport` share the CLI's app functions (07 §1.6, §7.6). In the TUI, versions and collections in `P` list switching (§9.1) are **not implemented**; export stays in the command panel.
