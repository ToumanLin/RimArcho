### 2.5 Plan editor

The plan page is the editor. It is implemented, including support for multiple plans; staging and history belong to each plan (07 §1, §2.2, §3). The all lists page (§2.17), sidebar context menu, `P`, and command panel provide new / import, rename, duplicate, and delete. New / import uses one form for an empty list, a copy of a list or version, a save, or an import. Renaming checks for duplicate names as the player types and is inline on all lists. Deletion requires confirmation and cannot remove the last plan. The plan currently written to ModsConfig.xml (the write record, 07 §1.3) no longer appears in the status line. With multiple plans, its sidebar child has a green dot with the tooltip the game is using <plan> v<n>. Home has no marker because the large card already shows the applied item; a single plan needs no marker. An unloaded external version adds an amber marker to the sidebar entry, plan page, and home row. The editor head actions changed on 2026-10-26: the amber external-version marker when needed, N unsaved, rename, delete, import / export (opens all lists with this list selected; import, export, and sharing live there, §2.17), and save changes (`w`, showing no changes and disabled when unchanged). The final solid button is launch for the current list (`L`, which visits launch), or make current for another list, which does not write game files. The launching X / make current hint, ⋯ menu, and build button are removed; building is on the packs page. The editor shows no environment chip. Undo is in the Enabled header, to the left of sort. Hide key hints below 1100px.

**Open and current lists** (decided 2026-10-25, 07 §1.3): opening a list from the sidebar, panel, or all lists shows it for editing without changing the current list used by the launch headline, launching, and CLI. Can it run, inventory, and building follow the open list. If it differs from the current list, the page head begins with muted launching <current list> text and a make current link; below 1280px, only the link remains. Saving this list or clicking launch makes it current.

**Page head** (since 2026-10-22, like other pages, §2.2): below the breadcrumbs, show muted 34 enabled text. Actions at the right are the external-version notice, N unsaved, undo, import / export, build, save, the ⋯ plan menu, and launch. Automatic sorting is in the Enabled header as sort S and acts only on that list.
- Undo uses u. Import and export use i / e and open their subpages (§2.17, 07 §7); the old panel is removed. S sorts immediately and reports sorted: N moved, K strong requirements satisfied, or only weaker requirements remain unmet, followed by undo. The panel's sort preview adds a why section listing each requirement violated by the current order, marked strong, weak, or harmless, with strong requirements first (08 §1.3). Build opens the subpage (§2.6). w writes ModsConfig.xml without launching, for players who launch through Steam or another route (09 §2).
- **The launch button, L, and the editor panel's launch action do not launch directly.** They visit launch (§2.3), make this list current and applied, and focus ▶ launch game. If another list is open, make it current first; if a pack was applied on launch, switch back to the current plan. Another L or Enter launches the game (decided 2026-10-22: launching happens only on launch). CLI and MCP launch remain unchanged. The TUI behaves the same with its simple launch page since 2026-10-31 (§9.1).
- All three actions require one click or key, without confirmation (§6). A refusal, such as a running game, unloaded outside changes, or a missing user data directory, reports its reason in the status line. A refusal that provides commands also opens a read-only dialog listing them. To preview writes and link creation or removal, use the panel's preview sort / save / launch (`view.DryRun`) or `archo … --dry-run`.
- List import and export (07 §7) are also in the action menu and command panel (`i` / `e`, §3.5). Export opens this list's export subpage; import opens the same import subpage as all lists (§2.17).

The backend also returns each Mod's finding count, maximum severity, short summary, and directly executable fixes. List-level findings share the needs cache, and edit results and events return updated summaries. The contract is in [8.7](8-gui-technology.md#87-list-findings-and-needs-cache-api).

See §5 for version hints in rows, their aggregate, ignored count, and restore entry. The problem panel still opens for inspection and restoration even when every version hint is ignored.

**Filters** (2026-10-25, shared with inventory > all): the filter bar sits at the top left, above details and history. When collapsed, it contains a search box, clear button, and filter toggle (`\`). Conditions live in the query text: clicking local adds source:local, without a permanent chip. Clicking search or pressing slash or ctrl+f opens a small popup below the input. It first shows available keys, then matches the current word against keys or values. Ghost text previews the completion; arrows select a candidate, Tab accepts it, and Enter ends input. The popup shows no Mod counts or duplicate values. Fixed help is localized, while author, tag, and custom-directory names remain unchanged (§3.7).

The filter toggle or backslash expands lists first, then tags, sources, and content; other keys are reached through search completion. The lists group offers every list except the one being edited and filters available copies by membership (see §3.7). The current launch list, when offered, comes first and is marked current list. Sources use directory roles: Workshop, SteamCMD, local, lock library, official, and other directories. Custom directories also show their names with stable source:<alias> values. Raw paths are not candidates, but remain copyable in details (03 §2.2). Each group initially shows up to 24 common values and counts, with a clickable N more to expand the rest and collapse to close it. There is no group-specific search; all searching uses the query above. Click, Enter, or Space includes a value; right-click or x excludes it; choosing it again withdraws the condition. Conditions follow §3.7 whether typed or clicked. Membership is loaded once with the board and refreshed after database changes; group building performs no per-row database reads.

Expanded filters take 35% of the left column by default, with a minimum of 120px, leaving the rest to details and history. Drag the gap between cards to redistribute the height, including the full height; double-click restores 35%. `ctrl+↑↓` moves it 40px per press. The settings remain `ui.gui.filter.split:plan` and `ui.gui.filter.split:library`. Losing focus collapses the bar immediately while retaining the query. Up/down changes groups, and left/right changes values, including expand and collapse buttons. Typing enters the query above with the current group's key; `esc` or backslash collapses the bar. Staging keeps its separate search.

- With filtering, positions always refer to the full load order. m numbers and before/after targets use the complete list, including hidden candidates (§3.6). Space enables at the suggested `App.SuggestAt` position independently of the filter. Dropping on a row uses that row's number. J / K cross the next **displayed** row: the moved row swaps with its filtered neighbor, landing immediately after it for J or before it for K in the full list. `alt+J` / `alt+K` cross 10 displayed rows. Without a filter, these retain the original 1-position and 10-position moves (`view.StepAt`, `TestStepAt`).

The GUI left column contains filters, compact details, collapsible sorting rules, and collapsible history, in that order. The middle is Enabled; the right contains Disabled and collapsible Staging. Staging defaults to open when populated and closed when empty; history defaults to closed. Preferences persist per browser. Expanded history defaults to 25% of the left height, with a minimum of 72px. Staging follows content height up to 38% of its parent, unless a custom dragged height takes precedence. Adjacent cards can be resized. Pressing 3 expands and focuses Staging, and dropping on its heading also works; t, space, and T are unchanged. `←→` follows the physical order details / Enabled / Disabled, while numbers `1`–`4` retain the logical order Disabled / Enabled / Staging / details.

- A basic row contains a muted, right-aligned number in Enabled only, a source icon, name, and status icon. Enabled Mods with multiple copies add the current copy below, such as └ locked version 2026/10/21 14:27. Disabled groups copies by Mod, showing abstract copy labels below the name. Each copy can be selected, enabled, or dragged; other disabled copies remain visible when one copy is enabled. Virtual scrolling, paging, and drop positions use actual row heights.
- Use the alias when present. Truncate Chinese names by display width without splitting a character.
- Rows that differ from the last save have an accent ● after the name.
- An unloadable Mod's entire row is muted.
- No area shows tags in rows. Read and edit them in details (§4.1), or search with tag: (§3.7).
- Status icons appear only on Mods involved in actionable can it run items, so they agree with badge counts (§5).

**Staging** (07 §2.2) persists in RimArcho and is never written to game files. It has two uses:
- **Preparation**: new subscriptions wait here until the player decides to enable them.
- **Investigation**: stage a batch of enabled Mods to investigate a problem, then restore their original positions in one action.
- Each Mod staged from Enabled remembers its original position and the preceding Mod as an anchor. Skip predecessors that were already staged, so the order of batch staging does not affect restoration. On restore, follow anchor chains through still-staged Mods, falling back to the original position if no anchor is found.
- add, drop, and restore each create one undo step, including edits that only change Staging. Undo and redo restore the enabled list as well as staging entries, order, original positions, and anchors. Reenabling a staged Mod by any route, including undo, enable, checkout, or import, persistently removes it from Staging within that edit. See 07 §2.2 for compatibility with old history.
- Use `archo stage list|add|drop|restore` (13 §4). Each plan has its own meta entry, `stage:<plan ID>`.
- T restores all staged Mods to their original positions. In Staging, t or space restores one.

**History** appears below the left details in the GUI and in the TUI's third column, filling it when Staging is empty:
- **This session's changes** lists undo steps newest first, one per row, such as enable Harmony position 2. `view.StepText` derives the text from the before and after lists. The cursor points to now, with redo steps muted above it. u / ctrl+r move now. Clicking a step, or selecting it and pressing Enter in the TUI, immediately returns to it; undo and redo still work afterward.
- **Versions** lists saved, launch, external, imported, and other plan versions, marked with their source (07 §3). Selection shows the diff from the current list. Enter or go back to this version directly runs `loadout checkout` without confirmation: the prior list remains in history, and u restores it (§6). An identical list only reports no changes, with no undo hint and no source or history change (07 §3.2).
- GUI history is a collapsible history N steps section, regardless of Staging contents. H opens a picker for steps and versions, navigated with arrows and Enter. Since 2026-10-31, TUI H opens the same picker (`view.HistoryItems`), initially selecting now. It remains available when populated or searched Staging hides area 3 history.
- When area 3 shows history, arrows, g / G, and Home / End navigate it; Enter returns to the selected step.

**Sorting rules** (2026-10-30, GUI `rules.js`, `view.BuildRules`, 08 §2.1): this permanent collapsible section sits below details and above history on the left. Its heading is sorting rules N, or just sorting rules when N is 0. It defaults to closed and persists per browser. When expanded, it takes at most 40% of the left column and has a draggable gap (`ui.gui.plan.rules`). Since 2026-10-31, the panel's sorting rules action expands the section and focuses its scope switch.
- Rules are global across games and lists. The first row switches between current list and all rules. **Current list is the default** because only rules with A or B enabled affect sorting in the edited list (08 §2.1); rules for other games or lists add noise here. Switch to all rules for global organization. The scope persists per browser without explanatory text. A rule is in the current list when any of its Mods is enabled (`RuleRow.InList`); an ignore rule uses its constrained Mod. Staged and disabled Mods do not count. N is the visible count after scope filtering. A row being edited remains visible until its form closes.
- Each rule is one sentence, newest first: Combat Extended after Dubs Bad Hygiene; RimHUD near start; ignore X's About.xml loadAfter Y. A muted note appears below. Clicking a Mod name jumps to its list row as in the panel; vanished Mods are muted and inert. Hover shows r:<n> and the creation time.
- Hovering or focusing a row reveals edit and delete at the right. Edit replaces the row with an inline form. Delete is immediate and shows removed rule … undo in the status line. Undo, or an immediate u, restores the original r:<n>. Rules are not list edits and do not enter the list's undo stack or history.
- Add a rule with r at the cursor Mod or add rule r at the bottom of the section. The inline form opens at the top (§3.1 rule 7), with the Mod name, kind (after, before, immediately after, incompatible, near start, or near end, using the row sentence's wording), another Mod, and an optional note. Typing the other Mod's name shows up to 6 distinct candidates, excluding the rule's own Mod, with enabled Mods first and numbered. Arrows choose a candidate; Enter or Tab accepts it. Enter saves; Esc closes candidates first, then the form. While this section has focus, it owns the keys and never passes them to list verbs.
- The form cannot create ignore rules. Suppress constraints through needs ignore or the references printed by archo sort (08 §2.2). Existing ignore rules only allow note editing and deletion here.
- A change rereads the editor and updates order findings, row icons, and the can it run badge without sorting automatically.
- **TUI** (2026-10-31, `surface/tui/rules.go`): sorting rules use a secondary screen rather than a left column. Editor r opens the form for the cursor Mod; the panel's rules action also opens the screen. Esc returns to the editor, and the position line shows sorting rules N / M. It uses the same model and scope switch; a toggles the scope, stored in meta `ui.tui.rules.scope`. Enter edits, Del deletes, an immediate u restores the deletion, o locates the rule's Mod in the list, and r adds another rule. The form has the same fields as the GUI. Tab / shift+Tab changes fields, left/right changes the kind, and candidate arrows with Enter or Tab select the other Mod. Letters are input while the form is open. The old after|before|… <ref> input in the hint line is removed; :archo rule add remains available.

**Widths and wrapping**:
- The three list areas have adjustable widths. In the TUI, < > shrink or widen the focused area by 2 cells, and = restores default widths without changing wrapping. The GUI has two column splitters, between the left column and Enabled, and between Enabled and the right column. Drag to resize or double-click to restore 38 : 31 : 31. The GUI keyboard equivalents use < > in 24px steps and = to reset.
- Store widths per environment in meta: TUI `ui.columns:<environment id>`, GUI `ui.gui.columns.v2:<environment name>`, in left / enabled / right order. Do not apply old-layout widths to the new layout. GUI and TUI values are separate layout state, not settings.
- Details need at least 40 cells. If space is insufficient, shrink the widest unfocused column first, to a minimum of 12 cells.
- In the TUI, z toggles focused-area name wrapping, saved per area. Long names wrap by display width, with continuation lines aligned under the name and retaining the selection background. The number, source, and status appear only on the first line; ● appears on the last. Wrapped rows show no tags, and the cursor row is always fully visible.

### 2.6 Build a pack

This implemented subpage belongs to the current plan: GUI `packs.js`, `API.BuildPage` → `view.BuildPageOf`, and `archo pack build` (10 §2). Open it through build in the editor head or the packs page action B. Breadcrumbs are library / lists / <plan> / create a pack, and the sidebar stays on the plan. The upper-right cancel or Esc returns to the editor. Use the create-a-pack layout from the historical RimArcho interface-design HTML prototype, with the current visual colors.
- **Left**: basic information contains the name, defaulting to <plan> <date>, with an explanation below when invalid or duplicated (`API.PackNameCheck`). The full / light choice was removed on 2026-10-22: packs always include files; share only the list through pack export list (§2.7). The what happens when creating card has five numbered rows, each with a bold title and sentence: 1 can it run; 2 remove unused; 3 textures (10 §2); lock versions; put in place. An error-level finding makes row 1's number a red !, shows N remaining errors, lists them, and provides go fix to needs. Otherwise, explain that sorting is specific to this pack, how many items move, and how many Mods lack declared version support, in amber. Row 2 retains only current-version content and reports how many Mods have other-version directories and the savings. Insufficient space or unreadable Mods are red; the row is muted until findings are fixed. Put in place writes the pack folder with its own saves and settings, leaving plan saves unaffected. During building, completed rows show checks and the current row shows a breathing circle. Pruning and locking happen together during copying. A progress bar and stop appear below (`view.ProgressOf`, with a Key for each row).
- **Textures** (`view.textureStep`): the selector has eight choices: no conversion, which copies PNG unchanged and is the default; pre-convert full size; and slim to 80 / 75 / 60 / 50 / 40 / 25% (`view.PackTextureChoices`, stored in `B.tex`). Opening measures no conversion. Changing the choice does not measure again (2026-10-24: reading PNG files takes tens of seconds). The row asks the player to select an option and scan statistics to see the file count and final size, with scan statistics on the right; the summary shows not measured for this option. An explicit scan calls `API.BuildPage(tex)` to measure the files, final size, and conversion peak in the background (§3.1 rule 9). Size fields show shimmer placeholders, and build is disabled until results arrive. Building without a measurement is allowed: `BuildPage.ToolOK` tracks todds separately, and the build itself rechecks peak space. Below, no conversion explains the benefit of DDS. A conversion shows N PNG → DDS, no PNG in pack, video memory A → B, final X / peak Y. List retained PNG counts for same-name DDS or other formats below, along with an amber warning if the pack grows. Check space against the peak; show the final size in the summary. If todds is missing, make the row red and show not installed: library > texture optimization with go install. Disable build and show install todds or do not convert, linking to texture optimization. This page never downloads todds. D selects the next choice and appears in help; Tab reaches the selector and arrows change it. The preview uses the same --textures [--texture-scale N].
- **Right summary**: show the name, environment, Mod count, before → after size once findings are fixed, own saves that are initially empty, and pack.dir. Below are build (B or Enter in the name) and see the list first, no disk (V).
- **Disabled build** (G14): errors disable building, with a red fix N problems link below the button to can it run. Insufficient space, unreadable Mods, an invalid name, or another build also disable it and show the reason.
- **Preview**: expand `archo pack build --dry-run` inline below the summary (`API.PackDryRun`), without writing to disk. Repeat the action or press Esc to collapse it. It is not a dialog (§3.1 rule 7).
- **Sizes require traversing Mod folders**: show the page first, perform checks under the lock, and measure in the background outside the lock with `PackPlan.Measure`. Fill in sizes when ready.
- **Unfinished builds** appear below through `view.UnfinishedRows`. Builds in another window show progress and stop. Interrupted builds offer rebuild or delete copied files. These unfinished artifacts belong to RimArcho and are deleted directly rather than recycled (10 §2).
- Building runs in a subprocess and opens the pack page on completion.

### 2.7 Packs

Packs are implemented in GUI `packs.js`; the TUI panel's packs action shows text with commands.
- The list shows each pack's name, Mod count, size, full build-time game version (03 §3.1), and last played time (`view.PackRows`). Click or Enter opens a pack, and arrows navigate. The page's build action uses B; unfinished builds appear above the list.
- Each pack is a sidebar child (`view.Nav`), like each plan. In the TUI, Tab / shift+tab switches sibling packs (§3.5) and Tab from the list opens the first pack; in the GUI they move the focus, and the sidebar, or ↑↓ and Enter on the list, open a pack.
- A pack page (`API.Pack` → `view.BuildPackPage`) shows spaced facts in the head: N Mods, size, supported versions, build date and environment, and last played. Actions are export (e, a save dialog, `pack export`); export list (E, a versioned RimArcho `.archolist.json` for sharing, `pack export --list`, 07 §7.3); recycle (Del, confirmed `pack remove`); and solid launch (L, `archo pack launch`, 10 §3). Below, Mods appear in load order with sizes and removed version directories; Core and DLC say from game. The folder location comes last.
- **Compare with game** (2026-10-24, 10 §5): a line after the facts appears only for a warning or error. Examples are created for 1.6.4633 rev1261, game 1.6.4871 rev590 in amber; missing DLC Biotech in red; and modified copies in red, naming the Mods. Info such as a missing recorded build or extra DLC appears only on hover. Errors disable launch, with a tooltip explaining why. `view.BuildPackPage` obtains `Check` from `app.CheckPack`. The page does not recompute digests; copies are verified during import and pack check.
- Import through the first-run guide's open action only extracts `.archopack`, supporting v1 zip and v2 tar+zstd (10 §4). The result reports verification and comparison (`pack import`). List files, including RimArcho lists, and collection links use the import preview. RimArcho lists mark Mods with different versions there (07 §7.1).

### 2.8 Environments

The GUI environment page opens through the pill; TUI E switches or deletes environments. These are implemented using `view.BuildEnvPage` and `view.EnvGroups`.
- All environments show their name, version, game directory, and current marker. Clicking one switches to it.
- **Remove** (2026-10-22): use remove game at the row end, Delete in the GUI panel's environment picker, or d in TUI E. `app.EnvRemovePreview` → `view.EnvRemovalLines` provides a preview and one confirmation. RimArcho forgets launch records, Mod identities read from Data / Mods, and that environment's history. Plans are shared globally and retained (07 §1.7). The game directory, all Mods, saves, shared folders, and player-authored Mod data remain. Refuse while that game is running. Removing the current environment first switches to another; if none remain, the GUI opens the add guide. CLI env remove <name> previews without --yes.
- Current directories include the game and user data directories (`env set --game|--user-data`, checking that the Mods are still the same and suggesting env rebind before a change, 03 §4.2), Workshop, SteamCMD, and extras. Removing a source forgets the folder but retains its files. Add a SteamCMD directory whose Mods can be enabled and linked into `Mods/` on write (09 §3), or add other Mod directories. Paths are entered directly without a system picker.
- Launch settings include steam / direct (`env set --launch`) and extra arguments (`env set --launch-args`), such as -popupwindow, stored in `env:<id>:launch_args`.
- Adding an environment uses the first step of the guide (§2.15).
