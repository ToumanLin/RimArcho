### 2.5 Plan editor

The plan page is the editor. Staging and history belong to each plan (07 §1, §2.2, §3). All lists (§2.17), the sidebar context menu, `P` and the command panel provide new / import, rename, duplicate and delete. New / import uses one form for an empty list, a copy of a list or version, a save, or an import. Renaming checks for duplicate names as the player types and is inline on All lists. Deletion needs confirmation and cannot remove the last plan. The status line does not name the plan written to ModsConfig.xml (the write record, 07 §1.3). With several plans, that plan's sidebar entry has a green dot with the tooltip the game is using <plan> v<n>. Launch has no marker because its large headline already shows the applied item; a single plan needs no marker. An outside version that has not been loaded adds an amber marker to the sidebar entry, the plan page and the Launch row.

**Open and current lists** (07 §1.3): opening a list from the sidebar, the command panel or All lists shows it for editing without changing the current list used by the Launch headline, by launching and by the CLI. Can it run, the Mod library and building follow the open list; Can it run's head names it (§2.4). Saving this list makes it current. A window whose open list is the current one follows a switch of the current list made anywhere else (`archo plan use`, MCP, another window), at its next read, a page reload included; a list the player opened here while another one is current stays open (`app.App.followCurrent`).

**Page head** (as on other pages, §2.2): below the breadcrumbs, a muted line says N enabled (its hover: "N enabled, in the order the game loads them"). The head stays one line: when the actions grow, the line is cut with an ellipsis (its hover keeps it whole) instead of the actions wrapping and pushing the lists down. The actions at the right (`planhead.js`) are three groups, in order. What the list has: N problems ("1 problem" for one; `p`, the problem panel, §5) when the list has something to fix (while its findings are `updating`, §8.7, its dot is a spinning ring, its count is faded and its tooltip starts with "updating…", so old findings do not read as current), and the amber outside-version marker when needed. The tools, as quiet icons without words (the word is the hover and the accessible name, §7 principle 9): rescan (`R`), rename, import/export (opens All lists with this list selected; import, export and sharing are there, §2.17) and delete (red on hover). Saving: save (`w`) with the number of unsaved changes as its badge, which is the only persistent display of that count (its hover: N unsaved, and that launching or saving writes them to the game); "no changes" and disabled when nothing changed. The last, solid button is launch (`L`, starts the game from here) for the current list, or "set current" for another list; the set current tooltip names the list the game is launched with and says that no game file is written. There is no ⋯ menu; building starts on the packs page (§2.6). The editor shows no Game Config chip. Undo is in the Enabled header, to the left of sort. Automatic sorting is in the Enabled header as sort `S` and acts only on that list. Key hints are hidden below 1100px.
- Undo uses `u`. Import and export use `i` / `e` and open their sub-pages (§2.17, 07 §7). `S` sorts at once and reports sorted: N moved, K strong requirements satisfied, or only weaker requirements remain unmet, followed by undo. When the sort finds required Mods that are not enabled, recommended replacements or entries with no folder, the steps after a sort open: one step at a time, each previewed, then applied or skipped on its own (§6.1). The command panel's sort preview adds a why section listing each requirement the current order violates, marked strong, weak or harmless, with strong requirements first (08 §1.3). `w` writes ModsConfig.xml without launching, for players who launch through Steam or another route (09 §2).
- **The launch button, `L` and the command panel's launch action start the game from the editor**, keeping the player on the list (GitHub issue #6). `editorlaunch.js` refuses launch while a game is running or the window is busy before it checks for unsaved changes. If the list has unsaved changes, the dialog shows their count and explains that launching saves the edits to the game. **Save and launch** continues, and Cancel or `esc` leaves the current plan and game files untouched. The launch then makes the open plan current if needed and runs the same checks as Launch's ▶ (§2.3): a severe RAM estimate asks once (09 §2, `API.HomeMemory`), missing required Mods ask once, and `API.Run` saves unsaved changes to the game and launches, or refuses with the reason (a running game, outside changes not loaded). A pack applied on Launch gives way: a plan launch clears `ui.gui.home.pack`, so Launch's headline names the plan that runs. The status line says "starting…", then the outcome. CLI and MCP launch directly too. The TUI editor's `L` still opens its simple Launch page, where a second `L` launches (§9.1).
- A refusal, such as a running game, outside changes not yet loaded, or a missing user data directory, gives its reason in the status line. A refusal that comes with commands also opens a read-only dialog listing them. To preview writes and link creation or removal, use the command panel's preview sort / save / launch (`view.DryRun`) or `archo … --dry-run`.
- List import and export (07 §7) are also in the command panel (`i` / `e`, §3.5). Export opens this list's export sub-page; import opens the same import sub-page as All lists (§2.17).

**Four areas**: the TUI uses four columns. The GUI uses three: filters, details, rules and history | Enabled | Disabled and Staging, with default widths of 38 : 31 : 31.

| Area | Content | TUI width at 160 columns |
| --- | --- | --- |
| 1 Disabled | Installed but disabled Mods: new Mods first, then in the chosen order (by name by default) | About 30 |
| 2 Enabled | Load order | About 40 |
| 3 Staging / history | In the TUI, Staging, when it has entries, appears above this plan's history; empty Staging leaves the whole column to history. In the GUI, Staging is below Disabled on the right, and history is below details on the left | About 26 |
| 4 Details | Details for the Mod under the cursor (§4) | The remaining width, at least 40 |

Data comes from `view.BuildBoard` for the columns and counts, `view.HistoryItems` for history, and `view.LoadDetail` for details.

The backend also returns each Mod's finding count, maximum severity, short summary and directly executable fixes. List-level findings share the needs cache, and edit results and events return updated summaries. The contract is in [8.7](8-gui-technology.md#87-list-findings-and-needs-cache-api).

See §5 for version hints in rows, their aggregate, the ignored count and the restore entry. The problem panel still opens for inspection and restoring even when every version hint is ignored.

**Filters** (shared with Mod library › All mods): the filter bar sits at the top left, above details and history. Collapsed, it has a search box, a clear button and the filter toggle (`\`). Conditions live in the query text: clicking local adds source:local, without a permanent chip. Clicking search or pressing `/` or `ctrl+f` opens a small popup below the input. It first shows the available keys, then matches the current word against keys or values. Ghost text previews the completion; arrows select a candidate, Tab accepts it, and Enter ends input. The popup shows no Mod counts or duplicate values. Fixed help is localized, while author, tag and custom-directory names stay unchanged (§3.7). Opening another list (sidebar, command panel, All lists, set current) empties the bar's search and filters, like the cursors and selections; the bar's matches are positions in one board's lists, so they are read again for every board read, even when the database did not change (opening a list only changes which plan is shown).

The filter toggle or backslash expands lists first, then tags (ending with no tag, `has:notag`, §3.7), sources, categories (`category:`, below) and content; other keys are reached through search completion. The added group (`added:`) has new (the Mods marked new above), within a week, within a month, within half a year and earlier, counted from when a scan first found the Mod. The lists group offers every list except the one being edited and filters available copies by membership (§3.7). The current list, when offered, comes first and is marked current list. Sources use directory roles: Workshop, SteamCMD, local, lock library, official and other directories. Custom directories also show their names, with stable source:<alias> values. Raw paths are not candidates but stay copyable in details (03 §2.2). Each group first shows up to 24 common values with counts, with a clickable N more to expand the rest and collapse to close them. There is no search within a group; all searching uses the query above. Click, Enter or Space includes a value; right-click or `x` excludes it; choosing it again withdraws the condition. Conditions follow §3.7 whether typed or clicked. Membership is loaded once with the board and refreshed after database changes; building the groups reads nothing from the database per row.

Expanded filters take 35% of the left column by default, at least 120px, leaving the rest to details and history. Dragging the gap between cards redistributes the height, up to the full height; double-click restores 35%. `ctrl+↑↓` moves it 40px per press. The settings are `ui.gui.filter.split:plan` and `ui.gui.filter.split:library`. Losing focus collapses the bar at once and keeps the query. Up/down changes groups, and left/right changes values, including the expand and collapse buttons. Typing enters the query above with the current group's key; `esc` or backslash collapses the bar. Staging keeps its own search.

- With a filter, positions always refer to the full load order. `m` numbers and before/after targets use the complete list, including hidden candidates (§3.6). Space enables at the suggested `App.SuggestAt` position, whatever the filter. Dropping on a row uses that row's number. `J` / `K` cross the next **displayed** row: the moved row swaps with its filtered neighbor, landing just after it for `J` or just before it for `K` in the full list. `alt+J` / `alt+K` cross 10 displayed rows. Without a filter, they move 1 and 10 positions (`view.StepAt`, `TestStepAt`).

The GUI left column has filters, compact details, collapsible sorting rules and collapsible history, in that order. The middle is Enabled; the right has Disabled and collapsible Staging. Staging is open by default when it has entries and closed when empty; history is closed by default. These choices persist per browser. Expanded history takes 25% of the left height by default, at least 72px. Staging follows its content height up to 38% of its parent, unless the player has dragged it to another height. Adjacent cards can be resized. Pressing `3` expands and focuses Staging, and dropping on its heading also works; `t`, space and `T` are unchanged. `←→` follows the physical order details / Enabled / Disabled, while `1`–`4` keep the logical order Disabled / Enabled / Staging / details.

- A basic row has a tag colour band (§3.8, empty when the Mod's first tag has no colour), a muted, right-aligned number (in Enabled only), a source icon (not in the window's Disabled, where copies are told apart by their labels; the TUI keeps it as a fixed column), the name and a status icon. Enabled Mods with several copies add the current copy below, such as └ locked version 2026/10/21 14:27. Disabled groups copies by Mod, with abstract copy labels below the name. Each copy can be selected, enabled or dragged; the other disabled copies stay visible when one copy is enabled. Virtual scrolling, paging and drop positions use actual row heights.
- The alias is used when there is one. Names are truncated by display width without splitting a wide character.
- Rows that differ from the last save have an accent ● after the name.
- **New Mods**: a Mod that a scan first found within the last 7 days (`app.NewFor`) has an accent `new` chip after its name, in every column, and comes first in Disabled's individual view, so a Mod just subscribed is at the top. The time is the Mod's earliest copy's `first_seen` (`app.Added`), so a locked version or another copy of a Mod already there is not new. Mods found by the installation's first finished scan that read every source are never new (`app.NewSince`: that scan finds everything already installed; a `--game-only` or source-limited scan, stats `partial`, does not count). Archo Monitor is never new: RimArcho installs it. In the tags view a new Mod stays under its first tag, first within it; `added:new` lists the new Mods in either view. The TUI shows `new` after the name. The mark goes when the week is over; nothing clears it sooner.
- An unloadable Mod's whole row is muted.
- **Categories**: a quiet glyph before the name (GUI only) says what kind of Mod it is; the category's name is its hover. The details do not show it (2026-11-25: its reason read as noise); `archo category <ref>` prints the reason. See "Mod categories" below.
- No area shows tags in rows. Read and edit them in details (§4.1), or search with tag: (§3.7). Disabled's tags view (below) shows a tag only as a group's header. The details' tags (below) are the Tag manager, whose all tags ends with no tag and the enabled Mods without one.
- **Disabled order** (GitHub #5): the Disabled heading has a sort choice before the view switch: A-Z (default), last updated (the Workshop's `timeupdated`; Mods without one, such as local Mods, follow), files modified (the Mod folder's modification time) and added (`app.Added`, when a scan first found the Mod). Times sort newest first; Mods with the same or no time follow by name. A Mod's copies stay together under its newest copy's time. **New Mods stay first in every order**, so a Mod just subscribed is always at the top; the order applies within the new Mods and within the rest. Go sorts the rows (`view.sortDisabled`) and the choice is kept in `ui.gui.plan.disabledsort` (`view.DisabledSortKey`); changing it reads the board again. Only files modified reads the disk: one folder stat per disabled copy, only while that order is chosen. The tags view keeps this order within each group. The TUI shows the order chosen in the window.
- **Disabled views** (GUI, `disabledgroups.js`): the Disabled heading ends with collapse all / expand all (tags view only) and an individual | tags switch (`v` from any editor area), kept in `ui.gui.plan.disabled`. Individual is the list above, with its copy groups. Tags puts a header row before each tag's rows: the tag's colour as a band in the rows' left slot when the board's `tagColors` has one (in line with its rows' bands, as on Mod library's Tags view), a chevron, the tag, and how many of its rows are shown (`3 / 5` when the filter hides some). A Mod sits under its **first** tag only (its tags' order, 07 §6.1), so each copy is still one row and the cursor, selection, dragging and the verbs work on unique rows; Mods without tags gather under no tag at the end. Groups follow the Tag manager's order (§3.8: pinned first, then by Mod count, `API.TagList`, read again when the data changes); rows keep the column's order and copy groups within a group. While filtered, a group shows only matching rows and a group with none is left out.
  - **The cursor lands on headers**, as in the Mod library's Tags view (§2.9): `↓` from a closed group's header goes to the next header. On a header, `←` closes an open group and `→` opens a closed one; otherwise the arrows change areas as usual. Enter and a click also toggle it; a double click does not enable. ctrl+click on a header selects its shown rows (again: unselects them); shift ranges and ctrl+a take only rows, and a closed group's rows are not shown. Space, `t`, `m`, `g` and the row menu do nothing on a header. Closing the group the cursor is in moves the cursor to its header; a row that moves into a closed group (undo, disable) leaves the Disabled cursor on that header. Full details' `←` `→` step past headers, and a jump to a Mod (command panel) opens its group.
  - **The details on a header are the Tag manager** (§2.9), as on Mod library's Tags view: the details area's heading becomes tags, the tag, and filter to this tag; the panel is the same (`tagmanager.js`: note, name, keep on top, facts, colour, similar, rename / merge into… / delete tag, all tags). On a header with nothing selected `F2` renames, `n` edits the note, `M` merges and `Del` deletes the tag; a chip in all tags moves the Disabled cursor to that tag's header. After a change the lists, the groups and the panel are read again and the cursor stays on the tag's header (its new name after a rename or merge). The facts line says how many of the tag's Mods Disabled shows (`%d not enabled`: rows are copies, and a header holds only Mods whose first tag it is). On no tag the panel says how to tag Mods. A Mod row shows the Mod's details again.
  - **Details | tags** (GitHub #28): the details area's heading is a switch, details | tags, in the view switch's style (`.seg.sub`, as Disabled's individual | tags). Tags is the Tag manager (§2.9, `tagmanager.js`), the same panel, keys and layout whichever way it opens; the switch shows tags whenever the details show it: chosen on the switch, the cursor on a tag group's header in Disabled, or a tag clicked in a Mod's details. The choice on the switch is kept per browser (`archo.detailview`), as the folds are. Chosen with no tag picked, the panel's top is empty and all tags lists every tag (the cursor moving through Mods leaves it there); a chip shows that tag above (on Disabled's cursor in the tags view: moves it to the tag's header, as before), and the tag stays while the cursor moves through Mods, until it lands on another tag's header. The heading then names the tag and has filter to this tag. In the editor all tags ends with a **no tag** chip and the number of enabled Mods without a tag (left out when there are none or nothing is tagged); a click toggles `has:notag` (§3.7), and the chip is marked while it is on. Details shows the cursor's Mod again (a tag clicked is let go; on a tag's header the Tag manager stays, as a header has no Mod).
  - **A tag clicked in the details** (the tags field, any list's Mod) shows that tag's Tag manager in the details, with the same heading, whatever Disabled's view; it stays while the list the details follow keeps its cursor (a chip in all tags then shows that tag), and the details follow the cursor again when it moves. The keys `F2` `n` `M` `Del` act only on a header; the panel's buttons work either way.
  - Collapse all / expand all act on every group shown. Closed groups are kept per tag in the browser (`archo.disabled.closed`); a new tag starts open. Individual hides the buttons: every copy is a row, so its copy groups never close.
  - Headers are rows of the virtual list (`listGeometry`), never extra elements per row; scrolling the grouped column costs what the plain column does (18 §2).
- Status icons appear only on Mods involved in actionable Can it run items, so they agree with badge counts (§5).

**Mod categories** (`app.CategoryOf`, `Index.Categories`): each installed Mod has one category, worked out from what is inside it, never from its name. The facts are what the scan already stored (04 §4), read by primary key and kept per snapshot in memory (`store.SnapshotContent`): the hashed file rows' XML under `Defs/` and `Patches/` and DLLs (any load folder, so every game version's folders count), `snapshot.kinds` (Languages, textures), and the requirements in About.xml (`decl_blob`, any game version). The first rule that holds wins:

| Category | Rule | Reason shown |
| --- | --- | --- |
| game & DLC (`game`) | Official content (Core, the DLCs) | official: the game or a DLC |
| library (`library`) | Ships a DLL, and at least 4 other installed Mods (Lineages, live copies) require it (`app.LibraryMinDependents`) | N installed Mods require it, and it ships a DLL |
| content (`content`) | Has Def files | N XML in Defs |
| code (`code`) | Ships a DLL, no Def files | a DLL and no Def files |
| patches (`patches`) | Patch files, no Defs or DLL | only patches: N XML in Patches, no Defs or DLL |
| translation (`translation`) | Languages, no Defs, patches or DLL | only translations: … |
| textures (`textures`) | Textures (PNG under a `Textures` folder), nothing above | only textures: … |

A Mod none of these fits (only sounds, an empty folder) has no category and no glyph. Interface and performance Mods are not told apart: both are code (or content), and nothing stored says which, so there is no such category. The player can set a Mod's category with `archo category` or MCP `set_player_data` `category` (07 §6.1); the window has no picker (taken out of the details on 2026-11-25); it replaces the automatic one everywhere, its glyph is a shade stronger, and its reason says set by you with the automatic one. The filter bar's category group and `category:` (§3.7) filter by the category shown. Categories are display only: sorting does not read them. Using them as sort tiers was considered and left out; the sort has its own top and bottom tiers (08 §1.5). The categories are worked out once per index (it is rebuilt after scans and player-data edits, 17 §7.3); an index rebuilt over the same snapshots only counts requirements again (18 §2). The TUI shows the category in details only.

**Staging** (07 §2.2) is kept in RimArcho and never written to game files. It has two uses:
- **Preparation**: new subscriptions wait here until the player decides to enable them.
- **Investigation**: stage a batch of enabled Mods to investigate a problem, then put them back at their original positions in one action.
- Each Mod staged from Enabled remembers its original position and the Mod before it as an anchor. Predecessors that were already staged are skipped, so the order of batch staging does not affect putting back. Putting back follows anchor chains through Mods still staged and falls back to the original position if no anchor is found.
- Add, drop and put back each create one undo step, including edits that only change Staging. Undo and redo restore the enabled list as well as the staged entries, their order, original positions and anchors. Enabling a staged Mod again by any route, including undo, enable, checkout or import, removes it from Staging within that edit. See 07 §2.2 for compatibility with old history.
- `archo stage list|add|drop|restore` (13 §4) does the same from the CLI. Each plan has its own meta entry, `stage:<plan ID>`.
- `T` puts all staged Mods back at their original positions. In Staging, `t` or space puts back one.

**History** appears below the left details in the GUI and in the TUI's third column, filling it when Staging is empty:
- **This session's changes** lists undo steps newest first, one per row, such as enable Harmony position 2. `view.StepText` derives the text from the lists before and after. The cursor points to now, with redo steps muted above it. `u` / `ctrl+r` move now. Clicking a step, or selecting it and pressing Enter in the TUI, returns to it at once; undo and redo still work afterward.
- **Versions** lists saved, launch, outside, imported and other plan versions, marked with their source (07 §3). Selection shows the diff from the current list. Enter or go back to this version runs `loadout checkout` at once without confirmation: the earlier list stays in history, and `u` restores it (§6). An identical list only reports no changes, with no undo hint and no change to the source or history (07 §3.2).
- GUI history is a collapsible history N steps section, whatever Staging contains. `H` opens a picker for steps and versions, navigated with arrows and Enter. In the TUI, `H` opens the same picker (`view.HistoryItems`), with now selected first; it stays available when Staging with entries or a search hides the area 3 history.
- When area 3 shows history, arrows, `g` / `G` and Home / End move in it; Enter returns to the selected step.

**Sorting rules** (GUI `rules.js`, `view.BuildRules`, 08 §2.1): this collapsible section is always there, below details and above history on the left. Its heading is sorting rules N, or just sorting rules when N is 0. It is closed by default and the choice persists per browser. Expanded, it takes at most 40% of the left column and has a draggable gap (`ui.gui.plan.rules`). The command panel's sorting rules action expands the section and focuses its scope switch.
- Rules apply across all games and lists. The first row switches between current list and all rules. **Current list is the default** because only rules with A or B enabled affect sorting in the edited list (08 §2.1); rules for other games or lists add noise here. All rules is for organizing rules globally. The scope persists per browser, without explanatory text. A rule is in the current list when any of its Mods is enabled (`RuleRow.InList`); an ignore rule uses its constrained Mod. Staged and disabled Mods do not count. N is the visible count after scope filtering. A row being edited stays visible until its form closes.
- Each rule is one sentence, newest first: Combat Extended after Dubs Bad Hygiene; RimHUD near start; ignore X's About.xml loadAfter Y. A muted note appears below. Clicking a Mod name jumps to its list row as in the problem panel; Mods that are gone are muted and inert. Hover shows r:<n> and the creation time.
- Hovering or focusing a row reveals edit and delete at the right. Edit replaces the row with an inline form. Delete acts at once and shows removed rule … undo in the status line. Undo, or an immediate `u`, restores the original r:<n>. Rules are not list edits and do not enter the list's undo stack or history.
- Add a rule with `r` at the cursor Mod or with add rule r at the bottom of the section. The inline form opens at the top (§3.1 rule 7), with the Mod name, the kind (after, before, immediately after, incompatible, near start or near end, in the row sentence's wording), the other Mod and an optional note. Typing the other Mod's name shows up to 6 distinct candidates, excluding the rule's own Mod, with enabled Mods first and numbered. Arrows choose a candidate; Enter or Tab accepts it. Enter saves; Esc closes the candidates first, then the form. While this section has focus, it owns the keys and never passes them to list verbs.
- The form cannot create ignore rules. Constraints are suppressed through needs ignore or the references printed by archo sort (08 §2.2). Existing ignore rules only allow editing the note and deleting here.
- A change reads the editor again and updates order findings, row icons and the Can it run badge without sorting automatically.
- **TUI** (`surface/tui/rules.go`): sorting rules are a secondary screen rather than a left column. In the editor, `r` opens the form for the cursor Mod; the command panel's rules action also opens the screen. Esc returns to the editor, and the position line shows sorting rules N / M. It uses the same model and scope switch; `a` toggles the scope, stored in meta `ui.tui.rules.scope`. Enter edits, Del deletes, an immediate `u` restores the deletion, `o` finds the rule's Mod in the list, and `r` adds another rule. The form has the same fields as in the GUI. Tab / shift+Tab changes fields, left/right changes the kind, and the candidate arrows with Enter or Tab select the other Mod. Letters are typed into the form while it is open. `:archo rule add` also works.

**Widths and wrapping**:
- The three list areas have adjustable widths. In the TUI, `<` `>` shrink or widen the focused area by 2 cells, and `=` restores the default widths without changing wrapping. The GUI has two column splitters, between the left column and Enabled, and between Enabled and the right column. Drag to resize or double-click to restore 38 : 31 : 31. The GUI keyboard equivalents are `<` `>` in 24px steps and `=` to reset.
- Widths are stored per Game Config in meta: TUI `ui.columns:<environment id>`, GUI `ui.gui.columns.v2:<environment name>`, in left / enabled / right order. Widths of the old layout are not applied to the new layout. GUI and TUI values are separate layout state, not settings.
- Details need at least 40 cells. If space runs short, the widest unfocused column shrinks first, to at least 12 cells.
- In the TUI, `z` toggles name wrapping in the focused area, saved per area. Long names wrap by display width, with continuation lines aligned under the name and keeping the selection background. The number, source and status appear only on the first line; ● appears on the last. Wrapped rows show no tags, and the cursor row is always fully visible.

**Narrow widths**:

| TUI width | Layout |
| --- | --- |
| ≥ 140 | All four areas |
| 110–139 | Area 3 is hidden; focusing it with arrows or `3` puts it in place of the first column. `t` still stages or puts back |
| 80–109 | Details are hidden; Enter or `4` opens full details, as in the GUI. The two lists share the width in proportion to their widths; PgUp / PgDn and the wheel page through lists |
| < 80 | One list at a time, with `[` / `]` switching and area 3 as the third tab. Width settings do not apply; `<` `>` explain this |

At GUI widths ≤ 680px, the filter spans the top, with Enabled and Disabled-Staging below. Compact details and history are hidden. Enter or `4` opens full details, and Staging stays usable.

#### Looks view

GUI only: `looks.js` (the shell and the gallery), `lookseditor.js` (the looks editor), `looksgrid.js` (the gallery's geometry), `looksconfirm.js` (the first apply's confirmation). Rules of the feature: [21](../21-looks.md). The words are look, texture and in game.

**Entering and leaving.** The plan editor's second row starts with the switch `editor | looks`; it is the row's first control in both views and does not move. `looks` hides the editor's board and shows the looks view in its place, for the plan and game version being edited; `editor` shows the board again as it was left (the board is hidden, not rebuilt: its lists, cursors, filter and scroll positions stay). The view is remembered in `ui.gui.plan.view`, so opening a list opens the view last used. There is no sidebar entry and no page of its own: the breadcrumbs, the row's actions (save, launch, undo and the rest) and the sidebar stay the editor's. The same row holds, after the switch, the way (`gallery` on layer 1 is empty; on layer 2 `gallery / <look title>`, the number of Mods that supply it and the Def that uses it) and `set preference to: current list | all`, which is where the next choice is stored (`ui.gui.looks.scope`; 21 §3.1). The position line reads `looks › <Mod or filter>` and, on layer 2, the look and the texture shown.

**Layer 1.** The gallery on the left and three cards in a column on the right; the gap between the two is a separator (§8.2, `ui.gui.looks.side`). While the looks view shows, the row's page actions (problems, rescan, rename, export, delete, save, launch) are not shown and `set preference to` sits at the row's right end.

**Filter bar.** A card of its own over the gallery: the plan editor's bar (`filterbar.js`; `/`, `ctrl+f` the query, `\` the panel) with one more group first, looks: overridden, overriding, mixed, chosen, no def, each with its count (`looks:<state>` in the query; one state at a time). Bare words search the looks of the whole plan (Mod names, Def names, labels and texture paths); every other condition (`tags:`, `source:`, `category:`, `content:`, exclusions) filters the Mods card exactly as it filters the editor's lists.

1. **Gallery** (`1`). Its head line has the refresh button (read the Mod folders again). The line names what is shown: the Mod with its source glyph and position, its looks and how many are overridden; or the search and filter with the count. The looks are grouped by category (the texture folder), each group under a heading with its count and, on hover or while a selection exists, `select all`. Groups smaller than a row share a row. A card is 152 px high and at least 124 px wide per texture with 3 px gaps: a look with several textures to draw takes one cell per texture (at most a row). A card shows the textures on a checkerboard in a fixed box, tagged `this Mod` and `in game` when both are drawn, `+N` for a folder look's further files and the format where no preview can be made; under it the look's title and its state in words (in game; overridden by `<Mod>`; mixed; your choice and its Mod; a broken or sleeping choice; no def). The list is virtual: only the rows near the scroll box are in the DOM (§10), and thumbnails load lazily in boxes of fixed size.
2. **Mods** (`2`). The Mods that supply textures in load order, one line each: row number, source glyph, name, and at the right the number of looks. The share of the Mod's looks a later Mod overrides is a tint across the row from the left, with no line of its own. The cursor row is the Mod the gallery shows: `↑↓` moves it and the gallery follows; a click does the same. The first Mod with overridden looks is shown when the view opens.
3. **Load-order rules** (`3`). The editor's own card (§2.5 above), moved here while the view is shown and numbered 3: the same rules, the same form. `r` adds a rule for the Mod the Mods card shows. A changed order changes what is in game, and the view reads again.
4. **Preference** (`4`). One row, `_Archo_Looks`: the choices by state (applied, not needed, asleep, broken), and under it the files, their size, how many are links and how many copies, and the folder (a copyable path, §3.1 rule 12). Selecting the row shows every look that has a choice in the gallery. It also says when a game runs (a choice is stored now and `_Archo_Looks` is rebuilt at the next write to the game), when the entry is not in the plan, and when a rebuild failed, with a `rebuild` button for the last two.

**Selection in the gallery.** A click on a look opens it in layer 2, as `enter` does on the cursor's look. `ctrl`+click and `space` toggle a look, `shift`+click and `shift`+arrows select a range, `ctrl+a` selects all shown; while a selection exists a plain click toggles too, so a selection is not lost to a stray click. With a selection, a bar at the bottom of the gallery offers `use <Mod> for these` (the Mod the Mods card shows; one `LooksApplyMany`: one undo step, one rebuild) and `undo` (the selection's choices in the current scope). `use` first asks Go for a dry run; when some looks would be mixed the bar says how many of how many and offers `only the N not mixed`, `use for all N` and cancel.

**Layer 2, the looks editor.** `gallery` in the way or `esc` returns to the gallery on the same Mod, at the same scroll position and cursor. Three columns, the gaps between them separators (`ui.gui.looks.which`, `ui.gui.looks.chain`):

1. **Which texture** (`1`). The axes Go derived (the data contract's `axes`): for a worn look `on the ground`, then the body types, then the facings of the body type shown; for a plain look its facings; for a folder look its files. Each entry has a thumbnail and the number of Mods that supply it, in amber where more than one does. `west` is offered as `east` mirrored when no Mod ships it.
2. **Compare** (`2`). The selected Mod's texture beside the one in game (or, when the selected Mod is in game, the Mod it covers). Switches in the head: `side by side | slider`, `fit | 2x | 4x`, `texture | mask` (when a mask exists). The two boxes are always the same size. Under each texture: the Mod's name and row number with `in game` or `covered`, the file's whole path on its own wrapping line (never cut), its size in pixels, format and bytes, notes (a second format, the same file as another Mod's, mirrored), and a visible `show in explorer` button. A format without a preview says so in the box and keeps the facts.
3. **Override chain** (`3`). The Mods that supply the texture shown, in load order, one row each with its thumbnail and `in game` on the one the game shows. A row only selects its Mod (`↑↓` when the card has the focus); it applies nothing. Under a rule, the `_Archo_Looks` row lists the look's choices per scope with their states. A mixed look is said here.
4. **Operation** (`4`). The head reads `operation for <look>` and, at the right, the scope in words. `selected <Mod>`; `apply in game` with a list of what Go offers to apply (the entire look, all worn textures, the texture on the ground, a body type, this texture) and the `apply` button; under it Go's prediction for that target, Mod and scope (already in game; mixed, with how many textures stay with which Mod; overruled by another choice; no texture). `undo` is enabled only when the look has a choice in the scope. There is no other operation.

**Keys.** `1`–`4` focus the cards in both layers. Arrows only move: the cursor in the gallery, the Mod in the Mods card and the override chain, the facing (`←→`) and the body type or file (`↑↓`) in layer 2, the zoomed texture in compare. Nothing is applied or undone by an arrow, `enter` or `space`; apply and undo are buttons. `esc` returns one level: the mixed warning, the selection, the search and filter; in layer 2, the gallery. The editor's plan keys that make sense stay (`w`, `L`, `u`, `ctrl+z`, `ctrl+y`, `ctrl+r`, `R`, `A`, `r`, `l`, `c`, `p`, `i`, `e`, `?`, `:`, `ctrl+k`); the editor's row keys (`space` to enable, `m`, `t`, `x`, `g`, `n`, `J`, `K`, `S`, `Del`) do nothing here. A palette entry that needs the board (filter, details, tags, a Mod without textures) switches back to `editor` first. `?` lists the view's keys.

**The first apply.** Until `do not show this again` is ticked (`ui.gui.looks.confirmed`), every apply first shows a confirmation (`popups.js`, §5) built from `LooksApplyPreview`: the look or the number of looks, the Mod, what is applied and for which lists; that RimArcho keeps the local Mod `_Archo_Looks` last in the list with links to the chosen textures and no Defs; the folder, the files, links and copies of the dry run and whether the list gains the entry; that the player's Mods and the load order are not changed and saves do not depend on it; and, set apart, "This feature is still in test. If something goes wrong, please report it." with a `feedback` button (§2.14 feedback). Cancel writes nothing.

**States.** While the index is built the gallery shows "reading the textures of this list…" with a progress bar of Mods read (`LooksProgress`). A plan without textures, a Mod without textures, no look under the filter (with `clear the filter`), no match for the search, and more looks than one answer carries each say so in the gallery's place. A failed read shows the error with `try again`. A game running is said on the Preference card and in the confirmation. A rebuild that failed after an apply stays on the Preference card until the next write. Long Mod names end in an ellipsis with the whole name on hover; paths wrap. A thumbnail that is gone (the index was dropped after five idle minutes) makes the view read the overview again once.

**Not verified in a window yet**: the page was written without running it; see `UserGuide/release-vm-tests.md`, "Looks view".

**Data contract** (`internal/view/looks.go`, `internal/surface/gui/looks.go`). A Mod is named by its 0-based position in the plan in reads and by its reference in writes. Every winner, state and prediction comes from Go (§1 rule 1): the page does not derive them.

- `LooksOverview()` → `view.LooksOverview`: the Mods that supply textures in load order (position, row number, Instance, reference, name, source kind as the editor's rows, looks, overridden and overriding counts; the `_Archo_Looks` entry as a row marked generated), the plan's totals, the scope the next choice is stored in, the `_Archo_Looks` card (entry position, choices by state, files, bytes, linked and copied counts, the looks directory or the one the first apply would choose, 21 §4), the number of files the index could not read, and whether a game runs (an apply then keeps the choice and does not rebuild). `LooksRefresh()` is the same after dropping the index in memory.
- `LooksGallery(mod, filter, search)` → `view.LooksGallery`: the looks of one Mod (`mod` its position), of the choices (`"chosen"`, or the position of the `_Archo_Looks` row) or of the plan (`""`), grouped by category. A row: id, kind, title (a Def's label, else the last part of the path), provider count, the selected Mod's state with the choices resolved (in game, or overridden by a named Mod), the load-order flags the filters use (overridden, overriding), mixed, the choice's state and Mod, no Def, and at most three textures to draw (the one in game; the selected Mod's own where the game shows another; a folder look's first files, the rest counted). Filters: `overridden`, `overriding`, `mixed`, `chosen`, `nodef`; the answer counts the rows of each. The search matches every word against the look's path, Def names and labels, and, when no Mod is selected, provider names. One answer carries at most 2,000 rows and counts the rest.
- `LookDetail(look, mod, scope)` → `view.LookDetail`: title, Defs (type, name, label, field, graphic class, defining Mod), tags, providers, the axes derived from the slots (a worn look: the texture on the ground and each body type's facings; a plain look: its facings; `west` drawn as `east` mirrored when no Mod ships it; a folder look: its files; the slot to open first, worn before on the ground), every slot's override chain (provider, file path, format, size in pixels and bytes, second format, identical-to, whether a picture can be made, the mask), the provider in game per slot and whether by choice, the choices on the look per scope with their states, and what an apply can name (the entire look, all worn textures, the texture on the ground, each body type, each texture) with its slot list and, for the selected Mod and scope, the prediction (the page shows these and does not call `LookPreview`). `LookPreview(look, mod, slots, scope)` is one prediction: `none` (the Mod has no texture for it), `inGame` (already in the game), `overruled` (a choice of this plan decides these textures, so one for all plans would not show), `mixed` (with the number of textures still from the named Mods), or `apply`.
- `LooksApply(look, modRef, slots, scope)`, `LooksApplyMany(looks, modRef, scope)` (the gallery's selection: one index, one undoable plan edit, one rebuild; a look the Mod has no texture of is reported and left alone), `LooksUndo(look, scope)`, `LooksUndoMany(looks, scope)`, `LooksRebuild()` → `view.LooksDone`: the status-line sentence, each look's outcome, whether `_Archo_Looks` was added to the plan, the looks directory, the generated Mod's files as links and copies, a rebuild that did not run, and the overview after the call. `LooksApplyPreview(looks, modRef, slots, scope)` is the same as a dry run that writes nothing: the first apply's confirmation shows it (21 §6). `LookShow(look, mod, slot)` opens the texture's folder in the file manager.
- **The index** is built once per plan state and kept in memory under `app.LooksKey` (game version; every entry's position, Instance and snapshot; the `_Archo_Looks` entry is no provider and is left out). The build runs outside the page lock, once for all waiting reads; the page polls `LooksProgress()` (building, Mods read, total) while a read waits. A changed key (the plan's Mods or order, a scan that found a changed Mod) builds a new index at the next read. An apply or undo keeps the index, since it changes no texture, drops the board (the plan may have gained its entry) and resolves the choices again; the choices are also resolved again whenever the database changed, so a choice made in the CLI shows at the next read. The index does not stay for good (§10): the page calls `LooksLeave()` when it leaves the looks view, and an index nothing read for five minutes is dropped; the next read builds it again from the header cache.
- **Textures**: the `/looktex/` route (§4.4).
- **Settings** (`Setting` / `SetSetting`): `ui.gui.plan.view` (`editor` or `looks`), `ui.gui.looks.scope` (`plan` or `all`; the overview carries it), `ui.gui.looks.confirmed` (`1`: the first apply's confirmation is not shown again; the overview carries it), and the separators `ui.gui.looks.side`, `ui.gui.looks.which`, `ui.gui.looks.chain`.

### 2.6 Build a pack

This sub-page belongs to the current plan: GUI `packs.js`, `API.BuildPage` → `view.BuildPageOf`, and `archo pack build` (10 §2). Open it with create a pack (`B`) on the packs page. The breadcrumbs are Library / Lists / <plan> / create a pack, and the sidebar stays on the plan. Cancel at the upper right or Esc returns to the page it was opened from (the editor by default). The layout follows the create-a-pack page of the RimArcho interface-design HTML prototype, in the current colors.
- **Left**: basic information has the name, by default <plan> <date>, with an explanation below when it is invalid or already used (`API.PackNameCheck`). When the name is an existing pack's (`API.PackRevision`), “make revision N of this pack” (off) appears: its Mods are replaced, its saves and settings stay (10 §2 “New revision”), and create becomes “create the new revision”. “include Mod options” (on) carries the list's Mod settings, written into the pack's own settings on its first launch (10 §1, §3); off is `--no-settings`. Packs always include the Mod files; to share only the list, use export list on the pack page (§2.7). The what happens when creating card has five numbered rows, each with a bold title and a sentence: 1 can it run; 2 remove unused; 3 textures (10 §2); lock versions; put in place. An error-level finding makes row 1's number a red !, shows N remaining errors, lists them, and offers go fix, which opens Can it run. Otherwise the row says that sorting is specific to this pack, how many items move, and, in amber, how many Mods declare no version support. Row 2 keeps only current-version content and says how many Mods have directories for other versions and how much that saves. Insufficient space or unreadable Mods are red; the row is muted until the findings are fixed. Put in place writes the pack folder with its own saves and settings, leaving the plan's saves alone. While building, completed rows show checks and the current row a breathing circle. Pruning and locking happen together during copying. A progress bar and stop appear below (`view.ProgressOf`, with a Key for each row).
- **Textures** (`view.textureStep`): the selector has eight choices: no conversion, which copies PNG unchanged and is the default; pre-convert full size; and slim to 80 / 75 / 60 / 50 / 40 / 25% (`view.PackTextureChoices`, stored in `B.tex`). Opening the page measures no conversion. Changing the choice does not measure again, since reading the PNG files takes tens of seconds. The row asks the player to select an option and scan statistics to see the file count and final size, with scan statistics on the right; the summary shows not measured for this option. An explicit scan calls `API.BuildPage(tex)` to measure the files, final size and conversion peak in the background (§3.1 rule 9). Size fields show shimmer placeholders, and build is disabled until the results arrive. Building without a measurement is allowed: `BuildPage.ToolOK` tracks todds separately, and the build itself checks the peak space again. Below, no conversion explains the benefit of DDS. A conversion shows N PNG → DDS, no PNG in pack, video memory A → B, final X / peak Y. Below that are the counts of PNG files kept (beside a same-name DDS, or in other formats) and an amber warning if the pack grows. Space is checked against the peak; the summary shows the final size. If todds is missing, the row is red and says not installed: Library › Texture optimisation, with go install. Build is disabled and the row offers install todds or do not convert, linking to Texture optimisation. This page never downloads todds. `D` selects the next choice and appears in help; Tab reaches the selector and arrows change it. The preview uses the same `--textures [--texture-scale N]`.
- **Right summary**: the name, Game Config, Mod count, size before → after once the findings are fixed, own saves (empty at first) and pack.dir. Below are build (`B`, or Enter in the name) and see the list first, no disk (`V`).
- **Disabled build** (G14): errors disable building, with a red fix N problems link to Can it run below the button. Insufficient space, unreadable Mods, an invalid name or another build in progress also disable it and show the reason.
- **Preview**: `archo pack build --dry-run` expands inline below the summary (`API.PackDryRun`), without writing to disk. Repeating the action or pressing Esc collapses it. It is not a dialog (§3.1 rule 7).
- **Sizes need a walk through the Mod folders**: the page shows first, checks run under the lock, and `PackPlan.Measure` measures in the background outside the lock. Sizes are filled in when ready.
- **Unfinished builds** appear below through `view.UnfinishedRows`. Builds running in another window show progress and stop. Interrupted builds offer rebuild or delete copied files. These unfinished copies belong to RimArcho and are deleted directly rather than recycled (10 §2).
- Building runs in a subprocess and opens the pack page when it completes.

### 2.7 Packs

Packs are GUI `packs.js`; the TUI command panel's packs action shows text with commands.
- The list shows each pack's name, Mod count, size, full game version at build time (03 §3.1) and last played time (`view.PackRows`). Click or Enter opens a pack, and arrows move. The page's create a pack action uses `B`; unfinished builds appear above the list.
- Each pack is a sidebar sub-entry (`view.Nav`, §2.1), like each plan. In the TUI, Tab / shift+tab switches between sibling packs (§3.5) and Tab from the list opens the first pack; in the GUI they move the focus, and the sidebar, or ↑↓ and Enter on the list, open a pack.
- A pack page (`API.Pack` → `view.BuildPackPage`) shows spaced facts in the head: N Mods, size, supported versions, build date and Game Config, and last played. The actions are export (`e`, a save dialog, `pack export`); export list (`E`, a versioned RimArcho `.archolist.json` for sharing, `pack export --list`, 07 §7.3); recycle (Del, confirmed, `pack remove`); and a solid launch (`L`, `archo pack launch`, 10 §3). Below, the Mods appear in load order with their sizes and removed version directories; Core and DLC say from game. Each size has a faint bar behind it scaled to the largest Mod, as on the Packs list and in the Mod library (§2.9, §7 principle 9). The folder location comes last.
- **Compare with game** (10 §5): a line after the facts appears only for a warning or an error. Examples: created for 1.6.4633 rev1261, game 1.6.4871 rev590, in amber; missing DLC Biotech, in red; and modified copies, in red, naming the Mods. Info, such as a missing recorded build or extra DLC, appears only on hover. Errors disable launch, with a tooltip saying why. `view.BuildPackPage` gets `Check` from `app.CheckPack`. The page does not compute digests again; copies are verified during import and pack check.
- Importing through the first-run guide's open action only unpacks `.archopack` files, v1 zip and v2 tar+zstd (10 §4). The result reports verification and comparison (`pack import`). List files, including RimArcho lists, and collection links go to the import preview, which marks Mods whose versions differ in RimArcho lists (07 §7.1).

### 2.8 Game Configs

`view.EnvironmentRows` supplies a name-sorted list to GUI and TUI pickers and the Game Config page; the GUI pickers show it flat, the TUI's `E` groups it by installation (§9.1). Each picker row shows the config name and RimWorld major.minor version, with the current config marked. A Proton game (03 §3.2) is badged “Proton” wherever an install is shown (`view.ProtonBadge`): the pickers' installation label reads “RimWorld 1.6  Proton” (`EnvRow.Installation`), the Game Config page's row has a “Proton” chip beside the name (`EnvRow.Build`), and its game folder row says “Proton” after the version. The GUI picker is titled switch Game Config, its last action is + Add Game Config, and its remove action says remove Game Config. No installation settings are exposed. The chip retains its name and version.

The GUI Game Config page has the lead “Game Config = game version + Mod options; RimWorld starts from it” (§7.2) and three numbered sections, in this order:
1. **game versions on this computer** (`view.GameRows`, `EnvPage.Games`): one row per installation a config uses, “RimWorld 1.6” (with the Proton chip), the full version and the game folder with its copy icon, and on the right the names of the configs that play it as chips, the one in use tinted (`chip cur`; the sentence “Game Configs using this game: …” is the chips' hover and accessible name). Then the games `env.DetectAll` finds that no config uses (Steam's library list and the fixed folders of 03 §3.2: a few stats, no folder walk, so it runs on every page read, 16 §10), muted, with a “not added yet” chip and Add Game Config (the add page, below). Used games are ordered by version, then folder; detected ones follow. The label's hover says what a game version is: a copy of RimWorld downloaded on this computer.
2. **all Game Configs**: name (Proton chip), the game it plays as “RimWorld 1.6” (`EnvRow.Installation`; full version and folder on hover, they are in section 1 and 3), in use or use this one, remove.
3. **this Game Config**: the in-use config's settings (`view.EnvGroups`, below).

Add Game Config is a page, not a dialog: the first-run guide's page entered from the Game Config page, the switchers and the empty Launch page (§2.15, `S.guideFrom` "env"; dialogs are for warnings and confirmations only). Its step 1 keeps both ways, a game you have (detected or a chosen folder, a game another config already uses included) and download a version with SteamCMD, with one game picked; under the game list it asks the config's name, **start with** (copy the settings of the current config, or game defaults; the line below names game settings and Mod settings and excludes Mod files and saves), the **Mod list** (every global plan, the current config's first, and New empty list) and the **saves folder** (shared, the game's default folder, only for a game whose default folder no config uses; own folder in RimArcho; or a folder you choose with the native picker). Add Game Config (`API.GuideAdd` with `view.GameFound.AddConfig`, `Saves`, `Like`, `List`, `NewList`; `view.CreateGames`) then reads a game no config used yet (step 2, whose last button is done), or, for a game already read, switches to the new config at once and shows the Game Config page. The core's refusals show in the page's footer (a Proton game's own or chosen saves folder, a copy to another game folder, a taken name). The download way adds the downloaded game with its default folder as on a first run. The Game Config page's “copy the game folder…” beside “Add Game Config” opens it on a third way, copying a Game Config's game folder (03 §3.5). TUI creation uses its existing command line.

`view.EnvGroups` is one Game Config section (titled this Game Config) on the Game Config page only (Settings does not repeat it), in order: name, game folder with version, saves folder, Mod list, launch method, arguments, remove. The saves folder is a choice, shared (the game's default folder), own folder in RimArcho or a folder you choose, with the folder itself below (`env set --saves shared|own`; choosing a folder opens the native picker and runs `env set --user-data`). A relocation preview says how many other Game Configs follow the folder and lists their names; reattaching one config to a different known game folder affects only that config. Name edits preserve paths and history. Argument arrays preserve token boundaries (03 §6.4).

Removal previews which records go and which stay, never deletes files, and names the next config. A notice identifies legacy configs that use the same game folder and stays until the player presses got it (`app.AcknowledgeAliasNotice`; the TUI picker's x acknowledges the same notice, §9.1). There is no merge feature.
