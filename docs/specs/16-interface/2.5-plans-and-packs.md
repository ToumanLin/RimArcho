### 2.5 Plan editor

The plan page is the editor. Staging and history belong to each plan (07 §1, §2.2, §3). All lists (§2.17), the sidebar context menu, `P` and the command panel provide new / import, rename, duplicate and delete. New / import uses one form for an empty list, a copy of a list or version, a save, or an import. Renaming checks for duplicate names as the player types and is inline on All lists. Deletion needs confirmation and cannot remove the last plan. The status line does not name the plan written to ModsConfig.xml (the write record, 07 §1.3). With several plans, that plan's sidebar entry has a green dot with the tooltip the game is using <plan> v<n>. Launch has no marker because its large headline already shows the applied item; a single plan needs no marker. An outside version that has not been loaded adds an amber marker to the sidebar entry, the plan page and the Launch row.

**Open and current lists** (07 §1.3): opening a list from the sidebar, the command panel or All lists shows it for editing without changing the current list used by the Launch headline, by launching and by the CLI. Can it run, the Mod library and building follow the open list. Saving this list makes it current.

**Page head** (as on other pages, §2.2): below the breadcrumbs, a muted line says N enabled, in the order the game loads them. The head stays one line: when the actions grow (problems, unsaved, save), the line is cut with an ellipsis (its hover keeps it whole) instead of the actions wrapping and pushing the lists down. The head stays one line: when the actions grow (problems, unsaved, save), the line is cut with an ellipsis (its hover keeps it whole) instead of the actions wrapping and pushing the lists down. The actions at the right are, in order: N problems (`p`, the problem panel, §5) when the list has something to fix; the amber outside-version marker when needed; N unsaved; rescan; rename; delete; import/export (opens All lists with this list selected; import, export and sharing are there, §2.17); and save changes (`w`; no changes and disabled when nothing changed). The last, solid button is launch (`L`) for the current list, or "set current" for another list; its tooltip names the list the game is launched with and says that no game file is written. There is no ⋯ menu; building starts on the packs page (§2.6). The editor shows no environment chip. Undo is in the Enabled header, to the left of sort. Automatic sorting is in the Enabled header as sort `S` and acts only on that list. Key hints are hidden below 1100px.
- Undo uses `u`. Import and export use `i` / `e` and open their sub-pages (§2.17, 07 §7). `S` sorts at once and reports sorted: N moved, K strong requirements satisfied, or only weaker requirements remain unmet, followed by undo. The command panel's sort preview adds a why section listing each requirement the current order violates, marked strong, weak or harmless, with strong requirements first (08 §1.3). `w` writes ModsConfig.xml without launching, for players who launch through Steam or another route (09 §2).
- **The launch button, `L` and the command panel's launch action do not launch directly.** They open Launch (§2.3) with this list current and applied, and focus the launch button. If another list is open, it is made current first; if a pack was applied on Launch, the current plan is applied again. Another `L` or Enter launches the game: launching happens only on Launch. CLI and MCP launch directly. The TUI behaves the same with its simple Launch page (§9.1).
- All three actions take one click or key, without confirmation (§6). A refusal, such as a running game, outside changes not yet loaded, or a missing user data directory, gives its reason in the status line. A refusal that comes with commands also opens a read-only dialog listing them. To preview writes and link creation or removal, use the command panel's preview sort / save / launch (`view.DryRun`) or `archo … --dry-run`.
- List import and export (07 §7) are also in the command panel (`i` / `e`, §3.5). Export opens this list's export sub-page; import opens the same import sub-page as All lists (§2.17).

The backend also returns each Mod's finding count, maximum severity, short summary and directly executable fixes. List-level findings share the needs cache, and edit results and events return updated summaries. The contract is in [8.7](8-gui-technology.md#87-list-findings-and-needs-cache-api).

See §5 for version hints in rows, their aggregate, the ignored count and the restore entry. The problem panel still opens for inspection and restoring even when every version hint is ignored.

**Filters** (shared with Mod library › All mods): the filter bar sits at the top left, above details and history. Collapsed, it has a search box, a clear button and the filter toggle (`\`). Conditions live in the query text: clicking local adds source:local, without a permanent chip. Clicking search or pressing `/` or `ctrl+f` opens a small popup below the input. It first shows the available keys, then matches the current word against keys or values. Ghost text previews the completion; arrows select a candidate, Tab accepts it, and Enter ends input. The popup shows no Mod counts or duplicate values. Fixed help is localized, while author, tag and custom-directory names stay unchanged (§3.7).

The filter toggle or backslash expands lists first, then tags, sources and content; other keys are reached through search completion. The lists group offers every list except the one being edited and filters available copies by membership (§3.7). The current list, when offered, comes first and is marked current list. Sources use directory roles: Workshop, SteamCMD, local, lock library, official and other directories. Custom directories also show their names, with stable source:<alias> values. Raw paths are not candidates but stay copyable in details (03 §2.2). Each group first shows up to 24 common values with counts, with a clickable N more to expand the rest and collapse to close them. There is no search within a group; all searching uses the query above. Click, Enter or Space includes a value; right-click or `x` excludes it; choosing it again withdraws the condition. Conditions follow §3.7 whether typed or clicked. Membership is loaded once with the board and refreshed after database changes; building the groups reads nothing from the database per row.

Expanded filters take 35% of the left column by default, at least 120px, leaving the rest to details and history. Dragging the gap between cards redistributes the height, up to the full height; double-click restores 35%. `ctrl+↑↓` moves it 40px per press. The settings are `ui.gui.filter.split:plan` and `ui.gui.filter.split:library`. Losing focus collapses the bar at once and keeps the query. Up/down changes groups, and left/right changes values, including the expand and collapse buttons. Typing enters the query above with the current group's key; `esc` or backslash collapses the bar. Staging keeps its own search.

- With a filter, positions always refer to the full load order. `m` numbers and before/after targets use the complete list, including hidden candidates (§3.6). Space enables at the suggested `App.SuggestAt` position, whatever the filter. Dropping on a row uses that row's number. `J` / `K` cross the next **displayed** row: the moved row swaps with its filtered neighbor, landing just after it for `J` or just before it for `K` in the full list. `alt+J` / `alt+K` cross 10 displayed rows. Without a filter, they move 1 and 10 positions (`view.StepAt`, `TestStepAt`).

The GUI left column has filters, compact details, collapsible sorting rules and collapsible history, in that order. The middle is Enabled; the right has Disabled and collapsible Staging. Staging is open by default when it has entries and closed when empty; history is closed by default. These choices persist per browser. Expanded history takes 25% of the left height by default, at least 72px. Staging follows its content height up to 38% of its parent, unless the player has dragged it to another height. Adjacent cards can be resized. Pressing `3` expands and focuses Staging, and dropping on its heading also works; `t`, space and `T` are unchanged. `←→` follows the physical order details / Enabled / Disabled, while `1`–`4` keep the logical order Disabled / Enabled / Staging / details.

Enabled Mods with several copies add the current copy below, such as └ locked version 2026/10/21 14:27. Disabled groups copies by Mod, with abstract copy labels below the name. Each copy can be selected, enabled or dragged; the other disabled copies stay visible when one copy is enabled. Virtual scrolling, paging and drop positions use actual row heights.
- The alias is used when there is one. Names are truncated by display width without splitting a wide character.
- Rows that differ from the last save have an accent ● after the name.
- An unloadable Mod's whole row is muted.
- No area shows tags in rows. Read and edit them in details (§4.1), or search with tag: (§3.7). Disabled's tags view (below) shows a tag only as a group's header.
- **Disabled views** (GUI, `disabledgroups.js`): the Disabled heading ends with collapse all / expand all (tags view only) and an individual | tags switch (`v` from any editor area), kept in `ui.gui.plan.disabled`. Individual is the list above, with its copy groups. Tags puts a header row before each tag's rows: the tag's colour as a band in the rows' left slot when the board's `tagColors` has one (in line with its rows' bands, as on Mod library's Tags view), a chevron, the tag, and how many of its rows are shown (`3 / 5` when the filter hides some). A Mod sits under its **first** tag only (its tags' order, 07 §6.1), so each copy is still one row and the cursor, selection, dragging and the verbs work on unique rows; Mods without tags gather under no tag at the end. Groups follow the Tag manager's order (§3.8: pinned first, then by Mod count, `API.TagList`, read again when the data changes); rows keep the column's order and copy groups within a group. While filtered, a group shows only matching rows and a group with none is left out.
  - **The cursor lands on headers**, as in the Mod library's Tags view (§2.9): `↓` from a closed group's header goes to the next header. On a header, `←` closes an open group and `→` opens a closed one; otherwise the arrows change areas as usual. Enter and a click also toggle it; a double click does not enable. ctrl+click on a header selects its shown rows (again: unselects them); shift ranges and ctrl+a take only rows, and a closed group's rows are not shown. Space, `t`, `m`, `g` and the row menu do nothing on a header. Closing the group the cursor is in moves the cursor to its header; a row that moves into a closed group (undo, disable) leaves the Disabled cursor on that header. Full details' `←` `→` step past headers, and a jump to a Mod (command panel) opens its group.
  - **The details on a header are the Tag manager** (§2.9), as on Mod library's Tags view: the details area's heading becomes tags, the tag, and filter to this tag; the panel is the same (`tagmanager.js`: note, name, keep on top, facts, colour, similar, rename / merge into… / delete tag, all tags). On a header with nothing selected `F2` renames, `n` edits the note, `M` merges and `Del` deletes the tag; a chip in all tags moves the Disabled cursor to that tag's header. After a change the lists, the groups and the panel are read again and the cursor stays on the tag's header (its new name after a rename or merge). The facts line says how many of the tag's Mods Disabled shows (`%d not enabled`: rows are copies, and a header holds only Mods whose first tag it is). On no tag the panel says how to tag Mods. A Mod row shows the Mod's details again.
  - **A tag clicked in the details** (the tags field, any list's Mod) shows that tag's Tag manager in the details, with the same heading, whatever Disabled's view; it stays while the list the details follow keeps its cursor (a chip in all tags then shows that tag), and the details follow the cursor again when it moves. The keys `F2` `n` `M` `Del` act only on a header; the panel's buttons work either way.
  - Collapse all / expand all act on every group shown. Closed groups are kept per tag in the browser (`archo.disabled.closed`); a new tag starts open. Individual hides the buttons: every copy is a row, so its copy groups never close.
  - Headers are rows of the virtual list (`listGeometry`), never extra elements per row; scrolling the grouped column costs what the plain column does (18 §2).
- Status icons appear only on Mods involved in actionable Can it run items, so they agree with badge counts (§5).

**Staging** (07 §2.2) is kept in RimArcho and never written to game files. It has two uses:
- **Preparation**: new subscriptions wait here until the player decides to enable them.
- **Investigation**: stage a batch of enabled Mods to investigate a problem, then put them back at their original positions in one action.
- Each Mod staged from Enabled remembers its original position and the Mod before it as an anchor. Predecessors that were already staged are skipped, so the order of batch staging does not affect putting back. Putting back follows anchor chains through Mods still staged and falls back to the original position if no anchor is found.
- Add, drop and put back each create one undo step, including edits that only change Staging. Undo and redo restore the enabled list as well as the staged entries, their order, original positions and anchors. Enabling a staged Mod again by any route, including undo, enable, checkout or import, removes it from Staging within that edit. See 07 §2.2 for compatibility with old history.
- `archo stage list|add|drop|restore` (13 §4) does the same from the CLI. Each plan has its own meta entry, `stage:<plan ID>`.
- `T` puts all staged Mods back at their original positions. In Staging, `t` or space puts back one.

**History** appears below the left details in the GUI and in the TUI's third column, filling it when Staging is empty:
- **This session's changes** lists undo steps newest first, one per row, such as enable Harmony position 2. `view.StepText` derives the text from the lists before and after. The cursor points to now, with redo steps muted above it. `u` / `ctrl+r` move now. Clicking a step, or selecting it and pressing Enter in the TUI, returns to it at once; undo and redo still work afterward.
- **Versions** lists saved, launch, outside, imported and other plan versions, marked with their source (07 §3). Selection shows the diff from the current list. Enter or go back to this version runs `loadout checkout` at once without confirmation: the earlier list stays in history, and `u` restores it (§6). An identical list only reports no changes, with no undo hint and no change to the source or history (07 §3.2).
- GUI history is a collapsible history N steps section, whatever Staging contains. `H` opens a picker for steps and versions, navigated with arrows and Enter. In the TUI, `H` opens the same picker (`view.HistoryItems`), with now selected first; it stays available when Staging with entries or a search hides the area 3 history.
- When area 3 shows history, arrows, `g` / `G` and Home / End move in it; Enter returns to the selected step.

**Sorting rules** (GUI `rules.js`, `view.BuildRules`, 08 §2.1): this collapsible section is always there, below details and above history on the left. Its heading is sorting rules N, or just sorting rules when N is 0. It is closed by default and the choice persists per browser. Expanded, it takes at most 40% of the left column and has a draggable gap (`ui.gui.plan.rules`). The command panel's sorting rules action expands the section and focuses its scope switch.
- Rules apply across all games and lists. The first row switches between current list and all rules. **Current list is the default** because only rules with A or B enabled affect sorting in the edited list (08 §2.1); rules for other games or lists add noise here. All rules is for organizing rules globally. The scope persists per browser, without explanatory text. A rule is in the current list when any of its Mods is enabled (`RuleRow.InList`); an ignore rule uses its constrained Mod. Staged and disabled Mods do not count. N is the visible count after scope filtering. A row being edited stays visible until its form closes.
- Each rule is one sentence, newest first: Combat Extended after Dubs Bad Hygiene; RimHUD near start; ignore X's About.xml loadAfter Y. A muted note appears below. Clicking a Mod name jumps to its list row as in the problem panel; Mods that are gone are muted and inert. Hover shows r:<n> and the creation time.
- Hovering or focusing a row reveals edit and delete at the right. Edit replaces the row with an inline form. Delete acts at once and shows removed rule … undo in the status line. Undo, or an immediate `u`, restores the original r:<n>. Rules are not list edits and do not enter the list's undo stack or history.
- Add a rule with `r` at the cursor Mod or with add rule r at the bottom of the section. The inline form opens at the top (§3.1 rule 7), with the Mod name, the kind (after, before, immediately after, incompatible, near start or near end, in the row sentence's wording), the other Mod and an optional note. Typing the other Mod's name shows up to 6 distinct candidates, excluding the rule's own Mod, with enabled Mods first and numbered. Arrows choose a candidate; Enter or Tab accepts it. Enter saves; Esc closes the candidates first, then the form. While this section has focus, it owns the keys and never passes them to list verbs.
- The form cannot create ignore rules. Constraints are suppressed through needs ignore or the references printed by archo sort (08 §2.2). Existing ignore rules only allow editing the note and deleting here.
- A change reads the editor again and updates order findings, row icons and the Can it run badge without sorting automatically.
- **TUI** (`surface/tui/rules.go`): sorting rules are a secondary screen rather than a left column. In the editor, `r` opens the form for the cursor Mod; the command panel's rules action also opens the screen. Esc returns to the editor, and the position line shows sorting rules N / M. It uses the same model and scope switch; `a` toggles the scope, stored in meta `ui.tui.rules.scope`. Enter edits, Del deletes, an immediate `u` restores the deletion, `o` finds the rule's Mod in the list, and `r` adds another rule. The form has the same fields as in the GUI. Tab / shift+Tab changes fields, left/right changes the kind, and the candidate arrows with Enter or Tab select the other Mod. Letters are typed into the form while it is open. `:archo rule add` also works.

**Widths and wrapping**:
- The three list areas have adjustable widths. In the TUI, `<` `>` shrink or widen the focused area by 2 cells, and `=` restores the default widths without changing wrapping. The GUI has two column splitters, between the left column and Enabled, and between Enabled and the right column. Drag to resize or double-click to restore 38 : 31 : 31. The GUI keyboard equivalents are `<` `>` in 24px steps and `=` to reset.
- Widths are stored per environment in meta: TUI `ui.columns:<environment id>`, GUI `ui.gui.columns.v2:<environment name>`, in left / enabled / right order. Widths of the old layout are not applied to the new layout. GUI and TUI values are separate layout state, not settings.

- In the TUI, `z` toggles name wrapping in the focused area, saved per area. Long names wrap by display width, with continuation lines aligned under the name and keeping the selection background. The number, source and status appear only on the first line; ● appears on the last. Wrapped rows show no tags, and the cursor row is always fully visible.

### 2.6 Build a pack

This sub-page belongs to the current plan: GUI `packs.js`, `API.BuildPage` → `view.BuildPageOf`, and `archo pack build` (10 §2). Open it with create a pack (`B`) on the packs page. The breadcrumbs are Library / Lists / <plan> / create a pack, and the sidebar stays on the plan. Cancel at the upper right or Esc returns to the page it was opened from (the editor by default). The layout follows the create-a-pack page of the RimArcho interface-design HTML prototype, in the current colors.
- **Left**: basic information has the name, by default <plan> <date>, with an explanation below when it is invalid or already used (`API.PackNameCheck`). Packs always include the Mod files; to share only the list, use export list on the pack page (§2.7). The what happens when creating card has five numbered rows, each with a bold title and a sentence: 1 can it run; 2 remove unused; 3 textures (10 §2); lock versions; put in place. An error-level finding makes row 1's number a red !, shows N remaining errors, lists them, and offers go fix, which opens Can it run. Otherwise the row says that sorting is specific to this pack, how many items move, and, in amber, how many Mods declare no version support. Row 2 keeps only current-version content and says how many Mods have directories for other versions and how much that saves. Insufficient space or unreadable Mods are red; the row is muted until the findings are fixed. Put in place writes the pack folder with its own saves and settings, leaving the plan's saves alone. While building, completed rows show checks and the current row a breathing circle. Pruning and locking happen together during copying. A progress bar and stop appear below (`view.ProgressOf`, with a Key for each row).
- **Textures** (`view.textureStep`): the selector has eight choices: no conversion, which copies PNG unchanged and is the default; pre-convert full size; and slim to 80 / 75 / 60 / 50 / 40 / 25% (`view.PackTextureChoices`, stored in `B.tex`). Opening the page measures no conversion. Changing the choice does not measure again, since reading the PNG files takes tens of seconds. The row asks the player to select an option and scan statistics to see the file count and final size, with scan statistics on the right; the summary shows not measured for this option. An explicit scan calls `API.BuildPage(tex)` to measure the files, final size and conversion peak in the background (§3.1 rule 9). Size fields show shimmer placeholders, and build is disabled until the results arrive. Building without a measurement is allowed: `BuildPage.ToolOK` tracks todds separately, and the build itself checks the peak space again. Below, no conversion explains the benefit of DDS. A conversion shows N PNG → DDS, no PNG in pack, video memory A → B, final X / peak Y. Below that are the counts of PNG files kept (beside a same-name DDS, or in other formats) and an amber warning if the pack grows. Space is checked against the peak; the summary shows the final size. If todds is missing, the row is red and says not installed: Library › Texture optimisation, with go install. Build is disabled and the row offers install todds or do not convert, linking to Texture optimisation. This page never downloads todds. `D` selects the next choice and appears in help; Tab reaches the selector and arrows change it. The preview uses the same `--textures [--texture-scale N]`.
- **Right summary**: the name, environment, Mod count, size before → after once the findings are fixed, own saves (empty at first) and pack.dir. Below are build (`B`, or Enter in the name) and see the list first, no disk (`V`).
- **Disabled build** (G14): errors disable building, with a red fix N problems link to Can it run below the button. Insufficient space, unreadable Mods, an invalid name or another build in progress also disable it and show the reason.
- **Preview**: `archo pack build --dry-run` expands inline below the summary (`API.PackDryRun`), without writing to disk. Repeating the action or pressing Esc collapses it. It is not a dialog (§3.1 rule 7).
- **Sizes need a walk through the Mod folders**: the page shows first, checks run under the lock, and `PackPlan.Measure` measures in the background outside the lock. Sizes are filled in when ready.
- **Unfinished builds** appear below through `view.UnfinishedRows`. Builds running in another window show progress and stop. Interrupted builds offer rebuild or delete copied files. These unfinished copies belong to RimArcho and are deleted directly rather than recycled (10 §2).
- Building runs in a subprocess and opens the pack page when it completes.

### 2.7 Packs

Packs are GUI `packs.js`; the TUI command panel's packs action shows text with commands.
- The list shows each pack's name, Mod count, size, full game version at build time (03 §3.1) and last played time (`view.PackRows`). Click or Enter opens a pack, and arrows move. The page's create a pack action uses `B`; unfinished builds appear above the list.
- Each pack is a sidebar sub-entry (`view.Nav`, §2.1), like each plan. In the TUI, Tab / shift+tab switches between sibling packs (§3.5) and Tab from the list opens the first pack; in the GUI they move the focus, and the sidebar, or ↑↓ and Enter on the list, open a pack.
- A pack page (`API.Pack` → `view.BuildPackPage`) shows spaced facts in the head: N Mods, size, supported versions, build date and environment, and last played. The actions are export (`e`, a save dialog, `pack export`); export list (`E`, a versioned RimArcho `.archolist.json` for sharing, `pack export --list`, 07 §7.3); recycle (Del, confirmed, `pack remove`); and a solid launch (`L`, `archo pack launch`, 10 §3). Below, the Mods appear in load order with their sizes and removed version directories; Core and DLC say from game. The folder location comes last.
- **Compare with game** (10 §5): a line after the facts appears only for a warning or an error. Examples: created for 1.6.4633 rev1261, game 1.6.4871 rev590, in amber; missing DLC Biotech, in red; and modified copies, in red, naming the Mods. Info, such as a missing recorded build or extra DLC, appears only on hover. Errors disable launch, with a tooltip saying why. `view.BuildPackPage` gets `Check` from `app.CheckPack`. The page does not compute digests again; copies are verified during import and pack check.
- Importing through the first-run guide's open action only unpacks `.archopack` files, v1 zip and v2 tar+zstd (10 §4). The result reports verification and comparison (`pack import`). List files, including RimArcho lists, and collection links go to the import preview, which marks Mods whose versions differ in RimArcho lists (07 §7.1).

### 2.8 Environments

The GUI environment page opens through the environment chip; in the TUI, `E` switches or deletes environments. Both use `view.BuildEnvPage` and `view.EnvGroups`.
- Every environment shows its name, version, game directory and current marker. Clicking one switches to it.
- **Remove**: remove game at the end of the row, Delete in the command panel's environment picker, or `d` in TUI `E`. `app.EnvRemovePreview` → `view.EnvRemovalLines` gives a preview and one confirmation. RimArcho forgets the launch records, the Mod identities read from Data / Mods, and that environment's history. Plans are shared by all environments and kept (07 §1.7). The game directory, all Mods, saves, shared folders and player-authored Mod data stay. Removal is refused while that game is running. Removing the current environment first switches to another; if none remain, the GUI opens the add guide. CLI `env remove <name>` only previews without `--yes`.
- The directories are the game and user data directories (`env set --game|--user-data`, which checks that the Mods are still the same and suggests `env rebind` before a change, 03 §4.2), Workshop, SteamCMD and extra directories. Removing a source forgets the folder but keeps its files. The player can add a SteamCMD directory, whose Mods can be enabled and are linked into `Mods/` on write (09 §3), or other Mod directories. Paths are typed directly, without a system picker.
- Launch settings are steam / direct (`env set --launch`) and extra arguments (`env set --launch-args`), such as -popupwindow, stored in `env:<id>:launch_args`.
- Adding an environment uses the first step of the guide (§2.15).
