# 16 · Interface · Settings (§2.14)

### 2.14 Settings

The settings page is implemented in the GUI. In the TUI, “settings” in the command panel shows the same groups as text, with the command that changes each value. Each item is a value and the command that changes it; the interface only runs that command. It runs only commands that `view.SettingCommand` allows: `env set`, `env rebind`, `folder add`, `folder remove`, `folder set`, `folder move`, `config set`, `db backup`, `db vacuum`, `cache clear`, `data update`, `gc`, `deps install`, `deps remove`, `source clean`, `source decompile`, `update` and `update --check`. The data comes from `view.SettingsPage`. Choices may have display labels (`choiceLabels`). Address display, native path selection and URL editing follow §3.1 rule 12. Locating and moving folders keep their command semantics. To move a folder, the player first chooses the destination parent directory; RimArcho then shows a preview and asks for confirmation.

**Order**: About comes first, then the common settings, then maintenance. The GUI and TUI follow the order of `view.SettingsPage`; the TUI inserts “this game” (the environment page's content) after About. The first 9 group headings take the focus keys `1`–`9` (§3.5). Keep group headings short.

- **Folders**: one row per directory, with the path as its value and “locate” and “move to…” at the right. “locate it after moving it yourself, or move it to a new location” appears once below the group heading (`SettingGroup.note`). Each row shows only its own status, such as “not used yet” or “directory unavailable; enter its new location, or reconnect the drive” (§7.3 item 7). Managed directories and Mod folders form one group, with the add rows last. If there is no Workshop folder, a Workshop row comes before the add rows. Clicking its address or “add…” chooses a folder; “use it” takes the one found in a Steam library.
- **Source library**: its Folders row shows the resolved path, the stored generated size, “locate”, “move to…”, “remove unused” and “decompile the current list's mods”. Opening Settings does not walk the library. “remove unused” computes a count and size preview without holding the page lock, asks for confirmation, then queues the cleanup, which checks again what is still in use. Decompiling queues a task with progress, stop and history (§2.16). Storage has no decompilation cache row. Retention and identity: 05 §5.4.
- **Accounts**: `view.AccountGroup` has one row per service, showing only the service name, a one-line status and “log in”. A signed-in row has “log in again” and “log out” instead. There is no permanent account field and no Apply or Verify button. SteamCMD sign-in expands a small inline field, prefilled with a known account name. `enter` signs in; `esc` cancels and returns the focus to the button. The password and Steam Guard code are entered only in SteamCMD's own console. After it closes, RimArcho verifies the session and checks game ownership (11 §3). The sign-out confirmation says that if Steam is offline or sign-out fails, RimArcho forgets the local login caches of all accounts in this managed SteamCMD. An external SteamCMD only says that it manages its own login, with no buttons.
- The SteamCMD status line, when not signed in, says “mod downloads available, not logged in”. When signed in, it says that Mod downloads are available, whether game downloads are available, and the account (“mod downloads available, game downloads available, account: <name>”). An unconfigured LoversLab shows only “log in”; it shows no account status in settings, subscriptions, automatic-check descriptions, or CLI and MCP summaries. Once enabled, its available status includes the cookie expiry (“available, Cookie expiry: <date or N/A>”). If sign-in is required, say why. The account row includes the last check time. Settings and subscription-source rows share the short statuses.
- The first LoversLab sign-in asks the player to confirm the adult content, the site rules, the use of their own account and the local encrypted session storage. There is no separate enable action, and later sign-ins do not repeat the explanation. The separate native window keeps the site's Remember me option and stores no password. Logging out only forgets the local session. Opening settings reads only the local status. Automatic checks (§2.16) renew the session and warn before sign-in becomes necessary; the account row shows a pending confirmation. File choices list the actual file names, sizes and dates inline, and fall back to the button text only when that metadata is missing. The player confirms the site's declarations each time. If the process fails, manual ZIP input remains available.
- The External tools group shows the last check time in muted text below its heading and “new version available: <version>” on each tool row with an update, which reuses “update tool”. A todds version that RimArcho has not verified is only a notice, with no install button. Updates and removal are refused while a tool is in use; boundaries: 17 §2.1.
- On / off switches (automatic checks, Workshop descriptions, description images, GPU acceleration and similar) show localized on / off labels; the command values stay `on` / `off`. The GUI and TUI both use `ChoiceLabels`.
- Account actions use a separate player API with an allowlist of services and actions. They never go through the CLI, MCP or generic setting commands. Sign-in and network requests use their own worker connections and do not hold the main UI mutex. Progress shows at once; a late result cannot reopen a page the player has already left (§3.1). All app text uses the text tables. Site content, Mod names and paths keep their original text.
- The environment page (§2.8) holds only what belongs to one game: its game folder and version, how the game is started (Steam / the game's own exe), saves (shared default / its own, with the actual directory below) and extra arguments. All of these are `env set`. Deleting an environment is also on that page (§2.8).
- Folders also lists the Workshop folder of a game downloaded through SteamCMD (03 §2 item 3), shown and removed like a SteamCMD folder the player added.
- **Interface appearance**: the theme, accent and launch-page background share the Interface card. Each swatch and theme choice takes the focus with `tab`. The arrow keys only move the focus; `Enter` or Space applies the choice. The focus stays and the page does not reload.
- **Launch-page background** (GUI Settings › Interface): the GUI setting `ui.gui.home.bg` stores a JSON object with the image, dimming, blur, focal point, rotation, starred images and custom images.
  - The top half has a miniature launch page at the left, with the list at the left, the launch button at the bottom right and the same dimming overlay as the launch page. The image name and “From <Mod name>” appear below it. The right side has dimming (0–80%, default 30%), blur (0–20, default 0), focal point (left / center / right: which part survives cropping) and rotation (a random starred image each time the window opens; if none is starred, tell the player to press `*`). Dragging a slider updates the preview; releasing it saves. Other changes save at once.
  - The bottom half has one tab per source group, each with a grid of thumbnails. The selected image has an accent border and ✓; starred images have ★ at the top right. The groups are:
    - **Game images**: read the current game's `Data/Core/Defs/Misc/ExpansionDefs/ExpansionDefs.xml` for the names and background packages. Core is always available. A DLC is listed only when the current game has its `Data/<defName>` directory; a shared cache or another game with the DLC does not make it available. All installations share one pair of menu JPEGs per packageId. Extract only missing or corrupt packages, using the source game's ExpansionDef `backgroundPath`:
      - **1.7**: when `Assets.zip` exists, read its unique `Resources/Textures/<backgroundPath>.*.dds` or `.*.dds.split` entry. Matching ignores case; several entries across the two suffixes also count as not unique. `.dds.split` supports DX10 BC7. Use the block counts of the full mip chain to parse the command table and the grouped endpoint and index streams. Validate the commands, record boundaries, fields and total length, then rebuild the blocks for the DDS row decoder. Other split formats fall back to the preview image. If candidates are missing, not unique or unsupported, log the resource path, the candidate entries and the preview fallback.
      - **1.6 and earlier, without `Assets.zip`**: read only the SerializedFile metadata and Texture2D objects in `RimWorldWin64_Data/resources.assets`. Read the mapping from `textures/<backgroundPath>` to an external file and object ID from the ResourceManager in `globalgamemanagers`, and resolve it exactly into `resources.assets`. Only when that mapping is unavailable may a unique, case-insensitive texture-name match be used; never guess among duplicates. Pixels come from the embedded object data or from the range of `resources.assets.resS` that `m_StreamData` names. Read only mip 0 and flip it, because Unity stores it upside down. The known Unity 2018–2022 Texture2D layouts are supported; other layouts use the fallback below. A DLC needs the current game's `Data/<defName>` directory. In 1.6, the Core and all five DLC menu images are in that `.resS`, so no DLC AssetBundle is read. If another version keeps the images in AssetBundles, skip extraction and use the preview images.
      - Prefer an extracted menu image. If the resources are missing or not unique, the layout is unsupported, or decoding or validation fails, fall back to the official Mod's `About/Preview.png` through the ordinary image cache. If neither is available, leave the image out. If the selected image is unavailable, use the default image, then a solid color. Extraction may use another registered game, but the preview fallback always comes from the current game.
      - Show one cell per available image, named by the ExpansionDef `label`. In Chinese, read the `ExpansionDef` translations from the game's Simplified Chinese Languages directory or `.tar`, falling back to `defName`. Preview images keep the official Mod names. The Core planet is the default. In the background, first publish the shared cache available for the current game, then fill in missing packages. This never blocks the page and does not enter background-task history (§3.1 rule 9). Try the registered installations from newest to oldest by `Version.txt`, including the current one; if a newer version lacks the artwork or extraction fails, continue with older versions. A cache hit opens no `Assets.zip` or Unity file and builds no texture catalog. Use a solid color until artwork is available, and push a refresh only if the list changes. The `game:<packageId>` keys stay the same, so selections, stars and rotation follow the available images. The last cell is Solid color, which uses no image and follows the theme.
    - **One group per background Mod**: installed Mods with “background” in their names, ignoring case, whether or not they are in the plan. Read their `VBE.BackgroundImageDef` (the Vanilla Backgrounds Expanded format, also used by Shella Backgrounds). The `label` names the image; `<path>.png/.jpg` is under any `Textures/` directory. Skip entries whose images cannot be found. If a Mod has no such Defs, list the landscape images at least 1280 pixels wide under its `Textures/` directory, reading only their headers. Only these Mods' folders are searched. Images packed in `Assets.zip` or available only as DDS are not supported.
    - **Custom**: the player adds PNG or JPG images with “Add image…”, which opens the system file dialog. Hovering shows ×, which removes only the entry and never deletes the file. Images from Mods without “background” in their names can be added here too.
  - Keys: `tab` enters the thumbnails, the arrow keys choose an image, `Enter` applies it (or adds an image on Add image), `*` stars it, `[` and `]` change the group, and `Delete` removes a custom image.
  - If the selected image cannot be found because the Mod was unsubscribed or the file was moved, use the default image; if that is also unavailable, a solid color.
  - **Cache and memory**: decode each original once, one image at a time. Resize it to two JPEGs in `cache/backgrounds/`: 1920 pixels wide for the launch page and 480 pixels wide for the thumbnail and preview. Ordinary images are named by path, size and modification time. Game menu pairs use the first 12 bytes of the SHA-256 of the lowercase packageId plus the format version: `menu-shared-v1-<hash>-1920.jpg` / `-480.jpg`. These names do not depend on the installation path, game version, ZIP or Unity fingerprint, or interface language. Store only one pair per package. Validate the JPEG size, dimensions and full decode. Within a process, remember a validation by path, size and modification time; while these are unchanged, only check the file status. Extract again only a package whose pair is missing, corrupt or the wrong size. Older `menu-<stamp hash>-*.jpg` files are ignored and kept; player files are never deleted. A game update does not invalidate the shared cache. To refresh the artwork, close RimArcho, delete only `cache/backgrounds/menu-shared-v1-*.jpg` (or only the target package's pair) and open the app again; an external browser also needs a hard refresh. During extraction, validate the source fingerprints. If a source changes or the operation is cancelled, discard the temporary files and keep the existing ones. Replace JPEGs atomically through temporary files. Game ZIP reading supports zstd (method 93) and deflate and verifies each entry's full size and CRC-32. DDS and Unity decoding support BC7, BC1 and BC3; Unity also supports RGBA32. Decode 4 rows at a time, straight into box scaling. ZIP entries are capped at 128 MiB. For split data, validate the DDS dimensions (each side ≤ 16384, at most 40 million pixels), the mip count and the payload bounds derived from the block counts before allocating one split buffer of the declared length. The command table refers into that buffer. After checking the ZIP size and CRC-32, rebuild 16-byte blocks as needed, without allocating a fully restored DDS or full-size pixels. After the thumbnail is done, still read the remaining mip records to validate their fields; if validation fails, publish no JPEG. Ordinary DDS uses no whole-entry buffer. Unity metadata has a size limit; pixel ranges are read without loading the whole `.resS`. Never allocate or store full-size RGBA, a restored DDS or a PNG, and release the memory after each image. Scale other images straight from the decoder output, without another full-size bitmap. Memory is released after batches with a debounce (§2.16.1 M03). Thumbnails load only when they scroll into view. `/bg` serves only images listed for the current environment, never arbitrary paths. The URL includes the image path's version. Shared menu images use the same URL in every game; ordinary images keep their own cache versions.
- **Uninstall RimArcho** (02 §2): the button in the last settings group opens a separate page with the breadcrumb “settings / uninstall RimArcho”. It has no environment label because it covers all games. The command panel can also open it. The data comes from `view.UninstallPage` (`API.UninstallPlan`, recalculated from the player's choices).
  - A relocated source library is its own step, with its path, size and direct deletion, in the shared GUI/TUI confirmation. Generated code can be regenerated, so the step has no keep/delete choice. If a scheduled deletion of the data folder already covers it, it is not listed or counted again. Refuse library links, linked ancestors and links inside the library; check the recorded root again under exclusive library access before deleting. Remove only that root and leave outside links unchanged. Retained saves and packs cannot be moved into it.
  - The page has one card with one row per step: the name, one sentence on the consequences with counts and sizes, and checkboxes at the right for steps with choices. For the game's Mod list, offer to restore the list from before RimArcho's last write, only when a backup exists. For lock-library copies, offer to keep them as ordinary Mods; checking this adds a choice of the destination environment's Mods folder, omitted when there is only one game. For packs, own saves and downloaded games, offer deletion to the recycle bin. If packs inside the data directory or own saves are kept, a following “move to [folder] change…” row appears, defaulting to `Documents\RimArcho packs` and `Documents\RimArcho saves`. Each step's folders and files are collapsed under its counts (`details`; `enter` expands them). All questions stay inline instead of a sequence of dialogs.
  - “uninstall RimArcho…” at the bottom opens the only confirmation dialog (§6). For each step, it lists what will change or be deleted and what will be kept, with counts, sizes and how each is handled. It tells recycling, permanent deletion and deletion after closing apart, and shows where moved content goes. Sizes that were not measured are labelled as such, never shown as zero. The destructive-color Uninstall button runs the plan; Cancel has the initial focus. `Enter` acts on the focused control, `Esc` or a click outside cancels, and `Tab` stays inside the dialog. The GUI and TUI share `view.UninstallConfirmation`. When TUI parameters change the choices, the TUI shows the new summary before `uninstall` asks for confirmation. If uninstall is blocked by a running game, another RimArcho process or conflicting choices, the page shows the reason in red at the top and disables running it.
  - Running it opens a progress page with a centered progress bar by step and text naming the current step. The full step list is collapsed by default and can be expanded with the mouse or keyboard. Finished steps show ✓, the current step shows “in progress”, later steps are muted, and the last two deferred steps show “after closing”. A running step is never marked finished early. During uninstall, the explanation for a blocked window close appears only on this page. Navigation and page keys are unavailable. Go keeps the progress and the report, so they survive a frontend refresh. The final report shows an overall result and, for each step, ✓, ✗ with the reason, or … for deletion after closing. Failed steps expand automatically. After full success only “close RimArcho” remains; the development browser page tells the player to close the window instead. If any step failed, offer to uninstall again, which reopens the plan.
  - During uninstall, Go intercepts window close and application exit (`uninstall.go`), independently of frontend flags. Alt+F4, taskbar close, and the native and custom close buttons all go through the close hook. The page explains that uninstall must finish before the window can close. Closing works again after success or failure. On Windows, RimArcho also registers a shutdown-block reason in the current interface language, from the view text table, and refuses the current shutdown or sign-out request. A forced shutdown, killing the process or a power loss cannot be blocked reliably.
  - The page uses native controls throughout. `tab` or `shift+tab` moves among checkboxes, choices, path copying, change…, collapsed counts and buttons. Space toggles a checkbox; `Enter` presses a button or expands a collapsed section. Checking a box or changing a folder keeps the focus on that control.
  - `uninstall --yes` in the GUI or TUI command line enters the same protected flow. Without `--yes`, it only previews the plan. The CLI and MCP behave as described in 02 §2.
  - In the TUI, the command panel opens a panel with the same plan as the GUI. `enter` requests `uninstall`; CLI parameters may be added to change the choices. Any other input cancels. Uninstall runs in a separate background session while the panel shows the steps and i / n. While it runs, `ctrl+c`, `q` and `esc` do not exit; the status gives the same explanation, and other navigation is disabled. The final report restores the exit keys.
- **Feedback** (GUI `feedback.js`; data `view.FeedbackAttachments`, `view.ComposeFeedback` and `view.SendFeedback`; body, links and sending in `internal/feedback`; relay in `feedback-relay/`): a Settings subpage with the breadcrumb “settings / feedback”, also reachable from the command panel. The form is a page, never a dialog (§3.1 rule 7). Both routes create a public issue in [ToumanLin/RimArcho](https://github.com/ToumanLin/RimArcho):
  - **Send** needs no GitHub account. RimArcho POSTs the report to a Cloudflare Worker relay, which creates the issue through a GitHub App with Issues read/write permission on this repository only. The private key stays in the Worker's secrets; RimArcho contains only the relay URL.
    - The URL is compiled into `feedback.Relay` (`internal/feedback/relay.go`). `RIMARCHO_FEEDBACK_RELAY` overrides it, so a deployment can be tested before its URL is built in. An empty URL hides Send and the contact field, leaving only the GitHub route.
    - Only HTTPS is accepted; localhost HTTP is allowed for tests. The timeout is 30 seconds.
    - Against abuse, the relay accepts 1 report per sender per minute, 5 per sender per day and 30 in total per day. It also limits the length. `@someone` does not notify anyone.
    - For privacy, the IP is hashed only for the relay's counters and never appears in an issue.
    - Deployment and changing the limits: `feedback-relay/README.md`.
  - **Open GitHub** is for players with an account. The browser opens a prefilled new-issue page, and the player submits the issue there; see the bottom controls below.
  - 1 Content: a title and a description. With a relay, there is also an optional, non-public contact field, such as a Discord name or email address. The contact goes only to the relay, which stores it separately for the maintainer (`contact:<issue number>`, 180 days); it never appears in the issue. A blank title takes the first line of the description, up to 60 characters. The draft survives leaving and returning while the app stays open. A successful send clears the title and description and keeps the contact.
  - 2 Attach: basic information (the RimArcho and game versions and the OS, read from the registry by `feedback.System`) is always attached and cannot be unchecked. Enabled Mods (the current list in load order, with name, packageId and Workshop ID), paths (the game, game data, Mod folders and RimArcho data) and the game log (up to 40 clusters from the latest Player.log, as on the log page) are unchecked by default. Unavailable attachments are disabled with the reason. Attachments replace the user directory with `%USERPROFILE%` to hide the Windows user name. If the chosen log is still being analysed, say so and read it again every second.
  - 3 Preview: a readable view, not raw Markdown: the title and description, the basic information lines, then one collapsible section per attachment (`<details>`, collapsed at first). Open sections stay open while editing. No HTML or Markdown syntax is shown. The full body that is sent or copied is Markdown: the player's description, a separator, the basic information, and each attachment in a collapsed `<details>` code block. The body does not repeat the title, and there is no explanation beside the buttons. The TUI uses `view.FeedbackPreview` with the same sections, two-space indentation and no folding. Beside the heading, “public on GitHub” warns that the report will be public for both routes. The sent body is capped at 60,000 characters (`feedback.MaxBody`; GitHub's limit is 65,536). If it is too long, lines are trimmed from the end of the longest attachment and “… N more lines” is appended (`Draft.SendBody`). The relay appends a small line saying that the report was sent from RimArcho.
  - With a relay, the bottom has “copy the text”, “open GitHub” and the primary “send”. Send is disabled while both title and description are empty and says “sending…” during the request. On success, the status and the bottom line say that the report was sent as GitHub #N; clicking the bottom line opens the issue. A rejection gives the reason in plain words: one per minute, this computer's daily allowance, the total daily allowance (with the GitHub route as the alternative), or too long. The draft is kept.
  - Without a relay, the bottom has one status sentence, “copy the text” and the primary “open GitHub”. In both variants, “open GitHub” opens the repository's `issues/new?title=…&body=…` URL without a token. RimArcho submits nothing itself; the player signs in and submits on GitHub. The URL is capped at 2000 characters (`feedback.MaxURL`; Windows ShellExecute fails above 2083, while GitHub accepts about 8 KB). If the full body does not fit, the URL carries only the title, the description if it fits, the basic information and an instruction to paste the full text. The bottom line then becomes an amber explanation (absent when a relay is available), and the button becomes “copy and open GitHub”, which copies the full body before opening the browser.
  - In the TUI, feedback in the command panel opens a text panel with the same three optional attachments. `m`, `p` and `l` toggle them; `r` reads them again. A warning that the report is public on GitHub and the readable `view.FeedbackPreview` appear below.
    - With a relay, `s` asks for the title, the description and the contact in turn. Each input is one line; `esc` cancels. Sending runs in the background, and the status reports GitHub #N and its address, or the reason for a rejection.
