### 2.14 Settings

The settings page is implemented in the GUI. In the TUI, “settings” in the command panel shows the same groups as text, with the command that changes each value. Each item is a value and the command that changes it; the interface only runs that command. It runs only commands that `view.SettingCommand` allows: `env set`, `env rebind`, `folder add`, `folder remove`, `folder set`, `folder move`, `config set`, `db backup`, `db vacuum`, `cache clear`, `data update`, `gc`, `deps install`, `deps remove`, `source clean`, `source decompile`, `update` and `update --check`. The data comes from `view.SettingsPage`. Choices may have display labels (`choiceLabels`). Address display, native path selection and URL editing follow §3.1 rule 12. Locating and moving folders keep their command semantics. To move a folder, the player first chooses the destination parent directory; RimArcho then shows a preview and asks for confirmation.

Per-config settings, including removal and shared-folder move confirmation, are on the Game Config page (§2.8); Settings does not repeat them. Shared Mod folders remain global.

**Number keys.** `1`–`9` focus the groups in the order the page shows them (§3.5), whatever the group numbers in the table say; only the first nine take a key. In 1.1 there is no Archo Agent group (15 §7.0): External tools is 8, Community data 9, and Storage and Uninstall have no key. In a build with it, Archo Agent (7a) exists on Windows only, so there it is group 8 and pushes External tools to 9 and Community data, Storage and Uninstall past the keys; on other systems External tools is 8, Community data 9, and Storage and Uninstall have no key. The table's numbers name groups, not keys.

      - **1.7**: when `Assets.zip` exists, read its unique `Resources/Textures/<backgroundPath>.*.dds` or `.*.dds.split` entry. Matching ignores case; several entries across the two suffixes also count as not unique. `.dds.split` supports DX10 BC7. Use the block counts of the full mip chain to parse the command table and the grouped endpoint and index streams. Validate the commands, record boundaries, fields and total length, then rebuild the blocks for the DDS row decoder. Other split formats fall back to the preview image. If candidates are missing, not unique or unsupported, log the resource path, the candidate entries and the preview fallback.

Read the mapping from `textures/<backgroundPath>` to an external file and object ID from the ResourceManager in `globalgamemanagers`, and resolve it exactly into `resources.assets`. Only when that mapping is unavailable may a unique, case-insensitive texture-name match be used; never guess among duplicates. Pixels come from the embedded object data or from the range of `resources.assets.resS` that `m_StreamData` names. Read only mip 0 and flip it, because Unity stores it upside down. The known Unity 2018–2022 Texture2D layouts are supported; other layouts use the fallback below. A DLC needs the current game's `Data/<defName>` directory.   - If the selected image cannot be found because the Mod was unsubscribed or the file was moved, use the default image; if that is also unavailable, a solid color.
  - **Cache and memory**: decode each original once, one image at a time. Resize it to two JPEGs in `cache/backgrounds/`: 1920 pixels wide for the launch page and 480 pixels wide for the thumbnail and preview. Ordinary images are named by path, size and modification time. Game menu pairs use the first 12 bytes of the SHA-256 of the lowercase packageId plus the format version: `menu-shared-v1-<hash>-1920.jpg` / `-480.jpg`. These names do not depend on the installation path, game version, ZIP or Unity fingerprint, or interface language. Store only one pair per package. Validate the JPEG size, dimensions and full decode. Within a process, remember a validation by path, size and modification time; while these are unchanged, only check the file status. Extract again only a package whose pair is missing, corrupt or the wrong size. Older `menu-<stamp hash>-*.jpg` files are ignored and kept; player files are never deleted. A game update does not invalidate the shared cache. To refresh the artwork, close RimArcho, delete only `cache/backgrounds/menu-shared-v1-*.jpg` (or only the target package's pair) and open the app again; an external browser also needs a hard refresh. During extraction, validate the source fingerprints. If a source changes or the operation is cancelled, discard the temporary files and keep the existing ones. Replace JPEGs atomically through temporary files. Game ZIP reading supports zstd (method 93) and deflate and verifies each entry's full size and CRC-32. DDS and Unity decoding support BC7, BC1 and BC3; Unity also supports RGBA32. Decode 4 rows at a time, straight into box scaling. ZIP entries are capped at 128 MiB. For split data, validate the DDS dimensions (each side ≤ 16384, at most 40 million pixels), the mip count and the payload bounds derived from the block counts before allocating one split buffer of the declared length. The command table refers into that buffer. After checking the ZIP size and CRC-32, rebuild 16-byte blocks as needed, without allocating a fully restored DDS or full-size pixels. After the thumbnail is done, still read the remaining mip records to validate their fields; if validation fails, publish no JPEG. Ordinary DDS uses no whole-entry buffer. Unity metadata has a size limit; pixel ranges are read without loading the whole `.resS`. Never allocate or store full-size RGBA, a restored DDS or a PNG, and release the memory after each image. Scale other images straight from the decoder output, without another full-size bitmap. Memory is released after batches with a debounce (§2.16.1 M03). Thumbnails load only when they scroll into view. The list is kept per game installation, not per Game Config: the configs of one game show the same images, so switching between them reads nothing again. The preview fallbacks come from the Game Config's Mods (`BackgroundTargets`) and are recomputed when they change (a scan), without a Settings visit. `/bg` serves only images listed for the current game, never arbitrary paths. The URL includes the image path's version. Shared menu images use the same URL in every game; ordinary images keep their own cache versions.
