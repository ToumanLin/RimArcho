### 2.14 Settings

The settings page is implemented in the GUI. In the TUI, “Settings” in the command palette displays text with commands. Each item consists of a value and the command that changes it; the UI only invokes that command. The UI runs only commands allowed by `view.SettingCommand`: `env set`, `env rebind`, `folder add`, `folder remove`, `folder set`, `folder move`, `config set`, `db backup`, `db vacuum`, `cache clear`, `data update`, `gc`, `deps install`, `deps remove`, `source clean`, `source decompile`, `update`, and `update --check`. The data comes from `view.SettingsPage`. Choices may have display labels (`choiceLabels`). Address display, native path selection, and URL editing follow §3.1 rule 12. Relocating and moving folders retain the existing command semantics. To move a folder, first select the destination parent directory, then show the preview and ask for confirmation.

**Order**: show About first, followed by common settings, with maintenance settings last. The GUI and TUI follow the order in `view.SettingsPage`; the TUI adds “Current game,” containing the environment-page content, after About. The first 9 group headings have focus keys `1`–`9` (§3.5). Keep the group headings short.

- **Launch-page background** (GUI Settings › Interface, 2026-10-24): the GUI setting `ui.gui.home.bg` stores a JSON object containing the image, dimming, blur, focal point, rotation, starred images, and custom images.
  - The top half has a miniature launch page at the left, showing the list at the left and the launch button at the bottom-right, with the same dimming overlay as the launch page. The image name and “From <Mod name>” appear below it. The right side has dimming (0–80%, default 30%), blur (0–20, default 0), focal point (left / center / right, determining which part survives cropping), and rotation (a random starred image each time the window opens; prompt the player to press `*` if none are starred). Dragging a slider updates the preview; releasing it saves the change. Other changes save immediately.
  - The bottom half has source-group tabs containing thumbnail grids. The selected image has an accent border and ✓; starred images have ★ at the top-right. The groups are:
    - **Game images** (2026-10-24): read the current game's `Data/Core/Defs/Misc/ExpansionDefs/ExpansionDefs.xml` to determine the names and background packages. Core is always available. List a DLC only when the current game has its `Data/<defName>` directory; a shared cache or another game having the DLC does not make it available. All installations share a pair of menu JPEGs per packageId. Extract only missing or corrupt packages, using the source game's ExpansionDef `backgroundPath`:
      - **1.7**: when `Assets.zip` exists, read its unique `Resources/Textures/<backgroundPath>.*.dds` or `.*.dds.split` entry. Matching is case insensitive; multiple entries across the two suffixes also count as non-unique. `.dds.split` supports DX10 BC7. Use the block counts for the full mip chain to parse the command table and the grouped endpoint and index streams. Validate the commands, record boundaries, fields, and total length, then reconstruct the blocks for the DDS row decoder. Other split formats fall back to the preview image. If candidates are missing, non-unique, or unsupported, log the resource path, candidate entries, and preview fallback.
      - **1.6 and earlier, without `Assets.zip`**: read only the SerializedFile metadata and Texture2D objects in `RimWorldWin64_Data/resources.assets`. Read the mapping from `textures/<backgroundPath>` to an external file and object ID from the ResourceManager in `globalgamemanagers`, and resolve it exactly into `resources.assets`. Only when that mapping is unavailable may a unique, case-insensitive texture-name match be used; never guess among duplicates. Pixels come from embedded object data or the range of `resources.assets.resS` specified by `m_StreamData`. Read only mip 0 and flip it to account for Unity's inverted storage. Support the known Unity 2018–2022 Texture2D layouts; other layouts use the fallback below. A DLC requires the current game's `Data/<defName>` directory. Measurements show that the 1.6 Core and five DLC menu images all reside in that `.resS`, so no DLC AssetBundle reads are needed. If other versions store the images in AssetBundles, skip extraction and use previews for now.
      - Prefer a successfully extracted menu image. If resources are missing or non-unique, the layout is unsupported, or decoding or validation fails, restore the official Mod's `About/Preview.png` fallback through the ordinary image cache. Omit an image if neither source is available. If the selected image is unavailable, fall back to the default image, then to a solid color. Extraction may use another registered game, but the preview fallback always comes from the current game.
      - Show one cell per available image, using the ExpansionDef `label` as the menu image name. The Chinese UI reads `ExpansionDef` translations from the game's Simplified Chinese Languages directory or `.tar`, falling back to `defName`. Preview images retain the official Mod names. The Core planet remains the default. In the background, first publish the shared cache available for the current game, then fill in missing packages. Never block the page or add this work to background-task history (§3.1 rule 9). Try registered installations from newest to oldest by `Version.txt`, including the current installation. If a newer version lacks the artwork or extraction fails, continue to older versions. A cache hit does not open `Assets.zip` or Unity files or build a texture catalog. Use a solid color until artwork is available, and push a refresh only if the list changes. Retain the `game:<packageId>` keys so that existing selections, stars, and rotation automatically correspond to the available images. The final cell remains Solid color, which uses no image and follows the theme.
    - **One group per background Mod**: list installed Mods with “background” in their names, case insensitive, whether or not they are in the plan. Read their `VBE.BackgroundImageDef` (the Vanilla Backgrounds Expanded format, also used by Shella Backgrounds). The `label` names the image; `<path>.png/.jpg` is under any `Textures/` directory. Skip entries whose images cannot be found. If a Mod has no such Defs, list the landscape images at least 1280 pixels wide under its `Textures/` directory, reading only the headers. Inspect only the folders of these Mods whose names match; do not search other Mods. Images packed in `Assets.zip` or available only as DDS are unsupported for now.
    - **Custom**: the player can add PNG or JPG images through “Add image…”, which opens the system file dialog. Hovering reveals ×, which removes only the list entry and never deletes the file. Images from Mods without background in their names can also be added here.

  - If the selected image cannot be found because the Mod was unsubscribed or the file was moved, use the default image. If the default is also unavailable, use a solid color.
  - **Cache and memory** (2026-10-24): decode each original once, one image at a time. Resize it to two JPEGs, 1920 pixels wide for the launch page and 480 pixels wide for the thumbnail and preview, in `cache/backgrounds/`. Ordinary images are named using the path, size, and modification time. Game menu pairs use the first 12 bytes of the SHA-256 of the lowercase packageId plus the format version: `menu-shared-v1-<hash>-1920.jpg` / `-480.jpg`. These names are independent of the installation path, game version, ZIP or Unity fingerprint, and UI language. Store only one pair per package. Validate the JPEG size, dimensions, and full decode. Within a process, memoize validation by path, size, and modification time; when these are unchanged, perform only file status checks. Re-extract only the package with a missing, corrupt, or dimensionally mismatched pair. Ignore and retain old `menu-<stamp hash>-*.jpg` files; never delete player files. Game updates do not automatically invalidate the shared cache. To refresh the artwork, close RimArcho, delete only `cache/backgrounds/menu-shared-v1-*.jpg` (or just the target package's pair), and reopen the app. External browsers require a hard refresh. During extraction, validate the source fingerprints. If the source changes or the operation is cancelled, discard the temporary files without replacing existing members. Replace JPEGs atomically through temporary files. Game ZIP reading supports zstd method 93 and deflate and verifies the full entry size and CRC-32. DDS and Unity decoding support BC7, BC1, and BC3; Unity also supports RGBA32. Decode only 4 rows at a time, directly into box scaling. ZIP entries are capped at 128 MiB. For split data, validate the DDS dimensions (each side ≤ 16384 and ≤ 40 million pixels), mip count, and payload bounds derived from block counts before allocating one split buffer of the declared length. The command table references that buffer directly. After validating the ZIP size and CRC-32, reconstruct 16-byte blocks as needed, without allocating a fully restored DDS or full-size pixels. After completing the thumbnail, still traverse the remaining mip records to validate their fields; do not publish a JPEG if validation fails. Ordinary DDS uses no whole-entry buffer. Unity metadata has a size limit; read pixel ranges without loading the entire `.resS`. Never allocate or store full-size RGBA, a restored DDS, or PNG, and release the memory after each image. Scale other images directly from the decoder output without copying another full-size bitmap. Debounce memory release after batches (§2.16.1 M03). Load thumbnails only when they enter view. `/bg` serves only images listed for the current environment, never arbitrary paths. The URL includes the image-path version. Shared menu images use the same URL across games; ordinary images retain their individual cache versions.
- **Uninstall RimArcho** (2026-10-22, 02 §2): the button in the final settings group opens a separate page with the breadcrumb “Settings / Uninstall RimArcho”. It has no environment label because it covers all games. The command palette can also open it. The data comes from `view.UninstallPage` (`API.UninstallPlan`, recalculated from the player's choices).

Retained saves and packs cannot be moved into it.
  - The page has one card, with one row per step: the name, one sentence describing the consequences with counts and sizes, and checkboxes at the right for steps with choices. Collapse each step's folders and files under its counts (`details`; enter expands them). Keep all questions inline rather than opening a sequence of dialogs.
  - “Uninstall RimArcho…” at the bottom opens the sole confirmation dialog (§6). - **Feedback** (2026-10-31; GUI `feedback.js`; data `view.FeedbackAttachments`, `view.ComposeFeedback`, and `view.SendFeedback`; body, links, and sending in `internal/feedback`; relay in `feedback-relay/`): this is a Settings subpage with the breadcrumb “Settings / Feedback,” also available in the command palette. The form is a page, never a dialog (§3.1 rule 7). Both routes create a public issue in [ToumanLin/RimArcho](https://github.com/ToumanLin/RimArcho):
  - **Send** requires no GitHub account. RimArcho sends the report by POST to a Cloudflare Worker relay. The relay creates the issue through a GitHub App with Issues read/write permissions limited to this repository. The private key stays in the Worker secrets; RimArcho contains only the relay URL.
    - The URL is compiled into `feedback.Relay` (`internal/feedback/relay.go`). `RIMARCHO_FEEDBACK_RELAY` overrides it so that a deployment can be tested before its URL is embedded. An empty URL hides Send and the contact fields, leaving only the GitHub route.
    - Only HTTPS is accepted; localhost HTTP is allowed for tests. The timeout is 30 seconds.
    - The relay limits abuse to 1 report per sender per minute, 5 per sender per day, and 30 in total per day. It also limits the length. `@someone` does not send a notification.
    - For privacy, the IP is hashed only for the relay counters and is never included in an issue.
    - See `feedback-relay/README.md` for deployment and changes to the limits.
  - **Open GitHub** is for players with accounts. The browser opens a prefilled new-issue page, and the player submits the issue there; see the page-bottom controls below.

If the title is blank, use the first line of the description, up to 60 characters. The draft survives leaving and returning during the current opening of the app. A successful send clears the title and description but retains the contact information.

If the selected log is still being analyzed, say so and reread it every second.

Show the title and description, the basic information lines, then one collapsible section per attachment (`<details>`, initially collapsed). Preserve open sections during edits. Show no HTML or Markdown syntax. The full body sent or copied remains Markdown: the player's description, a separator, basic information, and each attachment in a collapsed `<details>` code block. Beside the heading, say that the report will be publicly visible on GitHub for both routes. The send body is capped at 60,000 characters (`feedback.MaxBody`; GitHub's limit is 65,536). If it is too long, trim lines from the end of the longest attachment and append “… N more lines” (`Draft.SendBody`). The relay appends a small attribution line saying it was sent from RimArcho.
  - With a relay, the bottom has Copy full text, Open GitHub, and the primary Send button. Disable Send when both the title and description are empty, and show Sending during the request. The bottom line becomes an amber explanation, absent when a relay is available. The button becomes Copy full text and open GitHub and copies the full body before opening the browser.
