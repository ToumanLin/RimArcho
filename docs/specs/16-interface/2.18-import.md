### 2.18 Import

Import is one page where every import starts, so a player who wants to bring something in finds it without knowing which feature owns it (C1 of `docs/design/2026-11-18_ux-scenarios.md`). Since 2026-11-20 it has no export side: the page was “Import & export” before (see “Export” below). It is the first entry in the sidebar's Library group (§2.1), above Lists, with no `shift+` key: `shift+1–8` stay the eight pages the TUI also has (§3.5). The page ID stays `import` (deep links, the `imp` reference numbers, the palette and `i`). The breadcrumb is “library / import”; the group's “library” crumb still opens Lists. The TUI has no Import page; its imports are commands (07 §6.2, §7; 10 §4).

**Entries**: the sidebar entry; `i` in the list editor (All lists' `i` keeps its own import mode); a file dropped on any page (“Dropping files” below); Settings' “import from RimSort, RimCrow or RimPy” row (§2.14); the command palette's “import a list”; and the first-run guide after its scan (§2.15), which opens the page's first-run view (below). They all open this page. All lists' “new / import” form keeps its own import mode for now (§2.17), and the guide still chooses a pack itself.

**Layout** (under review, 2026-11-20: two arrangements are compared in `docs/design/2026-11-20_import-page.md`; `<html data-import-layout>` or `?import-layout=` switches them until the player's pick is written here): the lead asks “What do you want to bring in?” and has no buttons (`esc` leaves, as the hint line says). The first column lists the **kinds of import**, one per row as an icon and a short name, what it takes on hover; ↑↓ move through them (a vertical tab list). The picked kind's **source** (a button, a drop area, a field, or the managers found) and the **preview** of what it brings fill the rest: in “2col” the source sits over the preview, in “3col” beside it. The kinds column stays in view while a long preview scrolls. The page remembers the picked kind while the window is open; it opens on the game's list when the game has one, else on the list file. The preview is drawn like the sections of Settings: one card of rows on the page's type scale (13px names, 12px lines), with its own label (“Preview”, “Adding a pack”, “What comes over from RimSort”, “Moving in from RimSort”, “Not imported”). Its foot holds its buttons at the right, the filled one last, and stays at the bottom of the view while a long result scrolls past. A new source replaces it; “close” empties it, and the empty preview shows a quiet dashed area that says a file can be dropped anywhere. While the player looks at another kind, the kind the preview came from carries a dot. The hint line shows `tab` import destination and `enter` import only while a list preview is shown.

| Kind (icon) | You get | Source |
| --- | --- | --- |
| Game's list (start) | the current Game Config's ModsConfig.xml as a list, compared with yours; its Mod count after the name (`Exchange.Game`) | “The game's current list”, “N Mods”, its path on hover, “read it”; picking the kind reads it at once (one click to the preview). Disabled when the game has none |
| List file (lists) | a new list, or changes to one of yours | a drop area (an import icon, “drop it here”, the extensions as chips, the sentence on hover) with “choose a file…” (`API.PickAnyImport`); a click on the area opens the dialog too |
| Link or code (link) | the same, from a Steam collection or Rentry link, a share code or a copied list | a three-line field with “paste” (from the clipboard) and “read” (`enter` in the field; `shift+enter` adds a line); “read” says in its tooltip that links are read from Steam or Rentry |
| Pack (packs) | a pack you can launch; its Mods are copied and checked file by file | a drop area for `.archopack` with “choose a pack…” (`API.PickPackFile`) |
| Other managers (import) | lists, notes and tags, sorting rules and, from RimCrow, Game Configs; the files are only read | a row per manager found on this computer, then “Somewhere else” with “another folder or file…” (`API.PickManagerImport`); the kind shows how many managers were found, with a dot when one has something new |

“choose a file…” and a dropped file send a file where it belongs: a pack to the pack's task, a RimCrow database, a RimSort `aux_metadata.db` or `userRules.json` (`API.ManagerFileKind`) to the managers (it joins the survey and its manager is picked), anything else to the list preview. The kind follows the file.

**Dropping files** (since 2026-11-20): a file dragged over any page dims the window under one dashed box, “drop to import” with the list, pack and manager icons (`.xc-dropover`; it takes no pointer events, so the drop reaches the page). Dropped, the file opens the Import page with its kind picked. What it is follows from its name (`dropKind` in `exchange.js`): `.xml`, `.rml`, `.json`, `.txt`, `.rws` are lists; `.archopack` is a pack; a `.db` file or `userRules.json` is another manager's data; a folder is a manager's data folder; anything else is refused in the preview (“Not imported”, the file's name after a red stop mark, and what RimArcho imports), with Archo shaking and the status line saying so. Several files: the first is read and the status line says one file at a time. A form that takes drops itself (All lists' new / import, §2.17) handles them first. A dropped list is read from its content; a dropped pack, database or folder needs its path, which only a native drop gives (`dropped({path})` sends it where “choose a file…” would). **Known gap**: the Windows window uses WebView2 composition hosting (§8.2), under which the window has no OLE drop target, so files dropped on the native window do not reach the page yet; until the window registers one (options in `docs/design/2026-11-20_import-page.md`), drops work in the browser harness only, and without a path a pack, database or folder is answered “choose this file with “choose a file…”” (amber mark).

**List preview and destinations** are those of the editor's import subpage (§2.17), as rows: the source row (the format, such as “RimSort list”, then installed and not installed as a two-part bar, green and red, with “✓ N” and “✕ N” after it, named by the summary “RimSort list: 212 mods, 205 installed, 7 not installed” (§7 principle 9); then the source, the list name, the game version and the suggested versions on one line; another game version in amber); then **the comparison** with what the player has now: one bar of four kinds, each with its icon and count under it (✓ already in your list, green; + installed but not in your list, accent; the versions mark for another version, amber; ✕ not installed, red; a kind with none is faint), named by its words (“165 already in your list, 37 installed, not in your list, 3 in another version, 7 not installed”, `compareParts`), and at its right the current list's name (faint) with what replacing it does as + − ↕ ⇄ marks; a “Mods” group with “not installed: N” (with “subscribe all N”, a plain button, and the Mods indented below it) and “installed: N” (“N enabled now”, “N in another version”; folded unless some are in another version); an “import destination” group of choice rows picked with a click and a round mark: “import as a new list” with its labelled “new list name” field at the right, “replace <list>” and “add the ones you lack”, each with what it does as Saves' change marks (“+1  −2  ↕8”, ⇄ for a Mod switched to another version; named by `ImportEffect.Text`, “1 added, 2 removed, 8 moved  121 enabled after it”, §7 principle 9); then “follow this collection from now on” as a check row for a Steam collection. The foot has “close” and “import [enter]”; while the import runs the button is busy (a turning mark, `aria-busy`), the status line says “importing…” and Archo thinks. A list the selected list already is (`ImportEffect.Same` for replace), with no collection to follow and no Mod settings, shows “<list> already matches the game.” (the game's current list) or “<list> already is this list.” and only “close”. “new list name” for the game's current list starts as the current Game Config's name, not the file's. A read that fails shows “could not read it” and the reason in amber. The lists' new / import form (§2.17) shows the same source and Mods rows in its form. A RimArcho list that carries Mod settings (07 §7.3) adds the fact “Mod settings of N mods” and a “Mod settings” group of check rows: “apply settings” (off), which when ticked shows the per-Mod preview (`API.ImportSettings`, dry run): a box per Mod (on; a Mod not installed is disabled) and what applying does to its files (N new, N replaced, N kept, N the same), with “replace settings files I have” (off; the old ones go to the recycle bin). The import button applies the chosen Mods' settings after the import and the status line adds how many files were written. The selected list is the current list, or the list selected on All lists or in the editor when the page was opened from there. “cancel” (`esc`) returns to the page the player came from.

**A pack** is added as a background task in the RimArcho queue (`pack-import`, §2.16; `API.StartPackImport`, 10 §4). A newer revision of a pack the player has (`API.PackUpdateOffer`) first asks “update pack <name> to revision N” with the revision the player has, that saves and settings stay, and the Mods added, removed and changed; “update the pack” starts the task with the update, cancel adds nothing. The preview (“Adding a pack”) shows its name, “adding the pack…” with a moving bar, and “background tasks”; when it ends, the pack's report and “open packs”, or the reason it was not added (amber) with “close” and “choose another pack…”. Leaving the page does not stop it.

**Everything from another manager** (07 §6.5): when the page opens, the page looks for the managers found (`app.FindManagerImports`, 07 §6.2 locations, never whole drives) while `API.ImportSurvey` reads each source in its own session (dry runs; nothing is written) and fills in what it holds. While it reads the source says “looking for RimSort, RimCrow and RimPy…”; with nothing found, “No RimSort, RimCrow or RimPy data found.”

- **A row per manager**, laid out like the section's other rows, with a check box, its mark (two letters on the neutral pill colour) and name; nothing is ticked when the page opens. A manager never imported shows what it holds (“profiles 3, notes and tags, rules, saved lists 6”). One imported before shows “imported 11-09” after its name and either a “new” tag and one line of what is new since (“notes 4, tags 2, lists 1, changed lists 1”, cut with an ellipsis, whole in the tooltip; it sorts first) or “nothing new since then” (its mark faded; it sorts last). What is off by default (RimCrow's switched-off rules) is not news.
- **Clicking a row picks the manager**: its new parts that are on by default are ticked, and the preview shows its tree; clicking again removes it. Groups with something new open by themselves after an earlier import.
- **The tree**: manager › kind of data (profiles, notes and tags per source or RimSort instance, rules, saved lists) › part. A part is a profile, a list file, or one kind of player data (aliases, notes, groups, tags, colour marks, ignored warnings; user rules, rules switched off there, interlocks). Each row says what it becomes (“41 notes”, “a new list”, “a Game Config with its list”) or “not brought over”; a kind says what its ticked parts become, or “N of M chosen”. A box turns its whole branch on (only what is new), or off when all of it is on; a parent shows a bar when partly on. RimArcho's check box is drawn by the page with the GUI's tokens: 16 px, the small radius, a hairline outline, the accent with the `ok` icon's tick when on.
- **Already in RimArcho**: a part whose values RimArcho already has is grey with a disabled box and “✓ already in RimArcho” (a profile: “✓ already the Game Config …”); a part with new values shows its total and, after an earlier import, a “4 new” tag. A profile that cannot come over (its game is not here) is greyed with the reason. A part the source does not have is not shown.
- **Lists imported before** are not ticked by picking the manager or the kind: “already the list Main colony · import another copy”. When the file changed since, it has a “changed” tag and “your list Main colony, changed since · update it · another copy”. “update it” replaces that list's content (one undoable edit; the list is not opened), “another copy” makes a new list (“Main colony 2”).
- The manager row and the summary under the tree count what is chosen (“5 of 6 parts”, “everything new”, “lists again 1”). The footer says the files are only read, that what is already in RimArcho stays, and that only a list's content can be undone; “cancel” clears the choice; “bring over the selected” starts the run.

**The run** is one background task in the RimArcho queue (`migrate`, `API.StartMigration`), an item per part, brought over one at a time; the window's lock is held for one part at a time, so the window answers between parts. The tree turns into the run in place: the managers' names, “moving in… 5 / 16” and a bar; each part waiting (a dot), running (a spinner), done (a tick and what it came to: “1 added, 3 already there”, “1 kept yours”, “a new list Latest_ModList  1 not installed”, “a Game Config Vanilla+”) or failed (the reason). The manager row says the same with a thin bar. The footer says it runs as a background task and the player can leave; “background tasks” opens it there; “stop” finishes the part in progress, keeps what is done and marks the rest “not done: stopped”, then offers “continue N” and “choose again”. At the end: “retry N” for failed parts, “open lists” when lists came over, and “done”, which reads the managers again, so what came in now shows as imported (or returns to the guide when the page was opened from it). No page-wide loading bar.

**First-run view** (§2.15): opened by the guide after its scan, the lead asks “Where does your first list come from?”, the game's list is the picked kind, its row has its name in the accent and its button is “use this list” (the page's one filled button), which ends the guide (the scan made that list already); the other kinds are there too, and bringing in a list, a pack or another manager's data ends the guide as well; the header's “skip” (`esc`) ends it with the game's list. The managers are not surveyed on the first run.

**Export** is not on this page (removed 2026-11-20 at the user's request; it was a “Share” section with the current list's formats and a pack's file or list). The lists' Export subpage (§2.17: All lists' `e`, the editor's `e`), the pack page's `E` and `e` (10 §4), `archo loadout export`, `archo pack export` and MCP `exchange_list` are unchanged.

**Not on this page**: CLI parity for picking parts (`archo import rimcrow` and `archo import rimsort` still bring everything over); a record of list imports from a file or a link (the record is only for what managers left on this computer).
