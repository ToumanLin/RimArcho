# 16 · Interface · Information architecture; sidebar, top bar, Launch, Can it run (§2–2.4)

> Part of [16 · Interface](README.md). Section numbers run through all of 16 and stay unchanged when split across files.

## 2. Information architecture and pages

The GUI uses the sidebar below (`shell.js`, `view.Nav` and `NavPath`). Unplayed, Worth playing and Archo have no pages yet and are not shown. The `shift+1`–`shift+8` shortcuts follow the sidebar order, skipping Saves. The TUI consists of a four-area plan editor and secondary screens; `P` opens plan switching and management (§9.1). Each page description names the implemented parts and the view functions it uses.

### 2.1 Sidebar

The sidebar has two groups and expands only the sub-entries of the current entry. Playing covers what the player wants to play or handle now; Library covers what the player has.

| Group | Entry | Sub-entries |
| --- | --- | --- |
| Playing | Launch (§2.3) | — |
| | Can it run (§2.4) | — |
| | Game log (§2.10) | — |
| Library | Lists (plans; §7.2) | All lists first (§2.17), then at most four lists: the current list, then the other lists in the order they were last enabled (made current, in any game), then lists never enabled, by their last edit or launch. The remaining lists are in All lists, which then shows the total ("all lists (N)"). |
| | Packs (§2.7) | At most four packs, the most recently played; with more, "all packs (N)" comes first. |
| | Saves (§2.11; no `shift+` key) | — |
| | Mod library (§2.9) | All mods, Updates, Add a subscription, Search files, Mod settings |
| | Texture optimisation (§2.13, 10 §2) | — |
| | Game (environments; §2.8) | — |

Lists opens the current list. A list's page is its editor; its sub-pages are Create a pack and Export. Opening a list in the editor does not move it in the sidebar; only enabling it does. Clicking a list only opens that list and does not change the current list (07 §1.3), so browsing the sidebar does not change the list used for the next launch. When the current list changes, the sub-entries slide from their old positions to the new order with `motion.slideFrom` and `--t-layout`, as editor rows do; with reduced motion, the order changes at once. Opening the Mod library opens its first sub-entry, All mods (§2.9).

Only Can it run displays a number. Its amber badge counts the items that need the player's attention (§5); it excludes advisory hints and hidden or locked Mods, which are handled outside that page (§2.4). No other entry or sub-entry displays a count. The sidebar does not show the RimArcho name or icon. The navigation toggle occupies the top row, level with the breadcrumbs; the first group heading follows it directly.

The dimensions follow the magpie sidebar. The default width is 212px, or 184px when the window is narrower than 860px. Dragging the right edge changes the width within 168–360px and saves it in `ui.gui.side`; double-clicking the edge restores the default. Horizontal padding is 10px. Group headings use muted 12px text with .04em tracking and a 14px gap from the previous group. Entries are 30px high, with 13px text and 14px icons. The icon, name and right-side count align to the same edges on every row. The current entry has a raised-card background that slides between entries like the thumb of a view switch. A small arrow follows the name of an entry with sub-entries and points down when it is open. Sub-entries are indented 16px along a muted hairline tree guide, which does not indicate selection (§7.3). Sub-entry rows are 26px high with 12px text; the current one is bold with a soft background that also slides between rows. When the player changes entries, the old sub-entries collapse while the new ones expand (§7.1).

The foot of the sidebar has two rows:
- **Background tasks** (§2.16) is always shown, above Settings. Normally it shows an icon and "background tasks". While tasks run or wait, a ring showing overall progress replaces the icon, the text becomes "background: N", and the percentage appears on the right. Unseen failures add a red badge on the right. The row has the raised current-entry background when its page is open. Clicking it or pressing `ctrl+j` opens the page.
- **Settings** opens settings (§2.14). The side and top navigation use the same six-tooth gear outline for it (`icons.js`, `settings`).

An Archo row that opens its panel from any page (§2.13) is planned for 1.1 and not implemented.

**The game's runtime status is not in the sidebar.** Polling through `view.LiveTracker.Update` (§2.16.1 G01) updates the current-run findings and the Can it run badge without a dialog. The running status appears in the launch block and the Last game link at the top right of Launch (§2.3), and under Current run on Can it run. **New logs are read automatically:** when `view.Live.NewLog` first appears after the game exits, or when opening RimArcho finds a run launched elsewhere, the GUI reads `Player.log` once in the background through `API.ReadNewLog`. It uses the same read as Can it run, marks the log as seen, starts no analysis, and then releases memory normally. The sidebar badge and any open Can it run or Launch page refresh without a click. The TUI keeps a hint at the right of the status line (§9.1).

**Navigation can be at the side or the top.** The toggle switches between the two and saves the choice in `ui.gui.nav`: `top` selects the top, and an empty value the side.
- **Side:** the sidebar described above, with the Playing and Library group headings and tree sub-entries. Its right edge can be dragged within 168–360px (`ui.gui.side`).
- **Top:** as in magpie, the same entries form a centered, text-only row without icons in a 46px bar at the top of the window, with a thin rule below it. There are no groups, group headings or separators. If the current entry has sub-entries (Mod library's All mods and Updates, the lists, the packs), they become switch buttons where the breadcrumbs would be, like magpie's second row. A deeper detail or build page appends / name. Pages without sub-entries show the page name without the group name. List buttons have the same context menu as in the sidebar. The Settings gear is at the right. The raised selection background and the Can it run badge remain. The bar scrolls horizontally when its contents do not fit.
- The toggle is at the top of the sidebar, level with the top bar, or at the left end of the top navigation. Its shortcut is `ctrl+b` (§3.5). The top bar has no page action buttons; the navigation bar provides navigation.
- Switching moves the navigation and page to their new positions with a view transition using `--t-enter`. Under `prefers-reduced-motion`, the change is immediate.
- The `tab` key reaches every navigation button. Within navigation, `↑↓` moves between side entries, `←→` moves between top entries, `enter` opens an entry, and `esc` leaves navigation. The `shift+1–8` shortcuts and sub-page `tab` / `shift+tab` keep working.
- The implementation is `navLayout`, `toggleNav`, `navKey` and `kidOwner` in `shell.js`. `renderCrumbs` draws the sub-entry buttons; `#app` carries `nav-side` or `nav-top`.

See §2.2 for the style and position of the window buttons, and §3.5 for the command panel.

### 2.2 Top bar, status line, hint line

The Windows controls are flat buttons with square corners, separated by hairlines. The close button uses the theme's danger color on hover; the other states use the navigation theme variables. See §2.1 for the Settings icon.

**The GUI top bar** shows breadcrumbs, such as Library / Lists / Main colony, in 15px text with the last level bold. An adjacent chip names the environment, such as main 1.7; on Can it run it names the plan and environment. Launch has no chip and no breadcrumbs (§2.3): it spans every environment, and its large headline supplies the title. In top navigation, the sub-page switches sit in this position (§2.1). **No page has page action buttons in the top bar.** The sidebar toggle is at the top of the sidebar (§2.1), and launch is available only on the Launch page (§2.3, §2.5). The Windows controls occupy the right end of the topmost row: the top bar in side navigation, or the navigation bar in top navigation (§8.2). Each breadcrumb level can be clicked to return to it. There is no separate large page title. The first line below the breadcrumbs is the **page heading**. Its left side shows a muted current status or conclusion only when informative, such as the Can it run conclusion or 34 enabled in the editor; it never explains the page's purpose (§7.3). **Page actions occupy the right side** of `.page-head`, in `.page-acts`, even when there is no status text. They are quiet, borderless buttons with an icon and text; only the primary action is solid. The plan editor also has this row (§2.5).

**The TUI top bar** shows the brand, an environment pill, Can it run N and N unsaved, separated by two spaces. The position (§3.2) and `L Launch` are on the right; launch is dropped first when space is short. On secondary screens, breadcrumbs replace the left side, for example `RimArcho › Can it run` or `RimArcho › Enabled › Combat Extended`. The runtime status is at the bottom right (§9.1).

Both interfaces have these lines at the bottom:
- **Status:** a single sentence with a green `✓` for completion, a red `✗` for failure, or a secondary-color `…` for progress. The next key clears it. In the GUI editor and full-screen details, the position appears on the left (§3.2); other pages omit it because the breadcrumbs already show the location. The status line does not say which list the game uses (§2.5). Undoable results include an Undo link. For screen readers and agents (§11 A11, A12) the line is a polite status and a failure an assertive alert; while work runs it is busy and its text is a progressbar with the count it shows; the same sentence is not announced twice. Undo is a button outside the Tab order (`u` / `ctrl+z`). Rescan and check the mods' files show their … sentence as soon as they are asked for; if RimArcho does not start the work, the sentence goes. A reply that arrives after its work already ended (a pack build or texture conversion that failed at once) leaves that outcome on the line. Work that ends on its own names itself, since the player may be doing something else: a failure starts with the job, as its task row does (`create a pack  <name>: <reason>`).
- **Hints:** the actions available for the current object, as `key description   key description`, with three spaces between groups, or 16px in the GUI (§7.3). At most 7 items, ending with `? All keys`. Keys use the text color and descriptions the secondary color, with no dot separators. Can it run is left out because its count is already in the top bar or sidebar; `shift+2` opens it and the help lists the shortcut.

N unsaved means that edits are stored (07 §1) but not yet written to the game. The count and the row's `●` mark entries that differ from the last saved list; they are written to ModsConfig.xml only on save or launch. They are informational and never block launch (09 §2).

### 2.3 Launch

The TUI Launch page is a simple column (§9.1).

The GUI page is `home.js`, laid out on a Swiss grid. A twelve-column grid centers the large headline. Below a thick rule, three areas run from left to right: 01 Game → 02 List or pack → 03 Launch. The numbers `1`, `2` and `3` focus their columns (§3.5 `1`–`9`, §7.3 rule 8); the focused number uses the accent color without a frame. The background (§2.14) extends from below the top bar to above the status line. This root page has no breadcrumbs (§2.2).
- **Four font sizes:** 12px for column headings, counts, versions, problems, the top-right links and small launch-block text; 17px for row names and the subtitle; 26px for the launch-block heading; and the responsive headline size described below. This is an exception to §7.3 rule 4.
- The page lists plans and packs from **all environments**. `view.AddOtherEnvs` uses `app.PlansIn` without loading the other environment. Plans are shared across games (07 §1.7), so every game lists all plans and marks its own current plan. There is no page-heading text or page action row. Rescan is in the list editor and Mod library › All mods; new list and import are on All lists (§2.17).
- **The headline** names the applied item. `view.PickFeatured` selects the current environment's current plan, or the last pack applied here if the current plan has not changed since. A trailing `[…]` Workshop tag, such as `[UPDATED 1.7]`, moves from the name to the start of the subtitle; parentheses stay in the title. **A headline is never truncated on a single line** (`fitHeadline`). It uses the maximum size, `clamp(48px, 7.6vw, 124px)`, if it fits; otherwise it shrinks to 64px, then wraps to two lines and shrinks from 64px to 48px. Only if two lines at 48px still do not fit is the second line ellipsized. Hover shows the full name, and resizing recomputes the fit. There is no line above the title. The subtitle has the tag, Mod count and play date; the state is in the 02 markers and the 03 problem line. A new headline slides in from below.
- **01 Game** (`1`) lists the environments that have plans or packs on the page. The game of the applied item comes first and slides into that position when it changes; the others follow by name. Each row shows the name and a short version chip, such as `1.7`, left out if the name already contains the version, as in `1.6`. Hover shows the full version, such as `1.6.4871 rev590` (`HomeRow.GameVersion`, 03 §3.1). The name is on the left and may be ellipsized; the version is on the right without wrapping and is blank if unknown. Clicking a game first switches the environment, then applies the item last applied in this session, or otherwise its most recently played item.
- **02 List or pack** (`2`) lists the selected game's plans before its packs. Within each group, items follow last-played order from the launch records (09 §2), with never-played items afterward by name. The applied item slides to the first position; the column scrolls beyond 6 rows. Each row shows the name and a muted Mod count on the right; packs say pack N, plans show only the count. **Only the applied row has problem markers:** ▲ for problems and ○ for not checked; 03 explains the problem. Other rows put their state in the first hover line. Unselected rows are muted; the selected row uses bold text color and a small accent square that slides with the selection. When the game changes, these rows enter in sequence.
  - **Clicking a row applies it.** The environment switches first if needed. A plan becomes current; a pack is saved in `ui.gui.home.pack` with the environment, pack name and the plan current at that time. `API.HomeApply` writes no game files. Clicking the applied row again, or pressing `Enter`, opens its editor or pack page.
  - **Switching progress appears in the launch block.** The page stays visible without a switching dialog. The 01 and 02 squares move at once. For a game switch, the block shows "switching to X…" and "loading the game, please wait…"; for a list switch, "applying X…". An indeterminate progress bar runs along the bottom edge. On completion, the headline changes and the block text enters from below. Reads happen in the background (§3.1 rule 9), and **the window remains usable**: sidebar navigation works, and other pages show their previous content before refreshing. Only launch and actions that write to this game are disabled until completion, with a switching-to-X tooltip. If another item is selected, the latest selection wins and earlier results are discarded. Background sessions prepare data for switching or adding a game and return it through events that carry request sequence numbers. Scanning and the first analysis run in the background.
- **03 Launch** (`3`, which focuses the button) is the page's only accent block, labeled "launch" (`L`), with only → at the bottom right; 01 and 02 already name the target. Both plans and packs launch directly (09 §2, 10 §3). An unsaved current plan adds an outlined "save N changes" `w` button at the bottom left. Clicking it or pressing `w` writes without launching, using the editor's `ui.run("save")`; hover explains that launching also saves. It is a separate button overlapping the corner, outside the launch button. It has square corners and uses the block's text color for its outline and text, like the `L` badge at the upper right. Only this button brightens on hover, and the launch block remains the only accent block. The save button is hidden while the game runs, while switching or launching, and when a pack or another plan is applied; only the current plan has unsaved changes. The hint line has no room for an eighth action, so `w` appears on the button and in help. Pressing launch shows "starting…", then "the game is running" with N errors when the runtime status arrives. While the game runs the button is disabled and has a text-colored background; only one game runs at a time (09 §4).
  - **The applied item's problem** appears below the block as a thin rule and one line of text. For the current plan, `view.LaunchHint` and `Home.Launch` choose the likeliest problem: the first kind in `app.LaunchChecks` (09 §2, ordered from highest to lowest corpus observations per opportunity) that has a counted item on Can it run. The line shows that item's title, with N more of the same kind when there are more. The text is amber, the rule is neutral, and overflow is ellipsized. The reason and corpus figures are in the tooltip. Clicking opens Can it run, and only items present there are chosen. If no such kind exists, the line says N problems break the game and still opens Can it run. Otherwise it shows pack links left in `Mods/` in neutral text (10 §3), then an outside version that has not been loaded, in neutral text. With none of these, there is no line. It never blocks launch.
  - An × on the right appears only when the problem is hovered or has keyboard focus. Dismissing it hides the line until the applied item, its game, its Mods or the problem changes. The fingerprint includes the applied item, environment chip, Mod and unwritten counts, version, state, problem text and count, and changes since last play. The `ui.gui.home.hidden` setting keeps the dismissal across restarts. The Can it run badge is unaffected.
- **The top-right area** has two lines, or three when a new RimArcho version is available. Each line appears only when it has content. Their left edge aligns with 03 in grid columns 9–12. If a label and its text do not fit on one line, the text wraps below the label:
  - **Last game** shows only the result, such as Oct 21  3 errors →. A run without errors opens the game log; one with errors opens Can it run. While the game runs, it says "the game is running" with N errors. Opening the page or refocusing the window reads `Player.log` again if it is newer than the last read (`app.NewLog`; a single read is cheap). The line is hidden if there has never been a game record.
  - **The current list** describes only the current plan, for example 5 Mods updated since last play, 1 needs attention → (`view.ChangeHome`; "needs attention" counts rows that affect launch). Clicking opens Mod library › Updates (§2.9) with exactly that plan and time range. The line is hidden when nothing changed. If the plan has never been played, the range starts at the last scan. If it has never been scanned, clicking rescans.
  - **RimArcho** (17 §5.1) adds a line such as RimArcho  1.0.1 can be updated → below the other two when a newer version exists. It opens the RimArcho row in Settings › About, with the install button focused. The line is hidden without a newer version and in development builds. `view.Home.Update` (`view.SelfUpdateHome`) reads a single check record.
  - Untouched content (1.1, 12 §3) is not shown yet.
- **Keys:** `1`, `2` and `3` focus the three columns. With focus in 01, `↑` and `↓` change the game; elsewhere they apply the previous or next item in the selected game. The `←` and `→` keys change the game. `Enter` opens the applied item, or launches when the launch button is focused. `L` launches; `w` saves unsaved changes to the current plan (in 03); `shift+1–8` changes pages. The hint line lists areas, ↑↓ lists, ←→ games, enter edit, L launch, shift+1–8 pages, and ? all keys.
- **Color and motion:** the page uses the §7 color variables and fonts and follows the light or dark theme. Problems are amber. The page has no animations when the system requests reduced motion.
- **Text over a background:** when an image is present, the page and top bar use fixed light text even in the light theme. The image has the configured dimming layer and extra shading on the left, at the bottom behind the three columns, and below the top bar. A flat `.hm-floor` sits below the thick rule: its gradient starts 64px above the rule and reaches an 80% mask, black in the dark theme and white in the light theme. It extends to the page's sides and bottom, so the three columns sit on a flat base and the image shows only in the headline half. It is left out below 720px. Solid color has neither an image nor this floor and follows the theme. Below 1000px, the top-right lines disappear and 03 moves to the next row; below 720px, the layout becomes one column.
- **Memory** (§10): the page uses only the cached 1920-wide JPEG at `/bg` and never loads the original. Leaving Launch removes the background layer with `setBackdrop` and `dropBackdrop` so WebView2 can release the decoded bitmap.
- The data comes from `view.BuildHome`: each plan and pack (`view.PackRows`) and the launch records (09 §2). The current plan's state uses `BreakCount`. Other plans use `view.PlanProblems`, which reads saved `view.PlanCheckOf` results and never starts an analysis; without a result they say "not checked yet". Pack rows say "checked when created"; packs have no analysis of their own. The background comes from `API.HomeBackground`.

**Memory hints at launch** use the RAM levels in §2.4. At the severe level, the whole launch button turns red and says Insufficient memory, launch game. Clicking it or using the launch key opens a dialog that lists the estimated loading need and the available memory separately, suggests closing other programs or removing Mods, and offers Cancel and Launch anyway. Cancel has the default focus; Enter activates the focused button and Esc cancels. At the warning level, the whole button turns yellow and says Memory is tight, launch game; it launches directly. Normal and unknown levels keep the ordinary button. VRAM does not affect it. Both the GUI and TUI first show the cached comparison and estimate them again in the background; see §2.4 for comparison caching and hardware refresh. Confirmation is bound to the environment and a snapshot of the current list; changing the environment, list or scan version invalidates it. Packs have no loading estimate and keep their ordinary launch.

### 2.4 Can it run

Can it run is a GUI page and the TUI `@` screen. The view model provides sections and evidence through `Need.Section` and `Need.Evidence`; both interfaces group the items by section and attach an evidence chip to each item. The GUI page has two columns (draft `docs/design/canitrun-drafts/a.html`, decision 00 §6 D22).

**The game Mod links panel** groups links by game, with a heading showing the name, version and path. Each row shows the folder name → target path, a short localized reason (target missing, unknown target with unconfirmed ownership, duplicate entry, or unreadable), and a final Will remove / Keep label, or the matching restore action. Long paths are ellipsized in the middle, with the full path on hover. The repair confirmation reuses these groups and rows. The TUI and CLI use the same short reasons and keep full paths in the terminal. Healthy entries are left out. The current game comes first. Other games collapse to an expandable line such as Game "1.5 test" also has 1 link needing attention; repair still handles all games together.

Each page read checks link health again across all known games and groups the results by game path. A single repair confirmation reuses the grouped rows and action labels, with full paths on hover; technical ownership evidence stays in the CLI inspection. By default, the repair includes only links with ownership evidence that can be repaired. A link whose ownership is not proven needs the explicit Include this link action before confirmation. Real directories, unknown types and inaccessible entries have no delete action. Confirmation is bound to the original server preview; a change to the path, identity, type or target needs a new check. Repair is refused while the game runs. Broken links in the selected game block plan or pack launch; problems in other games are only summarized. See [09 §3](../09-launch.md#3-link-deployment).

- See §5 for focused finding views and action buttons. When details open, providers query only existing caches (05 §4.3); page loading adds no Def file scans.
- **RAM and VRAM:** `view.MemoryNeed` and `Needs.Memory` compare the current list's loading RAM budget and its VRAM estimate with the machine's capacity, separately. See §2.17 for resident and loading measures and calibration. The budget is not a promised upper bound of the peak and leaves out saves, maps and allocations made by Mods. RAM uses the physical memory available now (`app.RAMBudget`): below the budget's lower bound is severe (`severe` / `StatusErr`), within the interval is a warning (`warning` / `StatusWarn`), and at or above the upper bound is normal (`ok`). VRAM below the estimated upper bound gives only an ordinary warning. For 1.6 the RAM side includes the VRAM the card cannot hold (§2.17, `MemoryAssessment.VRAMInRAMLow` / `High`), and the item says how much. A shortage of physical memory does not guarantee a crash; commit headroom and paging also affect the result.
  - The page shows existing data first. The GUI and TUI measure in the background, cache results by each Mod's file fingerprint, and reject stale results after a list switch. A missing estimate, unreadable hardware, or an integrated GPU without dedicated VRAM is unknown, never zero or a pass; for 1.6 such a computer's RAM side counts the whole VRAM estimate. Normal and unknown items appear in worth knowing; shortages appear in breaks the game and count as one item. Only shortage items add the note that saves and Mod allocations are not included. Re-estimate memory refreshes the result. CLI `plan cost` and MCP `estimate_memory` use the same assessment.
  - `internal/machine` reads machine information. Native probing does not block the page and is cached for 30 seconds. It reports total and available physical RAM and dedicated VRAM capacity. DXGI picks candidate GPUs in Windows high-performance order, or by dedicated VRAM on older systems. The display says explicitly that the game's actual GPU choice is not confirmed. It neither sums the VRAM of several GPUs nor treats shared memory as dedicated. Unsupported platforms and read failures show unknown.
  - The page reads only compact estimated totals from SQLite. A change to the list, game version, scan snapshot or model invalidates them. Totals older than one hour still display and set the level while a background re-estimate runs, so the button does not first turn normal and then change color again. The cache stores no hardware snapshot. File changes not yet scanned may leave the old totals in use; an explicit re-estimate checks the file fingerprints again.
  - See §2.3 for the launch interaction. CLI `plan cost` and MCP `estimate_memory` also report normal, warning, severe, or `unknown` when no comparison is possible.
- The data comes from `view.BuildNeeds`. While the game runs, Current run items from `view.LiveNeeds` come first in the errors from the last run section. `view.Do` performs the actions.
- The last run groups the actual error kinds by Mod. Open game log opens that run's Player.log at the matching cluster (§2.10); see §5 for wording.
- When a run has explicit phase records (06 §7, 19 §4), its log card has muted headings for Loading game, Loading save, Starting new colony, Playing and Main menu, for nonempty groups only. A Mod with errors in two phases appears once in each, with that phase's counts and kinds. Counts whose phase cannot be recovered appear under Phase not recorded. Headings have no cursor and add no item count; items do not repeat the phase words. Current run uses the same grouping and stays before the last run. Older logs without markers keep the flat list.
- The scope is the current plan, named in the GUI breadcrumbs and title. During a pack run, Current run names the pack, for example errors from pack X, not this plan.

**Sections** follow the order below (`view.Section*`); `1`–`9` focus them in the same order (§3.5).

| Section | Contains | Counted |
| --- | --- | --- |

Missing dependencies: absent or disabled dependencies, patches whose targets are disabled, and missing inherited Defs. Conflicts: incompatible Mods enabled together. Also duplicate package IDs in `Mods/` (`pkg.duplicate-mods`; Move into lock library is the first action when an ordinary folder can be moved; also pack links that duplicate a local copy, 09 §3, 10 §3), and game Mod links. | Yes |
| worth knowing | Hints learned from shared logs, with Shared logs evidence (`dep.observed-missing`, `combo.known-bad`, `mod.known-error`, §5 corpus hints). **Items handled elsewhere** (`SectionElsewhere`) are not items on this page: upstream updates to locked versions, unsubscribed residue and individually hidden Mods (09 §5) are handled by states and actions in Mod library › All mods (§2.9), and stale converted textures (`texture.stale`) on Texture optimisation (§2.13). They do not affect whether this list can run. Muted links at the bottom of the page show their counts (`Needs.Elsewhere`): 3 hidden/locked Mods in library opens All mods with the search `state:hidden state:residue state:updated`; 2 Mods have stale converted textures opens Texture optimisation. These items are not counted here. They still appear in the editor's row icons and popovers (§4.2), the CLI and MCP.

- Missing or disabled dependencies merge by the missing packageId and name every Mod that needs them; patches targeting the same disabled Mod also merge. A single action enables and positions the dependency, or subscribes to a Mod that is not installed. DLC keeps the store link. The editor uses the same snapshot; see [8.7](8-gui-technology.md#87-list-findings-and-needs-cache-api).
- Each item has a plain sentence, an evidence chip and all its actions. `view.Evidence` distinguishes Mod declaration, inference, log, community data, shared logs and your rules. The chip is followed by a specific source, such as an author-listed metadata dependency, 3 `Player.log` clusters at Oct 19 21:04, or patch `1.6/Patches/X.xml:4` finding no target. Shared logs include measured ratios.
- See §5 for name links, wording, merging, buttons, confirmations, completed items, counts and corpus cutoff dates. Raw finding severity is in 05 §4.3.1; ordering-constraint strength is in 08 §1.3.
- The page actions are Auto-fix (`F`, shown when possible, §5), Recheck files (`A`) and Select log (`l`). Beside the heading, the page says Mod files never checked, changed since last check, or Checking Mod files… as appropriate.
- **The GUI layout** is `drawNeeds` in `screens.js`. The heading states the conclusion, for example Main colony is not ready: 11 items before playing, 4 last-run error groups. The breadcrumb chip names the plan and environment. The page actions are auto-fix, recheck and game log. Two columns fill the window as on the game log page (§7 rule 12):
  - **The left column, Before you play,** has Mod-file and shared-log findings: breaks the game with a red heading, then worth knowing with an accent heading, then for you to confirm with an amber heading. Worth knowing is expanded by default; clicking its heading toggles it and remembers the choice for this session. The Elsewhere links are at the bottom.
  - **The right column, When you last played,** has log findings: last-run errors with a log-colored heading and the run's identity beside it, then the stale-log row at the bottom. While the game runs and has current errors, the column becomes This run and the last, and the section becomes This run's errors, with a green dot and Game running, or the pack name for a pack. An empty right column says Last run had no errors.
  - The gap is draggable (§3.1 rule 10), and the left width is saved in `ui.gui.needs.left`. Double-clicking restores the default of 55% on the left. Each column scrolls on its own with sticky section headings; empty sections are hidden. Below 900px, the columns stack with the left one first.
  - Each section is a card. Each item has a status icon and bold `Title`, falling back to `Text`; a plain explanation in `Why`; and any extra content below it: link rows, a See N list whose rows expand one by one, an `Also` line, or links between the columns (§5). The bottom row has **all** actions on the left and the evidence chip and source on the right. Evidence wraps to the next line when necessary. Buttons and evidence align with the title's left edge. There is no `⋯` menu.
  - The cursor uses a soft background and an accent title (§7.3). Up/down (`j` `k`, PageUp/PageDown, Home/End) moves within the current column. Left/right changes columns, each remembering its cursor. The `1`–`9` keys focus sections, with left-column sections first. Action keys act directly (§3); button keys appear only on the cursor item. The `tab` key enters the buttons; left/right moves between the current item's buttons, and `esc` returns to the list.
  - The sidebar badge equals the counted page items plus current-run errors. For the Archo panel (1.1, not implemented) `screens.js` has only the empty `archo.ask` hook.
- **The TUI layout** (`needs.go`) has one column: the GUI's three left sections, then last-run errors. Elsewhere appears as the final muted lines. The top shows the same conclusion as the GUI through `view.NeedsLead`, followed by the checking or changed-since-check text. Each heading has the section name, two spaces and the counted-item total. Breaks the game uses error red, worth knowing the accent, and other headings are muted. Last-run errors also name the run as pack X or `LastRun`. While the game runs with current errors, the section heading matches the GUI's This run's errors. Each item shows a status icon and `Text`, then a muted evidence line with the icon, kind, two spaces and source, such as Mod declaration  author metadata dependency. The cursor item's keys appear on the next line. Icons follow §7, using Nerd Font in full mode and the characters below in compatibility mode:

  Up/down (`j` `k`, PageUp/PageDown, Home/End) moves between items, and left/right jumps between sections. The page actions match the GUI: `F` auto-fixes, `A` rechecks and `l` selects a log. When auto-fix is available, the hint shows N from `view.AutoFixCount`. Completion leaves a u Undo hint in the status line. The automatic follow-up check changes only the page heading and keeps that undo status; an explicit `A` check still shows progress and Analysis complete in the status line. On an item, `c` opens subscriptions filtered to that Mod. `u` / `ctrl+z` undoes the previous step. The top bar's Can it run N equals counted analysis items plus current-run errors, the same number as the GUI sidebar badge.
