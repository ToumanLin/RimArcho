# 16 · Interface · Mod library, updates, game logs (§2.9–2.10)

### 2.9 Mod library, updates

**All mods** is GUI `library.js` and the TUI command panel's Mod library entry, using `app.Library` → `view.BuildLibrary`. It answers which Mods the player has, how many copies each has, where they are, where they are used, and how much space they take. It only manages Mods already installed locally; it does not acquire Mods or browse and search the Workshop (01 §3).

**The layout has two parts, like the plan editor.** The left column is about as wide as the editor's left column. A collapsible filter bar, shared with the editor, has its own card at the top. Below a gap, a permanent Mod and copy detail card fills the remaining height. A wide table takes the right. Both pages therefore have filters at the upper left with a column beneath them. The left width defaults to `clamp(280px, 26%, 440px)`. Dragging the divider resizes it, saved in `ui.gui.library.side`; double-click resets it. The page fills the window without a centered maximum width. As the window widens, the name column takes the surplus width, while resized or reordered columns keep their saved widths. Below 900px, filters sit above the table, and `enter` overlays details. The table follows Explorer's Details view: one row per Lineage (04 §3), expandable to show each Instance.

| Name | Size | State | Source | Used in |
| --- | --- | --- | --- | --- |
| Vanilla Expanded Framework (expand) | Total size | Most urgent state | Workshop / Lock library / Local | 2 plans |
| └ Workshop | 43 MB | Hidden by another manager | Workshop | — |
| └ Locked version 2026/10/21 14:27 | 42 MB | Upstream updated | Locked version 2026/10/21 14:27 | Main colony |

- **Filters** share the input, popup, ghost text, `tab` completion and collapse-on-blur behavior of §2.5 and §3.7. Conditions exist only in the query text, without separate chips. Lists expands first, followed by Tags, Source and Content; version, state, usage, update date, has, name, author and package ID are entered through the popup. Lists offers every list, with the current list first and marked current list. Its counts use Lineages, once per Mod as in the other groups; membership comes from the lists already loaded, without per-row database reads. All conditions must match the same Instance; one copy's source cannot combine with another copy's version to satisfy a query. Source filters use directory roles and stable aliases rather than copyable raw paths. The expanded bar takes 35% of the left height by default. Drag its gap to resize, double-click to reset, or drag to the full height, leaving only the details heading. Common group values may show counts; the search popup does not. The TUI keeps its own input and keyboard completion. Background tasks filters task records and does not offer list membership.
- **Table**:
  - The default columns are Name, Size, State, Source, and Used in. The header context menu can add Updated, Version, Author, Tags, and Last played; hide default columns except Name; or restore the defaults.
  - Clicking a header sorts by the column; clicking again reverses it, with an arrow showing the direction. Name, source, author and tags start A–Z; size starts largest first; dates and versions start newest first; state starts most urgent first; usage starts most used first. Drag headers to reorder, or their right edges to resize. Order, width and visibility are saved in `ui.gui.library.columns`. The table scrolls horizontally when the combined widths exceed its card.
  - The name cell has only the Mod name on a Lineage row. Expanded Instance rows use the editor's abstract copy labels: Workshop, Local, locked version with its creation time, SteamCMD, or a custom-directory name, never raw folder names or Workshop IDs. The source column uses the same label; paths and IDs are viewed and copied in the detail fields. Tags appear only in details, search and the Tags view's header rows (below). A Lineage with one Instance shows that copy directly, without expansion. An expanded copy's label lines up with the Mod names, its `└` where the chevron is.
  - The table heading has collapse all and expand all (icon buttons before the view switch): in the Mods view they close or open every Lineage with several copies (collapsing keeps the cursor's Lineage open, since the cursor never rests on a Lineage row); in the Tags view, every tag group (collapsing takes the cursor to its group's header). The header row menu offers the same two.
  - The state column shows only the actionable states marked below, at most one per row: the most urgent. Details show all states.
- **Tags view** (GUI; draft `docs/design/library-tag-drafts/index.html`): the table heading ends with a Mods | Tags switch (`v`), kept in `ui.gui.library.view`. The Tags view puts a header row before each tag's rows: the tag, how many of its Mods are shown (`3 / 5 mods` when the filter hides some), on top for a pinned tag, and the first line of the tag's note. It spans the columns and has no cells. Rows under it are the usual Lineage and copy rows, sorted by the current column; a Mod with several tags is listed under each. Mods without tags gather under No tag at the end. Groups follow the tag bar's order (§3.8: pinned first, then by Mod count, from `API.TagList`); a group the filter empties is left out. Filters, sorting, columns and selection are shared with the Mods view, and switching views keeps the cursor on the same Mod (from a header: that group's first Mod).
  - The cursor rests on header rows. `←` / `→` close and open a group (closing the one the cursor is in moves it to the header), `enter` and a double click toggle it, `→` on an open header focuses the Tag manager, and `←` on a Mod row that has nothing to close goes to its header. ctrl+click on a header selects the group's Mods; ranges and ctrl+a take only rows they cover. The header's context menu (and menu / shift+F10) offers rename, note, merge into…, delete tag, filter to this tag, collapse all and expand all. Full details' `←` `→` step past headers.
  - Indents: a Mod's chevron stands under its tag's name, every Mod name one step in from the tag's, and a copy's name lines up with the Mod names, its `└` in the chevron's place, as in the Mods view.
  - **Tag manager**: with the cursor on a header, or the Tags view empty, the details become the Tag manager, laid out as a copy's details are (the same note card, title, facts line, field rows and action buttons). Heading: Tags, the tag, and filter to this tag on the right (adds `tags:<tag>` to the query). Then the tag's note card (click or `n`; `enter` saves, `shift+enter` adds a line, `esc` cancels, leaving saves); the name as the title (F2 or a double click turns it into a field: `enter` renames, `esc` or leaving cancels; a name another tag has asks to merge instead), with keep on top / stop keeping on top (`tags.pinned`) on its right; the facts line (its Mod count, how many are shown when the filter hides some, on top); the field similar when there are tags spelled almost the same (case, spaces, dashes, a trailing s, or one a longer form of the other), with merge in; and the actions rename (F2), merge into… (`M`) and delete tag (`Del`). Merge into… opens a picker dialog (§3.1 rule 5): type to find a tag, or a new name; arrows move, `enter` picks, `esc` closes. On No tag the panel says how to tag Mods (`g`).
  - Below it, all tags: every tag with Mods as a chip with its Mod count, in the groups' order, the cursor's tag highlighted; clicking one moves the cursor to its header (the panel keeps its scroll position from one tag to another) and clears the picked tags. ctrl+click picks several, starting with the cursor's tag as a file list's selection would; a bar under the chips then names how many are picked and offers merge into… (the same picker; picking one of them keeps it), delete tags, and clear the selection. Tags kept on top in `tags.pinned` that no Mod has are named in one faint line after them. Merge and delete always confirm (§6) with `API.TagPreview`: the tags, the Mods that change, how many already had the target, and that tag changes cannot be undone. The edits are 07 §6.1's whole-tag edits (`API.RenameTag`, `MergeTags`, `DeleteTags`, `SetTagNote`, `PinTag`); after one the page reloads and the cursor goes to the resulting group.
  - The TUI Mod library has no Tags view; the CLI and MCP have the same edits (`archo tag rename|merge|delete|note`, MCP `set_player_data`).
- **Copy details** stay below the filters and follow the cursor copy. A Lineage row uses the current plan's copy, or else the first copy. They load after the cursor rests for about 90ms. View full details Enter ↵ in the heading and `enter` open the same full-screen details as the editor (§4.2); `esc` returns. In a narrow window, `→` overlays these details on the table, and `enter` or `esc` returns. On a copy, `→` focuses details, arrows and PgUp / PgDn scroll them, and `←` returns to the table. Below 900px, the permanent details are hidden and `enter` opens the full overlay. The order is the copy note (below), applicable actions, fields (§4.1, adding state, usage, size, supported versions, update date and last played), then the Mod image, name, description and history. There is no separate Instance block.
- Multiple selection reveals an action bar at the bottom, so actions are not only in the context menu. Each button shows its key.
- Row menus, detail actions and the multiple-selection bar offer library actions only. Adding, enabling, disabling, repositioning, staging, switching copies and removing from all plans stay in the editor. The Mod library does not edit `About.xml` or bind `space`, `m`, `t`, `x`, or the plan's undo and redo keys.

**States** appear only when something is abnormal:

| State | When | In row | Action |
| --- | --- | --- | --- |
| Cannot load | No readable `About.xml`, etc. (`mod.unloadable`) | Yes | open the folder |
| Subscribed but missing on disk | An ACF subscription has no folder on disk | Yes | Open webpage |
| Game ignores this copy | Another copy with the same package ID comes first in `Mods/` (07 §4.2, `pkg.duplicate-installed`) | Yes | Back up locked version |
| Unsubscribe residue | A Workshop folder remains after its subscription is removed | Yes | Delete or resubscribe |
| Hidden by another manager | `About.xml` was renamed About.xml.disabled (09 §5) | Yes | Restore or delete |
| Upstream updated | A locked version's upstream has changed (07 §5.3) | Yes | View the diff or update the locked version |

The first four also count as needing attention: unloadable, missing and ignored copies need the player to act. Unsupported current game and unused are not states, and are not in filters, `state:` values and completion, or CLI and MCP output: they are normal conditions for most of a library with more than a thousand Mods, so showing them in rows or filters adds noise. Supported versions belong in their facet and detail fields; unused copies are found through Used in › No plans (`used:none`).

**Actions**: the six copy-detail actions appear only when applicable, in a fixed order:
1. **Restore** (`unhide`) makes a copy hidden by another manager visible to the game again.
2. **Unsubscribe** for a Workshop copy, or **Delete** for an owned copy: unsubscribe calls the running Steam client (11 §2). Steam then deletes the Workshop folder, so the `--dry-run` text naming the folder is shown and confirmed, as for deletion. It is refused while the game runs. An enabled copy, or one a plan uses, can still be removed without first editing the lists. The confirmation names the affected lists; after confirmation the action runs and their entries are left marked missing, for each item of a batch. Only when Steam is unavailable, `steam_api64.dll` is missing from the game directory, or the DLL cannot load does the action fall back to opening the Workshop page; the status explains the Steam connection failure and asks the player to unsubscribe on the page. Delete moves the folder to the recycle bin (`trash`, 02 §3). It is available only for RimArcho's own copies in `Mods/` or the lock library, SteamCMD copies without a subscription that would download them again, and unsubscribed residue or hidden Workshop folders. Used copies get the same list warning. It is refused if the copy itself is a link, such as `_Link_*`, without touching the target. The dry run is shown before confirmation.
3. **Resubscribe** applies to Workshop originals, including residue, with a numeric Workshop ID, provided the copy is neither a link nor a locked version. It is previewed and confirmed first. For a subscribed copy, RimArcho unsubscribes first; after Steam confirms success, it recycles the original folder, verifies that the original path no longer exists, and subscribes again. Items whose cleanup failed are not subscribed; the reason is reported. The preview warns explicitly that RimArcho recycles the folder before Steam downloads it again, losing local changes. Enabled or used copies are allowed, but a running game causes refusal. The original path, Workshop ID, Instance and Lineage identities, and list references are kept. Residue skips unsubscribe and cleanup. After the subscription is confirmed, including for residue, RimArcho explicitly requests the Steam download and waits for the files on disk, with per-item progress in background tasks. A stall suggests checking Steam. If Steam is unavailable, the same webpage fallback applies. See 11 §2 for call rules.
4. **Back up locked version**, meaning move into the lock library as below, applies to an extra `Mods/` copy.
5. **open the folder** opens its folder.
6. **Open webpage** is available when a Workshop ID exists.

The context menu and multiple-selection bar also offer tags, copy note, do not list as a copy, pin, update locked version, unpin (07 §5), and subscription-source check, update and remove. A single copy has no Convert textures to DDS action, but has Clear converted textures when converted files exist; batch conversion is on Texture optimisation (10 §2). All actions come from `view.OpTable`, which defines their code, name, key and menu group. `view.CopyOps` returns only the codes that apply to the page and copy state. Names and keys are sent once with the page data.

**do not list as a copy**: this button appears in Mod and copy details, for the selected copy in the full-screen Copies section, and in the shared organization menu. It is available only for one copy that has another locally installed sibling, never for a multiple selection. Clicking splits the copy into an independent Mod, copying its alias, tags and Mod note and keeping the copy note. After the refresh, the separated copy stays displayed, without the button. The identity change applies globally; actual loading conflicts between identical package IDs are still checked. This action does not enter plan undo history (04 §3).

The confirmation previews for moving copies to the lock library, deleting and unsubscribing list every affected game, full link path, original target, and detach or rebuild action. Duplicate-copy moves use the same preview without another prompt. Moving a managed directory shows the same inbound-link plan in its dialog before confirmation. Unfinished ledger operations appear as recovery items in Can it run, using link repair's single confirmation (09 §3). Opening a page writes no files.

The copy-detail action area does not repeat open the folder, Open Workshop page or Steam page buttons: the location and Workshop entries in the fields (§4.1) open them, and context menus and shortcuts can also open them.

**Copy note** (`instance_note`): each Instance has a paragraph at the top of details. If the player has not written one, RimArcho's generated first version shows in gray. For example: this locked version was created on Oct 21 for the Test plan; its upstream has updated twice since; reason: the new version changed the save format. Copies not created by RimArcho also get a first version describing their origin and first discovery date, and later Workshop updates when both coexist. Examples include Workshop subscription, first seen Oct 19; game Mods folder, first seen Oct 19, Workshop updated twice since; and unsubscribed, Steam left the folder. A subscription without a folder has no generated note:
- Provenance is recorded when the copy is created: `made` names pin, update pin or move-to-library, with the time, plans and the player's `--reason`. The text is computed on display, so the count of later Workshop updates in the same Lineage stays correct.
- Clicking edits the displayed text. `enter` saves, `shift+enter` adds a newline, and `esc` cancels. Empty text restores the generated version. In the TUI Mod library, `n` edits the note, choosing a copy first if there are several.
- The CLI uses `archo note <ref> <text> --copy` (`--clear` clears), `archo pin … --reason` and `library move-to-locked … --reason`. MCP uses `copy_note` in `set_player_data` and `reason` in `pin_mod` and `manage_library` (14). `archo library --lineage` lists `note:` beneath each copy.
- The Mod note (`archo note <ref>`, §4.1 Note, search `has:note`) belongs to the Lineage and is shared across copies and plans; it describes the Mod. The copy note explains why this copy is kept. `has:note` checks only the Mod note; the Mod library's text search searches both.

**Move into lock library** (`archo library move-to-locked`): alternate versions of a Lineage are kept in the lock library, leaving at most one copy per package ID in `Mods/`. The plan chooses which copy to use (07 §5). Extra copies left by manual copying or other managers can move there after confirmation. On the same volume the folder is renamed. Across volumes it is copied, every file is verified, and the original is recycled. Its Lineage identity and plan references are kept: before scanning, the Instance is pointed at its new location so source and path reconciliation matches it (R1). Its ID, Lineage and history stay unchanged; the next write or launch exposes it through an `_Archo_` link. If `.rimarcho/origin.json` is missing, it is created with the Workshop copy of the same Lineage as upstream, or the copy itself if there is none. `origin_snapshot` is this copy's own snapshot, so Upstream updated means its content differs from the Workshop copy. Only folders inside `Mods/` with another copy in the same Lineage or an existing `origin.json` are moved. Links inside the folder that point outside it cause refusal, even for a same-volume rename. `pin --move-to-library` uses the same move but only accepts old copies with `origin.json` (07 §5.4). See 02 §1 for file writes.

**Updates** (data in 11 §1; one list plus details, draft `docs/design/subscriptions-drafts/c.html`): players come here to update subscriptions managed by RimArcho and to see what Steam updated. The list shows waiting updates first, removed Workshop copies next and completed changes last. Add a subscription is a separate sub-page (below). The source summary selects Update checks in the right detail pane.

Automatic check results (§2.16) fill the waiting list and source summary, with a quiet notification when updates are found. Opening the page only reads saved results. SteamCMD, Git and download-page check records are saved with the shared subscription and stay visible across games; old per-environment records are still read. Update all still needs confirmation. Download-page subscriptions keep their file-choice flow. Updates are refused while any registered game runs.

- **Scope bar above the left column**: show List <current list> / All Mods (`a`), with a starting point such as since last play Oct 22, or since last scan if never played. Show the starting point for either scope. The scope applies to pending updates, removed Workshop copies, and history. List scope hides pending updates used only by other lists and shows N in other lists with View all Mods. When viewing one Mod as below, replace the bar with a removable Only <name> × condition.
- **Left list**, area `1`, in this order:
  1. **waiting for you to update** contains known new versions not yet installed, one copy per row. Show name, source (Git, download page, SteamCMD, or Workshop), and installed → available as a version, short commit, or date. Download-page copies also show Choose file. Update all (`U`) at the right of the heading affects the listed items, skipping download-page items and reporting that a file must be selected first. Its confirmation is one preview request built on one session, and confirming queues at most two tasks (Steam client copies; Git and SteamCMD copies), not one per row (11 §1 rule 7). When none need updating, say up to date. Omit local copies without a source.
  2. **won't update any more** lists installed Workshop and SteamCMD copies whose last saved check returned deleted/private (code 9), one row per copy with its name and removed from the Workshop. It follows waiting updates and precedes completed history. Scope follows the current list / All Mods bar. These copies do not appear as pending updates or failed checks.
  3. **already updated** contains the changes described below: one Mod per row with its name, one-sentence summary, and a tier label at the end. Follow it with the arrival/removal summary, then Earlier, with one expandable row per day (`enter`).
  - The selectable source summary below the list says how many sources were checked and when, appending only real check failures, for example checked 4 sources, the last at 14:02, 1 check failed. Clicking, tabbing to it, or moving to it with arrows shows **Update checks** on the right. The existing `SubscriptionsPage` reply supplies all data; the summary never expands inside the list.
  - **Update checks** has one plain row per source: name, Mod count, last check, result in words, and Check (queues a background task, §2.16). Failed checks list Mod names and reasons directly. Only SteamCMD and configured LoversLab sources show account status and Accounts → (§2.14). Tab reaches each button and Enter activates it. Local Check scans files.
  - Workshop and SteamCMD checks batch 100 items per `ISteamRemoteStorage/GetPublishedFileDetails` request, with at most 4 concurrent requests. A network, HTTP, or parse failure waits 1 second and retries once. Items with busy, timeout, or rate-limit codes 2, 16, 20, 25, and 84 are also retried once. Only unanswered items after retry count as failures. Code 9 means removed from the Workshop (the author deleted it or made it private); the check still succeeds if there are no real failures.
- **Right details**, area `2`, follow the left cursor:
  - A waiting item shows its name, source, installed → available with their times, and tracked branch, tag, or commit. Update (`u`) shows `--dry-run` text before confirmation and refuses a running game; Steam downloads client Workshop subscriptions. For a LoversLab page, read its file list after sign-in through Settings › Accounts. The player chooses a file; if the site has a download agreement, display it and require acceptance before downloading, then preview and install. For other sites, unsigned accounts, or mandatory manual downloads, explain the reason and offer the page and an already downloaded ZIP or folder. Also offer the source page (a two-commit comparison on GitHub or GitLab, the download page, or Workshop release notes), pin current version with `pin --dry-run` first, open in inventory, and used lists with the current list emphasized.
  - An updated row shows its tier and summary, grouped file summary and remaining facts, individual files (`i`), and the row actions below. `ctrl+o` opens the folder.
  - Arrival/removal group titles name the kind of change: 1 new mod: Name, 3 new mods, 2 new subscriptions, or 1 mod removed: Name. A single item includes its name; multiple items include the count. Omit the redundant new and gone badge. Details list what happened to each Mod (new Workshop subscription, found in Mods, or removed from Mods); installed copies link to the exact Instance in Mod library, including when multiple copies share a name. A missing Mod still used by the current list says that the list still uses it.
  - A removed Workshop copy explains in two short sentences that the author deleted or made its page private, the installed copy still works but will never update, and unsubscribing prevents downloading it again. Offer Lock this version (`p`, dry run first) and Show in the mod library (`l`). Pending details use the same exact-Instance library helper and `l`.
- **Heading**: explain that waiting updates come first, followed by Steam's completed updates. On the right, Check updates (`K`) queues one background check per source, and add a subscription (`+`) opens its subpage. `R` still rescans.
- **Keys**: `↑↓` moves across list items; `u` updates the cursor item; `U` updates all; `K` checks; `a` switches scope; `enter` expands a day. `i`, `ctrl+w`, `D`, `S`, `p`, and `ctrl+o` use the changes actions below. `+` opens Add; outside an input, `ctrl+v` opens it with the clipboard address. `esc` removes the single-Mod condition. `tab` reaches detail links and buttons, and `enter` activates the focused action; on the source-summary or arrivals row it focuses the first detail action. There is no multiple selection; `u` updates one item at a time.
- Launch's current-list line (§2.3), details' see all changes, and TUI `C` land here, the last two scoped to one Mod. The TUI has three simple lists: `1` Sources, `2` waiting for you to update, and `3` already updated. Its scope row follows the GUI, for example List Main colony, since last play, a All Mods. Check, update and Add use the keys above. Removed Workshop copies appear between pending updates and history, with Enter for the explanation, p to lock, and l to select that Instance in the Mod library; l also works on pending and installed history rows. U shows in hints only when more than one update is available. Del removes a subscription, and Enter on a source checks only that source (§9.1).

**add a subscription** (Mod library › add a subscription, a sidebar sub-entry and Updates `+`): a single paste box, with no choice of type first. This flow does not use the name Download page.

- The paste box has focus on entry. Recognize a Git repository URL (`https://…` / `….git`), LoversLab file page, other webpage to read as a download page, or Workshop links and IDs, including multiple space-separated entries. For unknown input, give one sentence describing supported inputs.
- After recognition, show a card with the source icon and address, asking only the decision required for that kind. Below it, show `--dry-run` evidence. Subscribe (`enter`) queues a background task (§2.16), followed by a scan on completion:
  - Git asks what to track: the default branch, a branch, tag, or commit. The last three choices have inputs.
  - Workshop offers Steam subscription, recommended with Steam handling future updates, or SteamCMD download without the client, with RimArcho checking future updates. If SteamCMD will use the account signed in to Steam, the preview warns that its login signs Steam out until Steam is restarted, because an account has one session. Read the signed-in account from registry `ActiveProcess` fields `ActiveUser` and `pid`, then `config/loginusers.vdf` (`env.SteamSignedIn`, `App.SteamCMDSignsOutSteam`).
  - For another webpage, read its name and version. If it has one main repository, default to subscribing through Git so future updates require no file selection. Otherwise, choose a downloaded ZIP or folder.
  - For LoversLab, read the file list, then choose and download through the agreement, download, preview, and install flow above. If unsigned or manual download is required, explain why and offer Open page or Choose downloaded ZIP or folder. Record the page after file selection so future checks still work.
- With empty input, show three source cards: Git, LoversLab, and Workshop. Each explains its use, gives an example address, and shows account status: LoversLab sign-in, running Steam, and the SteamCMD account. Clicking a card focuses the paste box.
- Explain that local Mods are added by copying them into Mods and scanning, with an open the Mods folder link.
- Recently added at the bottom shows the latest 5 installed subscriptions, with name, source, and date. Each name is a Tab/Enter-accessible link to its exact Instance in Mod library, clearing filters and expanding that copy's Lineage; `RecentSubscription.ID` supplies the identity.
- Esc clears the input first, then returns to Updates.

- **Source column**: a subscribed copy shows Git, Download page or SteamCMD. Source filters have `source:git` and `source:page`, beside `source:steamcmd`.
- **State**: source update available (`state:source-update`, shown in rows), after Upstream updated. It uses the last saved check, without network access when the page opens.
- **Fields** (§4.1): the subscription source, whose URL opens in a browser, including Git HTTPS; the tracked branch, tag or commit; the installed short commit and time; and the last check's time and result, with the reason on failure.
- **Actions**: in copy details, Remove subscription takes the place of Delete; it recycles the copy and uses the same `--dry-run` preview, confirmation and warning about plans that use it. A download-page copy also offers Open download page; updating it needs a newly downloaded ZIP or folder. Check updates queues at once. Update appears only when an update is known, previews before confirmation, and refuses a running game. The multiple-selection bar also offers check and update.
- The TUI shares these detail fields and has the Add sub-page, a command-panel entry, and the subscription check, update and remove actions (§9.1). In the TUI, a download page can only be subscribed through its unique Git repository; choosing a ZIP, a folder or a LoversLab file needs the GUI or CLI `--from`.
- All mods keeps the source column, filters, subscription fields, and the copy's check, update and remove actions, with `Del` behaving like deletion. Add is reached only from Updates and the sidebar, not from All mods.

**Data**: sizes come from scan snapshots, which already read each file and record its byte count. Usage comes from all plan workspaces and the packs' `pack.json` files; last played comes from launch records (09 §1); subscriptions come from Workshop ACF. The commands are `archo library [--search <term>] [--include <key:value>]… [--exclude <key:value>]… [--sort <column>] [--lineage <ref>] [--facets] [--all]`, `library remove-from-plans <ref…>` and `library move-to-locked <ref> [--dry-run]`. `--sort` accepts name, size, changed, played, state, source, used, updated, version, author and tags; a `-` prefix reverses it. MCP has the read-only `list_library` and the write tool `manage_library` (13 §1.2, 14 §2). Filter keys include `tag`, `source` (workshop, local, locked, steamcmd, git, page, extra, monitor), `version`, `state` (unloadable, missing, ignored, residue, hidden, updated, source-update) and `used` (`plan:<name>`, `pack:<name>`, `none`). Mods in other games' `Mods/` folders are included, with sources such as `local-<game name>`, `local-main` and `local-1.6`, displayed as Local-main. `source:local` matches every game's Mods folder; the location stays that game's folder (07 §1.7). Enabling one in the current game links it in on save. Usage counts each globally shared plan once, and packs (07 §1.7); Remove from all plans also acts on them, with one undo step per plan. The snapshot table's `total_size` is summed per file during scanning, excluding `.git` and `.rimarcho`. Without a snapshot, the size shows —. Game ignores this copy applies only to duplicate package IDs inside `Mods/`; a Workshop copy with the same package ID loads as `_steam` (07 §4.1) and is not ignored.

**GUI implementation notes**: rows have equal height, and only visible rows are drawn. With 1284 Lineages of real data, scrolling takes about 4ms and a filter round trip about 20ms. Facets show only values with a positive count or that are selected, at first 6 per group, with the rest behind N more. A single-copy Lineage shows its copy directly. If a filter matches only some copies, the Lineage expands automatically to show those matches. **Mod settings** (`app.ModSettings`, `app.ModSettingsOf`, `app.ReadSettingsFile`): which Mods of the current list have settings and what their files store. Simple values change here while no game runs (`app.EditModSettings`); everything else changes in the game.
- **Which Mods**: each Mod the current list registers (official content excluded) that has a settings file under the folder the game sees it under (`app.SettingsFile`, 09 §3), or that Archo Monitor recorded with a settings window or settings read through the game (19 §2). One row per Mod class. The window title comes from Monitor's record for this folder, else the package's newest record; without a record it is unknown. A class without a file uses the Mod's defaults until its settings change in the game.
- **HugsLib** (`app.HugsLibRows`, `hugslibsettings.go`): Mods built on HugsLib keep their settings in `<user data>/HugsLib/ModSettings.xml`, one element per settings pack, not in `Config/`, and change them in HugsLib's own dialog. A pack is one more row of its Mod (title `HugsLib: <entry>`, or `HugsLib` without a record; no size). A pack is the Mod's when Archo Monitor's HugsLib record (19 §2) names the Mod as its owner, or when the file stores it under the Mod's package id (HugsLib's default identifier; `_steam` ignored); a pack under another name without a record is not shown. With the record, the values list every setting the record names, in its order, by title (its stored name and description on hover): a changed value with its default, a value at its default greyed; then values the file stores that the record does not name. Settings the Mod keeps out of HugsLib's window (`hidden`) are left out, with a note counting them. Without the record, the stored values only, and a note that the next start with Monitor adds titles and defaults. The record is kept per save-data root (newest per pack, at most 200), so it stays after its log is gone. The Mod details' settings row counts Config files and the pack under the package id only (no record read on a cursor move).
- **The game's window** (Archo Monitor 0.11.0, 19 §2): when the player has opened a Mod's settings window, its last record is shown with the file: headings, and each control's label and value as the window drew them then (on/off, a chosen choice, a slider's value and range, text, a number; buttons in brackets), with the date. A window alone lists its Mod. Labels cannot be matched to the file's keys, so the two stay separate lists.
- **Values**: `ReadSettingsFile` reads the children of `<SettingsBlock><ModSettings Class=…>`: text values as on/off (`True`/`False`), numbers or text; lists (`<li>`), dictionaries (`<keys>` and `<values>`), nested objects and `IsNull` nulls as read-only counts. It reads at most 5,000 values and 64 MiB; a file with another root is unreadable. A file stores only values that differ from the Mod's defaults, so a missing value is at its default; output says so.
- **Changing values** (`modsettingswrite.go`): RimArcho changes a value only when it understands it: on/off (`True`/`False`), a whole number where the file stores one (RimArcho cannot tell an integer setting from a float one stored as a whole number, so it writes only whole numbers there), a number with a decimal point (a whole number entered for one is written with `.0`, so it still reads as a fraction), one line of text, and for a HugsLib setting with Archo Monitor's record its type (Boolean, integer types, Single / Double, String, or an enum's names as a choice). Lists, dictionaries, nested values, nulls, multi-line text and HugsLib types RimArcho does not know stay read only, and so does an empty element (`<X />`, shown as empty): Scribe writes an empty list and an empty text alike, and text written into a list breaks the Mod's settings when the game loads them (for example XML Extensions' `PinnedMods`: a `NullReferenceException` in `XmlModBaseSettings.ExposeData`). A Config file changes only values it already stores (its other keys are not known); a HugsLib pack also takes any visible setting its record names, created under the pack (and the pack or the file when missing), and a value set to its recorded default is removed, as HugsLib would. Reset removes the stored value, so the Mod uses its default. Each change: refused while any environment's game runs (a running game keeps its settings and writes them back); refused when the stored text differs from what the page showed (`old`); the file is copied to `<file>.rimarcho.bak` (one copy, replaced on every change), then the new bytes are written to a temporary file renamed over it (`loadout.WriteFile`). Only the changed value's bytes differ: other values, comments, indentation, line endings and a byte order mark stay. Uninstall removes these backups with the ModsConfig item (02 §1); the changed values stay.
- **CLI and MCP**: `archo mod-settings` lists the rows (ref, name, title or `-` (`HugsLib: <entry>` or `HugsLib (<pack>)` for a pack), file, size, `stored` or `defaults (no file yet)` / `defaults (HugsLib stores none)`), 30 without `--all`. For a HugsLib pack `archo mod-settings <ref>` shows `Title (name): value  [default x]` for a changed value and `[default]` for one at its default, with how many changed. `archo mod-settings <ref>` shows one Mod's files and stored values; `archo mod <ref>` adds a settings section with up to 10 values per file; with several files each names its file key (Mod class or `hugslib:<pack>`). `archo mod-settings set <ref> [<name>=<value>…] [--reset <name>]… [--file <key>] [--dry-run]` changes values as above (a HugsLib setting by name or title; `--file` when the Mod has several files) and lists each change (`from → to`, `added`, `removed (the Mod uses its default)`) and the backup. MCP `get_mod_settings` (core, read only) and `set_mod_settings` (`--tools all`) map to them (14). `ModSettingsOf` reads only the index, never taking in an outside change of the list (07 §4.3), so `archo mod` stays a read.
- **GUI page** (Mod library › Mod settings; `modsettings.js`, `view.ModSettingsRows`, `view.ModSettingsFileDetail`): the page head says how many of the current list's Mods have settings (N mods of <list> have settings), with open the Config folder (`ctrl+o`). Area 1 is a data table (§3.9, `ui.gui.modsettings.columns`), one row per settings file: Mod, settings window (`—` unknown), stored values (`defaults` without a file), size, and the hidden file column; rows without a file are muted. When a game runs, the page says values change once it is closed and shows no controls. Area 2 shows the cursor's file: name, window title (`HugsLib: <entry>` for a pack), settings type, stored value count, the full path (copyable), then, when Monitor saw the window, "in the game's window (date)" with its headings and controls and "stored in the file", then each stored value as key and value (on/off, number, quoted text; lists, dictionaries, nested values and nulls as counts), then the notes. A value RimArcho can change is a control: on/off a switch (click flips it), a choice a list, others the value as a button that becomes a field (Enter saves, Esc or leaving it cancels); a stored value has a reset button, shown while the row is hovered or focused. Each change writes at once (`SetModSetting`): the status line says the new value and the backup's name (its path clickable), the values are read again and focus returns to the control, and the row's count follows; a refusal (the reason translated, e.g. not a whole number, a game runs, the file changed) reads the file again. Arrows, `j` `k`, PgUp / PgDn and Home / End move the cursor; the values follow once it rests (80 ms) and an older reply is dropped. The gap between the cards drags (`ui.gui.modsettings.side`, default 55%). Reads use a page session over the persisted list (§8.4); the page passes an instance and class, never a path. No Mod with settings: one card says so and that a file appears once a Mod's settings change in the game. A Mod's details have a Mod settings row (§4.1) whose open button comes here with the cursor on that Mod's first file.
- **TUI**: command panel Mod settings opens a text panel: each file or HugsLib pack with its title, up to 10 window controls and up to 10 values (a HugsLib value with its default) (§9).
