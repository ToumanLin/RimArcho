# 03 · 事实与分析

> 本文定义：生效内容的解析、事实类型、分析器、问题（Finding）目录、程序集元数据、日志归因。
> 身份与快照见 02，Loadout 见 04，对外接口见 05。

## 1. 生效内容（Effective content）

游戏实际加载的并不是 Mod 目录里的全部文件。所有内容层的分析，都只针对“生效内容”。

### 1.1 版本目录选择

给定环境的主次版本 `V`（例如 `1.6`）：

- **有 `LoadFolders.xml`**：选择不高于 `V` 的最高版本标签；没有时取最低的那个。该标签下：
  - 无条件的 `<li>` 一律生效；
  - 带 `IfModActive`、`IfModNotActive`、`IfModActiveAll`、旧式 `IfDLCActive`/`IfDLCNotActive` 的 `<li>`，按当前 Loadout 求值。
- **没有 `LoadFolders.xml`**：根目录下的公共目录，加上不高于 `V` 的最高版本目录（目录名匹配 `^[vV]?\d+\.\d+$`）。
- 版本比较按数字元组：`1.10 > 1.6`。

### 1.2 依赖于 Loadout

条件 `<li>` 会让生效内容随 Loadout 变化。因此生效内容的缓存键为：

`快照哈希 + 游戏主次版本 + 该 Mod 引用到的那些条件的求值结果`

而不是整个 Loadout 的哈希。这样，大多数 Loadout 修改不会让 Mod 的事实失效。

## 2. 事实类型

| 事实 | 字段 | 来源 |
| --- | --- | --- |
| `ModDecl` | 依赖、loadBefore/After、forceLoad*、incompatibleWith、支持版本 | 快照的 `decl_blob` |
| `Def` | 类型、`defName`、`Name`、`ParentName`、`Abstract`、所在文件和行号、所属 Instance | 生效的 `Defs/**/*.xml` |
| `PatchOp` | 操作类、XPath、子操作结构、`value` 摘要、文件和行号、序号 | 生效的 `Patches/**/*.xml` |
| `TypeDef` | 程序集、命名空间、类型全名 | 生效 DLL 的 .NET 元数据 |
| `HarmonyPatch` | 目标类型、目标方法与参数、补丁类型（prefix/postfix/transpiler/finalizer）、补丁方法、是否可能跳过原方法 | 同上 |
| `HarmonyId` | 疑似 Harmony ID 字符串 | 同上（启发式） |
| `Rule` | 主体、关系、对象、来源（用户/社区/替代）、作用域 | 04 §5 |

每条事实都带 `instance_id` 和 `snapshot_id`。生成它的分析器版本号写入事实，分析器升级后可以强制重建。

## 3. 分析的执行方式

- **按需**：TUI 打开 Problems 视图、CLI 或 MCP 请求内容层信息时才触发；只重建失效的部分。
- **子进程**：Def、Patch、Harmony 分析在 `archo analyze` 子进程中执行，结果写入事实库后退出，主进程的内存不受影响（01 §5.2）。
- **分层**：声明层（毫秒级，随时计算）→ Def 层 → Patch 层（依赖 Def 层）→ Harmony 层（独立）。上层失败不影响下层结果。
- **进度**：子进程向父进程按行输出进度。TUI 显示进度条，CLI 显示文本进度，MCP 返回“仍在计算”与已完成的部分。

## 4. 问题（Finding）

### 4.1 结构

| 字段 | 说明 |
| --- | --- |
| `code` | 问题代码，见 §4.3 |
| `severity` | `error` / `warning` / `info` |
| `subjects` | 涉及的实体引用，第一个是主体 |
| `claim` | 一句话结论 |
| `evidence` | 证据列表：每条是“引用 + 说明 + 来源类型（declared / inferred / log / community / user）” |
| `confidence` | `certain` / `likely` / `possible` |
| `suggestions` | 可执行的命令，例如 `archo enable #b21c` |

### 4.2 原则

- **不把出现位置当原因。** 例如堆栈里出现了某个 Mod 的补丁，只能记为“相关”，不能记为“原因”，除非有其他证据。
- **忽略**：玩家可以忽略某个问题，忽略记录挂在 Lineage 上，并记下忽略时的快照。Mod 更新后，忽略自动失效。

### 4.3 MVP 问题目录

**声明层**

| code | 严重度 | 判定 |
| --- | --- | --- |
| `dep.missing` | error | 依赖的包在本环境中不存在 |
| `dep.inactive` | error | 依赖的包存在但未启用 |
| `order.violated` | warning | 当前顺序违反 loadBefore/After 或依赖顺序 |
| `order.cycle` | error | 排序约束成环，列出环上每条边及其来源（04 §4.2） |
| `incompat.active` | error | 两个声明互不兼容的 Mod 同时启用 |
| `version.unsupported` | warning | `supportedVersions` 不含当前主次版本 |
| `pkg.duplicate-active` | error | 同一 packageId 的多个 Instance 同时启用 |
| `pkg.duplicate-installed` | info | 同一 packageId 有多个 Instance，但只启用了一个 |
| `replacement.available` | info | 社区替代规则推荐了更新的 Mod |
| `official.order` | error | Core 和 DLC 不在列表最前，或顺序不对 |

**Def 层**

| code | 严重度 | 判定 |
| --- | --- | --- |
| `def.override` | info | 同类型、同 defName 由多个 Mod 定义，按加载顺序后者生效 |
| `def.parent-missing` | error | `ParentName` 找不到对应的 `Name` |
| `def.abstract-collision` | warning | 多个 Mod 用同一个 `Name` 定义抽象父节点 |

**Patch 层**

| code | 严重度 | 判定 |
| --- | --- | --- |
| `patch.no-match` | warning | XPath 在模拟时没有命中；附带原因分类（§4.4） |
| `patch.contested` | info | 多个 Mod 用 Replace 或 Remove 修改同一节点 |
| `patch.unknown-op` | info | 自定义 PatchOperation 类，无法模拟，结果不确定 |

**Harmony 层**

| code | 严重度 | 判定 |
| --- | --- | --- |
| `harmony.shared-target` | info | 多个 Mod 补丁同一方法 |
| `harmony.skip-prefix` | warning | 某个返回 `bool` 的 prefix 可能跳过原方法，且同一方法还有其他 Mod 的补丁 |
| `harmony.multi-transpiler` | warning | 同一方法上有多个 Mod 的 transpiler |
| `harmony.manual` | info | 程序集通过代码手动调用 `Harmony.Patch`，目标无法静态确定 |

**日志层**：见 §6。

### 4.4 `patch.no-match` 的原因分类

对应现有 error-debugging 指南中的分类：

| 原因 | 判定 |
| --- | --- |
| `target-inactive` | 目标所在的 Mod 存在但未启用 |
| `target-missing` | 任何已安装的 Mod 中都找不到目标 |
| `target-later` | 目标由排在后面的 Mod 定义 |
| `wrong-version-route` | 目标存在于磁盘，但不在生效内容中 |
| `stale-name` | 目标 Mod 已启用，但不存在该 defName；给出名字相近的候选 |
| `unguarded-optional` | 补丁针对一个可选依赖，却没有放在 `PatchOperationFindMod` 或条件下 |

## 5. 分析器实现要点

### 5.1 Def 层

- 流式解析 XML，只抽取 §2 的字段，不保留完整 DOM。
- 继承解析：先收集全部 `Name`，再解析 `ParentName`。同名抽象节点按加载顺序后者覆盖，与游戏一致。

### 5.2 Patch 层：按加载顺序模拟

1. 按 Loadout 顺序，把各 Mod 的生效 Defs 合并成一个内存文档（`<Defs>` 根）。
2. 按同样顺序依次应用各 Mod 的 PatchOperation，记录每个操作的命中节点数。
3. 支持的操作：`Add`、`Insert`、`Remove`、`Replace`、`AttributeAdd`、`AttributeSet`、`AttributeRemove`、`SetName`、`AddModExtension`、`Sequence`、`Conditional`、`Test`、`FindMod`。其他操作类记为 `patch.unknown-op`，并跳过。
4. `success` 属性（`Always`、`Normal`、`Invert`、`Never`）按游戏语义解释。

XPath 引擎必须兼容 .NET 的 XPath 1.0 行为。M0 需要用真实 Mod 集合中的全部 XPath 做兼容性测试，不兼容率必须低于 0.5%，并记录下差异清单。

内存控制：合并文档只在子进程中存在。目标峰值见 01 §5.2。

### 5.3 程序集（D5）

**原生元数据读取**（Go，不依赖 .NET 运行时）：
- 读取 `TypeDef`、`MethodDef`、`MemberRef`、`TypeRef`、`CustomAttribute`、`#Strings`、`#US` 表与堆。
- `HarmonyPatch` 特性：合并类级和方法级的特性参数（目标类型、方法名、`MethodType`、参数类型数组），得到目标方法。
- 补丁类型：看方法上的 `HarmonyPrefix`/`HarmonyPostfix`/`HarmonyTranspiler`/`HarmonyFinalizer` 特性，没有时按方法名 `Prefix`/`Postfix`/`Transpiler`/`Finalizer` 推断。
- 可能跳过原方法：prefix 的返回类型为 `bool`。
- 手动补丁：存在对 `HarmonyLib.Harmony::Patch` 的 `MemberRef` 引用时，记为 `harmony.manual`。
- Harmony ID：`#US` 堆中形如反向域名（`a.b.c`）的字符串，作为候选 ID，标注为启发式。
- 跳过已知的公共库程序集（Harmony 本体、HugsLib 等），清单可配置。

**按需反编译**（ilspycmd）：
- `archo source <实例> [--type <类型>]`：只反编译所请求的程序集或类型，结果按 DLL 哈希缓存。
- `archo source search <模式> [--in <实例>...]`：在缓存中搜索；未缓存的实例先反编译。
- 找不到 ilspycmd 时，给出安装命令，不自动安装。

## 6. 日志归因

### 6.1 解析

1. 把 Player.log 切分为条目：消息行，加上紧随其后的堆栈行。
2. 归一化消息：把数字、地址、实体 ID 替换为占位符，以此作为聚类键。相同键的条目合并为一个错误簇 `log:E<n>`，记录次数和首次出现的位置。
3. 分类：`xml-load`、`patch-failed`、`xref-missing`、`exception`、`harmony-stack`、`material`、`other`。

### 6.2 归因证据（按强度从高到低）

| 证据 | 说明 |
| --- | --- |
| 消息中的 Mod 名或文件路径 | 例如补丁失败消息里的 `[Mod 名]` 和文件路径；对照生效内容，定位到 Instance |
| defName | 交叉引用缺失的 defName，查 Def 事实，找出引用方和潜在提供方 |
| Harmony 补丁行 | 堆栈中 `- PREFIX <harmonyId>: ...` 这类行；harmonyId 对照 `HarmonyId` 事实 |
| 堆栈帧的类型 | 帧中的类型全名，对照 `TypeDef` 事实，得到所属程序集和 Instance |

### 6.3 输出

每个错误簇产出一个 `log.*` 问题：
- `subjects`：候选 Instance，并为每个标注角色：`source`（错误由它产生）、`patcher`（只是补丁了相关方法）、`dependency`（被依赖方）、`mentioned`（只是被提到）。
- `suggestions`：下一步要查的内容。例如：`archo patches --target Verse.Pawn.Tick`、`archo source search "AllComps.Remove(" --in #a3f9`。
- 对 `Pawn.Tick`、`ThingWithComps.Tick` 等已知热点，附带现有 inspector 工作流中的检查清单。

### 6.4 验收

| # | 场景 | 期望 |
| --- | --- | --- |
| B1 | 补丁失败日志 | 归因到具体 Patch 文件和行号，并给出 §4.4 的原因分类 |
| B2 | 交叉引用缺失日志 | 给出引用方 Mod 和文件；说明是否存在任何提供方 |
| B3 | `Pawn.Tick` 异常，带 3 个 Mod 的 Harmony 补丁行 | 3 个 Mod 都被标为 `patcher`，不被标为 `source`；给出下一步检查 |
| B4 | 同一异常重复 500 次 | 合并为一个错误簇，次数为 500 |
| B5 | 用现有 inspector 的测试用例回放 | 结论与 inspector 一致或更准确 |

## 7. 本层验收（声明层、Def 层、Patch 层、Harmony 层）

| # | 场景 | 期望 |
| --- | --- | --- |
| C1 | 启用一个依赖未安装的 Mod | `dep.missing`，建议中给出工坊链接 |
| C2 | 同一 packageId 的工坊版和本地版同时启用 | `pkg.duplicate-active` |
| C3 | 两个 Mod 定义同一个 `ThingDef` | `def.override`，指明哪个生效 |
| C4 | 补丁的目标 Mod 未启用，且补丁未用 FindMod 保护 | `patch.no-match`，原因为 `target-inactive` 和 `unguarded-optional` |
| C5 | 两个 Mod 用 transpiler 修改同一方法 | `harmony.multi-transpiler` |
| C6 | 一个 Mod 只用代码手动打补丁 | `harmony.manual`，不误报为“无补丁” |
