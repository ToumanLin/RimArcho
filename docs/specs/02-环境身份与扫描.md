# 02 · 环境、身份与扫描

> 依据：[00-顶层设计 §6](../00-顶层设计.md)（D8）。
> 本文定义：环境与来源、扫描流程、Instance 对账、Lineage、变更事件，以及对应的存储结构。

## 1. 术语

| 术语 | 定义 |
| --- | --- |
| Environment | 一份游戏安装加一个用户数据目录。玩家可以有多个环境，例如正版和测试版 |
| Source | 一个存放 Mod 的根目录，属于某个环境 |
| Instance | 磁盘上的一份 Mod，由 RimArcho 分配 ID |
| Snapshot | 某次扫描时，一个 Instance 的元数据和内容指纹 |
| Lineage | “同一个 Mod”的家族，例如原版、本地副本、改名前后 |
| Tombstone | 已消失但仍保留的 Instance 记录 |

## 2. 环境

### 2.1 字段

| 字段 | 说明 |
| --- | --- |
| `id` | 随机 ID |
| `name` | 玩家起的名字 |
| `game_root` | 游戏安装目录（含 `RimWorldWin64.exe` 或对应平台的可执行文件） |
| `user_data_root` | 用户数据目录（含 `Config/ModsConfig.xml`） |
| `game_version` | 从 `Version.txt` 读取，例如 `1.6.4633 rev1261`；比较时只取主次版本 `1.6` |
| `launch` | `direct` 或 `steam` |

### 2.2 自动探测（U1）

按顺序尝试，命中即停：
1. **游戏目录**：Steam `libraryfolders.vdf` 中各个库的 `steamapps/common/RimWorld`；然后是常见的手动安装位置。
2. **用户数据目录**：
   - Windows：`%USERPROFILE%\AppData\LocalLow\Ludeon Studios\RimWorld by Ludeon Studios`
   - macOS：`~/Library/Application Support/RimWorld`
   - Linux：`~/.config/unity3d/Ludeon Studios/RimWorld by Ludeon Studios`，以及 Flatpak 下的对应路径
3. **工坊目录**：游戏所在 Steam 库的 `steamapps/workshop/content/294100`。

探测结果只是建议，要等玩家在 TUI 或 CLI 里确认后才写入。

### 2.3 Player.log 位置

- RimWorld 1.7 及以后：`<user_data_root>/Logs/Player.log`
- 更早版本：`<user_data_root>/Player.log`
- 版本未知时两处都看，取 mtime 最新的一个。上一次运行的日志是同目录下的 `Player-prev.log`。

## 3. 来源（Source）

### 3.1 来源类型

| kind | 根目录 | 说明 |
| --- | --- | --- |
| `official` | `<game_root>/Data` | Core 和 DLC。永远排在最前，不可停用 Core |
| `local` | `<game_root>/Mods` | 玩家的本地 Mod |
| `workshop` | `.../workshop/content/294100` | 子目录名就是工坊 ID |
| `steamcmd` | 玩家指定 | 只读，结构同 workshop |
| `extra` | 玩家指定 | 其他目录 |

### 3.2 来源身份与重新绑定（U9）

每个来源有自己的 `source_id`。Instance 只记录 `source_id + 相对路径`，不记录绝对路径。

当某个来源的根目录失效（不存在），或玩家修改了环境路径时：
1. 在新根目录下随机抽取最多 20 个子目录，计算语义指纹（§4.3）。
2. 与旧来源下的 Instance 对比，若 ≥ 80% 的样本能按“相对路径相同且语义指纹相似度 ≥ 0.9”匹配上，就判定为同一来源，只更新根路径。
3. 匹配率不足时，不自动绑定，而是在 TUI 中提示玩家：“这是原来的来源吗？”，并显示匹配率和样例。

### 3.3 链接与别名位置

- 扫描前先把 junction 和符号链接解析成真实路径。
- 指向同一真实目录的多个位置，只算一个 Instance。多出来的位置记为该 Instance 的别名位置。
- Windows 路径比较不区分大小写，并展开 8.3 短路径。

## 4. 扫描

### 4.1 流程

```
列出来源子目录 → 过滤（必须有 About/About.xml）→ 读取观测 → 对账 → 写入快照 → 发出变更事件 → 标记过期的事实
```

- 工坊来源：游戏只加载**已订阅**的条目（M0 反编译确认，07 §6.1）。不在 ACF 订阅记录中的文件夹，记为 `residue`（残留），仍然建 Instance，但不能加入 Loadout，并在 Problems 中提示可以清理。没有 `About/About.xml` 的残留文件夹只计数，不建 Instance。
- `About/About.xml` 不存在、但有 `About/About.xml.disabled`（RimCrow 停用 Mod 的方式）时：读取该文件作为声明，建立 Instance，标记为 `unloadable: about-disabled`。这样的 Instance 不能加入 Loadout，在列表中可以筛选出来，会出现在问题列表（M3）和 RimCrow 导入报告（M5）中。RimArcho 不负责改回文件名，因为这些文件大多在工坊目录里（01 §5.3）。（M1 遗留问题 2 的裁定）
- 按来源并行读取，每个来源内部并发上限为 CPU 核数。
- 增量：文件的“相对路径 + 大小 + mtime”都没变时，复用上次的哈希。
- 扫描只更新身份和元数据。Def、Patch、Harmony 事实由分析层按需重建（见 03）。

### 4.2 每个目录的观测

| 类别 | 内容 |
| --- | --- |
| 位置 | `source_id`、相对路径、别名位置 |
| 声明 | About.xml：`packageId`、`name`、`author`/`authors`、`modVersion`、`supportedVersions`、`modDependencies`（含 `*ByVersion`）、`loadBefore`、`loadAfter`、`forceLoadBefore`、`forceLoadAfter`、`incompatibleWith`（含 `*ByVersion`）、`descriptionsByVersion`；`About/PublishedFileId.txt`；`LoadFolders.xml` 原文 |
| 外部状态 | 工坊来源：ACF 中的 manifest ID、`timeupdated`、大小；目录中有 `.git` 时：HEAD commit |
| 内容指纹 | 见 §4.3 |
| 出身标记 | `.rimarcho/origin.json`（如果存在） |

About.xml 解析要容忍：BOM、大小写不同的标签、`author` 和 `authors` 混用、`li` 中的空白、包名大小写。packageId 一律存两份：原文 `package_id_raw`，以及小写的 `package_id`。

### 4.3 内容指纹

| 层 | 范围 | 计算 |
| --- | --- | --- |
| 结构清单 | 全部文件 | 相对路径 + 大小 |
| 语义哈希 | `About/`、`LoadFolders.xml`、所有 `Defs/**`、`Patches/**` 下的 XML、`Assemblies/**/*.dll` | 每个文件取 xxh3-128 |
| 快照哈希 | 以上两层 | 按路径排序后整体哈希，用于快速判断“有没有变” |

贴图、音频等大文件只比大小，不读内容。

**相似度**：在两个快照的语义文件集合上，取两项 Jaccard 系数中较大的一个：
- `J(路径)`：只比较相对路径。用于识别“移动 + 更新”：内容变了，结构没变。
- `J(哈希)`：只比较内容哈希，不看路径。用于识别“重组”：文件挪进 `1.6/` 之类的子目录，内容不变。

（M1 修订：原文的 `J(路径, 哈希)` 恒不大于 `J(路径)`，在取最大值时不起作用，因此删去。R3、R4 另外要求声明一致，所以“路径相同但内容无关”的误配会被这一条挡住。小 Mod 新增文件导致相似度低于 0.85 时，走 R6 待确认，这是可以接受的保守结果。）

## 5. 对账（D8 §6.5 的实现）

### 5.1 输入与输出

- 输入：本次扫描的所有观测；数据库中现有的 Instance（包括墓碑）。
- 输出：每条观测对应的 Instance ID；变更事件；待确认项。

### 5.2 规则（按顺序执行，已匹配的观测和 Instance 不再参与后续规则）

| 步骤 | 条件 | 结果 | 事件 |
| --- | --- | --- | --- |
| R1 | 同一 `source_id` + 同一相对路径 | 同一 Instance | 快照哈希变了：`updated` |
| R2 | 观测来自 `workshop` 或 `steamcmd` 来源且未匹配；另有一个同样来自工坊类来源、目录名相同（即工坊 ID 相同）的 Instance 本次未出现 | 同一 Instance（例如工坊内容换了 Steam 库） | `moved` |
| R3 | 观测未匹配，某个 Instance 本次未出现；相似度 ≥ 0.85，并且 packageId 或工坊 ID 声明一致 | 同一 Instance | `moved` |
| R4 | 观测未匹配，某个 Instance 本次也出现了（未消失）；相似度 ≥ 0.6，并且 packageId 或工坊 ID 声明一致 | 新 Instance，加入对方的 Lineage，标记为“推断” | `copied` |
| R5 | 观测带有 `.rimarcho/origin.json` | 新 Instance，加入记录中的 Lineage，标记为“确认” | `copied` |
| R6 | 观测未匹配，某个墓碑 Instance 相似度 ≥ 0.6 | 新建待确认项：“这是不是 #xxxx 回来了？” | — |
| R7 | 其余 | 新 Instance，新 Lineage | `discovered` |

R5 先于 R3、R4 判断：有出身标记时以标记为准。

扫描结束后，仍未出现的 Instance 转为墓碑，发出 `disappeared`。墓碑重新被 R1/R2 匹配上时，发出 `reappeared`。

### 5.3 同一 Instance 内的字段变化

在同一个 Instance 的新旧快照之间比较，分别发出：

`package-id-changed`、`renamed`、`author-changed`、`version-support-changed`、`dependencies-changed`、`load-rules-changed`。

一次扫描可能对同一 Instance 发出多个事件。所有事件共用一个扫描批次 ID。

### 5.4 待确认项

- 在 TUI 的 Changes 视图里列出。玩家可以选择“是同一个”“是副本”“无关”。
- CLI 用 `archo identity resolve <id> same|copy|unrelated`。
- 玩家确认后才合并或关联。待确认项保留到玩家处理为止。

### 5.5 墓碑

- 默认保留 90 天，可在配置中修改。
- 墓碑保留它的 Lineage、规则、别名和历史快照。
- 过期后由 `archo gc` 清除；未处理的待确认项所引用的墓碑不清除。

## 6. Lineage

- 每个新 Instance 默认创建自己的 Lineage。
- 下列情况会把 Instance 并入同一个 Lineage：R4、R5，以及玩家确认“是副本”。
- 玩家可以手动拆分或合并 Lineage：`archo lineage split|merge`。
- Lineage 有一个“主 Instance”，用于显示默认名称。默认取工坊来源的那一份；没有工坊来源时，取最早发现的那一份。

## 7. 引用

| 引用 | 格式 | 示例 |
| --- | --- | --- |
| Instance | `#` + ID 的最短唯一前缀（至少 4 位） | `#a3f9` |
| Lineage | `L#` + 最短唯一前缀 | `L#7c2e` |
| 按包名 | `pkg:` + packageId | `pkg:ceteam.combatextended` |
| 按工坊 ID | `ws:` + ID | `ws:2890901044` |

`pkg:` 和 `ws:` 可能对应多个 Instance。此时命令会列出候选，而不是任选一个。ID 使用 128 位随机数，以小写 base32 表示。

## 8. 存储（SQLite，核心表）

```
environment(id, name, game_root, user_data_root, game_version, launch)
source(id, environment_id, kind, root, status)
instance(id, lineage_id, source_id, rel_path, status[live|tombstone], first_seen, last_seen, tombstone_at)
instance_alias(instance_id, real_path)
snapshot(id, instance_id, scan_id, snapshot_hash, package_id, package_id_raw, name, authors,
         workshop_id_declared, supported_versions, decl_blob, acf_manifest, git_head)
snapshot_file(snapshot_id, rel_path, size, hash NULL)   -- hash 只给语义文件
lineage(id, primary_instance_id, created_at)
change_event(id, scan_id, instance_id, kind, before_snapshot, after_snapshot, detail)
identity_question(id, observation_snapshot_id, candidate_instance_id, score, status)
scan(id, environment_id, started_at, finished_at, stats)
```

`decl_blob` 保存 About.xml 的规范化结构，供分析层使用。所有表都按 `environment_id` 隔离。Loadout、规则、玩家数据和事实的表结构分别在 04 和 03 中定义。

## 9. 验收

| # | 场景 | 期望 |
| --- | --- | --- |
| A1 | 首次扫描 300 个以上 Mod | 每个目录一个 Instance；`discovered` 事件数等于 Mod 数 |
| A2 | 工坊更新了某个 Mod | 同一 Instance，发出 `updated` |
| A3 | 作者在更新中改了 packageId | 同一 Instance，发出 `package-id-changed`；Loadout 和用户规则不受影响 |
| A4 | 把整个游戏目录移到另一块盘，再修改环境路径 | 来源重新绑定成功；Instance ID 全部不变 |
| A5 | 手动把工坊 Mod 复制到 `Mods/` | 新 Instance，与原版同一 Lineage，标记为“推断” |
| A6 | 用 `archo copy-local` 复制 | 同上，标记为“确认” |
| A7 | 本地 Mod 目录改名 | 同一 Instance，发出 `moved` |
| A8 | 退订后 30 天内重新订阅 | 同一 Instance，发出 `reappeared` |
| A9 | 同一工坊 ID 同时出现在 Steam 和 SteamCMD 目录 | 两个 Instance，同一 Lineage |
| A10 | 两个无关 Mod 使用相同 packageId | 两个 Instance，两个 Lineage；分析层报告“包名重复” |
| A11 | 一个目录通过 junction 出现在两个来源 | 只有一个 Instance，带一个别名位置 |
