# 06 · Game log

> Status: implemented: parsing of `Unity` (1.6 and earlier) and `Waylith` (1.7) logs, attribution, log ownership and staleness, the attribution cache, live tracking and the since cursor, companion logs (Archo Monitor, RimCrow), and the error pattern library. A few checks in §9 still need the VM or real 1.6 and 1.7 games.
> Basis: 00, 00a, 03, 05, 07, 09, 10 §3, 19

This document describes how RimArcho reads RimWorld's `Player.log`: parsing and clustering (§1), attributing clusters to Mods with the facts of 05 (§2–3), deciding which game, launch and plan a log belongs to (§4), caching (§5), live tracking while the game runs (§6), companion logs such as Archo Monitor's (§7; the Monitor itself is in 19), and the error pattern library (§8). Each cluster becomes a log-layer finding (05 §4.3).

## 1. Parsing

**A log uploaded by HugsLib** starts with HugsLib's own header: `Log uploaded on …` on the first line, the Mod list, the active Harmony patches, the Harmony versions, then `Log file contents:` and the game's log (2,061 header lines at the median in the corpus, where every log is such an upload). Skip the header; the game's log starts after `Log file contents:`, or at a `RimWorld X.Y.Z revN` or `=== Waylith log ===` line when an upload cut short lacks it. Line numbers stay those of the file.

**Two formats** are supported:

- In `1.6` and earlier (`Unity`), messages have no level. Read the version from `RimWorld X.Y.Z revN` in the first 50 lines of the game's log.
- In 1.7 (`Waylith`, identified by `=== Waylith log ===` within the first 50 lines), each message has the form `<date> <time> <level> [<category>] <message>`, followed by an exception stack, if any, and a call stack. Read the version from `Version: X.Y.Z.N`. Collect only `WARN`, `WARNING`, `ERROR`, `FATAL`, and `CRITICAL`; exclude `INFO`, `DEBUG`, and `TRACE` from error clusters. Discard the logging system's call frames (`Brutal.Logging.*`, `Verse.Log`) and mark the others as caller frames, separate from exception frames. A message with only a call stack is not an exception. Rewrite `- PREFIX owner: Target.Method <- Ret Type:Method(…)` into `Unity` format. Strip the leading dot and `_PatchN` from .NET 10 `.Ns.Type.Method_PatchN(…)` frames and mark them as patched methods.

**Entries** consist of a message line and its following continuation lines.

- Continuations include lines beginning with whitespace; lines beginning with `[Ref `, `(wrapper `, `Rethrow as `, `--- End of`, `file: `, or `Subnode:` (and its next line); multiline .NET exception messages beginning with `Parameter name: `, `Actual value was `, or `Object name: `; `Mono` native frames such as `<0x… + 0x…> <unknown method>`; bare frames without `at ` from inner exception stacks; and frames in Unity's own format, `Ns.Type/Nested:Method (args)` (sometimes with no space before `(` or with `:0` at the end).
- **Unity-format stacks** come in two kinds. When the player turns on full stack traces, Unity adds a stack headed by `UnityEngine.StackTraceUtility:ExtractStackTrace ()` to every message. Discard the logging frames (`UnityEngine.StackTraceUtility`, `DebugLogHandler`, `Logger`, `Debug`, `Verse.Log`) and mark the others as caller frames, as in 1.7. Without that header, Unity prints an exception's own stack after `ExceptionType: message` and `[Ref X] Duplicate stacktrace`. These frames are exception frames when the entry has a Ref, an exception frame or "Exception" in its message, and caller frames otherwise (a Mod's status message with a stack stays informational). Convert names to the `Mono` form: `/` → `+`, drop generic arguments, and turn a Harmony replacement `MonoMod.Utils.DynamicMethodDefinition:Ns.Type.Method_PatchN` into the patched method.
- A `(Filename: ` line or a blank line ends the current entry. Truncate lines longer than 4 KiB.
- `[Ref X] Duplicate stacktrace` refers to the earlier original stack with the same Ref.
- Combine an XML Extensions block (`[Mod - Start of stack trace]` … `[End of stack trace]` … `Source file: <path>`) into one entry: `[Mod] <first-failure-line>`. Treat the rest as continuations and the path as `file:`. In 1.7 the block's first line is an `ERROR` message and the lines up to `Source file:` carry no timestamp; the caller stack after it stays with the entry. A block whose `[End of stack trace]` is missing ends at the next timestamped line or `at ` frame.
- The entry's location frame (`Top`) is the first exception frame, or the first caller frame (the code writing the log) if there is no exception.
- A `Mono` frame keeps its IL offset, `[0x00076]` before ` in <…>:0` (`logs.Frame.IL`, `HasIL`); cluster details print it as `+0x76`. A constructor frame `Ns.Type..ctor` (also `.cctor`, also a bare frame without `at `) has the type `Ns.Type` and the method `.ctor`.

**Exclude engine or framework status lines from error clusters** when they have no exception stack: shader fallback messages (`Shader '…': fallback shader '…' not found`), XML Extensions statistics (`[XML Extensions] N total patch operations run`), `Curl error N: Callback aborted`, and `Mod … is missing supported versions list in About.xml`. These rules come from the corpus. Other `Unity` entries count as problems only if they have an exception stack, a noninformational category, a message that starts with `Tried to ` (the game's wording for its own errors, which 1.6 writes without a stack), or one of these terms: error, exception, failed, could not, couldn't, invalid, missing, or not found.

**Categories** are tested in this order:

| Category | Detection |
| --- | --- |
| `noise` | Known noise (`logs.KnownNoise`), with or without a stack: `Material 'SolidColorMat-…' with Shader '…' doesn't have a texture property …` (a material made in code by `SolidColorMaterials`) and `Translation data for language … has N errors`. Always a cluster, whatever its words. |
| `patch-failed` | The message starts with `] Patch operation ` or `Patch operation `, contains `Verse.PatchOperation…): Failed` or `Verse.PatchOperationSequence: Error in the operation`, or is an XML Extensions block whose first failure is an operation, `[Mod] Ns.PatchOperation…(`, whatever its class (`AnomalyPatch.PatchOperationRemoveIf`) or ending (`): Failed`, `): Error`, an xpath broken over lines). |
| `xref-missing` | `Could not resolve cross-reference`, `Could not load reference to`, or `Failed to find <X>Def named …` |
| `material` | The message contains `_MainTex`, or the stack contains `ResolveIcon`. |
| `xml-load` | XML errors, `Could not find parent node`, `Duplicate def`, `Could not find a type named`, `Config error in`, etc. |
| `texture-missing` | `Could not load Texture2D at`, `Failed to find any textures at`, or `Could not load Texture\|Material\|Shader\|AudioClip\|SoundDef` |
| `save-load` | An unresolved save reference: `Could not resolve reference to object with loadID`, `… is not deep-saved`, `Error in PostExposeData`, `Could not find think node with key`, `Exception loading … from save`, etc. |
| `harmony-stack` | The stack contains Harmony patch lines. |
| `exception` | There is an `Exception` stack, or the message contains `Exception`. |
| `game-error` | No stack, the message starts with `Tried to `, and it names a dotted type outside the game namespaces (§2), also when the game glued a word to the name: `Tried to add pawn X to lord with lord jobNs.LordJob_Y but this pawn is already a member of lord with lord jobRimWorld.LordJob_Z`. In the corpus these are mostly duplicate `RegisterforPostLoadInit` registrations, Mod lords adding pawns that are in another lord, and uninitialised `DefOf`s. `Tried to …` lines that name only game types stay `other`. The pawn's name in the lord message is left out of the cluster key, so the message for every pawn is one cluster. |
| `mod-report` | The Mod reports on itself with a prefix such as `[name]`, `<color=…>[name]`, `name :: `, or `MOD: `, excluding level words such as `ERROR:`. |
| `other` | Everything else |

The `mod-report`, `other` and `noise` categories are informational and do not appear in the finding list. `archo log` and MCP `analyze_log` hide informational clusters unless `--all` (`all=true`) is given, and test runs do not count them as errors (20 §2).

**Known noise** is a line found in nearly every log that reads like a problem but that no def, file or list setting causes (evidence: `docs/research/2026-11-04_mcp-transcript-review.md` §2.2). Unlike the excluded status lines above, known noise stays visible as clusters, so a reader of the raw log can see that RimArcho recognised it:

- the `hidden:` line names them: `hidden: 3 informational clusters (archo log --all); known noise, not mod problems: log:E5 material made in code, log:E6 translation error count`;
- the cluster detail gives the honest reading as a `detail:` line. For the solid-colour material, it says that no def or file causes it and that searching for `uiIconColor` finds nothing; no `material` checklist or `pattern:g:asset.maintex` route appears. For the translation count, it says that the problems affect only text and do not cause the log's other errors, and that the count names no Mod;
- other clusters' `nearby` lines end such a line with `(known noise: <label>)`.

A `material` cluster for a def's own material (`Material '<def material>' … _MainTex`, or `ResolveIcon` in the stack) is not known noise. Nor is `Object with load ID … is referenced … but is not deep-saved`, which dev mode writes while saving (a test run's autosave included): the corpus pattern `g:save.not-deep-saved` is in 3,224 public logs with fixes that disable or reorder another Mod, so a Mod can cause it, and as noise it would hide that. It stays `save-load`; a test run with ticks adds a note to it (20 §2).

**Category is not runtime phase**. Names such as `save-load` describe message content only. Determine phases only from explicit Archo Monitor markers (§7; their format: 19 §4), never from a category, stack, or vanilla text such as "Loading game…". `logs.Entry.Phase` is the latest marker before the entry. `logs.Cluster.Phase` keeps the phase of the first occurrence, and `Phases` counts occurrences in each phase separately. Cluster keys and numbers do not change with the phase. Logs without markers stay unphased. The game's own boundary lines, `Initializing new game with mods` (a new game) and `Loading game from file <name> with mods` (a save load, with the file name), are recorded apart as `logs.File.GameMarks` (`logs.GameMark`, also in a 1.7 message after its level and category, within the first 40 characters); they set no phase and stay ordinary messages. Only test runs read them, to place a cluster of the player's log without Monitor phases by its first line (`LogReport.GameMarks`, 20 §2).

**Clustering** follows these rules:

- Normalize the first 300 message characters: replace paths with `<path>`, addresses and long hexadecimal IDs with `<hex>`, and numbers with `#`. Replace the pawn name in "Tried to add pawn … to lord", and in "Exception ticking …" errors (also "world pawn …" and a hediff's "for pawn …"), with `<pawn>`: one bug in a pawn comp throws for every pawn. A ThingID there (a defName followed by its number, such as `Wall12345`) stays, because it names the kind of thing.
- The key combines the category, normalized message, continuations for `patch-failed` (to distinguish files), and the location frame's `Type.Method`. Merge entries with the same key into `log:E<n>`, numbered by first appearance. Record the count and the first 5 line numbers.
- A **template** combines the category with a further-normalized message. Replace color tags, `defName=…`, quoted contents, names after `named / loadID / Type / field / at / for def / key`, the `Def` in "found to give to X", parenthesized type names, and `packageId` with placeholders. Templates count kinds of problems: each missing texture has its own cluster but the same template. Cluster keys keep these names because attribution needs them.

## 2. Evidence

Attribution uses the fact store (05): effective content, `Defs`, Patch simulation results, `TypeDef`, and `HarmonyId`. The last two exist only after an analysis, so `archo log` and MCP `analyze_log` first bring the environment's analysis up to date for its own logs, logs of unknown owner and pasted text (`App.EnsureAttributionAnalysis`; the MCP wait is bounded by 14 §1, after which the output says `analysis: still computing`); a test run does the same for the tested plan (20 §2). Otherwise a freshly scanned environment names no Mod for clusters such as `static constructor of T` (MCP eval c3). Another environment's log is refused, and a log of unknown owner from another game version starts no analysis of that version (§4). While enabled Mods other than Core and DLC have no analysed content for the attributed version (`LogReport.Unanalysed`), the output says `analysis: assemblies not analysed yet for N enabled mods`, and a detail that would say nothing defines a type or matches a Harmony owner says `owner unknown, assemblies not analysed yet (N enabled mods)`: missing facts say nothing about the Mods. The same analysis lists the assemblies whose string literals the texture-path rule searches. Match Mod names from About.xml; the game prints `[Name]`, not the player's aliases. Core and DLC (the `ludeon.rimworld` prefix) never become sources through text matches or `Def` ownership.

Use the following evidence, strongest first:

| Evidence | Rule |
| --- | --- |
| `[Mod name]` prefix | A self-reported issue identifies the Mod as source. XML Extensions uses full names (`[[FSF] Vanilla Bionics Expansion] Verse.PatchOperation…`). |
| File path | An absolute Windows or native Linux file path recognized by `winPathRe` / `unixPathRe` in `internal/app/logs.go` (including XML, assemblies, textures and audio) in the message or continuations inside an Instance directory identifies it as source. Spaces within a path are preserved. For logs from other machines, match Mod directories: `…\workshop\content\294100\<id>\…` or `…\Mods\<directory>\…`, with either separator, including HugsLib-redacted `[Rimworld_dir]\Mods\…` paths. |
| Patch failure versus simulation | Match `patch-failed` to the simulated failure by `[Mod]\|description` or `file:` and mark the Mod as source, with `file:line` and 05 §4.4 reasons. A disabled target provider is dependency, with `archo enable`. Match XML Extensions failures by XPath. If the operation no longer fails, state "the mod or the Loadout changed since the log"; the Mod stays the source. |
| `defName` (`xref-missing`) | Record the missing `def:<Type>/<name>` and list its enabled and disabled providers from the `Def` facts. A disabled provider is dependency, with `archo enable`; if none exist, state "providers: none among installed mods". For `Could not load reference`, explain that the error occurred while reading a save. **Wanter**: the enabled, nonofficial definer of the `Def` in "found to give to `<XDef>` `<name>`" is source. **Referrers**: search enabled effective `Defs` and `Patches` once for `>Name<` and `<Name>` (ThingDefCountClass lists such as `costList` and products). Skip Core and DLC and any `Mods` that define the name themselves. If over 3 `Mods` match, or the wanter rule already found a source, mark referrers only as mentioned. |
| `for def 'X'` in `texture-missing` | The definer of X is source. |
| File providers | For a missing texture with no enabled-Mod file reference, find installed nonofficial `Mods` with `Textures/<path>.*`. For nongame `Cannot resolve dependency to assembly 'X'`, find `X.dll`. A disabled provider is dependency, with an enable suggestion; an enabled provider is mentioned (perhaps the game does not read that loading folder). If none exist, state "providers: none among installed mods". If the assembly has no types and no enabled Mod loads it, list the installed DLL copies in the details. The scope is live Instances visible to the environment: shared folders (Workshop, SteamCMD, extra folders, Monitor, and the lock library), plus its own `Data` and `Mods` (03 §2, `Store.InstanceFiles`). Exclude other games' `Mods`. |
| Texture paths in code | For a missing texture, the enabled `Mods` whose assemblies' string literals (`#US`) equal the path are referrers (source), as are those with a literal shaped like a path prefix that the path extends: at least 8 characters, contains `/`, and ends in `/`, `_` or `-` (`OdysseyPatch/OutfitStands/OutfitStand_` + defName); the evidence says `builds the path from "…" + …`. When such a source exists and no installed Mod ships the file, the cluster's detail says `own art missing: the source mod's code asks for this texture and no installed mod ships it; a defect of that mod, rendering only (adding the file elsewhere hides it, it fixes nothing that loads)`, and test runs give it as the cluster's `note`, also in `fixed` (MCP eval h2). |
| `xml-load` | For `Could not find parent node named "X"`, an installed, disabled provider is dependency. For `Two ThinkNodes have the same unique save key`, enabled patchers of `ThinkTreeDef/<key>` are patcher. The definers of `<defName>` or `Name="…"` in `Context` or `Full node` are source. |
| `material` | Provide a checklist for a buildable `Def` with `uiIconColor` but no `uiIconPath`, `uiIconPathsStuff`, or `graphicData/texPath`, including abstract bases. Include `archo files search "uiIconColor"` and `"uiIconPath"`. |
| Missing types | For `Could not find type named NS.T`, `Could not find type named T from node <…>` (the game's wording for an unresolvable `Class="…"`, also a bare name; such lines are `xml-load`) or `expected class 'NS.T'`, a disabled provider is dependency. An enabled provider is mentioned (a possible version mismatch), unless an enabled Mod earlier in load order ships a DLL of the same file name without T (`asm.duplicate-name`): that Mod is source ("ships X.dll (N types) without T and loads before #P"), and the provider is mentioned ("its copy is never loaded"). When no installed Mod defines T (`app/logtypes.go`), the enabled, nonofficial `Mods` whose effective `Defs` or `Patches` name T, as element text (`<thingClass>NS.T</thingClass>`) or a `Class="NS.T"` attribute, are referrers under the `defName` row's rules (source when at most 3 and no other rule found one, with file:line). The details add `did you mean:` with up to 3 existing types under the same root namespace, from the analysed assemblies of installed `Mods` and the game (`Store.TypesUnder`, `GameTypesUnder`): the same simple name in another namespace, or an edit distance of at most 3 and at most a fifth of the name's length, each with its Mod and DLL or `game`. A misspelled root namespace finds no candidates (MCP eval h1, h5). |
| Harmony patch lines | A line such as `- PREFIX <owner>: …` is patcher evidence. Match the owner by patch type, Harmony ID, then `packageId`. If no match exists, state "no installed mod matches". **Caller patches**: when the throwing frame (the topmost frame outside `System.` and `Mono.`) is an enabled Mod's own code, a prefix, postfix or finalizer on a frame below it, by a Mod with no frame of its own in the stack, is listed (`listed`, "a patch on a caller of the throwing frame, no frame of its own in the stack"), not patcher; transpilers stay patcher, since they rewrite the caller's own code. When game code threw, patch lines stay patcher evidence: the rule was not measured on the log corpus (MCP eval h7: a freeze prefix on `Pawn.Tick` two frames below a profiler's foreach got `patcher` and steered 5 of 6 runs). The next step for a patch line is `archo harmony --target <frame>`, except for a patch class whose target the analysis could not read (`TargetMethod()`, 05 §5.3): then `archo harmony --mod <ref>` and `archo source <ref> --type <patch class>` (MCP eval h4); a listed patch line adds none. |
| List modifiers | For `Collection was modified`, or a hot-path stack (§3) with `InvalidOperationException` or `ArgumentOutOfRangeException` (`app/loglistmod.go`): the frame above `List.Enumerator.MoveNext` is the loop that threw, and the list was changed by code in its body, which is not on the stack. When that frame is a Mod's code, its IL says which member it enumerates with `foreach` (`dotnet.Assembly.Enumerated`); the cluster shows `enumerated: ThingWithComps.AllComps (foreach in <Mod>; the game's ThingWithComps.Tick indexes it)`, else the details carry that sentence. Unless the enumerated list is known and is not a comp list, every enabled, nonofficial Mod's effective assemblies (libraries skipped) are scanned for methods that change a thing's comp list (`dotnet.Assembly.CompEdits`, 05 §5.3). Overrides of `ThingComp.CompTick`, `CompTickRare`, `CompTickLong` or `CompTickInterval` rank first and are list-modifier candidates; the others are labeled "not in a tick method" and become candidates only for `Collection was modified` and while there are at most 3. For each tick override, `attached to:` names where XML attaches the comp: effective `Defs` or `Patches` that name the class as element text, or a `CompProperties` class whose constructor sets `compClass = typeof(T)`, found through the reference index (§5), with the def that holds it or the defs the patch operation touches in the simulation, at most 3. The scan is a heuristic on IL values (a list reached through a Mod's own field or reflection is not seen). Results are cached per DLL SHA-256 in `<data-directory>/cache/ilscan/`. |
| Stack frame types | Match frames in nongame namespaces against `TypeDef`. The topmost Mod frame is source, and lower frames are mentioned. Game namespaces are `Verse.`, `RimWorld.`, `System.`, `UnityEngine.`, `HarmonyLib.`, `Mono.`, `Unity.`, `MonoMod.`, `Ionic.`, `LudeonTK.`, `Steamworks.`, `Waylith.`, `Brutal.`, and `RimWorldWaylith.`. |
| Message type names | A type name is mentioned evidence. In "instantiating a mod of type T" or "static constructor of T", it identifies the source. So does the lord being added to in `Tried to add pawn X to lord with lord job T but this pawn is already a member of lord with lord job U`: code of T's lord adds the pawn without checking the lord it is already in, and U is mentioned (in all 9 corpus logs of this error, T was Progression: Education's class lord, against five different other lords). A name the game glued to the word before it (`jobNs.Type`) is matched without that word when the whole token matches no type. For that lord message, the details list every `Verse.AI.Group.Lord.AddPawn` call site in the source Mod's effective assemblies (`Lord.AddPawn call sites in #ref: Ns.Type.Method IL_0012 (no GetLord() check before it in the method); …`), whether a call of a method named `GetLord` comes earlier in the same method (an IL window check, not flow analysis), at most 8 per Mod; `next:` starts with `archo source <ref> --type <type>` for the types with unchecked sites (`app/loglordsites.go`, MCP eval h8 G7). |
| Null trace | For an entry whose innermost exception is `NullReferenceException` or `ArgumentNullException` (`app/logtrace.go`, MCP eval h4). **Dereference**: the first exception frame must be Mod code with an IL offset; its method is found in the Mod's analysed assembly by type, name and printed parameter types (compiler-generated methods and Harmony replacements are skipped). From the offset to the end of the statement (the next empty evaluation stack, or a branch), the first dereference of a value that can be null (`ldfld`, `ldflda`, `stfld`, `callvirt`, `ldlen`, array elements) is the one that throws; `dotnet.Assembly.DerefsAt` names its value: a parameter, a field of one, a local, a static field or a call's result. For `ArgumentNullException`, the parameter that `Parameter name: x` names, in the innermost of the first 4 frames whose printed signature has it. **Supplier**: while the value is a parameter, follow it down the exception frames. A frame that is a Harmony patch of the next frame (its Harmony line names it) maps by Harmony's injection names: a same-named parameter or `__N` is the original's parameter; `__instance`, `___field` and other `__` names end the trace with a line saying so. Otherwise the next frame's method (Mod code, or game code in the environment's `Assembly-CSharp.dll`) is searched for its `call`, `callvirt` or `newobj` of the frame's method, base-constructor calls included (the first one at or after its IL offset, else the only one, else all when they pass the same shape), and the argument's shape is read (`dotnet.Shape`: null, this, param, local, field, const, other; a local counts as null only when its one store is `ldnull` and its address is never taken). A parameter continues the trace in that frame; anything else ends it. When the callee is a game method, a `game contract:` line gives the call-site summary of 05 §5.4 for that parameter. **Output**: the cluster's `trace:` lines (`LogCluster.Trace`), for example `frame 1 Ns.Patch.Postfix +0x76 dereferences parameter recipient (ldarg.3, ldfld Verse.Pawn::genes)`, `frame 1 is a Harmony postfix of frame 2 Verse.PlayLogEntry_Interaction..ctor: recipient is the original's parameter recipient`, `frame 3 Ns.PlayLogEntry_Mutter..ctor passes null for recipient (ldnull at IL_0007, base constructor call)`, `game contract: recipient: game sites 7, null at 0 (…); Mod sites 1, null at 1 (…)`. Nothing is printed when the dereference cannot be decoded (no offset, an offset that is not an instruction of that method, as in another build of the Mod, or no matching method). **Attribution**: when the trace ends at a null passed by a non-official Mod frame, that Mod is source with the first evidence `log frame N passes null for the argument the throwing frame dereferences (trace)`; the throwing Mod, if another, becomes patcher when its frame is a Harmony patch (`log frame 1, its Harmony postfix, dereferences the null that log frame N passes (trace)`) and mentioned otherwise, even if a frame rule made it source. Both stay in the list. `next:` starts with `archo source <caller> --type …` and `archo source callers <game method>`. |

## 3. Roles and output

**Roles** are source (produced the error), list-modifier (its code changes the comp list the throwing loop walks, §2), patcher (only patched a related method), dependency (a missing, disabled dependency), mentioned (only mentioned), and listed (only a patch on a caller of the throwing Mod frame, §2). Rank candidates in that order. A listed Mod is shown with its evidence but is not a candidate: it is not a subject of the cluster's finding, not in the implicated Mods that source searches default to (05 §5.4), and not in a cluster's `--in` suggestions. Never promote a patcher to source without its own frames or files. The null trace (§2) is the one rule that moves a candidate down: the Mod whose patch only dereferenced the null another Mod passed. Candidates of the same role are ordered by their strongest evidence (`app.evidenceRank`): passing the traced null, then a file or patch, a message prefix, the topmost Mod frame, other frames and Harmony lines, anything else; equal candidates keep the order the rules found them, so the order is the same on every run. There is one exception to the ranking: for an installed, disabled `xref-missing` provider, dependency ranks before patcher. The missing `Def` belongs to the provider; `Mods` patching save or loading code have merely touched that code (Vanilla Expanded Framework patches `Pawn.ExposeData`, but a hairstyle missing from a save belongs to the Mod that defines it).

**Consequences of a def file that failed to load** (`app/logconseq.go`). `Exception loading def from file F` means the game dropped every def in F. Look up the non-abstract defs of files named F in the enabled `Mods` (`Store.DefsInFile`, any folder, Core included). Later clusters that exist only because those defs are missing are its consequences: an `xref-missing` cluster whose missing `def:<Type>/<name>` is one of them, and, when F defines `StatDef`s, `Config error in X: defines the stat base  more than once` (the label is empty because the stat is null). A consequence keeps its attribution, with confidence possible ("consequence of log:E<n>") and the first detail `consequence of log:E<n>: F failed to load, so <Type> <name> does not exist`. The root counts them (`Consequences`, `ConsequentLines`) and lists them with the lost defs in its details. `archo log` / `analyze_log` show the root with `+ N consequent lines in M clusters` and fold the consequences (`folded:` line); `--all` lists them with `(consequence of log:E<n>)`. Test runs fold them too (20 §2); `list_problems` still lists each as a `log.*` problem. `archo def` / `get_def` adds `log: not loaded: the newest log says F failed to load (log:E<n>)` when the effective definition's file is F in the cached report of the player's newest log. (MCP eval h1: one misspelled patch class in Core's `Stats_Basics_General.xml` gave 64 clusters, and the 1,000-line `Beauty` cluster named five `Mods` that merely use the stat.)

**Confidence** depends on the first candidate. A source with file or patch evidence is certain; a source with other evidence is likely. A dependency ranked first under the exception above is likely ("a mod that defines it is installed but not enabled"); if later rules find source evidence, the source conclusion applies. Candidates without a source give possible ("no source identified"), and no candidates give possible ("no mod identified"). Cached attribution reports carry `logCacheVersion`. Increment it when attribution rules change so that old logs are attributed again.

**Hot paths**. For stacks through `Verse.Pawn.Tick`, `Verse.ThingWithComps.Tick`, `Verse.Thing.DoTick`, `RimWorld.Planet.WorldPawns.WorldPawnsTick`, `Verse.Pawn.TickRare`, `Verse.ThingWithComps.TickRare`, `Verse.TickList.Tick`, or `Verse.ThingWithComps.CompTick`, include the tick-crash checklist: the game's `ThingWithComps.Tick` indexes `AllComps` with a cached count, so it survives a swap or reorder and a comp removing itself while it is the last one, throws `ArgumentOutOfRangeException` when any other comp is removed, and does not tick a comp added during the loop, while a `foreach` over the list throws `Collection was modified` on any change; check for `AllComps` mutation during iteration and runtime comp addition without `InitializeComps()`; remember that patch lines show only who last touched the method; also inspect ExposeData, SpawnSetup, DeSpawn, and Destroy. Include `archo source search "AllComps.Remove(" --active --yes --budget 10` and `"AllComps.Add("`: the mods named in the stack are mostly patchers, so the search covers every enabled mod (05 §5.4 "Search report").

**Each cluster produces one `log.<category>` finding**:

- The subjects are the candidate Instances whose role is not mentioned, or `log:E<n>` if there are none. A Mod that is only named by the message or a lower frame stays in the evidence and in `archo log --cluster`, but the cluster is not its problem: everything that lists a Mod's problems (Mod details, `problems --subject`) and a test run's `mods` leave it out (`LogCluster.Owners`; MCP eval h8 B4).
- The claim is `log:E<n> x<count>: <message>`.
- The evidence includes each candidate's `<role>: <evidence>` (log), plus category details such as reasons and providers (inferred).
- The first suggestion is `archo log --cluster E<n>` (MCP shows suggestions as tool calls, 13 §1.1), followed by next steps such as `archo patches --mod <ref> --failed`, `archo harmony --target Verse.Pawn.Tick`, `archo source <ref> --type <type>`, `archo def <Type>/<name>`, or `archo enable <ref>`.
- The key is the cluster key, with absolute Windows and native Linux paths reduced to their final three segments (05 §4.2).
- `findingKey` recognizes audio and other asset filenames as well as XML and assemblies, with either separator and spaces in install roots. Native paths are normalized on every host, including when a Linux log is read on Windows. Existing stable Windows path keys retain their text. Changes to these keys invalidate stored reports through `logCacheVersion` (§5).

**Cluster details** (`archo log --cluster E<n>`, MCP, and the interface) include the complete message and continuations, the top frames with their IL offsets, the null trace's `trace:` lines (§2), plus messages around the first occurrence (nearby: 4 before and 3 after, ≤30 lines, truncated to 200 characters per message), so that the reader does not have to look up the raw log (corpus G7). Lines of a transpiler's IL listing (`AdjustParms - ldfld …`, `IL_001a: ldarg.0`; `logs.ILDump`) are skipped and the next message counts instead (MCP review P13).

**List order**. `archo log` and `analyze_log` list the clusters by `ListRank`, then by first appearance: errors that stop code (`exception`, `harmony-stack`, `xml-load`), the other warnings, `texture-missing`, then informational clusters. The `next:` suggestion points at the first listed cluster. Cluster IDs keep the order of first appearance, so a cluster does not change its ID with the sort (MCP eval h4 B3).

**Rendering only**. Every `texture-missing` cluster that `own art missing` (§2) does not already describe carries the detail `rendering only: the game draws a placeholder (or nothing) where this texture belongs; nothing stops loading or playing because of it, and it causes none of the other errors in this log`. Test runs give it as the cluster's `note` (in `fixed` too), joined before the common-kind note (MCP eval h8 B4).

**Two sources**. A cluster of class `exception` or `harmony-stack` with two or more source candidates carries a `fixes:` line under the root: `N sources, <A> and <B>: one may have thrown and the other made it throw …`, telling the reader to report both and name both fix places (a guard or a different loop in the one that threw hides the error; undoing the action of the one that caused it removes it). It is not the pattern's `fixes:` line (§8), which lists kinds of fix and is indented under `pattern:` (MCP eval h7 G5).

**Saves**. `LogReport.LoadedSaves` lists the saves the run loaded (`Loading game from file <name> with mods:`). When one is in no `Saves/` of the environment (`<user data>/Saves`, and the `Saves` beside the log), `archo log` / `analyze_log` print `saves: this run loaded save "<name>", which is not in Saves/; a test run cannot reproduce errors that need that save, but still shows whether a changed Mod loads and a map starts` (at most 3 names; none for pasted text, which has no `Saves/` to look in; `App.MissingSaves`). Errors from loading a save cannot be reproduced in a test run without it (20 §2; MCP eval h8 G6), but a test run still checks a changed Mod: no agent of eval round 5 ran one before handing in a DLL that broke the game's start.

**Error patterns** (`pattern:<id>`, §8) appear on matching clusters as `[pattern:g:<id>]` at the end of the row and as a `pattern:` section in the details. Patterns provide background knowledge with community as the evidence source. They do not change attribution, roles, or confidence, or form standalone conclusions.

**Pasted text** (`AnalyzeLogText`, for example pasted stacks) uses the same parsing and attribution and is labeled `<text>`.

## 4. Which launch owns a log

**First identify the game that wrote the log** (`App.CheckLogOwner`), before log selection, attribution cache reads, attribution, log-version analysis, or marking the log as seen. Prefer an explicit absolute game path in the startup header, compared with the environment's `game_root`; RimArcho recognizes the `Unity` `1.6` line `Mono path[0] = '<game_root>/…_Data/Managed'`. Never infer ownership from Mod errors or source paths in stacks. The repository's `Waylith` 1.7 sample has a version but no verifiable game path, so 1.7 logs cannot be assumed to have `Mono` lines. Without a definite path, take the environment from the time-matched launch or ModsConfig write records below. If an explicit path conflicts with a record, the path identifies the game and the plan is unknown. **A version mismatch alone does not identify another game**: the same game directory may have been upgraded, so another environment matching the log version is not enough to exclude the log. Without enough evidence, keep the unknown or stale handling; never guess that another environment owns the log.

**Other games' logs do not belong to this environment**. Exclude them before attribution, attribution cache reads, `EnsureLogAnalysis`, or seen-state writes. They appear in no finding list (stale groups included), sidebar count, new-log notice, or errors from the last run; the game log page, the CLI problems, log and status commands, and their MCP tools share these rules. Recheck an existing selection if another game has overwritten the file; live tracking checks on each read and at the end, discarding clusters after an overwrite. **Explicit `log --file` and `--game-version` do not bypass ownership checks**: a file is refused only when another registered environment definitely wrote it (`log belongs to environment <name>`). Other explicit files remain viewable, and whether they count follows the staleness rules below. A header path outside all registered environments (shared logs, corpus logs, or this game before a move) means unknown ownership, not a foreign environment. `--game-version` changes the analysis version, not the environment identity.

**File selection**. For 1.7+, prefer `<user-data>/Logs/Player.log`; for earlier versions, prefer the user-data root (03 §3.3). Look for available `Player.log` and `Player-prev.log` files in both locations and exclude foreign files. If the current file is unavailable, the finding list, game log page, and default `archo log` use the available previous file. If neither is available, treat the log as absent. Packs use their own userdata in 1.7 and the environment's log in `1.6` (10 §3).

**Problem log**. Findings use the player's selected log (`archo log --select` or the game log page; `log.selected:<environment>`), or the current `Player.log` if it is newer. **While the game runs**, the file the current environment is writing (`App.LiveLog`, the same as `RunLog`) belongs to this run, so it is never the problem log, even if selected: `Player.log` yields to `Player-prev.log`, where the game moved the previous log on startup. The cache-only `LazyLog` sidebar counts follow the same rule; normal selection returns after exit. A 1.7 pack writes its own logs and is unaffected. `archo log` itself still defaults to the live `Player.log`. The CLI problems command and its MCP tool parse on demand; status and its MCP tool select the problem log the same way but read only the cache (§5). While a live log exists, status labels the problem log as a previous run and labels its contribution to the aggregate counts; it points to `archo log --follow` for the current run rather than parsing it. To save idle memory, the interface parses the log only when Can it run opens and reads only the cache before that (`App.LazyLog`, `App.LogCacheOnly`). Opening the page marks the log as seen (`log.seen:<environment>`). When an available `Player.log` is newer than both the last launch and the last seen log, the TUI status line shows "analyse this run's log", and the GUI reads that log once in the background without waiting for the page (`API.ReadNewLog`, 16 §2.1), then releases it.

**Analyze using the log's own version**. When a log of this environment has another major.minor version than the environment and no `--game-version` is given, first refresh the analysis for that version (`EnsureLogFileAnalysis` → `EnsureLogAnalysis`), attribute with it, and show `analysed: as 1.6 (log version); environment is 1.7` in the heading. A game directory upgraded from `1.6` to 1.7 can thus analyze its own `1.6` logs. **Logs of unknown owner are attributed against this environment**, the only candidate: `archo log` and MCP `analyze_log` refresh this environment's analysis first when the log's version is the environment's (or unknown), and never start an analysis for another version (attribution then uses the stored facts of that version). When the header names a game folder no environment has (`App.UnregisteredLogGame`), the log output says `game: log game path <path> is not this environment's game; attributed against env:<name>`, and the stale reason in problems and status is `source unknown: its game path <path> is not this environment's game`. Whether such logs count follows the rules below.

**Ownership and staleness** follow these rules:

- Match each log by its write time to the **latest launch record** whose start time is no later than the log's mtime. Include other environments sharing userdata. For logs under 1.7 `Logs/`, exclude pack launches because packs write their own logs. Launch records contain the environment, plan or pack, time, and list fingerprint (09 §2). A log is stale if any of the following applies:
  1. Its major.minor version differs from the analyzed version.
  2. The matched launch is not for the analyzed plan (another plan or pack in this environment; foreign logs were already excluded).
  3. The launch list fingerprint differs from the current enabled list because the plan was edited after launch. Replacing only the Archo Monitor version in the same position (19 §6) does not count as an edit: retrieve the list at the recorded launch or write version, verify its fingerprint, then compare each Monitor as the same item (`App.monitorSwapOnly`).

  Without a matching launch record (for a Steam or external launch), use the latest ModsConfig write record before the log time, which identifies the writer plan (07 §4.3). If no record matches, the source is unknown, and the heading says so. Such a log is **counted** as the last run when nothing says it is another game's (no header path, or this environment's): the heading reads `source unknown (no launch and no ModsConfig.xml write by RimArcho before it; counted as the last run)`. Otherwise a player who starts the game from Steam before RimArcho has written the list would see `0 error` over a log with errors (MCP review round 2 P25). A log whose header names a game folder no environment has (`UnknownGame`) stays stale. The ModsConfig.xml mtime is not used.
- Exclude stale findings from problems, status, and interface counts and from skip-prefix escalation. Collapse them to a title by default. The `--code`, `--subject`, and `--all` filters show individual entries; `problems show` still works and names the log.

**Heading**. Show one heading per log with the filename, declared game version, write time, current or stale status with a reason (for example `written by 1.6, the game is 1.7`), and severity counts. Add `not counted` and an expand command for a stale log (CLI and MCP forms: `archo problems --code log --all; MCP: list_problems code=log`). List its clusters below the heading.

## 5. Caching

- Parsing and clustering are fast; referrer searches take most of the time. Cache the **whole attribution report**, with one `log_cache` row per path and a copy in memory.
- The key combines the path, size, mtime, and an input fingerprint: `logCacheVersion`, `--game-version`, game major.minor version, analysis run, enabled list, and each installed Mod's ID, snapshot, name, alias, `packageId`, and directory. Reparse if any of these changes.
- The status and mod commands (MCP status and `get_mod`) read only the cache and never parse the log. A missing cache marks the log Pending; status explains that its errors are not counted.
- Store the report as gzip-compressed JSON: reports are often larger than the log itself (a 4 MB `Player.log` gives about 9 MB), and compression shrinks them about twentyfold. If a cached report cannot be decompressed, treat it as a cache miss and reparse.
- The report covers only the file size at read time, since the game may still append to it. Record the CRC-32C of those bytes for the cursor (§6).

**The first query for a new log** has a target of ≤500 ms on a cache miss (measured: 18 §2):

- **Indexed `Name` lookup** (`def_fact_named`, holding only the ~5% of rows with a `Name`, then filtered by the `content_state` version; 05 §3): missing-parent clusters query `Name="…"` for a provider. Query each distinct name only once per log.
- **Reference index** (`defName` referrers): keep one index per enabled set and game version. It records hashes of names appearing as references in each effective `Defs` or `Patches` file (`>X<` and `<X>`, without whitespace, and a tag's `Class="X"` value, for missing types). The analysis subprocess builds it after analysis; a query builds it if absent. Store it at `<data-directory>/cache/refindex/<key>.idx`. The key combines the game major.minor version and each enabled Instance, snapshot, and folder, independently of order. Keep only the latest 8 indexes. Search only the files selected by the index, verify the original forms, and take the earliest matching line. Reference evidence is sorted by file.
- **List-modifier scan** (§2): one IL pass per DLL, cached by SHA-256 in `<data-directory>/cache/ilscan/<hash>.json` (with `app.ilScanVersion`) and per path, size and mtime in memory; a later miss only hashes the DLLs. Only clusters the rule applies to start it.
- **Clustering**: classify each entry (level, message, continuations, and frames) once, with one `Classify` call. The `noiseRe`, `textureRe`, and `modReportRe` expressions use one leading `^`; branch-local anchors made Go retry at each position in a long message.

## 6. Live tracking

See 09 §4 for game detection. While the game runs:

- **Incremental read** (`app.LiveLog`): remember the `Player.log` path and read offset. Check each second and read up to 8 MiB, leaving the remainder for the next read. A smaller file means a new file (a game restart): reset the offset and clear the old clusters. Split new content into lines and keep an incomplete last line until the next read.
- Preserve parser state across batches. An entry ends at the next noncontinuation line or at game exit (`logs.Parser`).
- Preserve phase markers across batches too (§7). If an old cluster repeats in another phase, update that phase's count and the this-run entry without requiring a new cluster. The first marker assigns preceding entries to loading. Without any markers, keep the flat entries.
- **Memory**: keep clusters, not the raw log. Keep the first 3 sample entries and the count per cluster. Above 2000 clusters, discard the oldest informational clusters. Memoize the category by message, location frame, and continuations, so repeated messages are classified once; clear the table at 10000 entries.
- Fully attribute the first sample of each new cluster (§2). Show the result in the this-run part of errors from the last run on Can it run, in first-appearance order (16 §2.4). Update counts without dialogs. Show the game-running status and this run's error count on the GUI Launch page and the TUI status line.
- On exit, stop tracking and perform a full analysis, as with `archo log`. Replace the this-run section with the result.

**Companion logs** (Archo Monitor's `ArchoMonitor.log` or RimCrow's `RimCrow_Realtime.log`, §7) are read incrementally alongside `Player.log` to add timestamps, levels, counts, files, and related `Mods`.

**Interface**. CLI `archo log --follow` emits new clusters until game exit or Ctrl+C. See 13 §4 for `--json`, `--once` and the other log flags (`--cluster`, `--file`, `--prev`, `--text`, `--all`, `--select`).

**The since cursor** supports agent polling (MCP `analyze_log` since, CLI `archo log --since`):

- The cluster lists include `cursor: log1.<size>.<checksum>[.<companion-size>.<checksum>]`: the number of bytes read from `Player.log` and its paired companion (§7), in base 36, plus their CRC-32C checksums. The cursor stores no state on disk. The CLI and MCP results are identical.
- With since, analyze the current log normally, using the cache if possible. Recluster the first size bytes without attribution to obtain the counts at the cursor. Show only new clusters (new) and clusters with increased counts (`+N`), with the added and total counts in the heading and a new cursor. Also read the companion prefix, so companion-only entries after the game stops writing `Player.log` and increased companion counts are included. A changed companion session means nothing was known about it at the cursor.
- **Expiry**: if the prefix is shorter or its checksum differs, the game has restarted and written a new log. State that the cursor expired and list all current clusters. If the current `Player.log` does not match but the `Player-prev.log` prefix does, explain that the cursor's run is now `Player-prev.log` and suggest `archo log --prev --since <cursor>` (MCP `prev=true`). If the previous log itself does not match, explain that a newer run replaced it after another restart.
- The last line at the cursor may have been half-written. Count the entry as new when it is completed, preferring an extra report to an omission.
- This polls full analysis, not `LiveLog`: analyze the file size at each call. See §5 for first-query speed.

## 7. Companion logs

Archo Monitor (19) and RimCrow Companion write a companion log in the game's save-data root; its format is in 19 §4. This section describes how RimArcho reads it.

**Selection** is read-only; do not rename or delete the files.

1. The companion is in **this run's save-data root**: the environment's userdata for a plan, or `<pack>/userdata` for a pack (10 §3). When analyzing a `Player.log`, use its containing directory as the data root, or the parent of Logs for 1.7 `Logs/Player.log`.
2. If `Player.log` has a session marker, try the marker's path, the adjacent `ArchoMonitor-prev.log` (renamed on the next startup), then both files in the data root. Select the file with the same ID in its session line.
3. Without a marker, try the same generation's `ArchoMonitor.log` or `ArchoMonitor-prev.log`, which must have a valid session line, then RimCrow. If there is a marker but no matching session, fall back only to RimCrow. Pair RimCrow by generation: `Player.log` with `RimCrow_Realtime.log` (or `RMM_Realtime.log` if unavailable), and `Player-prev.log` with the same names containing `-prev`. Every candidate without a session match must be a nonempty regular file whose mtime is at or after the run's start and at or before `Player.log` mtime +1 minute. Do not pair files if ownership cannot be confirmed. Use the `Started:` time in `Player.log` (1.7, with a timezone), otherwise the Windows file creation time. If the start time is unavailable or later than the log's mtime, conservatively use the mtime. The current run's lower bound must also be later than `Player-prev.log` mtime, which avoids old creation times kept when `Unity` truncates and reuses a file.
4. The same companion, including a hardlink or path alias, cannot be paired with both Player.logs in the same directory. Prefer session-marker evidence; on equal evidence, assign it to the current generation. `app.CompanionFor`, full analysis, the log page, and live tracking share these rules. Recheck the pairing after a companion append or rotation even if `Player.log` has not changed.
5. For live tracking (§6), select the companion in the run's data root by these rules, preferring Monitor to RimCrow, and recheck the session when a marker arrives, including rotated files. A smaller companion restarts the read, as with `Player.log`. Read the companion before `Player.log` so classification hints are ready; a cluster attributed before its companion entry arrived is attributed again. A companion-only entry waits for its `Player.log` pair according to 16 §2.16.1 L03, since both files are written almost simultaneously. The wait ends at game exit, but continues while the matching `Player.log` entry is the unfinished last entry or an unread backlog remains. A `Player.log` entry that appears after the wait merges into the companion-only cluster: it becomes the first sample, the cluster is reattributed, and the larger of the two counts applies. As in full analysis, presence checks include all `Player.log` entries, even noise and informational lines; only normalized first-line hashes are stored, capped at 50,000 and cleared when full. A Monitor entry with a stack whose `Player.log` line is noise is still not an error. Known noise (§1) is classified by its message, so both copies form one informational `noise` cluster.

**Field usage**:

| Field | Use |
| --- | --- |
| `message` | Normalize the first line using §1 and match it to a `Player.log` cluster. For a RimCrow line with nonempty `relatedModIds` and a message beginning with `[`, first strip the prefix through the first `] `. |
| `id` | Merge Archo Monitor lines by entry id, and RimCrow lines by level plus normalized message. |
| `timestamp` | The time on the entry's first line is the cluster's first-occurrence time. Show it in the live this-run section and full-analysis cluster details. |

Only the companion knows the count after the game stops writing `Player.log`. |
| `kind:phase` | Assign each `Player.log` message and companion count row to its latest preceding phase. Take the larger count from the two sources per phase, then combine the cluster's phase totals without double-counting. If only the companion has markers and a `Player.log` entry has no companion record, keep its phase unknown; do not assume loading. |
| `details` | For Monitor `ERROR` and `WARNING` entries absent from `Player.log`, usually after its logging limit, pass message + newline + details to the §1 parser. | `relatedFiles` | An absolute path inside an **enabled** Instance identifies it as source, with `ArchoMonitor.log: <Mod-relative-path>` as evidence. Treat pseudo-paths (`patch:`, `xref:`, `def:`, `loadID:`, `<root:`) as refs. |
| `relatedModIds` + roles | xml or def with file evidence for the same Instance gives source; patch gives patcher; stack, text, or no role (RimCrow) gives mentioned. If the Instance already has a stronger role, only add evidence; never downgrade it. |

HugsLib packs are kept the newest per pack identifier, at most 200. Offsets of sessions whose log is gone are dropped. - **Interface**: on Can it run, a cluster with file evidence has an evidence chip of kind log ("log"). Its source is `file <Mod-relative-path>  ArchoMonitor.log  <time>` (or `…  RimCrow_Realtime.log` for RimCrow). Put the file first with the explicit "file" label and use the spacing from 16 §7.3: the window splits the text on two spaces. For several locations in the same Mod, show the first plus N more.
- **Game log page**: the companion area is in 16 §2.10. The page uses the same reader, which also keeps the session game, exit time and full line, and caches by file path, size and mtime; while the game runs, it uses the data live tracking has already read.
- **Phases and display**: when phase information exists, deduplicate companion entries separately at each phase boundary and keep their first-appearance order in the file. The same id can appear again after another save load to show the boundary. Global attribution still merges by id. See 16 §2.4 and §2.10 for Can it run grouping and log-page separators, and 13 §4 for the CLI and MCP. Logs without phase markers (from an older Monitor, RimCrow, or no Monitor) keep the count and display rules without phases.
- **Cache** (§5): add the paired companion's path, size, and mtime to the key.
- Skip and count invalid lines (live `BadLines`, or the full-analysis heading). Each companion entry table and interface phase-entry table is capped at 20000 entries. Once full, update only existing entries.

## 8. Error pattern library

The pattern library comes from the public HugsLib log corpus (`docs/research/00-log-corpus-design.md` §3 G5 and §9; integration plan in `docs/research/01-pattern-library-integration-draft.md`). It ships as embedded data (`internal/patterns/patterns.json`, like `internal/order/observed.json`) and contains only templates, packageIds, and counts. Generate the data from the research dataset with `go run ./spikes/patterns -export internal/patterns/patterns.json`. The `-verify <corpusrun-result>` option checks that the product matcher and research classifications agree for every cluster (v0: 0 differences over 610,910 clusters).

| Layer | Reference | Recognition | Cluster display |
| --- | --- | --- | --- |
| Generic | `pattern:g:<id>`, for example `pattern:g:xml.type-missing` | Match regex rules in order against the message part of the cluster template (§1, category\|message), optionally restricted by category. The first match wins. | Show a one-sentence explanation; `evidence: community: seen in N of M public 1.6 logs (x% of error clusters)`; common causes; a diagnostic route using MCP tools, omitting the current step and replacing `E<n>` with this cluster; fix kinds; and the error-disappearance rate after 1–3 list edits in the same player's repeated uploads, compared with an unchanged-list control. Hide the comparison with fewer than 5 pairs. |
| Fallback | Same, fallback | Bare `NullReferenceException` and other exception, XML, patch, or save-loading errors: describe only the category. | Hidden |
| Mod-specific | `pattern:m:<packageId>:<hash>` | The template matches exactly, and the Mod is attributed as source. | Show a `known-error:` line with the public-log count, first and latest months of occurrence, observed Mod versions, and "newer Mod versions may have fixed this". |

- Patterns describe what this kind of error usually means, not who caused it in this list. The principle that appearance is not causation still applies. The interface labels the pattern card "community background" and shows it only on a match (16 §2.10).
- **Common, unattributed.** A noninformational cluster with no candidate Mod whose generic, non-fallback pattern appears in more than 5% of the public logs (`patterns.CommonShare`: the pattern's `logs` over the library's `logs`, 40,326 public 1.6 logs in v0) is labelled `common kind, no source found`, wording that agents do not read as harmless background (MCP review round 2 P23). The label ends its `archo log` / `analyze_log` row, in place of the candidate; its detail has the `note:` line `common kind, no source found: this kind is in 6.7% of public 1.6 logs (pattern:g:asset.maintex)`, and `archo test run` / `test_run` gives the same text as the cluster's `note` (JSON) or `note:` line. The denominator comes from the library's metadata. Like the pattern, the label is information only: it changes no attribution, confidence or exit code, and guide's error kinds say that common is not harmless. Fallback patterns never qualify because they only name the category. The v0 counts predate the known-noise category, so `g:asset.maintex` (2,696 logs) also counts the solid-colour material (§1); regenerated data will count only def materials, and the pattern may fall below 5%.
- Keep Mod-specific templates only if they occur in at least 10 logs and 5 player sessions. Discard any template that appears to contain paths or user data (docs/research/00 §8).
- `archo pattern [<reference>]` (13 §4.2; MCP `analyze_log pattern=<reference>`) shows a pattern's recognition rules, phase, occurrence counts, common causes, diagnostic route, fix kinds, and repeat-upload evidence; without an argument it lists the generic patterns by cluster share, and `--mod <packageId>` lists a Mod's known errors.
- A checklist (MCP `guide topic=errors`, CLI `archo guide errors`, 14 §3) follows the corpus frequency order. It covers categories not addressed by `guide topic=diagnose`: save loading, missing assets, configuration checks, assembly loading, and noise. Step 3 of the diagnostic route links to it.
- Distribution: v0 ships with the program. Fetching newer versions through `archo data update`, like the community sorting rules (08 §2.3), is not implemented.
